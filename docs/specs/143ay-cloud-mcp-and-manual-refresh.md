# Spec143AY 本机 MCP 一键刷新与云端 MCP 接入

状态：三片已实现，纳入 0.5.10。公司 MCP 服务、Linux 开发机和 Windows 原机链路待验收。

## 1. 目标与范围

- 本机已接入 MCP。增强现有「刷新工具与模式」，一次点击即可重拉已启用服务的工具目录。远端只改同名工具的参数时，用户在原会话刷新后即可按新定义重新发起调用。
- 云端 Runner 支持远程 Streamable HTTP MCP。云端主智能体使用全部既有内置工具，以及已启用服务中通过校验的全部 MCP 工具。沿用云端任务执行助手的权限模式和会话边界。本片不增加工具勾选、工具级允许名单、交互审批、跨会话或长期记忆。
- 云端 MCP 请求由 Runner 发出，支持直接访问和复用现有 Windows SSH 反向隧道。Coordinator 管理配置与刷新状态。首版使用无需客户端发证的 MCP 端点，沿用现有云端管理与任务鉴权。
- 服务端不需要推送目录变化通知。用户显式刷新后再发送新消息。调用前检测目录变化仍按现有方式拦住旧定义；本片不自动替换模型已收到的定义、重新生成调用或重放请求。
- 云端新增能力只向主智能体暴露。保留本机的 `allowed_tools`、会话工具选择、审批规则和已有子智能体能力。

### 补充切片：本机和云端 MCP 请求头

每个云端服务接受与本机相同的 `headers_env`，将请求头映射到 Coordinator 进程的环境变量名。Coordinator 的刷新快照和摘要只保存配置引用，已鉴权的 Runner 控制帧另带当前用到的环境值；Runner 只把值传给 MCP 连接管理器，不改变进程环境。Runner 继续直接拨号或使用原 Windows TCP 入口。可配凭证的服务要求 Runner 声明新能力；未用凭证的旧配置与控制帧兼容。

本机和云端均允许已获准的明文 HTTP 请求带认证头。非回环 HTTP 仍沿用 `allow_insecure_http`，HTTPS 仍验证 CA 和服务名。配置或凭证变化经原刷新入口进入下一轮；更新系统服务环境后须重启相应服务进程使新值可见。缺少环境值时仅该服务发现失败，不发无凭证请求。Runner 与任务命令属于同一信任域。

影响共享设置与 MCP 资源管理、Coordinator 刷新、Runner 控制帧与工具装配。测试覆盖本机明文认证、不同服务的独立凭证、刷新更换凭证、旧 Runner、凭证不进入持久快照，以及云端 HTTPS 中转。

## 2. 分片一 · 本机一键重拉目录

现有链路是 Web「刷新工具与模式」或 CLI `:mcp-refresh` → 应用 MCP 刷新入口 → 读取 `settings.toml` 的 MCP 段 → `refresh_mcp` → `read_catalog` 与工具注册。现在服务配置相同就跳过发现，导致纯远端 Schema 改动只能通过停用、刷新、启用、再刷新处理。

1. 显式刷新绕过「配置相同就跳过发现」的分支，按启用的服务拉取并校验当前目录。普通模型请求保持现有准备流程，普通 MCP 调用保留现有的调用前目录核对。
2. 配置和目录指纹均一致时，保留已发布定义、授权身份与现有执行连接。指纹继续覆盖完整工具定义，包括同名工具的参数 Schema，不能用工具名或描述代替。
3. 目录变化时，复用现有按服务准备和发布机制。验证整套新定义后一起更新注册和资源视图。同名工具保留会话选择，旧定义的许可按现有身份规则失效。新工具按本机流程先加入 `allowed_tools`，刷新后再在会话里勾选。
4. 拉取或校验失败只影响该服务的本次更新，保留其原有效配置和目录，返回明确错误。原调用前校验仍拒绝与服务端目录不符的请求。已启用服务的连接配置变更继续沿用现有启停规则。

正常例：本机服务仍启用且配置原样，远端把 `search_logs.request_id` 改为 `trace_id`。用户点一次现有按钮，模型在刷新后的新请求收到新 Schema。发往服务端的是依据新定义生成的参数，已有会话不需重建。

失败例：远端启动失败，刷新返回不可达，注册表保留原目录。若远端随后提供不同定义，旧调用被拦在 `tools/call` 之前。已提交且响应丢失的调用继续按结果未确认处理。

影响面：`mcp_client/refresh.py`、必要的资源与注册接口、现有 Web/CLI 刷新测试及 `docs/mcp-client.md`。复用既有 API 和按钮。

## 3. 分片二 · 云端 Runner 直连与 Windows 中转

### 3.1 配置

在 Coordinator 启动所用的 `cloud.json` 中增加可选 `mcp.servers`。省略等价于无 MCP。每项用稳定服务 ID，复用本机 MCP 的服务 ID、URL 和定义预算校验。示意配置如下，地址与入口名需按实际环境填写。

```json
{
  "mcp": {
    "servers": {
      "logs": {
        "enabled": true,
        "url": "https://logs-mcp.example.internal/mcp",
        "route": "direct"
      },
      "nacos": {
        "enabled": true,
        "url": "https://nacos-mcp.example.internal/mcp",
        "route": "windows_tunnel",
        "network_slot": "nacos_mcp"
      }
    }
  }
}
```

- 首版仅接受 HTTP(S) 的 Streamable HTTP 端点。开发机直连和 Windows 中转按服务选择。中转必须指定入口 ID，直连不接收入口 ID。仅有 `stdio` 的 MCP 服务需先提供 HTTP 入口，进程管理不在本片。
- HTTPS 保留服务原 URL、Host、TLS SNI、证书校验与路径。中转只覆盖实际 TCP 连接地址。非回环的内网明文 HTTP 要求显式设置 `allow_insecure_http: true`。首版不下发凭证头。配置和 API 拒绝 URL 内用户名、密码、查询串和片段。
- 复用现有 MCP 请求、响应和目录大小上限。云端给连接和调用配置有限超时，按服务限并发，并给空闲连接有限保留时间。首版默认连接 15 秒、单次调用 30 秒、每服务每 Runner 并发 1、直连空闲 300 秒；已有任务占用、取消和关闭逻辑按资源管理器合同处理。中转连接仅在当前轮复用，轮终局前关闭连接及 SDK 后台任务。中转执行连接关闭时由服务端空闲回收会话，避免网络切换时旧连接继续请求。公司链路验收可按实测调整。

### 3.2 执行链路

```text
cloud.json → Coordinator 校验服务配置并解析任务路由 → Runner
Runner → MCP 客户端发现并校验工具 → 云端主智能体工具视图
主智能体 → Runner MCP 客户端 → 直连服务，或开发机 SSH 反向端口 → Windows → 服务
```

- Coordinator 复用任务的 `network_id` 和当前入口配置，只解析该任务对应的 `network_slot`。MCP URL 的原始主机及有效端口必须与已启用入口目标匹配。入口缺失、切换中、目标不符或 TLS 校验失败时，该服务不可用，禁止切到其他入口或直连兜底。现有网络切换与任务占用边界继续生效，路由身份变化后退休旧连接。
- Runner 复用 `MCPSessionResources`、目录发现、参数校验及 MCP `ToolSpec`。远端服务返回的工具通过整套校验后，注册成稳定的 `mcp__<server_id>__<tool_name>`。云端选择策略单独表达为「启用服务中的全部有效工具」，不把本机空白名单解释成全选。
- Runner 每轮固定生效的 MCP 工具目录。主智能体的工具视图由原内置工具与本轮有效 MCP 工具合成。MCP 名单不写入可被旧会话恢复覆盖的常驻工具选择。子角色仍取原配置，不继承这份目录。
- 启动时并行、按服务有界地发现。不可达的 MCP 服务记录错误，该任务仍可以使用内置工具和其他可用 MCP。连接与上下文在 Runner 管理，任务退出时关闭，Coordinator 不维护 MCP 会话或代转工具调用。
- 云端协议新增明确的 MCP 能力标记。老 Runner 没有该能力时沿用原云端行为，UI 可显示当前模板不支持。Coordinator 不向老 Runner 发送新配置字段或刷新帧。已有任务启用新功能需要支持该能力的 Runner，后续目录刷新不再要求重建容器。

影响面：`application/cloud/settings.py`、任务启动和路由解析、`contracts/cloud_runner.py`、`cloud_runner/kernel.py`、共享 MCP transport/注册与主工具视图。涉及超过 8 个生产文件，延续现有 LangChain Agent 图，不新增中转服务。

## 4. 分片三 · 原云端任务刷新、界面与验收

### 4.1 刷新合同

1. 云端输入区模型选择旁增加「MCP 工具」，打开只读面板。面板按服务展示工具、连接方式和状态，保留一个「刷新工具」入口。支持查看错误与当前生效工具，无逐工具勾选和服务编辑。新服务在原 `cloud.json` 登记，远端目录变化只需点一次按钮。
2. 刷新当前任务时，本机云端 API 沿现有项目、会话与绑定校验进入 Coordinator 的 Owner 路由。请求带唯一刷新 ID，作用域是当前任务。Coordinator 只重读其启动时确定路径的 MCP 段，保存有界配置快照与本次刷新 ID。通过静态校验的最新配置也作为新任务的配置来源。其他已有任务仍在各自的刷新边界应用。请求既不传文件路径，也不更改模型、权限、记忆或 Windows 隧道配置。未通过配置校验时返回失败并保留上一份有效状态。
3. Coordinator 通过既有 Runner 控制连接派发窄刷新消息并核对回报。刷新请求与回报至少绑定 `task_id`、`generation`、刷新 ID 和配置摘要；回报包含服务级状态、有效工具名及安全错误码。当前 ID 重复到达时复用已登记状态。已经被替换的近期 ID 拒绝重放；旧 Runner 或旧刷新结果不覆盖新状态。运行、删除或环境切换状态仍受原准入保护。
4. 空闲 Runner 收到刷新后立即开始有界发现。已有一轮运行时仅登记，等轮终局后再刷新，在下一轮取得工具视图前完成。待发送消息按原队列规则保留，排到刷新之后。若发送刚好撞上新的刷新，只有 Coordinator 明确在准入前拒绝时，才保留原排队意图并换子命令等待重发。受理结果不明时继续暂停。Runner 离线或环境未启动时显示等待，恢复可用 Runner 后应用已登记请求，按钮不隐式启动容器。
5. 同一配置下显式刷新也重拉远端目录。按服务准备并发布，成功后报告 Runner 实际应用的目录。刷新失败保留此前仍符合当前配置与路由的目录，页面明确标出失败服务及原目录状态。显式停用或移除在下一轮收回工具，即使其他服务刷新失败；路由变更或目标失配时旧连接退休，旧工具不能继续向失效目标调用。

页面状态为「可用」「正在刷新」「待下一轮」「等待 Runner」「刷新失败」。成功以当前 Runner 应用回报为准。刷新状态、草稿和运行状态分别保存。失败提示可重试且不包含真实 URL、服务响应正文或敏感参数。已开启工具只按有效目录计数。

并发与恢复：沿现有 CT1 和 registry DB 短事务完成刷新意图与任务准入协调；控制帧、MCP 发现、建连和收尾均在锁外。已派发刷新使用窄操作预留与明确期限，Runner 在发布前复核刷新 ID、代际、期限和当前无在途轮次。超时释放普通运行准入，允许再次刷新。若回报丢失，状态显示待核对；Runner 重连后用同一刷新 ID 和实际应用版本对账。下一轮命令固定 Coordinator 已确认的 MCP 版本，Runner 无法匹配时保留内置工具，并提示 MCP 状态待核对，不使用未经确认的目录。删除、停止和关闭仍能收尾。实现阶段按实际新增锁和消费者同步锁表。

### 4.2 可执行验收

| 场景 | 必须观察到的结果 |
| --- | --- |
| 本机同名工具只改必填参数 | Server 重启且不发通知。配置不变，用户点一次现有按钮，原会话下一条消息使用新 Schema。验证旧参数未发到服务端。 |
| 本机目录相同、刷新失败 | 未变目录不换授权身份、不退休现有执行连接；失败时旧目录保留且显示可见错误。 |
| 云端直连和 Windows 中转 | 同一云端任务的主智能体可使用两条路径上的 MCP。验证中转保留 Host、SNI、证书及 `/mcp` 路径；错误证书、错槽位、目标变更或 VPN 断开时给明确失败，直连 MCP 和内置工具仍可用。 |
| 云端新增工具及同名改参数 | 已有服务新增工具后，原任务点一次刷新，下一轮可用，无勾选。Server 重启且不发通知，再改同名工具必填参数，点一次刷新后验证服务端收到新参数。 |
| 刷新期间有运行、重连或旧模板 | 正在执行的调用按旧轮收尾；同一任务下轮拿到已应用的目录。断线和迟到回执不覆盖当前状态。旧模板不接收新帧。 |
| 停用、故障与旧调用 | 停用服务的工具下轮不可选。校验失败或过期目录不执行旧定义。已提交但响应丢失的调用不自动重放。 |
| Windows 页面 | 桌面与窄窗口验证入口、工具列表、刷新等待与失败、焦点返回，确认不遮挡输入或吞掉草稿。 |

本机回归优先复用 `tests/test_mcp_runtime_configuration*.py`、MCP 资源与调用测试。云端分片补 `tests/cloud` 中配置、Runner 控制、直连和 TLS 隧道测试，前端沿用现有 CloudTaskDetail 与 MCP 刷新测试结构。最后跑 MCP 与云端定向测试、前端测试和构建、`git diff --check`。真实公司端点从实际 Runner 验证，不用 TCP probe 或模拟 SDK 替代真实工具调用。

上线可撤下云端 MCP 配置并刷新以回收能力，原任务、草稿和会话历史继续沿原合同管理。三片总估算约 4–7 个开发日，包含共同刷新行为、Runner 两种路由、刷新状态与回归验收。公司端点可达性排查及 MCP Server 实现另计。


## 5. 验收入口

- 本机：在原会话打开工具菜单，点击「刷新工具与模式」，发送新消息。CLI 使用 `:mcp-refresh`。
- 云端配置：更新启动 Coordinator 所用配置的 `mcp.servers`，参考 [完整配置示例](../examples/full/cloud.example.json) 和 [字段说明](../examples/full/cloud-configuration-reference.md#云端-mcp143ay)。使用支持 MCP 的 Runner 模板。
- 原任务：在 Windows Agent 打开云端任务，点击模型旁的「MCP 工具 → 刷新工具」。确认状态后发送新消息。运行中可先登记刷新，下一条排队消息等目录确认后发送。对账超时允许仅使用内置工具继续发送。
- 实机中转：在 Windows 连接配置中，把分配给该任务的入口指向实际 MCP 地址。分别调用直连与中转 MCP，再更换入口目标或断开中转，观察只有失配服务不可用。恢复入口后点击刷新。
