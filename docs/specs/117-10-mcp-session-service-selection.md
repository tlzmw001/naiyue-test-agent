# Spec117-10 本机会话按 MCP 服务选择工具

已确认。基于 0.5.11，范围是本机主会话工具菜单，以及本机和开发机 MCP 请求头配置。

## 当前链路

配置的 `allowed_tools` 先筛选已发现的工具，登记实际的 `mcp__服务ID__工具名`。会话当前再持久化一份具体工具名，模型请求按这份选择构造工具视图。刷新可以重拉服务目录并更新允许名单，但新增工具仍需进每个会话勾选。远程请求头目前由 `headers_env` 读取。Windows 本机读取本机 Agent 的进程环境，云端读取 Linux Coordinator 的进程环境。

## 分片一 · 服务级选择

- 原工具菜单中每个 MCP 服务占一行，复用现有勾选控件。选项只显示服务 ID 和当前可用工具数量，刷新失败或在途收尾的提示独立显示。内置工具仍按现有方式勾选。
- 本机会话在现有 `active_tools` 列表使用保留项 `mcp:<服务ID>` 表达整组选择。沿用会话 API 和持久化字段。在主 Agent 取工具视图时，把已选服务展开为当前生效的工具名。执行、审批及历史继续使用具体工具名。配置的子智能体工具名和云端主会话行为保持原边界。
- 刷新成功后，下一次模型请求按最新生效名单展开，无需重新勾选。工具被移出名单后从模型视图收回。仍按现有刷新失败语义显示已生效状态。配置中暂时停用服务时保留会话选择并收回工具，恢复服务后再次展开。
- 旧会话只要保存过同一服务的一个或多个具体工具，视为选中该服务，按当前允许名单使用整组。旧默认工具名单中的具体 MCP 工具采用同样规则。
- 已登记工具以权限元数据中的服务 ID 为准。缺失的旧名字仅在分隔结构无歧义时推断服务；包含额外 `__` 时保留原选择但不展开、不显示其他服务已选中。用户可显式勾选正确服务，避免已移除服务的名字被另一个前缀相同的服务接管。后端、Web 和 CLI 使用同一规则。
- 配置文件中的具体默认工具名仍在发现完成后严格校验，拼错或未知名称不能被旧会话恢复的宽容规则接收；显式 `mcp:服务ID` 默认组与旧会话保存选择分别沿当前合同处理。

成功链路：会话勾选 `nacos` → 保存服务选择项 → 会话服务解析有效工具 → 模型获得当前允许的工具。修改名单并刷新后，用下一次模型请求验证新增和移除。

失败链路：服务发现失败 → 沿刷新合同展示失败状态 → 会话保存的选择继续存在。未成功发布的新增工具不进入模型请求，原有工具按当前生效目录和调用前校验处理。

影响入口为本机会话的选择、恢复和工具视图，MCP 目录与工具菜单。测试覆盖刷新增减、停用再启用、切换和重开会话、旧选择迁移、子智能体边界、桌面与窄屏工具菜单。

## 分片二 · 本机和开发机文件中的认证头

- 用户已确认凭证放在现有私有 `settings.toml`。拟使用 `[mcp.servers.<id>.headers]`，支持 Bearer、API Key 等固定头值。继续支持原有 `headers_env`；同一请求头不同时从两处定义。
- 保留本机连接配置的既有生效边界。已连接服务的认证头变化后重启本机 Agent 生效；单改允许名单仍用现有刷新入口。
- 复用现有 MCP HTTP 请求头校验和连接实现，凭证值只在配置加载、资源准备和发出请求时使用，API、工具目录、日志、历史和示例均使用安全投影或占位内容。配置和手册写明使用私有配置与凭证生效条件。
- 开发机的私有 `cloud.json` 同样支持每服务的 `headers`。Coordinator 将文件内的头值映射到已有控制帧凭证引用，注册表只保存引用。派发时以当前私有配置解析文件值，配置与已排队的服务快照不一致时不发送凭证。使用原「刷新工具」入口重读文件。Runner 的配置协议和直连、中转链路沿用现有实现。

成功链路：读取本机配置 → 绑定指定服务的认证头 → MCP 目录发现和工具调用携带该头。失败链路：头名重复、值非法或缺少环境变量 → 安全错误，失败文本和状态不含凭证。

影响入口为本机 MCP 设置解析、资源身份、HTTP 请求构造及说明。测试使用本地 MCP 夹具验证直接头和环境引用，核对无凭证出现在错误与对外状态中。
