# 从真实运行离线构建 Agent 评测数据集

S1 至 S4 已实施。现有评测从 JSONL 和测试工作目录（fixture）开始。本设计补齐它的上游，允许用户手动发现故障、按比例抽查日常使用、审核 AI 推荐的题目，再用同一个评测入口跑新增数据。适用范围为本机已登记项目保留的主 Agent 历史及可关联的子 Agent 证据。

## 用户从哪里开始

```text
产品侧   用户发起 Run → 已有会话归档、诊断和模型用量
                                  │ 手动启动，只读
离线侧   选项目和时间 → 整理 Run 索引 → 判断规则 → 按池采样
           → 读取入选证据并脱敏 → AI 或人工标注 → 预览与审核
           → 导出版本化 JSONL 和 fixture → 现有评测命令 → 评测报告
```

举例：本周主 Agent 的 `read` 报错后，哪些运行仍完成了任务？选择工具名和错误结果，保留整次 Run 的独立终态。命中项太多可以抽 20%，同时从有充分证据表明未命中的历史里抽 5%，观察成功回复里有没有用错材料。单纯想了解一周的使用情况，可以清空规则，直接按该周全部可识别的历史抽 10%。

## 1. 数据边界与只读入口

| 需要的事实 | 现有来源 | 使用边界 |
|---|---|---|
| 项目、会话、根 Run、起止和终态 | 项目登记库、项目库里的 `naiyue_diagnostic_runs` 及根 `run_finished` | `capture_state` 描述采集状态。缺终点的采集可能被标为 interrupted，运行失败须有独立终态证据。会话的最近一次状态不能回填到历史 Run。 |
| 模型调用、用途、结果和采集缺口 | `naiyue_model_invocations`、`naiyue_model_usage_runs` | 以唯一 `invocation_id` 计数。保留用途、根/子来源和结果；HTTP 重试不单算一轮。 |
| 工具请求、名称、结果状态 | `naiyue_diagnostic_events` 的开始与结束事件，以及可唯一关联的 AI 消息和 ToolMessage | 按所属执行作用域和 `tool_call_id` 配对、去重。诊断保存有限字段，归档存在时可补可见参数与结果文本。无回执、字段省略、正文截断分别标明。 |
| 用户当时说了什么、哪一轮更正、测试材料 | 可见对话投影、消息/回复边界、可关联的工具结果 | 保留 project、session、thread、消息 ID 和 revision 等证据引用。按可确认的分支补前文。重新生成可能删除原后缀，今天工作目录里的同名文件也可能已经改变。 |

源码入口见[只读连接与登记库校验](../../naiyue_test_agent/storage/cache_cleanup.py)、[根运行收尾和诊断裁剪](../../naiyue_test_agent/storage/observability_sql/diagnostic_storage.py)、[模型调用存储](../../naiyue_test_agent/storage/observability_sql/model_usage_storage.py)、[诊断字段投影](../../naiyue_test_agent/application/observability/diagnostic_persistence.py)、[可见消息投影](../../naiyue_test_agent/storage/conversation_sql/history_projection.py)和[重新生成的分支处理](../../naiyue_test_agent/storage/conversation_sql/reply_storage.py)。

扫描复用项目的只读打开、路径与身份校验，使用 SQLite 参数化查询。按项目分页读取必要字段，连接仅用于短读事务，先冻结本批实际读到的索引与证据版本，再做采样和模型工作。需要取正文时，仅对入选项重新短读并核对身份、版本与边界。扫描清单记录每个项目读取的起止和可见范围；分批读取不承诺多个项目在同一时刻冻结。注销、切库、修订、清理或锁忙造成的缺口登记原因，可重扫。扫描不构造产品 `Database` 或 `ProjectHost`，不进入迁移、恢复、清理或所有者锁路径。

每个项目按稳定键翻页，记录已扫上界。进入清单的依据是分页实际见到的已关闭证据；读取某页之后才收尾且本批未见到的运行留待下次扫描。跨页和跨表遇到同一来源键时先归并，根终态优先，用量关闭只补缺。若同一事实出现相互矛盾的已关闭版本，将对应字段标为证据不足。清单封存后，正文补取阶段不重新计算池和名额。

**时间与分母。** 时间窗口使用带时区的左闭右开区间，内部统一 UTC。首版按历史收尾归窗，优先用根运行的 `finished_at`。诊断已缺但用量记录已关闭，或诊断组因缺终点收尾时，可以分别用 `recording_closed_at`、诊断 `closed_at` 归窗，明示“采集收尾时间”及数量，保留运行终态未知。索引对已关闭的诊断与用量记录按 `(project_id, session_id, run_id)` 取并集。读取时仍可确认处于运行中的主 Run 暂缓；开放采集未稳定、没有可用收尾时间、仅有聊天且无法定位根 Run 的记录分别报告。无法定位时间的缺口不计入某个时间窗的分母。报告使用“窗口内可识别的历史运行”，并展示只剩用量、跳过项目等覆盖情况。

## 2. 先判规则，再做百分比采样

项目与时间是两种抽法共同的范围。每条规则可包含多个条件，条件全部满足才命中；配置多条规则时，任一命中即可进入命中池。记录所有命中原因。例：一条规则可以写“同一次工具调用的名称为 read 且结果为 error_result 或 exception”，另一条写“整次运行失败”。一次运行满足两条时保留两个理由，仅占一个抽样位置。

| 首版条件 | 口径 |
|---|---|
| 根运行状态 | 使用根终态；failed、stopped、interrupted 等可分别选择。工具失败后恢复、最终完成的运行仍可命中工具条件。 |
| 工具名与结果 | 同一调用绑定名称与结果。结果支持 success、error_result、exception、not_executed、outcome_unknown。常用“工具报错”选 error_result 和 exception。 |
| 模型调用次数 ≥ N | 默认只数根 Agent 中用途为 agent 的不同 invocation。摘要、子 Agent 和 HTTP 重试分别保留来源。 |
| 工具调用次数 ≥ N | 默认数根 Agent 已观察到的不同请求。开始、结束和归档回执对应同一调用只计一次，并发两条不同请求计两次。工具次数和工具错误规则都可以指定根、子或两者，默认根。 |
| 实际用户交互轮数 ≥ N | 数截至候选锚点、能明确关联的同会话同分支用户请求，记录采用的消息区间。该值用于发现多轮候选，标注时再确认几轮是否围绕同一目标。一轮里调用十次模型仍只算一轮用户交互。 |

规则返回**命中、明确未命中、证据不足**。合取中已有明确假值即可判未命中，析取中已有明确真值即可判命中，其余涉及未知的结果保留未知。即使诊断被截断，已有十次唯一工具调用也足以命中“至少十次”；只见九次且覆盖不完整则无法判定。保留的回执无法区分“未执行”和“执行报错”时，只计其能支持的事实。

| 用户的选择 | 分母及默认比例 |
|---|---|
| 无规则，从全部抽 | 可识别且在窗口内的唯一根 Run，按 `all_percent` 抽，默认 100%。包含诊断不完整但满足范围的记录。 |
| 有规则，从命中结果抽 | 所有规则命中的并集，按 `matched_percent` 抽，默认 100%。只想抽某条规则时，仅选择那条规则。 |
| 同时抽查规则外 | 从明确未命中的池独立按 `unmatched_percent` 抽，默认 0%。可将命中比例设为 0，只做规则外抽查。未知单列数量和原因，可在无规则抽查时入选。 |

采用**固定配额、无放回抽样**。比例接受 0 至 100 的十进制数。每池抽取数为 `floor(池内唯一 Run 数 × 比例 / 100)`，使用十进制运算。排除不合法或模式冲突的选项。非空小池取整为零时显示“本次选中 0 条”和该池分母，用户可以提高比例。0% 取零，100% 取全部。对规范编码的种子与三段来源键算 SHA-256，按摘要和来源键排序，取前面所需的条数。提供种子可以复抽，省略时生成并保存。相同冻结清单、规则、比例和种子得相同结果；换种子可换样，本次抽样不受数据库遍历顺序影响。

示例：共 1,000 个唯一根 Run，150 个命中、800 个明确未命中、50 个证据不足。命中抽 20%、规则外抽 5%，最终有 30 + 40 = 70 个候选。对同一窗口清空规则、全量抽 10%，结果是 100 个。子 Run、重试、为多轮题补的前置对话以及从一个候选派生的两道题，都不增加这次抽样分母。

每批冻结项目范围、归窗依据、规则及版本、种子、比例、来源键、池归属和命中理由，保存抽取算法版本、各池分母与入选清单。重开批次从本地清单恢复；重新读取增长中的生产历史属于新批次。采样后缺材料的候选保留原因，不暗中补抽或改分母。抽样报告用于发现与选题；偏向故障的候选集不直接估计生产成功率。

## 3. 入选后清洗、标注和预览

1. **抽取最少材料。** 先看选中 Run。本地按可验证的消息、调用和父子标识补关联历史。将用户约束、当时可见的输入、实际调用、终态、可核实的结果和缺失项分别记录。取正文前后校验版本；无法定位旧分支时保留候选并提示缺口。原始引用留在本机私有批次目录。
2. **清洗。** 提取允许的文本与参数字段，移除凭证、请求头、私人绝对路径和无关日志。相同文件、角色或 ID 的替代名在一个候选内保持一致。标注材料保留截断标记和时序。无法安全提取时进入待补状态；允许人工提供可重现的小型替代 fixture，并记录它是派生材料。
3. **生成评测方向。** AI 仅接收脱敏候选和现有用例合同，逐方向给出“测什么、依据、哪些内容改写过、缺哪些材料”，可以不推荐任何题。可选系统提示词、子 Agent 路由、工具调用、规划、系统轨迹、多 Agent 协作、动态多轮。每个推荐方向有自己的草稿，能独立采纳。端到端、耗时等由既有报告计算。
4. **预览成品。** 本地静态审核报告对每份草稿展示目标数据集、完整待导出的 JSONL、fixture 相对路径树和逐文件内容、被测 Agent 各轮可见的信息、模拟用户的隐藏目标、评分器用的 checks/rubric、通过与失败的例子、真实运行需要的模型角色。显示相似基线/已发布题以及新增的等价类或边界。人工也可以直接编辑草稿，跳过模型标注。
5. **审核一个明确版本。** 每个方向可采纳、待补、关联已有题或放弃，决定针对草稿及 fixture 的内容摘要。人工修改后重算摘要并重新校验，旧批准不能导出改过的内容。草稿、来源映射和审核决定留在评测私有目录；正式 JSONL 遵循现有严格字段合同。标注失败按候选记录原因，可继续其他项并从失败项恢复。

**如何判断一道题值得收。** 用户第二轮把报告改为 `after-final.json`，只留下对话时，可以派生“给出明确新路径，下一次 read 参数是什么”的工具题。要制成动态多轮题，还须有可区分新旧答案的报告、独立核验的标准答案，并只在模拟用户第二轮透露新路径。目前基线已有该场景，审核时可关联[已有多轮题](../../evals/data/multi-turn.jsonl)，没有新边界时沿用原题。用户指出一次错误可以作为发现信号，标准答案须依据约束、可核对材料或人工判断；历史最后一条模型回复不可直接充当评分依据。

## 4. 校验、导出与回归

- 格式校验复用现有 [load_cases](../../evals/cases.py)。预览和导出共用同一份草稿及 fixture 字节。另核对文件实际内容、路径能否越界、是否存在软链、是否夹带运行记录或评分材料。运行器会把整个 fixture 复制进被测项目，标准答案与模拟指令留在评分侧。
- 显示三种验证证据：结构可加载；断言能区分对错；真实模型运行结果。代码断言用已知正反例自检；语义细则由审核人确认依据与判分示例，真实跑分时显式提供裁判模型；动态多轮需模拟用户模型，按现有合同四次独立运行。模型在新题上实际答错可以成为回归样本。
- 本地同源去重按来源片段、方向及派生任务标识核对。内容相同或与既有用例相似时展示对照，允许把新事故关联已有题。同源派生题保留本地关联。模型生成的文件名与 ID 经过校验，不允许写入产品数据、原项目工作目录或覆盖基线。
- 导出生成**按评测方向组织的增量数据集版本**。首版创建独立目录，以后可指定上一版作为基线，保留既有增量题，合入本批采纳项，报告新增、沿用、重复和冲突。原始冷启动集继续单独运行。先在同一文件系统的临时目录写入 JSONL、fixture 和版本清单，调用加载器校验所有文件后，以目录重命名一次发布。版本清单记录父版本、数据集和 fixture 指纹。重复导出相同版本返回既有结果；同名不同内容报冲突；中断后上个版本仍能运行。真实来源引用与隐私材料不随可分发数据集导出。
- 回归使用现有 [evals run](../../evals/__main__.py) 对选定版本、方向的 JSONL 运行。报告沿用既有的断言、轨迹、端到端和性能指标。扫描、清洗、标注、审核耗时只属于本批制题过程。

## 5. 计划的代码与命令边界

采用独立模块入口 `python -m evals.curate`，沿用 [evals](../../evals/README.md) 的开发环境和目录。S1 已接通扫描与采样，S2 已接通选中材料提取和 annotate，S3 已接通 review 和 export，S4 已从合成项目的真实 Run 归档走通到现有评测入口。产品包只包含 `naiyue_test_agent`，离线评测代码通过单向依赖复用已有存储读工具、模型目录与用例加载器。

| 命令 | 输入 | 输出及接线 |
|---|---|---|
| `scan` | 本机登记库、项目与时间、可选规则和比例、种子、批次目录 | 分页只读扫描，冻结索引与入选清单、为选中项提取脱敏材料，产出可直接阅读的抽样与缺口报告。扫描无需模型配置。 |
| `annotate` | 本地已清洗候选、显式标注模型配置，或人工草稿 | 按候选与方向保存草稿、fixture、推荐理由和缺口。可只处理部分候选。AI 无工具和工作目录访问权限，只输出结构化结果。 |
| `review` | 本地批次，或指定草稿 ID、版本及人工决定 | 以同一份草稿渲染静态 HTML。接受人工编辑后刷新，并登记对指定版本的审核决定。HTML 对历史文本和模型输出转义。 |
| `export` | 批次、采纳版本、可选上一版、目标版本目录 | 校验、去重并原子导出数据集，输出可用的 `evals run --dataset` 路径和该方向需要的模型参数。 |

建议按职责在 `evals/curate/` 放 CLI、历史读取、规则和采样、标注、审核及导出代码；测试放在 `evals/tests/`，使用合成项目库和固定模型。候选和审核记录可用本地 JSONL/JSON，fixture 使用普通文件。无需常驻服务、新数据库或在线 SDK。并发启动两个进程修改同一批次时只允许单写者；不同批次独立，单写约束只覆盖评测私有目录。

S1 的调用方式如下。两个命令分别创建新批次。登记库由显式产品数据目录解析，输出选在被扫描项目以外。命中模式中的规则文件示例为 `{"any":[{"all":[{"tool_error":{"name":"read","outcomes":["error_result","exception"],"scope":"root"}}]},{"all":[{"run_status":["failed"]}]}]}`。同一工具条件中的字段必须由同一调用满足。

```sh
python -m evals.curate scan --data-dir "$AGENT_DATA" --project "$PROJECT_ID" \
  --from 2026-11-16T00:00:00Z --to 2026-11-23T00:00:00Z \
  --all-percent 10 --seed 42 --output "$CURATION_DIR/week-all"

python -m evals.curate scan --data-dir "$AGENT_DATA" --project "$PROJECT_ID" \
  --from 2026-11-16T00:00:00Z --to 2026-11-23T00:00:00Z \
  --rules "$RULES_FILE" --matched-percent 20 --unmatched-percent 5 \
  --seed 42 --output "$CURATION_DIR/week-selected"
```

## 6. 在线隔离与验收顺序

线上请求、工具执行和必要保存沿现有路径完成。手动离线任务没有后台订阅、产品侧 hook、诊断设置写入或产品库迁移。信息不足时宁可少出题。私有输出目录与产品数据及用户工作区分开，拒绝路径重叠；不用真实项目目录作为 fixture。默认单项目分页读取、串行标注，读库与模型请求之间不持有产品锁或长事务。源库忙时有界等待并跳过项目；批内其他项目保留结果。只读扫描仍消耗磁盘带宽，若标注复用前台模型端点则会共享额度；可使用独立端点或错峰。标注模型仅在显式启用时访问配置的端点，扫描、采样和人工审核可完全断网运行；沿用评测进程禁用 tracing 的做法。

| 切片 | 可独立验收的结果 |
|---|---|
| S1 · 只读扫描与采样 | 实现 scan 的索引和采样部分，断网、无模型配置即可得到清单。合成数据验证时间边界、根/子区分、缺终态与截断、两条规则重叠、全部/命中/未中抽样、0/100/小数比例、小池取整、同种子打乱行序、去重和空结果。有活跃写入和被占用的项目时，正常 Run 仍能写入、停止并提交其预期终态，扫描无产品数据写入，不为补数启动 Agent。 |
| S2 · 清洗与标注 | 扩展同一 scan 命令，在清单封存后为入选项提取脱敏材料，接通独立 annotate。只有入选项才读取必要正文，向标注模型发信还须显式启动。验证重新生成、材料过期、旧路径更正、脱敏一致性和密钥不外发；同一候选产出两种合法方向，缺 fixture 的多轮题显示待补。模型超时只影响该条草稿。 |
| S3 · 审核与导出 | 预览与导出字节一致；修改断言后旧批准失效；相似旧题可关联；验证断言正反例、私有答案隔离、重复导出、并发冲突和中断恢复。 |
| S4 · 用现有入口跑新题 | 在合成项目上从扫描到导出走完整链，固定模型分别跑一条正例和一条能检出目标错误的反例，生成现有报告。线上隔离另做并行读写测试；真实模型效果单独记录。 |

S2 的 scan 在冻结 manifest.json 后为入选 Run 生成 materials.json。scan --resume 从既有清单继续，并保留已提取成功的材料。提取最多保留截至本轮回复的 24 条可见消息，超过 1,600 字符的单条内容省略并标记。首版保留关联的文件类路径和分页参数，以及工具结果状态。子 Agent 正文和其他工具自由格式正文属于证据缺项。annotate 按候选写入 annotations 目录，通过现有用例加载器校验材料齐备的草稿。S3 从同一份规范化 JSONL 行和 fixture 文本同时渲染预览、计算审批摘要并写入版本。审核决定按候选与方向存在批次中，导出落在批次的 versions 目录。前版可从其它批次传入，先校验版本指纹，再合并。相似题按用户输入的文字相似度提示，正式去重依据用例语义字段和 fixture 内容的指纹。现有代码评分器可核验人工提交的正反例，语义细则和真实运行状态留待实际评测。

设计核对时用两个临时 SQLite 库验证了现有 `read_connection`。在 DELETE 和 WAL 日志模式下，读取方都只看到了已提交的第一条数据，写入方在短读结束后成功提交第二条，读取方尝试写入均得到 `SQLITE_READONLY`。S1 集成测试使用临时登记项目和固定模型，验证前台运行期间可以扫描已完成的候选、正常停止，以及下次扫描可读取停止终态。吞吐和长历史的资源占用需要单独测量。

### S4 从已归档的 Run 验证导出的题

[贯通测试](../../evals/tests/test_curation_roundtrip.py) 在临时数据目录登记项目，以正常会话接口运行两轮。用户先让 Agent 等待确认，再把读取目标从 draft.txt 更正为 final.txt。扫描按至少两轮用户输入和至少一次工具调用，从两个根 Run 中选中第二个。固定标注模型收到清洗后的两轮对话和回执；审核明确的草稿版本后，导出两轮轨迹题和两份编号不同的报告。测试通过公开命令入口执行 scan、annotate、review、export 和两次 evals run，只替换模型后端。

同一份数据集和 fixture 下，正例实际读取更正的报告，返回 RUN-47，命中参考步骤，端到端通过；反例实际读取旧报告，返回 RUN-18，工具正常完成，但参考步骤和最终编号均未命中。固定模型用于复现两条路径，真实模型的正确率另用显式模型配置评测。并行扫描和前台运行停止的隔离复用 [S1 的运行中扫描测试](../../evals/tests/test_curation_scan.py)。
