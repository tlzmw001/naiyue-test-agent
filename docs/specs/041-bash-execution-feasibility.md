# Spec 041：Bash 工具的隔离可行性与接线门槛

状态：2026-10-02；本片只完成隔离模式的阶段设计和本机探针，**隔离版 Bash 尚未实现**。随后用户明确改为先做本地宿主机版本，见 [Spec 042](042-local-host-bash.md)；该版本不满足本文的 OS 隔离门槛，不能用于无审批、多用户或 SaaS 场景。本文保留作为未来隔离执行模式的验收，不把宿主机版本混称为通过本 Spec。

## 当前数据流与问题

CLI 在 `--workspace` 下注册 `read/ls/find/grep/write/edit`，`build_local_application` 把工具交给运行层 `create_agent`。应用会话保存可信工作区；每次运行通过 `ToolRuntime.context` 注入工具。只读越界调用由运行层 HITL 暂停，应用层展示目标并恢复，工具执行前再核验；同轮工具调度由 `ToolBatchMiddleware` 处理。当前没有命令工具或执行生成 pytest 的隔离环境。`cwd=workspace` 只能设置相对路径基准，不能限制进程读写宿主机其它目录、访问网络或继承凭证。

Pi 本机 `a69bef789` 的 `bash(command, timeout?)` 在 cwd 用 `spawn` 执行，并处理超时、停止和输出截断；它的核心 Bash 实现不以 cwd 提供 OS 隔离。AIAutoTest 的 Pi 扩展把 Bash 设为 `ask` 或完全信任下的 `allow`，这是授权策略而非沙箱。AgentX 的 Docker WebTerminal 面向人使用已有容器，不能直接当作模型工具接线。本项目沿用自身分层：应用层拥有人工决定，运行层注册和路由工具，执行后端落实 OS 隔离与资源预算，模型只收到有界结果。

## 拟定的首个可实施切片

- 模型可见参数先限 `command: str` 与可选 `timeout`；命令全文、工作区和工具调用 ID 是审批对象。批准与恢复时重验同一调用，不把对 `read` 路径的批准转成命令批准。默认每次 Bash 都询问；没有可用交互审批时拒绝。未来 Auto/完全信任模式另立策略，不在本片默认开放。
- 工作区来自可信会话上下文，不让模型传 `cwd` 或覆盖运行环境。执行进程只获得必要环境变量；不继承模型 API key、代理凭证或宿主机用户配置。若后端缺失、配置无效或隔离验证失败，拒绝调用，不退回宿主机执行。
- 同轮 Bash 声明为 `sequential`，使它和文件写/编辑调用按模型顺序进入工具链；跨会话命令的文件副作用与冲突需隔离执行环境承担，不能靠进程内 `ToolBatchMiddleware` 冒称解决。
- 命令成功、非零退出、参数错误、后端不可用、输出截断等可确定结果以原工具调用 ID 回填说明性的 `ToolMessage`，包含退出状态和必要的有界 stdout/stderr，不包含宿主机凭证。超时、停止和执行进程丢失时先确定子进程树是否终止；若有副作用结果无法确认，按未知结果终局处理，不能让模型自动重放命令。原始命令和完整输出不进入普通日志。
- 首片只面向本地单用户 CLI 和指定工作区，不宣称 HTTP/RPC 外部请求已安全：网络默认关闭。测试执行需要的依赖、只读源码、临时输出、CPU/内存/进程数和墙钟预算必须在隔离后端明确配置并验证。无法证明的限制写作已知风险，不靠提示词约束。

## 隔离后端进入实现的验收门槛

在每次执行的临时工作区和独立的工作区外哨兵目录中，以真实后端运行无害命令，至少验证：工作区内文件可创建并读取；工作区外哨兵文件的读取和写入均被拒绝；本地回环和外部网络连接被拒绝；进程环境不含注入的假凭证；超过时限的命令及其子进程树退出；大量 stdout/stderr 被有界截断且不会阻塞；后端不可用时确实拒绝。探针必须记录后端/操作系统版本、实际命令和退出状态，不能只根据 API 名称或配置推断隔离。探针只碰临时哨兵，不触碰真实凭证、现有工作区或 `.env`。

本机候选与当前结论：

1. LangChain 1.4.2 的 `ShellToolMiddleware` 有 Host/CodexSandbox/Docker 策略；Host 明确无文件系统/网络沙箱。其固定 `workspace_root`、持久 shell 和默认环境/命令日志行为也与本项目的共享 Agent、每会话工作区及脱敏要求不直接匹配。当前仅可参考执行契约，不能直接注册。
2. 安装的 `CodexSandboxExecutionPolicy._build_command` 生成 `codex sandbox macos -- ...`；本机 `codex-cli 0.159.2` 的帮助显示 `codex sandbox [OPTIONS] [COMMAND]...`，实测 `codex sandbox macos --help` 把 `macos` 当作待执行程序并以 71 退出。按当前 CLI 语法使用 `-c sandbox_mode="workspace-write" -C <临时目录>` 时，又以 2 退出，要求 `--permission-profile`；当前用户配置仅有 `sandbox_mode`，`-P workspace-write` 以 1 退出并提示缺少 `[permissions]` 表。没有隔离进程成功启动，因此不能声称 Codex 后端已验证。不得为此自行修改用户配置文件。
3. 本机 `/usr/bin/sandbox-exec` 的最小 profile `(deny default) + (allow process*) + (allow file-read*) + 仅工作区写入`：临时工作区写入退出 0，工作区外写入退出 1 且未产生文件；但它允许读取工作区外哨兵，达不到数据隔离门槛。把读取收紧到系统目录与工作区后，连 `/bin/echo` 都以 134 退出；尚未定位最低可用系统读取集合，也未验证网络、超时、输出预算。不能把此 profile 包装为已可用的安全方案。
4. 本机没有 Docker 命令；不为这个探针自动安装依赖或改配置。可以在下一片比较无需改用户配置的隔离后端，先让同一组门槛探针转绿，再选具体实现。

## 后续实施与验证顺序

先确定一个通过以上隔离门槛的后端，并将后端选择和失败关闭策略补入本 Spec。然后写失败测试：审批拒绝时不执行、批准后命令和 ID 绑定、跨会话工作区隔离、无后端拒绝、非零/超时/截断回填、停止与未知副作用不重试；随后实现最小工具和 CLI 接线。改动预计涉及工具、运行层 HITL、应用层审批展示与恢复、CLI、测试和文档，必须对照本 Spec 逐项核查。全量 `pytest`、`compileall`、`pip check` 和假模型 `create_agent → bash → ToolMessage → 模型` 通过后，才在可重置的临时项目运行一条生成 pytest 的真实闭环。真实模型与真实业务效果另行记录，测试全绿不等于生产安全认证。

本片只运行了隔离可行性探针，未修改产品代码、依赖、配置或密钥文件，也没有 Bash 功能的红灯/绿灯测试。没有已验证的后端时不启动后续执行代码的实现。
