# Spec143BP-S4：整体与 Windows 验收

2026-11-19 按当前 143BQ 与 Wiki 主线修订。本机验收有运行证据，Windows x64 原生验收待执行。前置 S1—S3。本片验收本机手动清理的产品主链和失败保护。

## 1. 证据分层

1. 单元/故障注入：期限、身份、依赖、锁、结果与释放的确定性断言。
2. 集成：真实本机服务、实际临时目录和 SQLite、认证 HTTP、并发消费者与断线查询。
3. 原生 Windows：真实共享句柄、长路径、Unicode、只读/权限与父目录操作。macOS 上 monkeypatch `os.name` 不能代替这一层。
4. UI：真实后端删除结果进入窗口，不以 mock 成功当作产品验收。

断言齿轮策略、执行和结果查询引发的模型调用、云端 HTTP 均为零。并发附件操作或独立业务重试可使用临时测试对端，以操作来源分别计数。若 Windows 执行环境缺失，只报告对应证据未完成，不改写为全部验收通过。

## 2. 隔离夹具与安全范围

每次验收在专用临时 data_dir 创建 registry、P1/P2/P3 和 chats 库，创建真实格式 marker/包/回执。使用 `os.utime(ns=...)` 设定时间，业务时钟可注入；不用 sleep 构造日期边界。

- P1：已打开且有活动运行/后台进程。
- P2：仍登记、未打开，含过期与未过期归档/包。
- P3：先登记再移除，受管目录留下但本次不可扫描。
- chats：两个持久会话，其中一个不加载 actor；附加一份无会话行孤立目录，证明不扫描。
- 外部诱饵目录：放置普通项目文件、下载成果、日志和图片样本，建立可识别的链接/路径替换测试；预先保存哈希。
- 准备有 `input_id` 的已完成旧回执、确有恢复依赖的旧写入（含目的目录和私有证据）、新 files 交付及已保存项目文件。分别核对历史可读、必要依赖受保护、纯历史引用不阻塞清理。
- 准备两个已过期的真实上传包。一个属于已完成且无本机消费者的附件，另一个属于已退役绑定上的待释放附件；后者保留真实命名的上传日志和锁。构造释放响应丢失与原回执重试，用持久字段区分这两个包。

只删除该夹具明确列出的受管数据，测试收尾沿 TemporaryDirectory；不触碰真实 data_dir、工作区资产、Docker 容器和云端包。无法安全建立某 Windows 边界夹具时报告未验证，不偷换为简单路径测试。

## 3. 必过矩阵

| 组 | 场景 | 必须观察到 |
| --- | --- | --- |
| 时间 | 7/3 天前一纳秒、相等、后一纳秒；future；低精度文件系统 | 只删严格早于边界且无依赖的单元 |
| 分组 | raw 旧/text 新；archive 旧/upload journal 新 | 整组保留，目录 mtime 不影响 |
| 范围 | 已打开、未打开、移除、普通会话、孤立目录 | 前两者及仍存在普通会话参与；其余不扫描 |
| 冷读 | 冷项目分别使用可识别的 flat 25 与 Wiki 26；另设未知格式、恢复标记、缺模型配置 | 以只读方式判定已知格式；不打开主机、不调用 prepare_wiki、不创建迁移备份。无法核验所有权或依赖时保留并说明 |
| 并发 | 已运行、后台 writer 未关闭、会话终态已写入但 after_finish 尚占用归档根；服务或配套 CLI 正读取、写入上传日志或重试 | 用事件固定在途窗口；当前根/缓存跳过，其他独立范围继续，原工作可收尾 |
| 竞争 | 枚举后移除/改名/目录交换；新运行与清理同时准入 | 单一明确先后关系，不能穿透预留 |
| 锁 | 两上传并行；捕获与上传并行；清理获取失败 | 读者并发保持，清理不等待读者网络；失败释放已取锁 |
| 附件释放 | `cancelling`；完整删任务后绑定已退役、普通附件列表已清，`pending_attachment_releases` 尚有条目；含重启与重试 | 释放尚待完成时过期包及上传日志保留；既有业务可按原操作核对。成功落库且最后读者退出，下次主动清理可处理 |
| 上传文件 | 常规上传及附件上传各产生真实 journal 和包内锁；已有锁的 mtime 单独更新、夹入未知文件 | 已无依赖的正常完整包可退役，锁 mtime 不续期；未知条目不被冒认可删除 |
| 历史 | 旧交付 completed/prepared 与可能已经写盘的 executing/partial/unknown | 前者的历史字段本身不占包；后者按实际恢复依赖保护，归属不清则报告。原回执可查看，旧代码写请求仍返回 410 |
| 成果保存 | 主会话 `cloud_result` 或面板的文件保存进行中、中断待核对及已完成 | 成果副本、目标文件和交付证据可继续沿原操作使用；齿轮不触发成果面板的“清理未引用缓存” |
| 失败 | 枚举/stat/JSON/权限/unlink/rmdir/同步/控制记录故障 | 明确对象、步骤、原因；计数准确；安全范围继续 |
| 退役 | rename前/后中断；archive删后剩元数据；重新捕获同 ID | 无半包进入复用，旧残留不删新包，无自动启动删除 |
| 服务 | 重复 POST、错 ID、断线、GET、换实例、正常关闭 | 一次执行；可查询；未知不重发；资源最终释放 |
| 资源 | 扫描/时间/结果容量边界 | 显式未完成，后续单元不执行，已发生失败无静默截断 |
| UI | 折叠、375px、空会话、部分失败、项目切换、刷新 | 入口可达，结果与后端相同，无第二次 POST |
| 资产 | 会话、图片、项目、已保存成果、备份、诊断与 Wiki | 受保护文件与业务记录可核对，清理不调用会话保存后的 checkpoint/Wiki 到期维护；允许并发业务按自身合同写入和清理诊断正常追加 |

故障检查在测试末显式断言，不能把断言放进被业务异常隔离吞掉的回调。并发使用 Event/barrier 或状态查询，验证锁竞争的先后，不依赖 50ms 时间窗。

## 4. Windows 原生专项

最少覆盖 Windows x64 原生 Python；专用工作目录含中文、空格和非 BMP 字符。

1. 真实超过 MAX_PATH 的受管路径，通过当前 windows_api_path 操作；盘符根边界、UNC 路径转换。UNC 真实文件操作需有可用测试共享，否则分别报告转换已测/真实共享未测。
2. 用 CreateFileW 打开候选且不共享 DELETE，触发真实 WinError 32；窗口显示原文件与原因，其他项目继续；关闭句柄后再次主动清理成功。
3. 为夹具设置只读属性，删除明确失败且不自动清属性；用户模拟手动解除后新请求成功。ACL 拒绝只在隔离夹具且可恢复时测试。
4. junction/symlink/reparse point 不跟随；外部诱饵哈希不变。目录替换竞争在父句柄保护下被拒绝或变成明确跳过。
5. 验证目标文件/子目录自身句柄关闭顺序，父目录保护仍在；退役后输入新捕获可用，旧 payload 可下次清理。
6. 使用配套版本的服务和 CLI，两个独立进程可同时持有共享 readers.lock；第三个进程请求独占清理时立即得到忙碌结果。读者退出后显式新请求成功，文件锁句柄无继承泄漏。记录使用的两个版本；旧 CLI 未参加新租约，混用不在此项验证范围。
7. 保留旧 `changed_store_fields` 的 fstat/lstat ctime 差异回归；必要同步不重现只读 fsync/EBADF，不忽略注入的真实 IO 错误。

不通过自动重试、清除权限或关闭用户进程让测试“通过”。记录 OS/Python 版本、文件系统、完整命令、退出码及所用夹具范围。

## 6. 对照 Spec 收尾

- 每条外部接口、配置字段、占用入口、错误明细和 UI 动作均能指出真实生产调用者。
- 复查 cold path 没有 ProjectStore 初始化、模型准备、迁移/备份等隐含副作用；只读扫描不是用户历史重写。
- 复查服务/配套 CLI 上传和附件取消/退役收尾的实际本机读写入口。用独立进程验证共享租约覆盖从包及其上传锁首次访问到最后一个句柄关闭的区间；仅按云端 ID 创建任务的 CLI 无需本机包租约。
- 历史兼容用已有旧数据和退役路由测试。比对旧写入的原目的目录、已写文件与证据；已完成的普通文件保存及其冲突重试仍走现行 files 路径。[旧交付合同](143bq-02-result-ui-and-analysis-retirement.md#42-升级时正在写入的旧交付) · [主会话保存回归](../../tests/cloud/test_result_tool.py)
- 确认现有 CLI 清理、云端结果轮换、接收材料、日志、备份、诊断、Runner 行为未被改变。
- 缓存失败记录与 readers.lock 的新增文件均有明确所有权和保留规则；没有新增无限增长的成功清理日志。
- 更新当前用户说明和 handoff，明确手动触发、7/3 天、历史详细输出可能不可读、失败处置与重启未知边界。
- 回退 UI/服务功能不会触发任何恢复性删除；已经删除的缓存不承诺找回。旧业务事实不迁移，必要依赖事前保护。已退役残留由当前支持该格式的显式清理处理，旧版本不得猜测它的含义。

验收退出条件：确定性测试、认证服务集成、前端构建及要求的 Windows 原生矩阵都有记录；缺证据的项明确未完成。云端共享输入回收已独立接入 143BQ。它的临时实例测试和部署验收不能计作本机清理或原生 Windows 验收。[143BQ 实施状态](143bq-cloud-results-and-input-reclamation.md#9-实施状态)


## 7. 本机验收记录

- macOS 26.4 arm64、Python 3.12.14。隔离目录中的真实认证服务与 Chromium 已覆盖桌面折叠、375px、删除成功、部分失败明细、刷新与响应丢失恢复。两次显式点击对应两个 POST，恢复只查原请求。项目原文件哈希一致，未过期日志保留，模型调用和云客户端请求均为零。
- 冷项目版本 25 和 26 均完成清理，数据库哈希保持一致。未知版本的文件保留并返回 `unsupported_schema`。普通会话使用生产生成的无连字符 ID 参与清理。已移除项目和孤立会话目录均保留。
- 活动项目回执为 `scope_busy`，独立冷项目仍可完成清理。两个独立进程可同时持有输入包读租约，独占获取在读者退出后成功。创建关联缺失和附件释放待确认时保留输入包。两条旧交付各有经核验的恢复副本时，只清理本机输入缓存。
- 完整命令、退出结果、浏览器截图和回执见 [本机验收证据](../../build/spec143bp-final/)。浏览器探针注入一次文件删除权限错误，以便稳定验证部分失败。Windows 的真实句柄、只读属性、长路径、重解析点、跨进程租约和本机目标构建仍需要原生 Windows x64 环境。
