## 3. 建议项目定位

面向研发团队的测试工程 Agent，能基于可追溯知识设计用例、生成并验证自动化测试；通过统一轨迹和评测持续衡量检索、决策、执行和模型优化效果。

最小可用范围：一个可控服务/业务模块，完成“检索证据 → 设计用例 → 人工确认 → 自动化生成 → 隔离执行 → 缺陷验证 → 评测报告”。PDF、网页、Markdown 最终都覆盖，但可逐种接入；尚未明确第一种材料。

先建立模块化单体和明确契约。独立复用不意味着第一天部署多个微服务；隔离执行环境和模型服务可以有独立进程/环境，具体拓扑留到技术选型。

首期聚焦一个主 Agent 加可控业务阶段；多 Agent 仅在对照评测证实收益后增加。完整范围将涉及多个目录，不能作为一次小改动实施。

## 4. 模块和职责

### 4.1 RAG 核心与问答适配

- 输入：文档源、项目范围、访问身份、文档版本；支持 PDF、网页、Markdown。
- 解析：保留标题、页码/段落位置、表格、代码块及来源；扫描 PDF 的 OCR 需求由材料决定。
- 切分：按结构与语义边界设计，记录 chunk 到原文映射；不默认所有材料固定字符切分。
- 索引：可增量更新、去重、版本化、删除失效内容，保留解析/切分/embedding 配置版本。
- 检索：关键词与向量各自召回，再融合、重排、截取证据；权限约束在受限内容进入重排/模型前生效。
- 输出：证据片段、来源 ID、版本、定位信息、分数；业务用例生成放在上层，不耦合进通用检索模块。
- 问答：基于证据生成回答；校验引用存在、定位有效，并评估主张是否被证据支持；不足时拒答或澄清。
- 复用：首先库接口；需要跨进程复用时增加 API/MCP 适配，不绑定某一 Agent 的 session。

### 4.2 测试 Agent 与工具

- 业务阶段：理解任务、查证据、识别缺口、设计场景、审查确认、生成自动化、验证、归因。
- 模型决定需要哪些证据/工具及如何完善候选产物；确定性代码执行权限校验、结构校验、预算和执行约束。
- 有效工具调用中的参数、执行及结果后处理失败，若可归属原调用 ID 且模型能够据此调整，应回填安全且能指导下一步的错误工具消息并保留失败事件；模型响应解析失败、运行控制/持久状态故障及副作用结果未知要分别处理，不一律伪装成可重试工具错误。Read 已完成该消息契约的本地切片；其他工具和将来的结果后处理仍须逐片验证，见 [Spec 032](specs/032-tool-failure-feedback-boundary.md)。
- 工具候选：检索知识、定位源码符号、读取契约、生成/校验用例、校验 profile、编译用例、隔离执行、读取结构化报告。
- 稳定的测试业务工具可通过 MCP 对外复用；不将每个内部函数包装为 MCP。内部调用与 MCP 入口共享校验和权限边界。
- 基于源码理解调用方法、参数、依赖；正确预期优先来自已确认业务契约。源码中的现有行为不自动等于正确行为。
- 现有 codegen 路线优先作为可用起点；若无法满足真实场景，再对比受约束的直接代码生成路径。

### 4.3 上下文与长期记忆

- 当前任务状态/短期上下文、文档证据、长期经验是不同来源，分别管理。
- 上下文预算：区分规则、任务、证据、工具结果；长输出存产物，只注入摘要和可回读引用。
- 长期记忆记录项目约定、已确认失败教训及偏好，包含来源、作用域、版本、有效期/失效条件、确认状态。
- 记忆写入经过确认或确定性验证，不将未经核验的模型结论自动当作事实。
- 新旧知识冲突时保留证据，按权威来源/版本规则处理；未知冲突进入澄清，不静默覆盖。
- 评测开关：无记忆/有记忆、正确记忆/过期记忆，比较收益和错误传播。

### 4.4 安全、隔离与可靠执行

- 被测源码默认只读，生成测试写独立 workspace；测试代码在隔离执行环境运行。
- 权限、可访问目录、网络出口、资源和时间预算由执行层实施；MCP 和提示词不是沙箱。
- 2026-10-02 用户确认先提供单用户本地 CLI 的显式宿主机 Bash：每条命令人工审批，工作区仅是 cwd，工作区外文件和网络仍按当前登录用户权限可访问。这是开发实验入口，不满足本节生产执行隔离要求；Web/SaaS、无人值守及生产测试执行仍须另做隔离后端验证，见 [Spec 041](specs/041-bash-execution-feasibility.md) 与 [Spec 042](specs/042-local-host-bash.md)。
- 工具读写边界明确；审批绑定具体操作及内容版本，不能绕过工具入口实施副作用。
- 本地 `ls` 为目录名称发现：按用户选择显示包括 dotfiles 在内的所有名称，工作区外目录仍须审批；名称可见不等于 `read_file` 获得正文读取权限。当前仅为单用户进程内约束，不构成沙箱或 SaaS 授权。
- `find` 延续只返回名称的目录发现边界；`grep` 会读正文，只搜索 Read 策略允许的工作区文件，工作区外只接受逐文件审批，不把目录列名批准扩大成批量正文读取。两者当前以 `rg` 处理 `.gitignore`，因此 `rg` 是本地搜索运行前提，缺失时工具回填明确错误；见 [Spec 034](specs/034-find-and-grep-tools.md)。
- 记录重试、取消、任务恢复及外部结果未知；恢复过程不能默认重放可能产生副作用的动作。
- 故障验收：模型/API 不可用、工具超时、索引不可用、任务中断、恶意文档、越权访问、环境清理失败。
- 生产使用先定义支持的用户/环境/并发、恢复目标与数据边界，并以持续试用证据说明成熟度。

### 4.5 模型接入与训练

- 推理适配支持受配置控制的云端/本地模型；检测工具调用、结构化输出、流式、上下文窗口等能力。
- 本地推理能力与可训练权重/训练资源分开确认，API 兼容不代表 Agent 行为兼容。
- SFT 聚焦“需求和证据 → 合格用例/正确工具参数”等具体行为；DPO 等偏好优化聚焦同一输入的可审查优劣对。
- 训练在独立实验流程进行，服务侧加载明确版本的模型；不在在线请求中训练。
- 优先比较基础模型、提示词/RAG 改进、SFT、SFT+偏好优化，保持其他变量尽量一致。
- 按文档、需求族、代码版本或项目分组划分训练/开发/留出集，近重复样本不跨集合。
- 不为背诵经常变化的公司知识而默认微调；优先让模型学输出质量、证据使用和行为规范。

## 5. 可观测性与评测作为共同基础

统一关联 task/run/trace/span/case/artifact ID；记录代码提交、语料/索引、prompt/skill、工具、模型及评分器版本。

轨迹覆盖检索、重排、上下文组装、模型调用、工具参数与结果、审批、重试、文件变化和执行结论。记录可观察行为及必要证据，不假设能获得模型隐藏思维链。

正文可受控存储并引用；默认脱敏、最小权限、保留期限。大正文不无差别塞进日志。厂商未提供的 token/cache/成本指标标为不可用，不填虚构数值。

遥测回答“发生了什么”，评测回答“完成得怎么样”，执行控制记录负责恢复/授权；不能把可丢弃或采样的遥测日志当作唯一任务状态。

| 层级 | 样本/证据 | 主要判断 |
|---|---|---|
| 检索 | 问题及人工确认的相关证据 | Recall@k、MRR/nDCG、无答案识别、权限/版本正确性 |
| 问答 | 回答、引用和来源 | 正确性、证据支持、引用定位、拒答/澄清 |
| 用例设计 | 需求、参考测试点、生成用例 | 需求点覆盖、边界异常、步骤可执行、预期可验证、重复与臆造 |
| 自动化生成 | 测试资产、执行结果、正确/缺陷版本 | 收集/执行成功、误报、已知缺陷检出、有效变异体检出、稳定性 |
| Agent 轨迹 | 可观察调用和状态变化 | 必要查证、参数/依赖顺序、权限、重试上限、失败恢复、无效调用 |
| 系统 | 实际运行与故障演练 | 完成率、延迟分位数、单位成功任务成本、恢复与清理 |
| 训练 | 隔离留出集及重复实验 | 基础/SFT/偏好优化增益、退化、成本变化 |

评估生成测试至少包含正确版本与已知缺陷版本：正确版本通过、缺陷版本能检出。代码覆盖率和 pytest 全绿都不足以单独证明测试有价值。变异测试要记录等价/无效变异体处理规则。

结果评测和轨迹评测分开；允许多条合法轨迹，通过必要步骤、禁止操作、前后依赖和最终证据评价，不强制完全一致的工具调用序列。

代码规则先判断可确定事实；人工标注/复核建立参照；LLM Judge 用明确 rubric、证据、盲化和位置交换校准，允许平局/不确定，报告与人工的一致性和分歧类型。评分器不能只看被评 Agent 的自述。

版本对照用相同样本和预算；报告样本数、重复次数、失败分布及适当的不确定性，避免一次运行涨分就宣布有效。留出集不参与反复调参。

两种回放需区分：固定记录的工具结果用于定位回归；重置环境后重新执行用于验证真实效果。前者通过不代表外部集成现在也正常。

## 6. 推进顺序与每阶段产物

| 阶段 | 工作范围 | 阶段验收 |
|---|---|---|
| 0 任务与基线 | 选一个目标模块，整理需求/文档/用例，制定标签和 ID/版本规则，跑旧系统基线 | 一条失败能追到输入、产物和执行证据；有可重复的小评测集 |
| 1 RAG | 解析切分、关键词/向量基线、融合、重排、问答引用 | 同集比较关键词、向量、混合、混合+重排，能解释收益与退化 |
| 2 测试 Agent | 工具、上下文、人工确认、测试资产和隔离运行，嵌入轨迹 | 同一任务生成可用用例/自动化，正确与缺陷版本有有效区分 |
| 3 可靠性与复用 | MCP、恢复/取消、长期记忆、权限/注入防御，线上反馈归档 | 第二调用方能复用模块；故障和越权用例有证据；反馈进入回归 |

## 11. 自定义 Agent 循环与扩展能力边界

历史备选说明：本节记录 StateGraph 路线的讨论。用户现已确认第 12 节的 create_agent + middleware 路线，不再将本节当作当前待选决策。

2026-09-23 补充：核验 AgentX 后，下面 StateGraph 推荐仍为候选，不是自定义能力的必要条件。AgentX 使用 Java LangChain4j fork 的现成循环，并在外围接入工具、记忆、会话和追踪；Python 也可以只复用模型/工具组件而自行实现小循环。详见 [AgentX 源码参考](agentx_architecture_reference.md)。选型需按循环控制、恢复和开发预算取舍，不能仅以功能数量决定是否使用 LangGraph。

早期讨论区分三个层次：create_agent 的 middleware 扩展已有循环；StateGraph 自定义状态/节点/条件流转；原生 Python 自写循环及全部运行时。此前曾建议第二层；结合用户澄清，最终选择第一层。下面列举的是 StateGraph 路线的能力边界，供未来出现复杂编排需求时参考。

- 循环：自行决定上下文组装、模型调用、工具路由、权限判断、重试、产物验证、停止/等待人工条件。用图表达不意味着写死工具序列；模型仍可选择工具，条件边处理不同结果。
- 工具：可用普通 Python 函数/工具 schema；执行节点可以自行实现，也可复用 ToolNode 等组件。独立工具服务负责校验、权限和执行，工具名称不是授权依据。
- MCP 消费：通过 MCP client/适配库将外部工具接入本项目工具层；需管理连接、认证、超时与调用身份。
- MCP 提供：用 MCP Python SDK 等包装可复用业务服务对外提供工具；LangChain 的 MCP 适配不等于自动为整个 Agent 创建 MCP server。
- 会话：checkpointer 保存 thread 状态和执行进度；应用另行负责用户/项目归属、thread_id 映射、权限、同一会话并发策略及清理。thread_id 是逻辑会话标识，不是 OS 线程，也不自动保证访问隔离。
- 长期记忆：store 提供存取/命名空间等底座，写入判定、来源、检索、冲突处理和失效策略由应用设计；任务 checkpoint 不等于长期记忆。
- 持久化/恢复：持久后端需要配置，内存 checkpointer 不跨进程重启保存；节点恢复可能涉及重新执行，副作用幂等与结果未知需专门设计，不能宣称 exactly-once。
- 观测：节点与工具边界记录 run/span、版本和结果。框架可提供流式和追踪接口，但领域评分器、标准数据和安全边界仍属于本项目。

首期仅实现小循环和必要状态，逐项加扩展。原 Day 3–4 的 3h 是采用现成循环的草案估时；确定 StateGraph 路线后应重估并从首期可选项中腾出时间，不承诺自定义全套循环/恢复/记忆/MCP 在同样 3h 内完成。

核验资料：[Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)、[middleware](https://docs.langchain.com/oss/python/langchain/middleware/overview)、[MCP 接入](https://docs.langchain.com/oss/python/langchain/mcp)、[persistence](https://docs.langchain.com/oss/python/langgraph/persistence)。

## 12. 用户进一步澄清：标准工具循环与自定义接入

用户原意：需要类似 Pi Agent 的循环，在模型调用与工具执行之间往返；可以自定义上下文、工具和记忆系统；必须支持轨迹等评测。用户没有将亲自重写循环调度器作为独立目标，也没有批准替换现有 Pi 的实现。

据此，用户已确认 Python + LangChain create_agent + 自定义 middleware 和独立业务服务。复用标准工具循环，首期不手写 StateGraph。create_agent 底层仍使用 LangGraph，不能声称完全不依赖 LangGraph，也不能声称与 Pi 全部运行语义一致。

- 模型响应含工具请求时执行工具、回填结果并继续；无工具请求时通常完成，另有预算、取消、错误等终止条件。并非每轮必须调用工具。
- 上下文：在每轮模型调用前决定历史、摘要、检索证据、记忆及工具输出的使用；持久会话记录与本轮实际模型输入分别记录。
- 工具：自定义工具与 MCP 适配工具共享调用校验、授权和结果记录；工具实现独立于循环，MCP Server 提供侧另行设计。
- 记忆：独立服务负责召回、候选提取、验证、作用域和失效；middleware 只作为接入位置。不是每轮都强制召回或写入。
- 轨迹：模型和工具调用边界记录开始、结束、异常，关联 run/step/tool_call ID；记录实际输入、工具参数及结果、版本、耗时和可获得的 token 用量。SDK 内部重试若未暴露，需要在更低层补充观测，不把一次包装调用当作所有网络尝试。
- 评测：从固定版本的任务样本、轨迹、产物和环境证据评分；与 Agent 运行实现解耦。模型自述、工具调用返回和业务任务成功分别判断。

已核验官方扩展点：before_agent / before_model / after_model / after_agent，以及 wrap_model_call / wrap_tool_call。实现时需按选定版本和异步执行方式核对相应接口，并验证 middleware 顺序和重试记录语义。

首个技术验证计划覆盖：模型→工具→模型的多轮链路；工具结果进入下一轮实际输入；上下文/记忆注入；一次工具失败的记录与反馈；逐轮轨迹关联；一个独立轨迹规则评分器。截至 2026-09-29，真实诊断已验证前两项的一次受限样例，确定性测试另验证运行层的 A→工具→B 选模；上下文/记忆、错误反馈、完整轨迹及评分器仍未实现，不能把计划当成通过证据。

## 13. 清晰分层与多模型适配

当前边界（2026-10-18）：沿用Python + `create_agent`与多模型适配，移除独立`test_agent`测试策略层。其Discount源码已在Spec093C删除，本次清理遗留字节码/空目录；应用直接装配模型、运行时与注册工具，测试任务通过提示词/Skills和通用工具完成，不恢复固定业务流水线。下列职责说明以此为准；本文件前面的带日期“四层”记录仅代表当时方案。

1. 模型接入：复用 LangChain provider 包和标准模型接口；项目维护配置、模型选择、能力约束和必要的供应商差异处理，不重写通用模型 SDK。
2. Agent 运行：使用 create_agent 提供模型—工具往返、消息状态与流式执行；不依赖某个具体测试项目的业务规则。
3. 通用工具：`tools`提供文件、搜索、Shell、子任务等执行能力，运行时接调度、权限和审批；独立RAG、测试执行或MCP能力按实际需求接入。
4. 应用与入口：`application`装配模型、工具和运行时并管理会话；CLI/Web负责用户任务与结果展示，不承担供应商请求协议转换。

轨迹采集覆盖模型、工具、检索和记忆边界；评测独立消费轨迹、产物及环境证据。分层先通过模块和依赖方向体现，不要求拆成多个进程或微服务，也不再包一套与框架完全重复的消息/模型抽象。

多模型分四种情况：按任务/会话选择；Agent、摘要和 Judge 等角色分别选择；同一运行中在模型调用边界动态选择；失败后备用模型接替。初始建议优先前两种；随后用户明确要求同会话在 Pi 式 turn 边界切换模型，因此该能力需要进入首期设计与验证。自动 fallback 仍按实际需要另行判断，不随切换能力一起默认加入。

2026-09-29 用户补充确认：同一会话允许中途更换模型，并希望参考 Pi 的 turn 边界。候选设计是在当前模型回复和其工具调用完成后、下一次模型调用前读取更新的会话选型；已开始的模型流不被替换或拼接。用户命令的提交/并发语义仍待确定，见 [Agent 运行、会话与工具架构草案](agent-runtime-architecture-draft.md)。此补充不等于自动 fallback 已进入首期，也不代表相关能力已实现。

2026-09-29 会话恢复分期建议：长期目标是应用重启后继续会话，但首个模型—工具—轨迹技术切片先验证进程内连续性；半个月 MVP 不把跨重启恢复列为必须抢在业务闭环和本地 Web 之前的验收项。应用会话标识和内部 `thread_id` 分开，模型选择只经会话服务读写；持久化时再将会话元数据与 Agent checkpoint 作为同一恢复切片实现并测试。框架内存 checkpointer 重启即失效，不得宣称已有持久会话。此为实施建议，具体持久化存储尚未选定。

选择模型应绑定到本次调用/运行上下文，避免修改一个所有会话共享的“当前模型”。模型配置包含提供方、端点、模型 ID、凭证引用、支持能力及参数；凭证值不写入笔记或轨迹。本地模型通过实际支持的协议接入，不能因为普通聊天成功就声称支持工具调用。

中途切换需要校验目标模型的工具调用、结构化输出、上下文和多模态能力，转换可移植历史，处理供应商专有内容，并保持工具调用与结果的配对；在完整调用边界切换，不能把不同模型的半段流式输出直接拼成一个响应。相同消息不保证相同输出质量。

评测固定模型和参数；若试验动态路由或 fallback，明确作为独立策略版本记录，不能把混合模型结果标为单一模型成绩。每次实际模型调用记录模型身份和切换原因。聊天模型、embedding 模型、重排模型配置分开；更换 embedding 模型通常涉及重建向量索引。

已核验参考：本地 Pi README 的 pi-ai / pi-agent-core / pi-coding-agent 职责说明；[LangChain 模型接口与动态选择](https://docs.langchain.com/oss/python/langchain/models)、[模型备用机制](https://docs.langchain.com/oss/python/langchain/middleware/built-in#model-fallback)。未进行实际跨模型调用或兼容性验证。

## 15. 当前开发顺序修正（2026-09-30）

用户明确要求自底向上推进四层架构，每层以一个小切片按 TDD 开发；当前暂停通用工具设计，先审视已接线的模型接入层。已实现的模型配置与四类适配对象构造不等于该层已达到生产目标。接下来的模型层问题是思考等级的供应商映射、提示词缓存控制及命中证据、运行时错误处理。三者的具体字段、作用时点和验收方式须先讨论，再选定单个切片写失败测试；不得一次堆入全部能力。

思考等级不是跨供应商完全一致的参数，模型层应负责能力校验及映射；运行层只传本次调用的选择。供应商提示词前缀缓存与 LangChain 整体响应缓存分开，必须依据响应 usage 等实际证据判断命中，不能以传入标记宣称命中。错误处理区分本地配置校验、模型请求失败和 Agent 任务失败；先记录可观测的失败路径，再决定有限重试或降级策略。本文仅记录设计方向，尚非实现或验证结果。

2026-09-30 新增候选：用户建议采用 Pi 式项目级 thinking level；模型不支持请求等级时，按有序等级先向上寻找首个支持值，找不到再向下寻找。进入 Spec 时应按具体模型能力映射，而非按供应商名称推断；记录 requested/effective/native 三个值，避免实际降级或升档不可见。运行时收到供应商“参数不支持”的错误不自动改等级重发；先报告能力表与服务实际不符。此项尚未实现，具体等级集合和生效时点待定。

错误边界候选：在框架模型调用边界捕获供应商失败，产生不含密钥或原始请求的结构化事件，并将失败显式传播给上层；上层负责展示、标记任务失败及后续是否重试。项目模型接入层提供能力映射及错误分类，Agent 运行层负责在 `create_agent` 的 `wrap_model_call` 边界观测调用；不为复制 Pi 事件流而重写框架循环。重试次数、超时与取消语义作为独立设计项，先验证调用失败不会被伪装为正常 `AIMessage`。此为讨论中的建议，需阶段 Spec 和测试确认。

## 16. 模型层 thinking 与失败分类设计（2026-09-30）

项目级显式等级参考 Pi：`off < minimal < low < medium < high < xhigh < max`。请求等级由具体模型的能力表按“自身 → 向上 → 向下”解析，再映射供应商参数；没有能力证据的 OpenAI 兼容网关或本地模型不凭供应商名称假定支持。无效等级应在请求前拒绝，不参与回退。回退记录请求等级、选中等级、原生参数及模型 ID；“选中”只证明发送了参数，不证明供应商实际执行了该等级。若服务返回不支持参数，不以运行时降级重发掩盖能力表错误。

用户已确认 `model_default` 作为**未指定等级的独立选择**，不放进上述有序集合，也不触发回退：表示不向供应商传显式等级。它与 `off` 必须区分，否则启用项目等级功能可能改变现有模型的默认推理行为。

模型层失败采用稳定的 `category` 加细分 `reason`，只覆盖模型配置、模型请求与框架接线；业务工具和测试执行失败另有类型。以下八类作为本阶段的设计基线，具体细分值、异常映射与事件字段仍需阶段 Spec 和失败样本确认：

| category | 典型 reason | 默认处理方向 |
| --- | --- | --- |
| `configuration` | 配置格式、私有权限、未知模型 ID、能力表无效 | 请求前失败；修改配置后重试 |
| `access_denied` | 认证失败、权限不足 | 终止；修复凭证或授权，不自动重试 |
| `request_rejected` | 参数不支持、远端模型不存在、上下文超限、供应商明确拒绝请求 | 原请求不自动重试；上下文处理另作策略 |
| `limit_exceeded` | 临时速率限制、额度/消费上限、无法区分的限制 | 仅确认是临时限流且预算允许时考虑等待重试；额度耗尽不重试 |
| `transient` | 超时、连接失败、供应商过载/服务端故障 | 仅在未产生不可安全重放的部分结果时考虑有限重试 |
| `cancelled` | 用户或上层取消 | 记为取消，不当作供应商故障或自动重试 |
| `internal` | 项目代码或框架接线缺陷 | 终止并记录内部诊断，不伪装成供应商故障 |
| `unknown` | 已知模型/SDK 边界的未分类错误 | 保守终止，不盲目重试；依据新证据补规则 |

分类不能只看 HTTP 状态：429 可表示临时限流或额度/消费上限；流式输出开始后还可能出现错误而 HTTP 状态仍为 200。事件可保存脱敏的供应商状态/错误码、请求 ID、阶段与是否已输出内容；不可保存密钥、原始提示词或未经处理的异常文字。`category` 和 `reason` 是诊断事实，是否重试还要看预算、响应阶段和调用策略。当前是设计基线，没有对应实现或验证；根据真实供应商证据可修订分类细节。
