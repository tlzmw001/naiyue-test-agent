## 2. 先区分三种数据和两次选择

- 聊天历史保留发生过什么；会话摘要为当前线程压缩上下文。
- 长期记忆抽出可跨会话复用的偏好、决策和经验，允许更正、替代、删除和限制作用域。
- 第一次选择：哪些原始内容值得成为记忆。
- 第二次选择：面对本次任务，哪些有效记忆值得进入有限上下文。

两个选择不能用同一个“重要度”替代。保存价值高的记忆也可能与当前问题无关；向量相似度高的历史内容也未必已经确认。

## 3. Pi：上下文文件与扩展入口

真实链：`resource-loader.ts::loadProjectContextFiles` → `agent-session.ts::_baseSystemPromptOptions` → `system-prompt.ts::buildSystemPrompt`。全局目录和项目祖先目录中的 AGENTS/CLAUDE 上下文文件进入项目提示词部分。模型可借助已有文件工具继续读资料。

`agent-session.ts` 在调用前还运行扩展的 `emitBeforeAgentStart`，扩展可以提供自定义消息或本轮 system prompt。这是接入外部记忆的入口，不代表扩展接点已经实现自动提炼或语义检索。核对的这条核心装配链未见内建的“对话自动提炼→向量召回”流程；不把这个局部结论扩大成所有 Pi 版本和扩展都没有记忆。

另外，`packages/agent/src/harness/session/memory.ts` 是内存会话存储，不是跨进程长期记忆。

## 4. Claude 与 ChatGPT：公开产品合同

Claude Code 区分人写的项目规则和模型写的 auto memory。后者使用同仓库共享的本地记忆目录，MEMORY.md 是短索引，启动读取前 200 行或 25KB 中较小的范围；主题详情按需由文件工具读取。支持查看、编辑和删除。这里没有公开证据说明必须依赖向量检索。[官方说明](https://code.claude.com/docs/en/memory)

Claude Chat 公开说明现在按对话过程中的独立主题保存记忆，既可自动保存也可明确要求记住；查历史聊天则使用 RAG 工具，并存在项目范围边界。这不是 Claude Code 的本地 Markdown 目录机制，私有提炼与排序算法未公开。[官方说明](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context)

ChatGPT 公开说明记忆可携带稳定偏好、重复工作流和项目惯例，同时与必须遵守的项目规则区分。ChatGPT Web 记忆与本地 Codex 记忆分开。官方披露本地 Codex 对符合条件的空闲会话在后台生成本地记忆，不能据此推断 ChatGPT Web 使用相同流水线。所读文档没有披露 ChatGPT Web 的具体重要度公式或召回排序。[个性化](https://learn.chatgpt.com/docs/personalize)、[记忆与本地 Codex 的区别](https://learn.chatgpt.com/docs/customization/memories)

可借鉴的产品职责：短常驻上下文、按需取详情、人类可改可删、明确使用范围。不能把产品体验写成已验证的底层算法。

## 5. remem：哪些内容进入记忆

生产链包含两条不同的提炼路径，不能只套用 README 的简图。

### 5.1 回合与会话范围提炼

1. 宿主 hook 捕获用户输入、工具或会话事件，记录 host/project/session/turn 与原始证据。
2. Stop 入口安排 `SessionRollup` 提炼任务；本提交不应把旧 SummaryJob 当成这一主路径。
3. `session_rollup::process` 使用模型处理有界事件范围及补充转录证据，生成 summary、request、decisions、learned、next_steps、preferences 和语义 topic segments。
4. `side_effects::promote_rollup_candidates` 把 decisions/learned/preferences 交给 `memory::promote::summary`，拆分和过滤成候选，携带具体来源事件。
5. 候选通过 `memory_candidate` 的晋升检查后，才进入可正常使用的记忆；失败可能保留为 pending_review。来源或输出触发污染隔离时，主链保留隔离摘要并阻止相应模型可见副作用。

摘要候选的 confidence 是代码固定的 **0.74**、risk 为 medium。摘要晋升门槛 **0.70** 之外，还检查 project scope、Decision/Discovery 类型、来源信任、仓库归属与路由置信度、证据 ID、敏感模式、声明语义以及来源文本支持；默认 gate mode 为 enforce。Preference 会生成候选，但不在这条摘要自动晋升类型白名单里。因此“提取出了 preference”不等于“已经自动作为有效偏好生效”。

### 5.2 工具观察提炼

`observation_extract` 先让模型提取 decision/bugfix/discovery 等观察，要求跳过例行输出、重复背景和未验证计划；随后 `memory_candidate::process` 通过另一次模型处理形成候选。

观察候选自动晋升要求 project + low risk、candidate confidence ≥0.80、路由置信度 ≥0.80、支持观察置信度 ≥0.75，以及来源/类型/证据/内容检查。模型产生的 confidence 和摘要路径的固定分数都不是校准后的真实性概率，源码中的词项或来源支持检查也不能证明每条事实一定正确。

源码：[Stop 生产入口](https://github.com/majiayu000/remem/blob/93d5a3d6f370c5991cc77e86f80891ac7922a2f9/src/summarize/summary_job/hook.rs)、[rollup 模型调用](https://github.com/majiayu000/remem/blob/93d5a3d6f370c5991cc77e86f80891ac7922a2f9/src/session_rollup/mod.rs)、[提炼提示词](https://github.com/majiayu000/remem/blob/93d5a3d6f370c5991cc77e86f80891ac7922a2f9/src/session_rollup/prompt.rs)、[摘要候选生成](https://github.com/majiayu000/remem/blob/93d5a3d6f370c5991cc77e86f80891ac7922a2f9/src/memory/promote/summary.rs)、[晋升规则](https://github.com/majiayu000/remem/blob/93d5a3d6f370c5991cc77e86f80891ac7922a2f9/src/memory_candidate/auto_promote.rs)。

## 6. remem：哪些记忆被检索和注入

### 6.1 SessionStart：用户尚未提出当前问题

`context/query.rs` 用项目名、分支、最近提交、未完成工作流和近期摘要构造最多 512 字符的隐式 query。它是启动线索，不能称为已理解用户尚未输入的任务。

注入检索使用全文 FTS、向量、实体、时间、结构化 fact 通道，以及可配置的 usage 排序信号；合并使用加权倒数排名融合。各通道是否有结果取决于配置和已建索引。一般 search 还支持图扩展等其他路径，不能把它们都说成每次 SessionStart 必跑。

当前默认 Context Bundle 渲染还对受管区段执行相关性筛选：分词后统计 query 词项在候选文字中的命中比例，按分数与 K 限额选取，不是又调用一次 LLM 判断。默认 relevance K 为 1，但只限制相关性管控的候选池，不代表整份启动上下文只有一条记忆。偏好、core 和工作流等有各自区段规则。还有总量与分区字符预算；默认总量为 **12,000 字符，非 token**。最终渲染存有选中、丢弃及预算原因审计。

### 6.2 UserPromptSubmit：已有当前用户问题

`observe/session_init.rs` 捕获本轮用户输入，调用 `context/prompt_submit.rs`。此时可直接以用户 prompt 做混合检索，过滤不适用/已注入/污染等候选。

此路径目标最多 **4 条记忆候选**，输出总限制 **1,800 字符**，还可能带首次回合的续接锚点。注入的是短索引，包括 ID、类型、标题、更新时间、估算详情读取成本，以及 `get_observations source=memory ids=[...]` 的读取提示。不是默认把候选正文整段塞入。模型被提示先打开详情，再据实际使用引用记忆。Claude Code 和 Codex 安装路径都登记了 UserPromptSubmit。

### 6.3 主动工具检索

MCP `search` 返回精选记忆的短结果和下一步详情入口；`get_observations` 按 ID 取详情；`search_raw` 用于字面对话回忆；知道稳定状态 key 时有 `current_state`。这是几个不同目的的工具，精选知识与原始聊天不能混为一个库视图。工具调用是否发生仍取决于模型和实际提供的工具集合。

### 6.4 向量和重排的实际默认

Embedding 默认 provider 为 Auto：先看可用 API 凭据，其次已安装本地语义模型，否则可以落到 feature-hash。feature-hash 不是学到语义关系的模型，不能把“存在向量”直接写成“同义表达语义召回已可靠”。本提交的额外 rerank 默认关闭。默认参数与真实部署效果必须分开。

源码：[隐式 query](https://github.com/majiayu000/remem/blob/93d5a3d6f370c5991cc77e86f80891ac7922a2f9/src/context/implicit_query.rs)、[注入检索通道](https://github.com/majiayu000/remem/blob/93d5a3d6f370c5991cc77e86f80891ac7922a2f9/src/context/hybrid_context/query.rs)、[最终相关性](https://github.com/majiayu000/remem/blob/93d5a3d6f370c5991cc77e86f80891ac7922a2f9/src/context/relevance.rs)、[Bundle 接线](https://github.com/majiayu000/remem/blob/93d5a3d6f370c5991cc77e86f80891ac7922a2f9/src/context_bundle/executor.rs)、[提交时索引渲染](https://github.com/majiayu000/remem/blob/93d5a3d6f370c5991cc77e86f80891ac7922a2f9/src/context/prompt_submit/candidates.rs)、[MCP search](https://github.com/majiayu000/remem/blob/93d5a3d6f370c5991cc77e86f80891ac7922a2f9/src/mcp/server/search_tools.rs)、[Embedding 选择](https://github.com/majiayu000/remem/blob/93d5a3d6f370c5991cc77e86f80891ac7922a2f9/src/retrieval/embedding/status.rs)、[rerank 配置](https://github.com/majiayu000/remem/blob/93d5a3d6f370c5991cc77e86f80891ac7922a2f9/src/retrieval/rerank/config.rs)。

## 7. AgentX 补充：更短的实现链

固定版本 `AbstractMessageHandler` 把当前用户文字交给 `MemoryExtractorService::extractAndPersistAsync`。模型提示词按 PROFILE/TASK/FACT/EPISODIC 判断复用价值。提示词要求 importance≥0.8、EPISODIC≥0.9，但读取的 XML parser 只解析分数和非空文本，没有在这里以阈值再过滤，不能把提示要求说成确定性门禁。

`MemoryDomainService::searchRelevant` 用用户过滤的向量候选，按 `0.7 * similarity + 0.3 * importance` 排序，返回最多 5 条给 `buildMemorySection`，正文进入系统提示词。这个实现适合说明最小数据流，但其同用户作用域、模型自评分和写库/写索引错误边界不能直接搬作我们项目合同。

## 8. 本项目的实际接点

当前 `_prepare_resources` → `prepare_run_resources` → `freeze_run_resources` 按 run 准备项目规则与 Skills。随后 `ToolSetMiddleware._inputs` → `compose_model_prompt` 装配每次模型请求；`session_context::context_view` 使用同一装配函数预览预算。图通过 AsyncSqliteSaver 按 thread 保存会话。

当前 `compose_model_prompt` 的统计分区是 base/project/skills/tool_guidance/subagent_roles；新增 memory 必须同步真实请求、上下文预览、统计分区、压缩预算和根/子作用域，不能只在一处拼接文本。若以后选择 run 冻结记忆，则当轮中途更新到下一 run 才生效；若选择每次模型请求检索，则需定义额外查询成本、一致快照和预览差异。这是待确认设计，不预先改变现在的冻结行为。

框架官方把 thread 状态与跨 thread 长期 Store 区分，Store 提供 namespace/key 等存储接口，不负责自动替项目决定提炼与纠错。我们沿用 create_agent，既有 checkpoint 不会自动升级成长记忆。[官方概念](https://docs.langchain.com/oss/python/concepts/memory)

## 9. 项目建议，尚未确认为 Spec

后续讨论约束更新：用户明确要求用 Python 在本项目实现，不直接接 remem MCP，不引入 Embedding 模型或独立记忆生成模型；需要语言模型判断时只使用项目配置中已有的语言模型。以下参考项目事实保持，项目建议按本约束收敛。

建议组合 Claude Code 的“小索引＋详情按需取”和 remem 的“有来源候选＋本轮检索＋使用审计”，保持本地 Python 应用形态。不要先复制 remem 的完整 worker、知识图谱、dream/compress 和多宿主 hook 平台。

1. **先解决同一工作区的新会话。** 默认跨会话、不跨工作区；个人全局偏好明确管理后再加入。使用稳定工作区身份，不能把端口、PID 或任意路径字符串当全局主体。
2. **记什么：** 用户明确确认的偏好/约束、已经选定的设计及原因、有验证依据的失败经验。例行输出、待讨论建议、单次进度、密钥不进入同一有效记忆池；任务接力状态另归原会话或后续独立能力。
3. **怎样选择：** 模型从有界且带来源的对话/必要工具证据提出结构化候选；程序校验作用域、来源存在、重复/替代和大小边界。明确“记住/更正/忘掉”与自动推断分开处理。低风险明确事实可自动有效化，含糊或冲突的候选先不用于回答；不把所有条目都变成人工逐条批准，也不相信一个 importance 数字足够。
4. **怎样用：** 少量稳定偏好常驻；当前问题检索出少量短条目，复杂经验先给索引再取正文。每条带来源与更新时间。若现有预算不够则少注入，不承诺每条旧记忆必入上下文。
5. **怎样改：** 纠正后旧版本退出默认检索；删除同时影响正文、索引、缓存和后续自动提炼，避免从未变的历史中立即“记回来”。并发更正必须有版本比较，不能仅依赖模型输出的主题 key。
6. **怎样存与接线：** 优先评估现有 SQLite 技术下的工作区记忆数据与索引，具体同库/独立库及备份迁移合同在 Spec 决定；不因 LangGraph 有 Store 就直接增加一套服务。回忆失败应记录并按无记忆继续本次任务；明确请求的记住/删除失败须返回失败，不能假称已经记住。

检索实验调整为不使用 Embedding：在同一中文语料和预算下，验证本地标题/标签/正文查询，以及现有语言模型生成检索词、别名和按需扩展查询的效果。覆盖改写、技术标识符、否定、已替代决定和无关任务；本地索引是否采用 FTS 及中文匹配方式须以实验决定。语义改写漏检的改进方向是查询交互与索引内容，不再把增加向量模型作为本项目选项。

最小实验先评估“选对哪些事实、是否混淆建议与决定、是否错用旧版本、注入成本、故障是否影响主 run”。真实模型写入的额外费用、延迟、触发时点和模型配置也应在实验中比较。自动触发最终可选模型主动工具或回合收尾独立提炼；本轮尚未决定，也不先建设新的后台任务系统。

remem 保留为源码机制参照。用户明确不准备直接连接其 MCP 或采用 Rust 运行依赖；后续实验围绕本项目 Python 实现和已配置语言模型进行。

下一步先确认目标场景、默认作用域、自动写入边界与实验验收，再决定具体切片。本轮未实现记忆功能、未运行应用测试，不把源码调研当成功能或效果验收。

## 10. 代码与测试使用场景的方案讨论

用户补充的重点：记住虚拟环境与网络选择、用例规则与测试结构、自动化工作流程，以及结合知识库、源码和实时配置排障。以下是推荐方向，尚未批准为实现合同。

- 环境选择：记录适用工作区/机器/测试目标/环境、上次选用方式、原因和最后验证证据；使用前检查当前配置和实际可用性。记忆中的代理选择必须注明属于 Web/MCP、测试进程还是待测服务，不能混用；不复制密码、token 或整份环境文件。
- 测试规则：已有 TEST_SPEC/Skill/配置为原始依据，记忆保存规则入口、适用范围和新确认的补充；读取当前版本。通用 pytest 规则不能覆盖 AITest 的 Markdown→Harness/profile→生成测试合同。
- 工作流程：已有 Skill 则保留选择依据和项目差异；新流程可先作为带条件的文字经验保存，不自动改写 Skill 或项目规则。

- 代码参考：记住用户认可、实际验证过的 Harness、fixture、测试类或 suite 的文件入口与适用条件，生成前读取当前代码；不复制整套代码到记忆。TC-ID 不默认全项目唯一，引用至少说明其所在目标/模块/suite。

首选复用主 Agent 和当前配置模型，让其通过记忆读写能力进行记录、纠正与检索；不默认每轮另发起一个整理请求。普通 Agent 循环仍可能增加模型轮数和 token，纳入现有观测。单独收尾提炼作为后续由遗漏证据决定的选项，不先建设后台记忆平台。

## 11. 无 Embedding 检索的定向核验与讨论

用户要求继续深入讨论，不把上一轮方向视为成熟实施方案；层级参考 Claude，记录和检索机制参考 Pi 社区扩展、remem 与 OpenClaw，重点适配中文代码/测试场景。本节只收敛检索问题，不确定存储格式、工具签名或评分权重。

### 11.1 参考实现与证据边界

- Claude Code 官方公开的是短 MEMORY.md 索引、主题文件、按需文件工具读取。本轮文档没有证明所有检索只用 grep，更没有说明因为用户规模而选择 grep。层级和加载粒度可参考，私有检索细节不做推断。[官方文档](https://code.claude.com/docs/en/memory)
- OpenClaw 克隆固定为 `c3f0c51d04ed12603fa9694a1d1cfa312128e010`，临时研究目录 `/tmp/naiyue-memory-retrieval-Lj0c4u/openclaw`。`manager-search-orchestration.ts` 有 lexicalOnly/fts-only 分支；`keyword-query.ts` 构造文本查询并区分 trigram 不足3字符的子串查询；`manager-search.ts::searchKeywordWithFallback` 先搜索正文和路径，两者均为空且无错误时才尝试较宽查询；SQLite 正文排名采用 BM25。没有运行整个 OpenClaw，未把混合检索写成纯关键词系统。[检索说明](https://docs.openclaw.ai/concepts/memory-search)、[实际查询入口](https://github.com/openclaw/openclaw/blob/c3f0c51d04ed12603fa9694a1d1cfa312128e010/extensions/memory-core/src/memory/manager-search.ts)
- 选取一个 Pi 社区扩展 feveromo/pi-hybrid-memory，固定 `068977fd09e3c3dd9b9fbeb7c5b7de71558282a4`，克隆位于 `/tmp/naiyue-memory-retrieval-Lj0c4u/pi-hybrid-memory`。`registration.ts` 的 context hook 调用 buildInjection；后者通过 scoreRecord 选择有界条目，工具搜索复用 searchRecordsWithOptions。实际打分是词项、路径、符号和标签命中，加类型/状态/pinned 等规则，不是 BM25，也不等于所有 Pi 扩展的做法。其 tokenize 正则 `[@a-z0-9_./:-]{2,}` 不提取纯中文词项，不能直接搬用。未安装依赖或运行扩展。[检索源码](https://github.com/feveromo/pi-hybrid-memory/blob/068977fd09e3c3dd9b9fbeb7c5b7de71558282a4/extensions/runtime/retrieval.ts)、[hook接线](https://github.com/feveromo/pi-hybrid-memory/blob/068977fd09e3c3dd9b9fbeb7c5b7de71558282a4/extensions/runtime/registration.ts)
- remem 的已核对固定版本包含 FTS BM25、实体等非向量通道，但整体也有向量和其他机制。只借鉴词项扩展、不同证据入口与有限候选，不能将其完整混合方案描述为无需模型。

### 11.2 算法职责

倒排索引解决“一个词出现在哪些条目”；BM25利用词项稀有度、频率饱和和长度归一解决候选排名。FTS5是可承载这套查询的数据库能力，支持列权重；三者不是互斥算法。中文分词、字符n-gram和技术标识符拆分决定词项本身是什么。编辑距离适合局部拼写纠错，但不宜默认模糊匹配TC-ID、配置名等精确标识。[FTS5官方文档](https://sqlite.org/fts5.html)

SQLite机制探针：项目 `.venv/bin/python` 使用仅内存 sqlite3 数据库，版本3.53.4，分别创建 unicode61 和 trigram FTS5表，插入“测试请求经过公司代理转发”。参数化查询结果：unicode61 MATCH“代理”=0行；trigram MATCH“代理”=0行；trigram MATCH“公司代理”=1行；trigram LIKE“%代理%”=1行。命令退出0。这只验证短中文词和默认切词限制，不是应用召回效果或性能测试；trigram的LIKE回退也不保证使用索引。[官方短于3字符限制](https://sqlite.org/fts5.html#the_trigram_tokenizer)

### 11.3 当前推荐候选

1. 分开讨论所有权范围（个人/项目，环境条目附机器/目标条件）与加载粒度（短索引/主题详情/来源），不把内容类型混作目录层级。
2. 在合法可见范围内、限制候选数量前排除已删除/被替代条目及明确失配的目标条件；这不是BM25分数能代替的工作。
3. 重点验证 BM25＋适合中英混合的切词与字段权重，保护完整技术标识符及必要拆分；中文二元字组或短词子串作为候选补充，不预先固化为唯一实现。
4. 用别名组与主Agent的查询改写衔接语言表达，例如虚拟环境/venv/解释器。别名应表示同一检索概念，不把超时、连接失败等不同事实当成同义词；不默认每次检索另发一次模型请求。
5. 已有明确匹配时保留精度，空结果或明确缺口时有限扩展；返回命中原因、短摘要和详情入口，供主模型检查原文与来源。词项相似不能证明否定、原因或适用条件相同。
6. 保留原文grep/子串查询作为精确定位和诊断能力；它与全文排序互补。索引更正/删除必须与有效记忆状态同步，不能仅更新正文却继续召回旧条目。

最小验证使用相同真实脱敏样本，比较原文grep、普通全文/BM25和场景适配后的全文/BM25；包括自然中文改写、2字关键词、NO_PROXY/路径/TC-ID、不同机器与目标、旧决定及无答案。评价相关条目是否进入有限候选、失配/过期条目是否被排除、注入成本和查询耗时。尚未进行这项召回实验，不能声称选定算法或质量达标。

## 12. 用户明确的刚需与任务续接边界

最新需求优先于前文“任务进度留在历史、另排”的假设：首版需求必须包含任务做到哪里、下一步是什么、同/跨会话续接、风格/决策/踩坑/环境，以及查看其他会话工作进展以减少相互干扰。现在先收敛需求和语义，不直接推进实施切片。

需要分开的数据职责：

| 职责 | 主要内容 | 读取与更新特点 |
| --- | --- | --- |
| 任务续接 | 稳定任务身份、目标、最后确认进展、下一步、阻碍、相关产物/证据、关联会话 | 已知任务直接读取当前记录；改名和换会话不自动产生新任务 |
| 长期复用 | 用户风格、决定和原因、经验、环境选择、流程及参考入口 | 按作用域和有效版本检索；正文与来源可按需读取 |
| 协作状态 | 当前负责会话、运行/审批/受阻状态、正在处理的范围与更新时间 | 以运行层事实及显式归属为准，不能由旧摘要推测当前占用 |

三种职责不等于三套数据库或调度服务。一个会话可能谈多个任务，一个任务可能跨多个会话和多个run；不能直接用session_id或任务标题替代任务身份。进展中的“计划”“代码已改”“验证已通过”应区分，消息回复完或busy解除不代表任务完成。

正常续接：新会话定位既有任务，读最后确认位置及必要源记录，检查当前工作树/环境和原会话是否仍执行，再选择继续、只读查看或明确交接。有多个可能任务时提供候选而非静默选择。历史中的未确认副作用和待审批状态继续服从现有恢复/审批合同，记忆摘要不能授权重放工具。

协作需求需区分“避免因信息缺失误干预”与“执行层拒绝冲突”。当前 Spec104 同服务多会话/独立运行已实现；Write/Edit 的 `_reserve_target` 保护写入执行期间的目标占用，未实现整任务范围归属、Shell写入范围限制或测试数据隔离。只共享进展不能保证互不影响；若要求阻止冲突，须在实际执行入口检查归属/状态/版本，具体保护对象和范围待讨论，不假称记忆本身提供隔离。共享配置、测试账号、数据库数据同样可能冲突，不能只按文件路径判断。

内容提炼可由主Agent使用现有模型进行，运行开始/结束、待审批、工具实际结果和必要保存状态应复用程序已有事实。缺少新语义进展时显示最后确认位置和其时间，不补造新进度；服务重启或异常结束后不得据旧记录宣称会话仍在运行或可直接重放。进度卡片保存失败要明确可续接信息的缺口，不能假称已保存。

### 12.1 remem相关场景的进一步源码核对

固定提交仍为 `93d5a3d6`。`WorkStream` 有稳定ID、status/progress/next_action/blockers及时间；`workstream/write.rs` 绑定会话并保留旧标题别名；`mcp/server/workstream_tools.rs` 提供工作流只读列表和指定条目更新；`context/prompt_submit/candidates.rs::load_first_turn_continuity` 在新会话首个prompt读取活动workstream和有next_steps的未完成摘要。这证明其续接不只是普通关键词搜索，但不能证明其提供跨会话执行锁。

其[任务身份连续性记录](https://github.com/majiayu000/remem/blob/93d5a3d6f370c5991cc77e86f80891ac7922a2f9/docs/specs/workstream-identity-continuity/PRODUCT.md)记录过同一任务因改名被分成三条workstream的事件；本项目应先确定稳定任务身份，而非依赖模型每次生成的标题。

其他与本场景相关的用途：找回决策原因与被否决方案；复用失败定位和预防经验；读取新旧决定的当前有效版本；精选记忆缺失时查原始会话；查看来源、更新时间和未被注入的原因。已核对 `search_tools.rs` 的 current_state/search、`raw_tools.rs` 的search_raw以及本报告前文候选/审计路径。不把这些入口的存在等同于当前项目已有能力，也不因此引入自动dream、知识图谱或额外模型。

### 12.2 对检索设计的直接影响

- “继续这个任务”：已知任务身份读当前任务记录；身份不明才检索或列候选。
- “其他会话现在做什么”：读同工作区当前协作状态，并呈现新鲜度和未知项，不用BM25推断谁在执行。
- “之前用什么环境／为什么这么决定”：全文/BM25/标识符/别名召回，然后读详情和来源。
- “某句话当时怎么说”：原始会话证据检索。

下一步优先讨论任务本身的边界、稳定身份、进度更新时机与跨会话交接，再回到中文检索算法。最新需求尚未批准任何产品实现或新的协调/隔离机制。

## 13. 澄清后的跨会话读取方案与分叉依赖

用户澄清目标来自ChatGPT的新会话了解旧会话进展的体验，认可先区分长期记忆与跨会话发现/读取。本轮问题是参考实现和是否必须前置会话树，不默认要求独立任务认领系统或执行互斥。

结论：无需先完成分叉。当前 `future-work.md` 第11项确为“历史消息编辑、版本选择与会话分支”，第14项为长期与跨会话记忆；待办的相对顺序不证明技术依赖。会话可发现、可读状态、有界读取消息，是跨会话上下文的基础；从旧点重建新模型执行路径是另一项能力。

### 13.1 本项目已经可复用的入口

- `AsyncPersistentApplication.alist_workspace_sessions` → `SessionStorage.list_workspace_sessions`：按工作区读取会话ID、title、state、updated_at、last_run_status等元数据，当前没有独立的语义进展摘要字段。
- `aget_session_status` → `SessionPersistence.astatus`：从持久元数据并结合已装载AgentSession读取busy/run/pending等；未准备和未知状态应保持未知，不能靠历史state猜测实时进展。
- `aget_chat_page/aget_chat_message` → `SessionStorage.read_chat_page/read_chat_message` → `chat_queries`：从独立消息档案分页/分块读正文，有消息revision、conversation_revision、history_version等保护。可以优先复用这个只读面，不要求保留全部旧checkpoint。
- `aprepare`不是纯查询：它可能装载会话、补录档案、保存准备状态；跨会话查看不应为了读取而调用该准备/恢复流程。

这些是应用能力，不等于模型现在已有跨会话工具。仍需设计本工作区可见范围、短目录/概览、主Agent只读调用、消息预算与来源版本。已读历史应作为本次工具返回的参考材料，不把旧ToolMessage和审批状态安装进新会话图。

### 13.2 更直接的参考

OpenClaw固定提交 `c3f0c51d`：`sessions-list-tool.ts` 的模型工具调用 `sessions.list`，可按workspace/project等筛选，按可见性和输出预算裁剪；`sessions-history-tool.ts` 解析目标并检查访问，再经受控范围调用 `chat.history`，返回分页/截断信息。它把“目录/历史读取”和创建/发送/派生等能力分开。本项目只借鉴发现与读取，不照搬其默认跨用户可见范围或完整Gateway。[会话工具说明](https://docs.openclaw.ai/concepts/session-tool)、[列表源码](https://github.com/openclaw/openclaw/blob/c3f0c51d04ed12603fa9694a1d1cfa312128e010/src/agents/tools/sessions-list-tool.ts)、[历史源码](https://github.com/openclaw/openclaw/blob/c3f0c51d04ed12603fa9694a1d1cfa312128e010/src/agents/tools/sessions-history-tool.ts)

### 13.3 候选推进方向

先复用现有元数据/状态/消息档案，提供同工作区的短会话目录及按需历史读取，验证新会话是否能定位、理解和继续旧工作。进展摘要若需要新增，由主Agent/现有配置模型整理并绑定覆盖位置，不默认新增独立模型请求。之后再补历史全文检索和长期记忆的检索组合。

本轮仅源码/官方文档核对及设计笔记；未执行产品测试、没有新的跨会话模型工具或分叉实现。下一步继续讨论会话概览的内容、生成/更新时点和有效范围，而非先实施第11项。

## 14. 已确认的索引交互与下一轮设计边界

用户确认：新会话接收其他相关会话的近期短索引，通过历史工具按需查询某个会话，不在每次启动注入全部详细历史。这是交互基线；以下字段、更新机制与调用频率仍是设计建议，尚未批准实施。

### 14.1 索引内容与新鲜度

- 第一版建议限同工作区，排除当前会话；按真实对话活动选取近期条目，配置条数与总文本预算，超出时说明还有未列出的会话。当前 `list_workspace_sessions` 的置顶/手工顺序不能直接充当近期活动排序。
- 程序提供会话ID、标题、运行状态、活动时间和来源覆盖位置；语义概览提供目标、已做到哪里与下一步。运行空闲或一轮正常结束不能解释为任务完成，无法取得实时状态时保留未知。
- 概览应区分“上次记录”与当前正在执行的轮次。来源会话运行中时允许概览落后，但要带覆盖位置；不能从一个run_started事件推断正在修改哪个文件。
- 尚无概览时只显示明确标注的原文摘录或元数据；最近用户消息若仅为“继续”，不包装成有意义的任务目标。原文摘录不是可靠的进展摘要。

### 14.2 概览生成仍需讨论

候选一由主Agent在正常工具循环内写进展笔记，可减少独立整理请求，但可能漏写、受上下文影响，写下的计划也不证明已经执行。候选二在根会话一轮正常完成且消息保存成功后，用现有配置语言模型整理“旧概览＋新增已保存消息＋必要工具结果”，输出短概览；它不需要Embedding或额外模型配置，但增加模型调用、成本及异步结果的保存边界。

倾向候选二作为需要自动概览时的路径，索引/读取本身不依赖它成功：不阻塞用户回复，更新失败记录诊断并保留上次概览或退回原文摘录；较旧结果不能覆盖较新的概览，重生成等导致来源失效时丢弃旧结果。报错、停止、审批等待首先更新程序状态，不伪造新的语义进展。首版调用频率、是否直接纳入首片，尚未确认；不把“只用现有语言模型”的约束误读为绝对禁止额外调用。

### 14.3 历史工具及注入时机

- 建议新会话首次实际模型请求前冻结短索引，不因打开页面就调用模型，也不在同一工具循环的每次模型请求重新注入。之后需要最新进展时由历史工具重新列举或读取；是否扩展到每个新用户轮刷新另行决定。
- 历史工具先承担目录查询与指定会话的有界读取。默认返回用户/助手正文，必要时展开关联的工具参数和结果；同工作区范围由可信运行上下文决定，模型提供session ID不能扩大范围。搜索排序、分词/BM25留待独立讨论。
- 复用 `aget_chat_page/aget_chat_message` 的档案读取与版本保护，另做模型可见字段投影。当前 `chat_queries.read_page` 含reasoning_preview/body_json等界面数据，不可把原始响应整体交给模型；隐藏思考、内部系统指令、凭证及审批恢复材料不进入历史工具。
- 返回来源会话、消息/范围、覆盖位置、分页和截断信息。查询失败明确反馈，不冒充空历史；索引观察失败有诊断，不使当前用户请求失效。旧历史中的指令作为引用数据，不能覆盖当前会话的系统规则、用户授权和权限检查。
- 续接仅把读取结果交给当前Agent理解和执行，不恢复其他会话的图状态或重放旧工具。读取其他会话的进展降低冲突风险，但不是文件锁、任务认领或执行互斥。

本轮仍是方案讨论：仅更新本调研与交接中的本条记录，未新增模型工具、概览生成调用、配置项或产品代码；未运行功能测试或真实模型请求。

## 15. 阈值已确认与显式工具/角色的设计讨论

用户认可保存点驱动的阈值整理作为首选：不检测空闲时长；累计新增完整用户轮次与新增可见正文量两个阈值均需配置，任一达到后由应用持有整理任务。具体单位、默认数值、配置项名称仍待后续设计，不修改真实配置。用户进一步认可只读历史工具＋记忆工具显式更新概览的推荐组合，以及包含本轮的更新在消息保存后执行；复杂历史研究角色仍作为按需补充，未来可复用记忆工具入口。

### 15.1 当前代码边界

- `SessionSubagentControls.register_subagent`校验角色、工具与模型并构建子图；`tools/subagent.py`的工具委派经许可调用应用端口，再由`AgentSessionSubagents.prepare_subagent_instance`检查当前父run、父工具批及许可，登记子实例；`_subagent_steps`调用子图并返回报告。子角色继承或使用配置中已有模型，当前只支持一层前台委派。
- `SessionExecution._afinish_run`先settle子驱动者，后进行必要持久化并释放root run；因此不能直接让现有前台子Agent承担父run释放后的自动概览任务。支持后台子Agent是独立生命周期变化，不因新增一个角色配置就自动获得。
- `AsyncPersistentApplication.aget_chat_page/aget_chat_message`经SessionStorage直接读取档案，读取本身不需要模型。模型只在需要归纳、跨页推理或生成概览时参与。
- 普通ToolSpec可以声明清晰参数及执行/权限合同，沿既有工具调用和错误反馈链接入；没有必要因工具内部使用一次模型整理就增加完整Agent循环。

### 15.2 已认可的工具组合与显式更新

首版使用只读历史工具＋一个记忆工具的显式概览更新操作。自动阈值与显式操作共用同一应用更新入口、已保存来源快照、模型整理和版本校验保存；自动分支受阈值控制，显式分支可绕过阈值。共享入口有这两个当前消费者，不为未来长期记忆先建设通用工作流平台。自动整理不伪装成获模型许可的工具调用；显式工具仍经现有工具授权。

显式请求如果要包含本轮尚未保存的工作，先登记“本轮成功保存后整理”，工具返回已安排而非已保存；不在工具内等待依赖本轮收尾的概览，避免互相等待。保存成功后交给应用处理器，覆盖范围包含本轮最终回复；保存失败时不发布包含该轮的概览。已保存目标的读取和概览状态可由查询面返回；调用方不能从已接受请求推断最终保存成功。

后续若需要多会话、多轮搜索与证据归纳，可增加只读历史研究角色，调用同样的历史工具并返回来源；角色不拥有数据库或额外权限，不默认改写来源会话概览。LangChain官方也将子Agent作为工具委派来提供上下文隔离，前台/后台是单独的执行取舍。[官方子Agent说明](https://docs.langchain.com/oss/python/langchain/multi-agent/subagents)

长期记忆可未来扩展同一个记忆工具的操作，但会话滚动概览与偏好/决定/环境等独立条目保留各自的来源、作用域、有效性及修改规则；概览更新不自动晋升为长期记忆。首版只公开已经实现的操作，不提前声明记忆写入、遗忘等能力。

### 15.3 工具调度与后台任务查看（2026-10-22用户确认）

当前ToolBatchMiddleware只依据execution_mode选择批次调度：任一工具为sequential则整批按模型顺序执行；全parallel批次用AsyncBatchPlan的有限并发。side_effects提供权限主体事实，不自动决定调度。已确认记忆概览更新工具注册为parallel/may_mutate、return_direct=false：普通工具调用阶段只鉴权、校验范围、登记待保存请求并返回收据，不在工具体内生成概览，不新增after_reply这类调度枚举，也不修改其他工具模式。登记可与Read/Grep并行；同批已有Shell/Edit等串行工具时仍沿原规则串行。

实际概览整理不占旧批次的并发槽：本轮正常结束且必要保存成功后才具备启动条件；应用另行限制整理并发，同会话一次只整理一个来源快照，待处理请求按覆盖目标合并。登记请求有内存/队列副作用，不标read_only；工具成功仅表示请求已接受。登记失败当场反馈，后续模型/保存故障保留旧概览并记录任务失败，不回头修改已结束run的结果。未来长期记忆写操作仍需独立评估调度与权限，不能继承当前概览请求的参数当作永久合同。

现有BackgroundProcessManager的_Operation、公有列表/输出、CLI和前端都带command/shell/ProcessCapture/exit_code/cleanup_confirmed；目前是进程内注册表，不是通用持久任务表。已确认在同一个后台任务查看入口显示概览任务，复用范围过滤、有限分页、状态/详情/停止的产品交互；保留Shell执行器和概览整理器各自的资源拥有权。查询层聚合两类记录并标明kind，公共字段为ID/归属/标题/状态/时间，详情按类型展示。概览条目显示来源覆盖及是否保存，不伪造Shell命令、退出码或日志；stop分发给真实拥有者。当前Shell详情字段/进程收尾合同须保持，UI与查询数据形状的必要调整写入后续Spec，不提前做通用任务调度平台。

概览任务建议区分等待本轮保存、排队、整理中、已保存/失败/取消；进程退出与派生数据写入成功不是同一终态。取消未发布任务保留旧概览；已经提交的版本不因随后stop回滚。概览正文和覆盖位置需持久化，任务条目先沿用进程内生命周期，不据统一列表承诺重启接管。自动概览更新不自动唤醒主Agent或循环产生新的用户轮次。

当前仍仅讨论及文档记录；未新增工具、角色、阈值配置或后台调用，未执行产品/模型测试。跨会话概览的调度/查看机制已收敛；下一讨论建议回到长期记忆的最小条目、作用域与生效规则，再确定更正/替代/失效及无Embedding检索/注入。概览阈值单位和默认值、整理输入/输出边界及预算等在合同明确后统一收束，之后才写实施Spec与切片；不将前文较早的候选切片视为已批准实施计划。

## 16. 长期记忆条目、作用域与生效规则（2026-10-22建议，待确认）

本节只讨论要记什么及何时成为可检索记忆，不批准产品实现。用户已确认的概览调度、工具登记和后台查看合同继续沿用；概览是会话进展，长期记忆是可复用条目，不能自动把整份概览当作有效长期记忆。

### 16.1 最小条目与两类依据

一个条目记录一个可独立更正的约定或经验：内容/标题、用途标签、作用域及适用条件、依据种类、来源引用、状态，以及程序生成的ID/版本/时间。需要时附规则/Skill/代码入口和工具验证证据；环境条目区分最后选用与最后验证，不因被读取而刷新验证时间。分类作为检索用途，不建设多套子系统或复制完整文件。

- 用户约定：用户明确要求保留的偏好、选定方案、测试规范等。它说明用户的选择，不证明对应环境现在可用。
- 历史观察：具体条件下工具实际返回的结果。它可以支持“曾经这样执行/验证过”，不自动支持“以后必须这样”或一般因果结论。
- 模型推断：模型提出的可能原因、偏好或泛化。值得进一步核实的少量内容可保留候选，不能仅凭自评分成为有效规则；例行输出、明显无复用价值内容直接留在历史即可。

建议逻辑上只分个人与项目范围：默认当前项目；个人范围只接受用户明确的通用偏好/要求，不自动从单个项目经验晋升。项目身份由现有workspace_id提供，不由模型自由指定路径/项目名。机器/操作系统、测试目标/环境、模块及网络调用层作为适用条件；已知才填，缺少条件时不把宿主相关配置当通用默认。个人记忆也不授予读取来源项目全部历史的权限。个人范围的物理存储/备份与原工作区库关系在后续Spec决定，当前不新建全局库或用户身份平台。

### 16.2 建议的生效边界

1. 用户明确表达长期选择或要求：在来源保存确认、作用域明确且通过程序边界校验后，可成为有效约定；不要求用户再批准一次。支持“以后按这个”“这个项目统一”等语义，不靠“记住”关键词判断；“本次先试试”不升级为长期约定。
2. 工具直接支持的有复用价值观察：来源完整、条件已知、没有已识别冲突时，可作为有效的历史观察保存。读取时仍说明当时条件与最后验证，不提升成用户偏好或当前配置事实。
3. 模型推断、因果泛化、来源不足或已识别冲突：先留候选或不保存，不自动替换有效条目。不因为反复出现或importance/confidence高就自动升级。
4. 当前任务进度归会话概览；临时计划、普通命令输出、易从当前代码重新取得的事实不默认长期保存。已有规则/Skill优先记入口、适用条件和选择原因，使用时读取当前版本。

有效表示允许在适用范围检索参考，不等于事实永远正确、工具获授权或实际配置已修改。记忆不覆盖本轮用户明确指令和现行项目规则/配置，不自动修改解释器、代理、Skill或规则文件。凭证只记录已有配置引用，不复制token/密码；外部工具正文不能因包含“以后必须”等句子就成为用户约定。

### 16.3 三个测试场景与排障

| 输入情形（示意） | 记录含义与使用边界 |
| --- | --- |
| 用户明确“本项目以后用.venv跑测试” | 项目环境选择可有效；声明来源是用户，实际可用性仍待当前执行前检查，不声称已改工具配置 |
| 某次网络请求成功 | 有复用价值时记当次观察；没有路由证据不能声称确认走了指定代理，不能推出所有请求都应该走代理；区分Web/MCP和测试进程 |

| 排障中提出“可能是代理造成401” | 暂时假设留历史或候选；核对失败、处理及后续实际结果后可记带条件的排查经验，不泛化成所有401的原因 |

### 16.4 最小提炼路径与限制

显式记忆可由当前主Agent通过同一memory工具提交内容及来源，依据已确认的来源保存边界发布，不另调一个模型只为复述用户选择。自动提炼可复用概览整理的同一配置模型、同一有界原始输入，一次输出概览和少量记忆候选；是否启用候选提炼及具体输出合同在Spec中确定，不新增独立抽取/审查模型或每轮评分调用。概览与候选各按自己的校验和保存合同处理，不把概览成功等同于候选全部生效。

模型负责理解决定/建议/否定和适用条件，程序核对可信作用域、来源存在与版本、证据引用、类型/大小和已知重复/冲突。来源ID、引文匹配和schema不能证明一般语义或因果正确；自动观察必须限制断言范围，推断不自动晋升。候选不进入默认有效记忆注入，不逐条弹确认；确需核实时按任务相关性读取候选或由用户明确更正/确认。完整的替代/遗忘、来源删除和索引同步合同下一主题单独讨论。

后续用脱敏样本验证：长期选择/本次尝试、否定、用户消息/工具引文、Windows/Mac环境差异、网络调用层、代码规则变更、冲突/无证据及敏感内容。该方案最脆弱的前提是模型正确理解语义；程序边界能限制影响范围，不能提供真实性保证，需要样本评测发现错存和错用。当前仅源码/官方文档与设计结构检查，未实现新记忆功能或运行模型效果评测。

- remem固定提交仍为93d5a3d6，MemoryType::ALL为decision/discovery/bugfix/architecture/lesson/preference/procedure/session_activity。候选链为build_candidate_prompt生成合法词表→parse_candidate_content/normalize_memory_type→通过既有晋升检查→apply/write保存memory_type并用于search_context构造。通用候选词表和parser排除session_activity，不能把完整枚举等同于同一条自动提炼链支持的类型，也不能据此省略生效门禁。[类型](https://github.com/majiayu000/remem/blob/93d5a3d6f370c5991cc77e86f80891ac7922a2f9/src/memory/types.rs)、[候选提示](https://github.com/majiayu000/remem/blob/93d5a3d6f370c5991cc77e86f80891ac7922a2f9/src/memory_candidate/prompt.rs)、[解析](https://github.com/majiayu000/remem/blob/93d5a3d6f370c5991cc77e86f80891ac7922a2f9/src/memory_candidate/parse.rs)
- AgentX此前已追踪的用户消息→MemoryExtractorService→parser→MemoryDomainService写入链采用PROFILE/TASK/FACT/EPISODIC，更接近广义个人助手。我们不照搬TASK/EPISODIC，任务续接由已确认的会话概览/历史负责。

### 17.2 推荐七个内容主类

| 主类（已确认） | 核心问题与保存对象 | 本项目示意 |
| --- | --- | --- |
| 用户与协作 user | 用户是谁、熟悉什么、希望如何协作 | 方案先讨论再实现；解释机制时先给具体数据形状 |
| 规范与约束 rule | 工作/产物必须满足哪些要求 | 测试用例须有前置条件/断言/清理；生成pytest不作为手工编辑源 |
| 决策与理由 decision | 选了什么、为何选、为何放弃其他方案 | MCP采用官方SDK的取舍；设计不采用某种重试方式的理由 |
| 项目与环境 context | 哪些稳定背景/业务含义/执行条件需要知道 | 项目解释器选择、网络调用层及代理选择、目标测试环境和集成前提 |
| 流程与方法 procedure | 某类任务在什么条件下怎样完成 | 资产检查→生成→收集→执行→读报告；排障时结合知识库/源码/实时配置 |
| 经验与教训 experience | 哪种现象下，哪些尝试/修复/验证值得借鉴 | 有条件的失败修复、无效尝试、成功经验及尚未证实的原因边界 |
| 参考与入口 reference | 需要的信息在哪里、何时去读 | 知识库文档、Nacos查询入口、参考fixture/测试类及其用途 |

同一存储合同下每条一个主类＋少量主题标签；environment/python/pytest/network等为主题细分，不为每个标签建立独立库/Agent。context只放有复用价值、不能简单由当前源码替代的背景/选择/条件，不做杂项桶。会话进度仍是独立概览，不新增长期task/session_activity主类。

### 17.3 合并与区分理由

- Claude user保留用户与协作职责；feedback按纠正对象进入user/rule/decision等，来源保留用户反馈，不因来自纠正就强制同类。
- remem decision与procedure保留；bugfix和lesson合并为experience，兼顾成功修复、失败路线与预防经验。修复/失败结果由证据描述，不凭类型名声称已验证。
- discovery与architecture中的稳定背景合到context；架构选型理由进入decision，可直接从代码取得的结构仅保留必要参考入口。
- 测试规范单列rule，便于区分必须满足的产物要求与完成任务的步骤；reference沿用指路职责，包含本项目需要的内外部资料入口，不因任何条目含来源路径就把它归reference。

### 17.4 语义边界与模型输入

主类按条目的主要用途选择，不按关键词或来源角色机械分类：回答简短→user；代码注释要求中文→rule；默认解释器选择→context；为何选择该环境→decision；如何切换并验证环境→procedure；切换后解决某次失败→experience；环境说明在哪→reference。例子均为分类示意，不创建实际记忆或改变配置。

一段话只有在包含可独立更正、独立复用的不同内容时拆条，不因涉及多个类就重复存储。类型、主题标签、作用域、依据和有效状态分别保存：如解释器选择可以是context/environment/project/user_declared/active，也可以是context/environment/project/tool_observed/active；归为rule不赋予更高权限或自动生效资格。

模型分类说明需包含定义、正例、反例及该类的最小有用信息：user的协作偏好；rule的适用对象/要求；decision的选择/证据支持的理由；context的条件/事实或选择/最后验证；procedure的触发条件/步骤/检查点；experience的现象/条件/尝试/结果/限制；reference的位置/内容/使用场景。未知信息留空，不为填完整结构发明根因或替代方案。程序校验合法类型和值域，语义归类仍需模型和样本验证，不新增独立分类模型。

后续固定样本重点检查user与rule、rule与procedure、context与decision、context与experience、reference与所有带来源条目，以及概览与长期记忆的混淆。当前尚未用模型进行分类实验，不能声称七类已证明提高准确率。本轮仅分类建议/源码与官方文档核对及本研究/交接条目更新，未改产品、配置或依赖。

## 18. 更正、替代、失效与遗忘（2026-10-22用户确认）

用户已认可第17节七类分类及本节生命周期方向，仍未授权产品实现。明确区分操作意图，避免单纯按时间覆盖或把从检索隐藏当作已遗忘；具体枚举、接口和迁移留实施Spec收束。

### 18.1 操作与权威状态

| 意图 | 建议行为 |
| --- | --- |
| 更正：原记录写错/漏了条件 | 对稳定memory ID发布新版本，保留更正来源，旧版本退出默认检索 |
| 替代：原来正确，如今改选方案 | 新选择/新版本明确指向被替代条目，原记录保留历史理由但不当当前默认 |
| 失效/停用：暂不再适用、尚无替代 | 停用对应条件下的有效条目，保留内容与原因供显式追溯 |
| 遗忘：不要继续保存这条记忆 | 清除记忆正文及旧正文版本、移出索引/缓存，保留最小删除/抑制标记防旧任务或原来源重建 |

存储可保持candidate/active/inactive＋失效原因等最小合同，具体枚举在Spec收束；遗忘后的最小标记不保存原正文。默认检索仅返回适用且有效的当前版本；显式历史查询才读未被遗忘的旧版本。记忆正文与必要状态/索引可见性及删除标记的提交需一并确认，失败不能声称更正/遗忘成功；任何搜索命中在最终返回前再核对权威状态，缓存按版本失效。

### 18.2 替代范围与并发

更新须识别原条目ID和预期版本，并核对同一主体/作用域及适用条件。项目规则不删除个人偏好，Windows和Mac环境不能只因同名就互相替代。更正同一条目与新增一条不同条件下的记忆分开；不能由模型生成的标题、topic_key或最新时间单独决定替换范围。

用户明确新选择可修改对应有效条目；自动提炼遇到已识别冲突只产生候选，不用模型分数替换既有约定。单次工具失败不自动推翻用户选定的环境：记录当前验证失败/需复核，不把可能是路径、依赖或网络问题概括成原选择已失效。

并发按预期版本提交：A/B均读v3，B先改为v4，A基于v3的更新失败并要求重新读；不做最后完成者覆盖。后台概览/记忆候选任务还须在发布时检查当前记忆版本、范围变更和删除标记，用户已更正/遗忘后旧任务不能写回。

### 18.3 防止从旧历史重新生成

删除标记最少绑定原条目/范围及已知来源身份或覆盖位置；登记任务和提交候选时均检查，队列里已受影响的任务取消或丢弃对应结果。遗忘不等于删除原会话或备份；原历史仍可能被显式查询，不承诺从所有介质/既有模型上下文擦除内容。

候选提炼以新增原始证据为依据，旧概览/旧记忆不能独立充当新证据；历史工具返回的旧对话保持原来源身份，不把一次新的查询动作当成事实刚刚发生。已失效版本被提炼时同样需要状态核对，不能作为新决定绕过现有版本。

这些检查能确定性阻止已识别条目、已登记旧任务和已知原来源的回写；另一段历史中的任意同义改写仍需语义识别，首版不能声称完全语义级防复活。用户明确“以后不要自动记录这类内容”与“忘掉这一条”范围不同，需记录相应排除意图，不能自动扩成整个类别禁用；重新记住须有新的明确用户意图。

### 18.4 到期、来源与执行时点

2026-10-22用户进一步调整并确认：候选与有效记忆均按类型配置过期时间；user/rule/decision不适用有效记忆TTL，context/procedure/experience/reference初始分别30/180/365/90天，候选默认30天且可按类调整。这替代此前仅按明确截止时间自动到期的建议；计时/续期合同及已确认初始值见[候选方案2.1—2.3](候选记忆转正与工具入口方案-2026-10-22.md)，尚未产品实现或效果评测。过期不等于事实被证伪或执行遗忘；惰性过滤、不新增空闲定时器。明确来源截止时间仍须遵守并取早，环境/代理/实时配置使用前复核，读取不续期。来源变化需重读或待核对，来源不可读保留未知缺口，不由未知推断已删除/已失效。

消息结束后执行只约束依赖完整本轮证据的概览生成/自动提炼。明确指向已有条目的更正、停用、遗忘可在工具调用内完成短事务及必要来源记录，保存失败当场反馈；不等待整轮成功，也不在锁内调用模型。memory工具可继续使用并行调度，靠条目版本与事务处理冲突；未来具体写入操作仍须在Spec验证。更正后不修改原历史、不自动改环境配置或回滚已发生的工具效果。
