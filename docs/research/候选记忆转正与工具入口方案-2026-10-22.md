# 候选记忆转正与工具入口方案

2026-10-22，用户已接受模型语义判断＋程序校验的候选转正机制，并确认2.1—2.3按类型配置候选/有效记忆TTL、豁免类型、初始时长和计时/续期规则；本轮确认history＋memory两个工具及首期聊天管理、不加独立管理页面。具体字段/返回格式在Spec收束，不批准产品实现。沿用七主类、来源/作用域/版本及遗忘合同，当前工作目录＋个人记忆默认直接允许，无额外Ask审批。自动整理仍阈值驱动、失败部分跳过，不保证覆盖、不建设失败补漏任务。本专题补齐候选如何再次被找到、依据什么转正、由谁提交，以及首期工具入口。

## 1. 先区分提取建议与持久候选

模型一次输出的“记忆候选”只是尚待校验的写入建议，不代表每条都必须先入库candidate再人工审批。入库结果按依据区分：

| 情形 | 入库建议 |
| --- | --- |
| 明确用户持久约定或有直接来源支持的可复用观察，条件/范围清楚且无已识别冲突 | 校验后可首次直接active，无第二次用户确认 |
| 有具体复用价值，但缺持久意图/实际验证/适用条件，或存在待解决冲突 | candidate，写清缺什么及所需依据 |
| 例行输出、重复背景、无复用价值猜测、敏感正文或来源不成立 | 不保存；不能把所有模型猜测都堆进候选库 |

持久状态仍用candidate/active/inactive等最小合同；“提取建议”是调用中的数据，不新增一套持久状态。candidate不是审批队列，用户未逐条点击也可以在满足已有生效条件后转正；个人范围允许写入不等于把项目经验自动改成个人通用偏好。

候选至少有现有ID/版本、主类/正文/条件/来源，加待核实原因及需要的依据描述，如缺明确持久选择、缺实际验证、条件不清或冲突待解决。该描述供模型理解，不执行模型生成的代码或任意表达式。

## 2. 转正条件

| 候选缺口 | 什么新依据足够推进 | 什么不够 |
| --- | --- | --- |
| 用户风格/规则/选择的持久意图不明确 | 后续用户明确表达适用范围及持续采用，来源保存可核对 | 重复使用某命令、回复短、模型认为用户大概喜欢 |
| 观察/排障经验尚未验证 | 后续真实工具记录支持收窄后的具体历史观察及条件 | 助手自述已修好、仅凭一次先失败后成功推出因果 |
| 与已有有效选择冲突 | 用户明确改选，或新证据解决候选本身的事实条件；明确用户选择不能仅凭工具成功覆盖 | 最新时间、重要性/置信度、相同标题 |
| 范围/机器/目标等条件不清 | 新来源补齐条件，且目标仍在可信当前目录/个人范围内 | 模型根据路径名字补猜；把Mac和Windows选择互相替代 |

转正时必要时收窄/更正正文，而非保留未经证实的强断言。例：“代理导致401”的候选后来只有同目标请求在代理路径失败、直连成功的证据，可保存当次条件与观察，不能说根因已证明。用户已确认“以后统一.venv”则是选择依据，不要求先跑测试才能记住这项选择；实际可用性另记验证时间。

没有新证据就保持candidate，或由用户丢弃/更正；时间、重复次数、检索次数和模型confidence都不自动触发转正。被否定的候选可按证据停用并保留原因；已遗忘/明确拒绝的内容不能通过自动重新提取复活。

### 2.1 候选与有效记忆按类型过期（已确认）

用户认可转正机制后追问：是否第一阈值提取、第二阈值评估，以及未转正候选如何处理。处理不是固定两阶段；每次阈值均同时处理新增建议和相关已有候选，首次可直接active，后续候选只有在相关新证据出现时重新评估，不逐次全库扫描。

建议未转正不在第二次直接丢弃，但也不永久留在待转正池：

- 新依据不足而仍有价值：继续candidate，保留待核实原因，不强行转正。
- 新证据否定、用户明确丢弃或内容已被替代：inactive并记录原因，退出自动候选查询。
- 长期没有实质新证据：使用对应类型配置的候选保留期，届满后inactive/expired，退出自动候选池。以创建或最近实质新证据为基准，普通读取、再次入选或模型改写不续期，避免候选永不过期；初始时长见2.3。
- 用户要求遗忘：执行既有遗忘合同，清理正文及旧正文版本并保留最小抑制标记。

候选到期不同于用户拒绝/遗忘，不自动永久禁止未来有真实新证据时重新提出；仍须检查既有拒绝/遗忘记录。到期只退出待转正池，按既定历史策略保留失效记录，不等于物理清除或磁盘空间回收。建议读取/整理时惰性判断到期，不新增定时清理或评分任务。

用户本轮进一步指定：配置中同时提供候选过期时间和有效记忆过期时间，按类型区分；部分类型不适用有效记忆TTL，其余按时间过期，以减少陈旧条目持续积累并影响检索。此决定替代上一轮“有效记忆仅明确截止时间才到期”的建议；不改变转正条件、来源/版本/遗忘合同。过期代表退出默认有效集合，不代表事实被证伪。

### 2.2 到期、失效与待复核的判断（已确认）

候选TTL解决是否继续等待依据，有效记忆TTL解决是否继续默认采用，事实是否改变则需要新依据。三者分开处理，不用一个“过期分数”判断，也不增加独立模型或定时巡检。

| 情况 | 判断依据及动作 |
| --- | --- |
| candidate长期未补齐依据 | 程序以创建时刻或最近实质新增证据时刻，加配置的保留时长计算期限；到期退出自动候选池，原因记候选等待到期，不声称内容已被证伪。按经过时间计算，不按触发整理次数。 |
| 已生效条目适用类型TTL | 程序按对应类型配置及首次支持成立/最近实质确认的可信证据时间计算；检索、注入、普通改写不续期，处理旧来源不当成本次新确认。没有新确认，到期退出默认有效集合。 |
| 已生效条目不适用类型TTL | user/rule/decision默认不按年龄自动停用；仍可更正、替代、停用、遗忘，不等于始终注入。 |
| 用户或来源给出明确截止时间 | 与类型TTL相比取较早截止点；不适用类型TTL的条目也须遵守明确截止时间。含糊的“最近/暂时”不由模型猜天数，日期边界及时区须明确。 |
| 用户明确更正/废止/改选 | 沿既定来源、同主体/条件、版本合同更正或停用；自动整理发现冲突仍先留候选，不凭新时间或模型置信度覆盖用户选择。 |
| 环境、代理、配置等可变事实 | 使用前通过当前资料/既有工具复核；旧验证时间只说明历史，不自动证明当前可用。读取或使用记忆不刷新验证时间；一次失败记当前验证失败，不自动取消用户的长期选择。 |
| 来源变化、无法读取或条件不匹配 | 来源变化需重读/待核对，无法读取保留未知缺口；机器/模块/目标不匹配只是不适用本次查询，不能全局停用。 |

候选续期必须带真正新增、与待核实问题有关的原始依据，如补齐目标环境、支持观察或用户持久意图；普通读取、重新表述、旧证据再次引用、仍然表示不确定都不续期。现有配置模型在正常整理请求中判断其是否补充了有效依据，程序核对来源身份/去重/版本并使用可信来源时间，不能由模型自由填写续期时刻。程序校验不等于已证明语义判断正确，仍需样本评测。

有效记忆续期同样要求新的明确确认或实际验证支持该记忆在相应条件下继续适用，不以命中/阅读次数续期。使用新的原始来源时间，不能用整理/导入时间给旧证据制造新鲜度；转正也不能让已经陈旧的依据自动获得一个全新有效期。续期不等于自动提高权限、修改配置或替代冲突的用户决定。

示例：候选保留期若设30天（仅示意，非已定默认），10月1日建候选、10月20日只是检索它，原期限不变；10月20日发生了相关真实验证、仍缺另一项依据，则可从该新依据时刻重新计算30天。重复处理10月1日的原始事件不伪装成10月20日的新验证；模型重新给出高confidence也不能续期或转正。未来真实新依据可重新提出到期内容，仍受拒绝/遗忘及当前版本保护。

环境记忆尽量分清两种断言：“该项目选用.venv”是选择，“某次.venv运行测试成功”是有限条件下的历史观察；不能把后者改写成长期保证该环境始终可用。旧观察不因今天失败变成历史假话，用户选择也不因一次失败被推翻；本次能否执行看本次复核结果，记忆不自动修改解释器或网络配置。

在候选选取、默认有效记忆检索/注入和提交时检查时间/当前权威版本；无需空闲生命周期回调、定时全库扫描或额外模型请求。即使尚未写回inactive，到期项也必须先从有效结果排除；若正常写入路径持久化到期状态，仍用版本检查，避免覆盖另一会话刚补证/延长的记录。现有失败区间跳过合同不变，不因候选未转正重新整理失败区间。

可参考remem固定93d5a3d6的`default_ttl_seconds→ttl_metadata`及`expire_active_memories`：类型/主题/正文时效线索生成期限，程序把到期active改为stale；主题线索检查早于部分持久类型保护，不能概括成这些类型绝不带TTL。本项目建议借鉴明确期限字段与程序执行，首版不复制关键词自动猜TTL策略。[源码](https://github.com/majiayu000/remem/blob/93d5a3d6f370c5991cc77e86f80891ac7922a2f9/src/memory/lifecycle.rs)。本轮核对本地固定源码，未运行参考项目或验证到期效果。

### 2.3 类型与初始时长（设计已确认，不是现行配置）

每类分别配置候选TTL和有效记忆TTL；首期候选TTL默认30天，仍支持按类覆盖。用户已确认下表作为初始默认，依据环境/资料/流程/历史经验的变化特点作出的工程取值，尚无本项目效果评测，不是参考项目默认或行业标准；设计确认不代表产品配置已接线。

| 主类 | 候选TTL初始默认 | 有效记忆TTL初始默认 | 理由 |
| --- | --- | --- | --- |
| user | 30天 | 不适用 | 持久协作偏好不应仅因久未出现丢失 |
| rule | 30天 | 不适用 | 约束以明确修改/废止为准 |
| decision | 30天 | 不适用 | 已确认选择与理由应由后续决定替代 |
| context | 30天 | 30天 | 环境、代理、测试目标变化较快 |
| procedure | 30天 | 180天 | 工作流随工具/项目演化，适合中期复用 |
| experience | 30天 | 365天 | 踩坑/排障经验可长期复用，但旧版本结论可能干扰 |
| reference | 30天 | 90天 | 文档、脚本、知识入口可能迁移或失效 |

“不适用类型TTL”与正整数天数须在配置中明确区分，不以0同时表示立即过期或永久保留；模型不能自行决定时长或把“不适用”授予某条重要记忆。分类仍按内容表达的核心问题，不为逃避TTL把当前环境事实改记成decision；明确长期选择的理由可以是decision，当前可用环境是context。

这控制陈旧条目参与默认检索/提示的范围，不保证总条数或磁盘容量有硬上限。到期过滤需在有限结果截断前生效；历史保留与物理回收另属存储策略，不因本次TTL决定自动删除正文。已有同条目版本更新、去重及有界注入仍然必要，不适用TTL的条目也只按任务相关性选择。

## 3. 再次找到候选及两条入口

自动入口：下一次阈值整理以新增原始材料进行现有词项/标识符检索，分别有界取得相关active与candidate短条目；候选带状态、待核实原因、现有证据和版本，作为同一次整理请求的参考输入。无关候选不全量注入，默认有效记忆搜索/提示仍不混入candidate，不保证每个候选都必然被召回或最终转正。

后续每次触发仍同时提取本批新记忆，不存在“第1次只建候选、第2次只转正”的轮换；无相关新依据的旧候选无需再次发给模型判定。

当前配置语言模型在该次输出中可提出新增条目，或指向已有candidate的更新/激活建议；必须附新来源及必要正文修订。后台整理器做确定性校验和版本事务后提交，不另调复核/评分模型，不定期扫描全部候选，也不主动启动工具验证任务。

显式入口：用户在正常对话中明确确认/更正，或主Agent完成当前任务时得到实际验证结果后，可先读candidate，再通过memory更新操作提交新证据/正文及预期版本。沿既定规则：已有条目可在工具调用中短事务保存必要来源及更新；新提取依赖完整本轮时仍登记后等必要保存，不修改普通工具调度。

“用户明确”必须来自可核对的用户消息，外部网页/工具正文不能冒充；模型自称用户已确认不构成来源。只有旧候选文本、旧概览或一次新的历史查询动作不能构成新发生的验证。后续用户明确要求重整某段旧历史可使用其真实原来源，仍核对原版本和删除标记，不伪装新证据。

## 4. 提交和失败合同

更新需候选ID、预期版本、建议正文/依据及来源。程序核对可信范围、当前candidate状态、来源角色/版本及引文、条件、已知冲突/敏感/抑制标记；模型负责理解否定、临时尝试、持久选择和观察断言。来源存在和引文相等不能证明语义正确，这一判断仍需实际样本评测。

符合条件时，同一条稳定ID在事务中更新正文/版本/证据和active状态及索引可见性；不再新增一份同文active条目留旧candidate无限挂着。旧版本保留状态变更理由，未来遗忘按已有合同清理正文版本。candidate已被另一会话更正/停用/遗忘时，旧expected_version提交失败，不最后写入覆盖。

材料不足返回仍candidate及缺口；更新失败如实反馈，不记成active。自动批次失败按已确认规则跳过，不建立补偿队列；后面真正出现新证据属于新的评估机会，不能以“候选未转正”为由重跑失败旧区间。

## 5. 首期工具与用户入口（已确认）

用户确认以下两个工具入口及聊天管理方式；调度/作用域沿既定合同，具体字段、操作枚举与返回格式在实施Spec按现有Pydantic/ToolSpec收束，无其他阻塞本项的产品选择：

| 入口 | 操作职责 |
| --- | --- |
| history | 当前工作目录的会话目录/概览、关键词查询和指定历史有界读取；返回真实来源、分页/截断，不恢复或操作其他会话 |
| memory | 列表/搜索/详情（默认active，可显式查询candidate）、记录、更新/补证/转正、停用、遗忘，以及登记更新概览 |

memory更新承担候选转正，不额外增加一个无条件转正工具。来源不足时返回仍candidate，不将模型提交的status=active作为最终状态。显式遗忘/更正仍按已获授权范围执行，无逐条审批弹窗；所有入口仍检查实际工具启用/许可、可信工作区和条目身份。

执行模式沿已讨论合同：history为parallel/read_only；memory为parallel/may_mutate、return_direct=false，内部短事务/CAS，更新概览仅登记。任何同批串行工具仍沿现有批次规则执行，不能用并行声明规避业务顺序；需要依赖前一步返回ID/版本的更新在后续工具调用进行。

返回明确区分找到的active/candidate、已保存、仍候选/缺什么、冲突/失败，以及概览请求已登记/task_id；登记不是保存成功。查询空结果和故障分开。工作目录/个人范围直接允许，不新增候选转正权限审批；语义上用户作出持久选择与权限审批是两件事。

首期不新增独立记忆管理页面：用户可在聊天中要求列候选、读详情、纠正或遗忘，模型调用同样工具；概览整理进度沿已确认的后台任务查看入口。目录/历史查询本身不需模型；多会话复杂归纳角色以后按需求补充，不在首期增加记忆审批Agent或通用任务平台。

## 6. 来源与验证边界

本项目ToolSpec已有执行模式/副作用/权限与注入runtime合同，ToolSetMiddleware从活动集合公开工具并由许可进入应用；工具返回不是运行机制控制。memory的scope应从可信runtime读取，不让模型自由指定数据库/任意项目。现有task_*只处理Shell进程，不直接把它的进程接口改名充当记忆执行器。

Pi固定a69bef789的agent-session._emitExtensionEvent将agent_end/turn_end交扩展，不能由此推断核心已有candidate转正。AgentX固定3fcfa0e的MemoryExtractorService.extractAndPersistAsync→extract→MemoryDomainService.saveMemories首次新建直接status=ACTIVE，没有本方案的待核实候选合同；不把其CandidateMemory类名当审核流程。
