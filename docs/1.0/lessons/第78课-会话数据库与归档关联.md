## 1. 同文件内的三类职责

| 数据 | 主要表 | 所回答的问题 |
|---|---|---|
| 应用会话元数据 | naiyue_sessions | 产品里的会话是谁，选什么模型/工具/模式，当前绑定哪个thread，上次必要确认在哪里 |
| 图持久状态 | checkpoints、writes | 该thread保存了什么执行状态、父子checkpoint和待处理写入 |
| 聊天归档与同步边界 | naiyue_chat_messages、naiyue_chat_sync | 按消息/分页展示哪些历史，已同步到哪一个checkpoint |

它们位于同一SQLite文件，但官方AsyncSqliteSaver和应用SessionStorage采用各自连接/提交路径，不是所有写入共同包在一个事务里。关联依靠应用使用字段建立，不等于声明了全部SQL外键。SessionStorage还有工作区绑定、schema、回复边界/重新生成、用量和诊断等表；本课不逐表展开。

## 2. 一个正常任务的记录形状

用户S1/R1要求读取note并解释，当前thread=TH1，根namespace=''。代表图消息H1用户、A1模型read调用call-read、T1工具结果、A2最终回答；假设最终checkpoint=CP4，中间还有CP1/CP2/CP3。仅为关系示意，实际每run可能有更多hook/节点checkpoint。

```python
# naiyue_sessions行的关键字段
{'session_id':'S1', 'thread_id':'TH1', 'model_id':'A',
 'workspace_root':'示意工作区', 'state':'ready', 'run_id':'R1',
 'checkpoint_id':'CP4', 'checkpoint_ns':'', 'last_run_status':'completed',
 'active_tool_names_json':'["read"]', 'permission_mode':'Default',
 'thinking_level':'model_default', 'conversation_revision':0}
```

run_id列可保留最近运行ID，完成时不一定置空；非空不能单独判断busy。数据库state、当前进程ActiveRun、恢复/阻断分类分别有职责；不能直接把一行数据库当完整AgentSession对象。

checkpoints的主键是(thread_id,checkpoint_ns,checkpoint_id)，每行另存parent_checkpoint_id/type/checkpoint BLOB/metadata BLOB。checkpoint为框架序列化的通道状态，不是每行一条聊天消息。writes按thread/namespace/checkpoint/task_id/idx保存channel/type/value，供框架还原待处理任务写入，不是工具业务审计表。

| naiyue_chat_messages主要投影 | 示例 |
|---|---|
| session_id/thread_id/checkpoint_ns | S1/TH1/'' |
| message_id | T1 |
| sequence/revision | 3/1 |
| message_type/kind | tool/message |
| parent_message_id | A1 |
| source_checkpoint_id | CP3（这份内容来自的checkpoint，不必是最终CP4） |
| body_json/body_hash | message_to_dict JSON及SHA256 |
| reply_id/source_thread_id | 任务关联ID/原来源thread |

消息主键为(session_id,thread_id,checkpoint_ns,message_id)，sequence在该作用域唯一，不是全库自增或事件sequence。ToolMessage的tool_call_id在body_json.data中，与parent_message_id作用不同：前者对工具调用，后者对承载该调用的AI消息。

同步头形状：{session_id:S1,thread_id:TH1,checkpoint_ns:'',agent_path:root,checkpoint_id:CP4,revision:1,history_version:0,stopped:0}。它表示归档已经处理到CP4，不是当前模型上下文的消息副本。

## 3. ID与版本的生产/消费者

| 身份/版本 | 来源与用途 |
|---|---|
| session_id | SessionService的创建路径生成uuid4，应用会话身份 |
| thread_id | 创建时另生成uuid4，传图config，Session行绑定；重新生成可换thread而保留session |
| run_id | 应用准入未传入时生成uuid4；同thread可有多次run |
| checkpoint_id | 框架创建checkpoint生成，saver保存；不是SQLite行号 |
| message_id | 输入/模型产生，缺失由图reducer补齐；归档沿用它而非重新发号 |
| chat_messages.revision | 初始1；同作用域同ID内容修订时增加 |
| chat_sync.revision | 成功应用一份ChatUpdate时推进，作为候选expected_revision比较值 |
| chat_sync.history_version | 已有归档消息修订/相关分支变化时使旧分页视图可判陈旧；普通追加不等于每次增加 |
| session.conversation_revision | 重新生成激活切换等会话分支版本，不是普通每次发送计数 |

## 4. 创建和保存的主链

open_async_persistent_application先开SessionStorage、构建模型/工具资源，再用同一路径创建官方AsyncSqliteSaver并setup，最后装配SessionService/persistence/图。初始化表/迁移不是执行用户任务；观察订阅和正式图装配分别接线。

创建会话先生成S1/TH1与内存对象，再storage.create插入ready行；写入失败会撤下内存安装。此时checkpoint_id可为NULL、尚无消息归档，并不要求建会话就调用模型。

执行时start将_active[S1]=R1保留拥有者，再mark_running写会话行；正式图使用config.configurable.thread_id=TH1，必要持久运行durability='sync'。图调用saver保存多个checkpoint。此时应用行的confirmed checkpoint列仍可保持上次确认值，直播事件也不代替归档。

必要收尾：SessionExecution._afinish_run → SessionPersistence.afinish → 验证当前_active[S1]仍为R1 → 根据观察结果/人工核对选应用state。正常ready时aget_state取得最新快照，要求checkpoint存在、没有next、没有任务interrupt/error → collect_chat_updates → storage.finish_run → 后续原收尾与run终局。用量flush仍是独立可降级统计，不决定此处必要保存结果。

## 5. 为什么收集祖先快照，而非只保存最后messages

collect_chat_updates读取当前thread及chat_sync旧头，从最新checkpoint沿选中父链回到已归档边界，官方历史按每页64条读取，跳过不在当前祖先链上的兄弟快照，再按时间顺序收集真实消息；最后也检查latest快照值。同ID同hash去重，修订保留最后候选。

这样同run中先产生工具结果、后又被压缩的原消息，也可从祖先快照收集。只读最终messages会漏掉被摘要替换的内容。摘要另记kind=context_summary，普通分页查询过滤kind=message，因此压缩不等于删聊天历史。

收集结果ChatUpdate包含thread/ns/agent_path、expected_revision、目标checkpoint_id、候选消息、stopped及回复边界；此时尚未写归档。snapshot身份检查thread与根namespace，消息必须是BaseMessage且ID有效不重复、正文可JSON序列化；缺父链或身份不符不推进游标。

## 6. 一次应用事务原子地改什么

```text
SessionStorage.finish_run
→ BEGIN IMMEDIATE（应用连接）
→ _write_chat_updates
    比较数据库chat_sync.revision与候选expected_revision
    新消息分配MAX(sequence)+1，初始revision=1
    同ID同hash及父关系相同则跳过正文写入
    同ID修订更新原行，sequence保留，message revision增加
    保存回复边界并更新chat_sync到目标checkpoint/revision
→ 结算对应重新生成操作状态（如有）
→ 更新session.state/checkpoint_id/checkpoint_ns/last_run_status
→ 正常退出连接事务则提交；异常则回滚本事务
```

示例：候选expected_revision=3，写入时当前head.revision仍为3，才应用并推进到4；若已为4，抛chat_history_stale，拒绝旧候选。该检查不是只比checkpoint字符串，也不等于普通运行一定有并发竞争；测试通过复用旧update验证此合同。

图此前保存checkpoint使用另一事务，不被这个事务回滚。标题等后续动作也不能自动说全部属于同一事务。

## 7. 成功、失败和重启

成功R1后：session ready/confirmed CP4；chat_sync CP4；消息归档含H1/A1/T1/A2。之后压缩，当前图可只有summary+保留消息，归档仍保留原消息。重新开应用时根据S1找到TH1，验证最新图状态和会话确认后恢复；不是从聊天归档拼接所有正文直接执行。

失败收尾时state不是ready会沿用上次应用确认checkpoint，但归档仍可收集更晚已保存事实，因此chat_sync.checkpoint_id与session.checkpoint_id不保证每种状态都相等。崩溃后running也不代表旧run还活着；恢复读取最新图事实与应用状态共同分类，不倒退到旧确认点掩盖结果。

必要归档事务失败：该事务的新消息/同步头/session完成标记都回滚，但图checkpoint可能已保存。SessionPersistence添加当前进程_blocked并抛session_save_unconfirmed，run不得报告completed；内存busy释放与允许再次运行是不同判断。跨重启按原恢复分类处理，不自动重放工具。

可选事件日志、用量和诊断表不作为正式归档生产者；collect走保存快照。这也是丢失直播片段后仍可从归档校准的基础，但不承诺未保存的流式草稿一定可恢复。

## 9. 追问收束：全部表与checkpoint写入时点

临时SessionStorage初始化并由官方AsyncSqliteSaver.setup后，sqlite_schema有14张表：11张应用表、2张框架表，加SQLite内部sqlite_sequence。应用schema版本13。

| 表 | 用途 |
|---|---|
| naiyue_store_info / naiyue_workspace | schema迁移版本 / 工作区身份绑定 |
| naiyue_sessions | 会话配置、状态、当前thread与应用确认checkpoint |
| checkpoints / writes | 图快照及父关系 / 所属执行位置的任务通道中间写入 |
| naiyue_chat_messages / naiyue_chat_sync | 消息归档及内容来源 / 归档同步到的checkpoint和版本 |
| naiyue_reply_boundaries / naiyue_regenerations | 输入前边界 / 重新生成操作幂等及阶段 |
| naiyue_model_invocations / naiyue_model_usage_runs | 单次模型调用事实 / run用量采集完整性 |
| naiyue_diagnostic_runs / naiyue_diagnostic_events | 有限诊断采集批次 / 诊断事件 |
| sqlite_sequence（内部） | diagnostic_runs的AUTOINCREMENT序号，不生成checkpoint ID |

第二个临时探针沿现有build/ToolModel/read入口，用HumanMessage H1、模型read调用A1、工具结果T1、最终AI A2走正式持久应用。实际框架ID按时间改标C0—C20，T1也是短别名。首次创建会话confirmed checkpoint为NULL；C0 input快照messages为空，C1才含H1，C5含A1，C11含T1，C14含A2，C20 next为空。中间多个middleware节点消息不变仍有快照，不能把一条消息等同一个checkpoint。

| 内容 | writes关联的执行checkpoint | chat_messages.source_checkpoint_id |
|---|---|---|
| H1 | C0 | C1 |
| A1 | C4 | C5 |
| T1 | C10 | C11 |
| A2 | C13 | C14 |

正常收尾后sessions.checkpoint_id和chat_sync.checkpoint_id均为C20。reply_boundaries中H1对应reply的source_checkpoint_id为C0，即首次含H1的C1.parent_config所指checkpoint。它表示消息进入messages前的边界，不等于系统尚未接收输入；C0已经有输入调度信息。边界指向C0，SQL行却是在后面的归档事务写入；INSERT OR IGNORE保留原边界，不随最新快照重写。

六张带专门checkpoint引用的表各有职责：checkpoints保存新快照与parent；writes归属执行上下文；sessions是应用确认位置；chat_sync是归档进度；chat_messages是该版内容来源；reply_boundaries是输入前边界。source字段不是全局最新指针。同ID同正文/父关系归档跳过；内容修订才更新消息来源和revision。独立save_chat_updates也可只推进归档；恢复/重新生成有专门会话checkpoint写入入口，不能说只有正常收尾才能改确认列。

这两次探针使用临时目录并清理，既非真实用户库，也非真实模型选择工具或业务质量证据；本轮未重新执行失败测试。后续失败示例沿源码解释：图最新F3且失败收尾提交成功时，sessions仍C20而chat_sync可到F3；若应用最终SQL事务失败，则session和同步头保持旧确认，图F3不回滚。重新生成保留消息可能移到新thread下，查询原来源要结合source_thread_id与原source_checkpoint_id。
