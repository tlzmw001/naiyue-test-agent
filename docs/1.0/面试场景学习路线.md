# Naiyue Test Agent 面试场景学习路线

基线为 2026-11-06 本机 `main`，已提交版本 `4629067`。本机 MCP 服务级勾选、文件认证头和记忆引文诊断还有工作区改动。涉及这些细节时，开课前再核对分支和实现。旧课保留，当前代码入口以本页和实际调用方为准。[旧场景索引](../2.0/阅读索引.md) · [开发交接](../handoff.md)

选题按三件事排序：能否解释项目主链，能否沿着失败场景追到代码和测试，是否能讲出本项目自己的设计取舍。先学读懂一条消息，再学运行途中会发生什么，最后跨过本机和云端的边界。面试价值是基于项目的判断。

## 当前起点 · 场景 01

前置装配地图先交代 `HostManager` 打开或复用 Host、`assemble_host` 创建 `SessionService` 并接入 `SessionAPI/RunAPI`，再进入测试准备和发送链。本场景读懂创建顺序、作用范围和共享关系；场景 06 进一步追项目/普通聊天 Host 的选择与复用、会话归属和持久化，关闭与运行收尾的交互在场景 08 展开。

按同一条消息的运行顺序分四段：① 测试准备，从定义工具和预设模型到应用组装完成。② 应用入口，从 `RunAPI.start` 到 `RunLifecycle.arun` 把输入交给图。③ 图内循环，从第一次模型请求到工具回填、第二次模型回答和图退出。④ 应用收尾，从图返回到处理保存、释放和终态，再回到测试断言。事件细节与日志留到场景 17。

四段开场先对齐普通本机网页会话的真实入口。`WebApi.start` 经 HTTP 路由 `start` 进入 `WebService.start → RunDelivery.start → _launch`，后台 `_produce` 再调用 `RunAPI.start`，从此与本节测试进入共同实现。网页提交返回运行受理信息，界面通过独立事件连接接收过程；测试直接等待 `runs.start` 的结果字典。带读 `_produce` 调用处，认清汇合点；HTTP 归属、幂等、后台任务与事件投递在对应场景展开。课堂模拟模型预设响应，实际模型依据请求返回结果，实际工具和项目资源也由应用配置装配。[网页启动 API](../../frontend/src/api.ts) · [网页投递](../../naiyue_test_agent/web/run_delivery.py)

设计问题是「谁负责管理这一轮，谁负责反复调用模型和工具」。本机入口 `RunAPI` 整理输入，`SessionService` 找到目标会话并处理运行准入，`AgentSession` 持有本会话的 `SessionRuntime`，其 `RunLifecycle` 负责一次运行的准备、调用和收尾。`create_agent` 组装的图负责模型与工具之间的循环，项目在图上接入工具、权限和运行控制等规则。[入口](../../naiyue_test_agent/application/sessions/run_api.py) · [会话组成](../../naiyue_test_agent/application/sessions/agent_session.py) · [图装配](../../naiyue_test_agent/agent_runtime/__init__.py)

开篇用一个设计变化来辨认职责。此前执行、控制、审批、子 Agent 的方法经由 mixin 混进 `AgentSession`，会隐式读取同一对象上的状态。重构后，它们由 `RunLifecycle`、`ControlQueue`、`ApprovalBook`、`SubagentRegistry` 分别负责，构造时收到同一个 `SessionRuntime`。这样可以从构造参数看出它们依赖什么，也能对照停止和保存的顺序，解释为什么四个对象共用一份当前运行记录。第一课只沿 `RunLifecycle` 走完一次，其他协作者留到相关场景展开。[重构设计与正常、失败路径](../specs/128-06-session-collaborators.md)

测试里的模拟模型先给出 `probe(value='PRIVATE_ARG')`，调用 ID 为 `c1`。工具返回 `PRIVATE_TOOL`，第二次模型调用结束于 `PRIVATE_ANSWER`。这些字符串是测试夹具中的值。先看 `result['messages']` 为什么依次包含人类消息、模型的工具请求、工具结果、最终模型回答。

从 `RunAPI.start` 进入 `SessionService.arun`，由当前会话的 `RunLifecycle.arun` 准备运行和调用图。第一遍在测试返回位置观察 `[(m.type, m.content) for m in result['messages']]` 及 `result['messages'][1].tool_calls[0]['id']` 和 `result['messages'][2].tool_call_id`。后续再到模型调用和工具执行的位置跟进同一组值。用直接调用 `create_agent` 的小探针理解框架钩子顺序，再回到项目实际注册的中间件。[项目用例](../../tests/test_application_message_events.py) · [框架探针](../../tests/test_agent_middleware_order.py)
