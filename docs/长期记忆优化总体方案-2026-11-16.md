阅读建议：先读第 1–3 节理解整个过程，再看第 4–8 节的边界；准备实施时从 Spec143BM 总索引进入对应分片。第 3 节中的 P1、M17、18 passed 为说明流程的虚构例子，不是项目真实用户数据或运行结果；第 12 节另列本次对话前期实际检查证据。

## 1. 这次具体要改善什么

推荐保留现有的核心分工：模型理解对话、提出值得记住的内容；程序控制来源、权限、状态和实际写入。在此基础上，把后台处理改为“先提议，再带着提议找旧记忆，最后集中比较”。前台则用少量完整问题分别检索。

我们希望得到以下可检查的行为：

1. 一段话不会仅仅因为超过固定字符数就失去前后关系；必须拆开时，模型知道它在读哪一轮、哪条消息、哪一部分。
2. 模型不用手抄引文才能证明来源，程序仍能还原其选中的真实原文。
3. 新信息与旧记忆谈的是同一件事时，先判断重复、更正、补充或不同适用条件，再决定保存方式。
4. 长用户消息包含多件事时，一件事附带的编号不会阻止另一件事的记忆被找到。
5. 失败或超出预算时记录实际范围和原因并跳过，不重试、不补偿；保留独立成功的结果，不把遗漏说成已成功整理。

这里有一条必须纠正的认识：**程序核实“这句话确实说过”，不能证明“模型对这句话的概括一定正确”。**例如引用“以后使用 `.venv`”，却生成“以后使用系统 Python”，引用可以是真的，结论仍然相反。新方案会集中做语义复核，并用负例评测；不承诺完全消除幻觉。

最小改法是只修输入边界和查询构造，仍保持一批一次模型调用。它成本低，但无法充分解决“提议生成前不知道该比较什么”“真引用支持不了新结论”等问题。因此推荐下面的两阶段方案；失败跳过与调用成本分别见第 7、8 节。两阶段不要求保存可恢复的中间提议。

## 2. 当前实现：哪些判断已经核实

| 环节 | 当前源码事实 | 对本次设计的影响 |
| --- | --- | --- |
| 输入切分 | `memory_batches` 按字符区间读取，再按预算缩短；默认读取块为 4096 字符，模型投影未携带完整回复/工具配对信息 | 不只是总预算装不下时才可能切断消息，需要同时改读取单位和模型输入结构 |
| 后台查旧记忆 | 先拼批次用户文本，取前部有限文本查询，然后将相关记忆放入同一次整理调用 | 查询还不知道具体会提议哪件事，相关条目也反过来挤占新对话预算 |
| 前台自动召回 | 使用最近真实用户消息的末尾有限文本；词法结果还受词段覆盖、技术锚点等条件影响 | 长消息会稀释覆盖率，独立事项可能被同一个技术锚点约束 |
| 引文核验 | 要求唯一精确匹配；空白/反引号差异当前仅诊断，不放行 | 确实存在格式性拒绝，但不宜直接改成模糊匹配放行 |
| 写入校验 | 来源、角色、真实用户输入、工具状态、遗忘抑制、版本和生命周期均有门禁 | 这些保护保留；要改善的是输入合同和语义判断，不是整体放宽 |
| 来源保存 | 已存短引文和位置，读取时仍要回查聊天归档；未持久保存全部新写入时认定的来源属性 | “已经有 quote”不等于“原文消失后可作为合格快照读取” |
| 清理 | 自动 checkpoint 清理不删除聊天归档；删除会话会删除归档，独立记忆保留 | 必须区分 checkpoint 清理、删会话和遗忘记忆 |
| 进度 | 接纳目标时自动位置已前移；任务执行对象在内存，接纳不代表全部处理成功 | 保留触发基线与实际成功/跳过的区别，不引入必须补齐的恢复账本 |

本次对话的隔离探针已复现：短中文被任意字符边界切开；短查询可命中而加长后的同意图查询丢失；附带无关技术编号会影响命中；真实引文加相反结论可通过当前来源门禁。这些是有限构造样本，不是生产错误率。此前两组现有测试实际结果为 92 passed、49 passed，说明既有合同仍被测试覆盖，不证明上述业务质量已经合格。

源码入口与验证命令集中在第 12 节，便于复查；不把历史方案当作当前实现证据。

## 3. 用同一段对话走完整个新流程

假设项目已有记忆 M17，版本 2，正文为“本项目本地回归使用系统 Python”，类型为现有环境上下文类，尚未过期。用户现在说：

> 以后本项目的本地回归统一用 `.venv`。CI 先保持原样。今天先试试关闭代理，看看下载能不能成功。

之后助手执行测试，某次工具返回“18 passed”。这一结果只证明这次具体运行的结果，不证明今后所有测试都会成功，也不替用户作出长期环境决定。

```text
已经保存的真实对话
        |
        v
程序整理：完整轮次/消息关系 + 有编号的原文片段
        |
        v
模型 A：更新会话概览 + 提出值得记住的独立事实
        |
        v
程序：绑定证据、检查范围，提议仅供本轮处理
        |
        v
按每条提议的“事项”查旧记忆，汇总去重
        |
        v
模型 B：新旧比较 + 结论是否得到证据支持
        |
        v
程序：核对版本/来源/遗忘等条件，逐项提交
        |
        v
后续提问：拆成少量完整问题 -> 检索 -> 有限注入
```

**第一步，程序准备能读懂的材料。**用户那段话保持完整；“CI 先保持原样”“今天先试试”不能只剩后半句。助手的计划、工具调用标识和工具结果保持关联。每个可引用片段由程序分配编号，例如 E12、E13，绑定原始消息版本与位置。

**第二步，模型 A 负责提议。**它可以提出 P1：“本项目本地回归使用 `.venv`”，适用条件是本地回归，依据是用户明确声明，引用 E12。关于代理，仅有临时尝试，不形成“今后必须关闭代理”的长期规则。CI 的信息可用于限制 P1；原来的 CI 具体设置未知，不能补写。

概览可以写“已确认本地回归环境；本次运行 18 项通过；代理下载仍待验证”。概览服务会话接续，P1 服务未来相关场景。**概览不是记忆证据，也不需要把每句话都转换成记忆。**测试结果是否另存为有期限的观察，由其复用价值与完整工具证据决定。

**第三步，程序找比较材料。**先围绕“本地回归的 Python 执行环境”查找旧项，找到 M17，而不是要求旧项必须包含新值 `.venv`。否则旧值“系统 Python”恰好会被过滤掉。模型建议的 subject 可以帮助表达事项，但不能作为要求字面完全相等的数据库条件。

**第四步，模型 B 比较。**它拿到 P1、E12 的原文，以及 M17 的正文、版本、状态和可用证据，判断为“同一项目、同一场景、用户明确更正”。它建议更新 M17，保留同一个记忆 ID，并附本次新证据；不是新建一条并让两条有效记忆互相矛盾。

**第五步，程序执行。**程序确认 M17 仍为版本 2、没有被用户遗忘、新来源仍合法，才写入版本 3。若 M17 已被其他操作更新，本轮跳过这组提议、保留当前旧项并记录版本冲突，不重新读取后再试。类型、有效期仍按现有合同处理；“用户说以后”不自动把环境上下文改成永久规则。

**第六步，未来使用。**用户问“跑一下本地回归，另外看看 TC-99 的页面”。程序分别查“本地回归”和“TC-99 的页面”，把 M17 的新版本提供给主 Agent；主 Agent仍负责结合当前环境决定操作。记忆中的命令不构成工具权限或执行授权。

三种变化用来检查这个流程是否理解正确：

| 新信息变化 | 应有结果 | 理由 |
| --- | --- | --- |
| “今天临时试试 `.venv`” | 不替换 M17 的长期选择；必要时只记录有限期临时情况 | 一次尝试没有推翻长期约定 |
| 新信息针对 CI，M17 针对本地 | 不错误覆盖，可以分别保存 | 若条件仅在正文，现有硬冲突检查仍可能把新项保留为 candidate，不承诺两者都自动 active |
| M17 原引文已找不到，但新用户声明完整明确 | 可以以本次新证据更新 M17，并标明旧证据不可用 | 更新当前决定不必重新证明旧决定当年的依据 |

## 4. 怎样组织输入，怎样让模型选择证据

### 4.1 先保留对话关系，再处理容量

优先单位是一次真实用户交互：用户发言、相应助手消息、期间工具调用和结果。多个短轮次可以共用一批；完整轮次装不下时，先减少轮次，而不是切断每条消息凑满额度。

单轮确实过长时，依次按完整消息、段落、句子或代码/日志自然边界分段。工具结果与调用标识、名称、状态绑定，禁止把一个孤立的成功结果错配给另一个调用。只使用已经允许读取的可见内容；不为补齐关系引入隐藏思考、完整原始工具参数或凭证。

分段后的后续批次带有限的当前轮前文与延续标记，重复上下文明确标为“帮助理解、已读过”。程序仍保留准确原文位置，重叠部分不算新证据、不推进两次进度。没有自然边界的超长字符串最后才按字符硬切，明确片段不完整；不能把它包装成完整语义单元。

工具正文很大时使用有界原文窗口并标明省略。缺少的部分只影响依赖它的提议，独立完整的事实仍可处理。概览覆盖、实际读过的消息区间、未提供的正文范围分别记录；“消息 ID 出现在输入里”不等于整条消息都已读过。

### 4.2 模型选原文编号，程序保存真正的原文

推荐的主要输入输出变化是：模型输出“P1 依据 E12 和 E14”，程序从本批允许引用的映射里提取原文，不再依赖模型把整段引文抄得一字不差。这保留了“模型说明引用哪句话”，同时减少空格、反引号和重复句带来的误拒绝。

编号由程序建立，记录消息身份、版本和真实起止位置；模型不能自行提交角色、成功状态、时间或扩大引用范围。同一消息里重复两次的相同句子，也能通过不同位置区分。片段尽量是可独立理解的短句；否定、临时性和适用条件不能因编号边界被剥离。需要多个片段才能支持的事实允许多个引用。

片段过长、缺少限定、模型引用不存在的编号、来源版本已变、命中遗忘抑制时，仍拒绝相关提议或保留明确缺口。超预算不能直接截掉支撑结论的唯一证据后激活。首版不引入模糊引文自动通过，也不让模型的“confidence 很高”代替校验。

现有显式 `memory` 工具的精确引文入口继续有效；新编号是后台批次内的引用方式，程序绑定后进入共同来源校验。不会要求主 Agent 用没有见过的内部编号调用公开工具。

### 4.3 哪些审核要变，哪些继续严格

| 类型 | 推荐处理 |
| --- | --- |
| 手抄引文导致的格式不一致 | 用原文编号绑定，减少模型抄写环节 |
| 同一消息两段必要证据被合并丢掉 | 以“消息版本＋位置”保存不同片段 |
| 全部旧证据不可回查 | 不一刀切禁止更新；检查本次新证据能否独立支持变化 |
| 引文是真的，但结论相反、范围扩大、试验变长期规则 | B 集中复核；明确不支持的丢弃，尚有推断价值但依据不足的只作候选 |
| 角色伪造、来源越界、敏感内容、遗忘后重提、版本覆盖 | 保留程序硬门禁 |

“多个片段”与“新确认”必须分开：同一旧消息换个引用位置，不能续期，也不能绕过遗忘抑制。片段身份用于证据展示，消息来源身份继续用于新旧证据判定和遗忘抑制。

## 5. 证据消失与范围：分别解决两个问题

### 5.1 原记录没了，旧记忆还能不能用

推荐把有限证据作为记忆的组成部分保存：必要短原文及相邻限定、原始来源身份/版本/时间、程序认定的用户来源或工具状态。保存的是当时校验过的依据，不复制完整聊天，也不用模型摘要冒充原文。

| 当前能观察到的情况 | 推荐的读取和比较行为 |
| --- | --- |
| 原归档仍存在且一致 | 可回查原文，标明当前核对通过 |
| 将来明确按普通保留期清理原归档 | 有合格快照及明确清理原因时，允许读有限快照；标明原归档已清理，不能展开完整聊天 |
| 用户删除会话 | 首版保持当前可见性：独立记忆正文保留，引文不可再展开；沿用在途任务与删除互斥，无额外持久草稿清理 |
| 用户遗忘某条记忆 | 清除该记忆所有版本正文/证据，并阻止旧来源重提；本轮内存中尚未提交的旧提议也不能绕过提交检查；不等于删除原聊天 |
| 旧版本被更正或当前不可见 | 不能用旧快照绕过版本/可见性约束，不把过去记录直接当当前事实 |
| 原文缺失但原因不明 | 证据不可用；记忆正文可作为“已有主张”参加比较，不冒充已验证原文 |
| 个人记忆来源在另一个项目 | 沿用正文访问范围；不能借快照跨项目展开原始引文 |

当前自动清理只涉及 checkpoint，不需要为这个假设新建聊天自动清理功能。首版先建立证据保存与读取合同；以后真加入归档保留期，清理流程必须同时记录允许的处置原因。**数据库查不到不等于正常清理，更不等于用户授权保留可读副本。**

旧证据缺失不会自动停用整条旧记忆，也不会自动允许新内容覆盖。若本次用户明确改用 `.venv`，新证据可独立支持更正；若只说“也许试试”，就不能借旧证据缺失推翻旧项。

来源不可用的 active 记忆，建议继续按原有状态、有效期和权限参与前台召回，同时携带来源不可用标记；这不等于重新验证，不能代替对当前环境的检查。若改为一律停止自动召回，会扩大这次行为变化，首版不这样做。

删除会话后的“引文不可展开”是读取行为，不代表现有来源表内所有引文字节都被物理擦除；首版不暗中改变这项留存语义。遗忘针对被指定记忆及其已知来源，沿用消息级抑制：同一消息中的其他提议可能受保守影响；用户以后用新消息重新明确陈述，仍可构成新依据，不承诺永久屏蔽所有相近内容。遗忘也不自动改写原聊天和会话概览，因此引用这些历史材料的上下文仍可能出现该信息。

### 5.2 “范围”有两种，不能混成一个字段

| 名称 | 回答的问题 | 例子 | 谁作最后约束 |
| --- | --- | --- | --- |
| 归属/访问范围 | 存在哪里，哪些上下文可以读取 | 当前项目环境选择；用户明确跨项目适用的个人偏好 | 应用提供项目/个人库和访问边界，模型不能自己扩大 |
| 适用条件 | 在允许读取之后，什么情况下适用 | 本地回归、CI、某个模块或目标服务 | 原文提供依据，模型整理；程序校验已有结构条件，未知保留未知 |

两种范围分别服务“能不能拿到”与“拿到后该不该用”。同一个项目里，本地与 CI 可以有不同 Python 环境；个人记忆能跨项目查，也不等于它能覆盖项目的特殊要求。

首版沿用现有 `subject/machine/module/target` 等信息。有对应字段的条件可用于明确过滤；“本地/CI”这类尚无专用字段的限定先保存在正文与比较材料，不随意塞进 machine，也不假装数据库已经能可靠过滤它。自动注入时保留限定和待核对标记，条件未知不能解释成适用于所有环境。

不为这个案例建设一套通用条件规则引擎。若评测证明正文限定频繁导致误用，再单独讨论结构字段；任何新增字段都必须同步调用、序列化、数据库和测试。

## 6. 找旧记忆与给当前问题找提示，采用不同查询策略

### 6.1 后台：寻找“同一件事”的旧主张

代码根据 A 的每条有效提议构造有限查询：事项、已有条件、必要对象身份。`.venv` 若是新值，就不能成为所有旧项必须具有的词；`TC-99` 若就是对象身份，则应保留。A 同时提供事项与具体主张，B 复核两者是否忠于原文。

建议后台比较搜索当前允许范围内 active/candidate 的现行版本，包含其中已过期者，并明确标示过期；这是对当前默认搜索排除过期项的扩展。再次命中不等于转正或续期，仍需独立的新证据；inactive/forgotten 不顺带纳入。前台继续排除过期项。不能要求 subject 字符串完全一致才算同一件事。检索仍用现有 FTS/BM25 和融合能力；比较查询不沿用前台“整段用户文本覆盖率”的全部筛选规则。

多个提议查到相同旧项时，按 ID/版本合并材料。整个 B 输入共享总预算，不是 8 个提议各读 8 条全文。相关旧项过多时先选取能完整容纳的比较组；放不下的组记录超限并跳过，不留到后续重试，不截掉已知冲突项却告诉模型“没有旧记录”。数据库查询失败也不能当零命中。

“完整比较组”指本次已发现且需要一起比较的材料，不表示已搜索完整个记忆库。查询达到候选上限、返回正文截断时必须传递“检索受限”；不能把受限后零结果当作无旧项直接新增。正常查询计划可按事项和已知条件执行有限查询，但执行失败、预算耗尽或无法形成可用比较材料时直接跳过受影响提议，不建立失败补查任务。

### 6.2 模型 B 输出关系判断，程序决定能否提交

| 比较结果 | 例子 | 提交效果 |
| --- | --- | --- |
| 新事实 | 没找到旧项，当前证据独立充分 | 允许新增；查不到仍不证明全库没有同义记忆 |
| 重复 | 同一事实、同一证据重跑 | 不写新版本，不续期 |
| 补充 | 新的独立确认，或不冲突的必要补充 | 更新同一 ID，并按真实新证据计算时间 |
| 更正 | 用户明确改变同一范围的旧决定 | 更新同一 ID；旧版本按现有规则保存 |
| 条件不同 | 本地与 CI 各自有明确设置 | 分开保留适用条件；纯正文差异仍可能命中 known_conflict 并保留 candidate，不绕过硬门禁 |
| 冲突未解决 | 两个互斥主张，缺少明确更正依据 | 保留旧有效项，新主张作为 candidate 并说明缺口 |
| 不值得记或不受支持 | 临时噪声、相反概括、无依据的泛化 | 丢弃提议，记录不含敏感正文的原因 |

同批多个提议指向 M17 时，要形成一个完整更新决定；程序拒绝模型数组中对同一旧 ID 连续覆盖的输出，不能按数组顺序让最后一条获胜。模型只能操作本次实际提供的旧 ID，提交前再次检查当前版本、权限、来源和遗忘状态。

比较采用证据原始发生时间，不按整理时间判新旧。第 30 条说系统 Python，第 100 条已明确改成 `.venv`，后来补处理第 30 条不能把当前设置改回去；它最多补历史依据或保留待核对信息。时间更晚也不自动代表更正，仍需同一适用条件与明确支持。

每条新记忆尽量只表达一个可独立判断的主张。若旧项混有“本地环境＋CI 环境”，新证据只确认本地，不能让 CI 一起获得新的确认时间。首版保守地让整个复合条目沿用原期限，不因局部确认整体续期或转正；若新确认部分需要独立生效，应作为独立主张处理。S3 将明确这种部分更新的提交结果，不新增逐句有效期系统，也不靠扩大正文概括解决。

比较门禁是语义质量的一部分，仍然需要评测。精确重复检查和版本比较只保护确定性边界；两个并发任务都没找到旧项时，仍可能新增两条同义记录。首版不承诺语义唯一性，不为消除这个限制引入全库模型锁。

### 6.3 前台：拆少量完整问题，不额外调用模型

短而明确的输入保留短查询。长输入按完整段落、句子、明确列项形成少量查询，也保守识别“另外、还有一个问题”等少量显式事项边界；普通逗号不自动拆分，例如“如果在 CI，先保持原样”必须保留条件。不能可靠拆出的句子保持完整。各查询保留路径、编号、否定和条件，再合并排序、去重和执行总注入预算。不把“本地回归”和“TC-99 页面”拆成孤立词，也不让后者的编号成为前者的强制条件。

首轮评测采用至多 4 个查询作为候选上限；超限要记录裁减，不能声称覆盖全部事项。独立查询不能仅作为旧全文 query 的 expansions，否则原全文的全局技术锚点仍可能限制全部分支。前台结果只注入允许自动使用的记忆，candidate 的比较用途不自动扩大成正常事实提示。

合并后在总预算内优先保留各查询有依据的高相关结果，再补其余名额；不能让第一件事的多个相近条目占满预算。确实放不下时记录哪个查询没有结果进入提示，不承诺每件事必有记忆。排序和覆盖策略用 S0 的多事项样本确定。

“那个方案”“还是按前面的”涉及指代，确定性拆分不保证理解。保留主 Agent 显式 `memory search/read` 补查的入口；模糊的“继续”不随便注入一批历史。数据库查询次数可能增加，目标先是减少漏召回，性能改善需实测。

最脆弱的前提是：事项级词法查询能找回足够多的旧主张。中英文切换、纯同义改写仍可能漏掉。评测单独统计这些情况；若它们成为主要误差来源，再讨论向量混合检索。本轮不切换存储或新增检索服务。

## 7. 失败直接跳过，保留独立成功结果（用户已确认）

### 7.1 允许遗漏，不为完成率降低正确性要求

用户已明确：记忆不是必须保证成功的模块，没有记忆优于写入错误记忆。本次沿用 2026-10-22 已确认的失败跳过合同，撤销上一稿的提议持久化、中断继续、7 天草稿保留和提交回执建议；不新增恢复队列、继续入口或重播流程。

A 生成的提议及其证据绑定只存在于本轮任务内存中，交给本轮 B 使用，任务结束后不保留可恢复的提议包。两阶段的目的是改善提取与比较质量，不承担最终一定存成记忆的义务。范围仍由程序约束，B 不能把项目事实自行扩为个人跨项目记忆。

本轮状态、计数、安全日志以及已有概览覆盖信息用于说明实际发生了什么；接纳位置仍只表示自动触发基线。必要的失败/不完整标记沿现有机制保留，不把失败范围重新放进自动待办，也不承诺重启后恢复每条提议的执行现场。

### 7.2 各类失败怎样结束

| 情况 | 处理结果 | 保留的边界 |
| --- | --- | --- |
| A 调用失败、超时或整体输出不可解析 | 本批跳过，保留旧概览和旧记忆 | 不追加模型修复调用，不从半截输出抢救权威状态 |
| A 有合格概览，但提议结构或证据无效 | 概览可独立保存，相关提议跳过 | 概览成功不能算记忆成功 |
| 检索失败、必要比较材料不完整、B 失败 | 跳过受影响的完整比较组；整次 B 不可用时跳过其全部提议 | 不把失败当零命中，不绕过 B 新增有效记忆 |
| B 的完整比较组装不下或任务预算用完 | 标记超限/未处理范围并跳过 | 不截去冲突材料，不保存待下次补跑的提议 |
| 提交前来源变更、版本冲突或命中遗忘抑制 | 跳过该项或该组，保留当前库中数据 | 不重新比较后再试，不改成新增绕过门禁 |
| 一部分已经提交，另一部分失败 | 保留已经独立提交成功的结果，失败部分跳过 | 不要求项目库/个人库跨库全部成功 |
| 停止、任务级超时或进程退出 | 不自动恢复，不重放尚未完成或未确认的写入 | 确认过的成功保留；提交结果未知如实标未知，不能当成未写入再提交 |

candidate 继续表示“正常完成判断后，存在依据但尚不能作为确定事实使用”的业务记忆。它不能作为 B 失败、证据校验失败或写入冲突的临时收容状态；运行失败就是跳过，不以保存候选的方式掩盖失败。

例：P1 已通过比较并保存，P2 提交时发现版本变化，P3 因预算耗尽未处理。结果就是“P1 保存；P2 冲突跳过；P3 未处理”，后续不会重新执行 P2/P3。用户下一次新对话仍按新增内容达到阈值后正常整理，不因旧失败重复触发，也不会被旧失败阻塞。

同一次任务中，未尝试且能独立理解的后续批次，在剩余预算允许时仍可正常推进；这是处理新批次，不是重试失败批次。依赖失败前文才能解释的材料不能猜测补全。已经失败的部分不因切换阶段、改变查询或后续新增消息而自动重做。

用户以后明确要求重新整理某段历史时，沿用已有的有界历史整理入口，视为一次新的请求；这不新增失败重试功能，不承诺复用旧提议、恢复中断位置或跨请求语义去重。已有单库事务、精确重复检查、版本和来源校验仍保留。

### 7.3 概览与记忆分别记录成功

概览保存成功而 B 失败时，可以保留新概览，记忆标失败跳过。反之，概览保存失败也不回滚已经独立满足条件的记忆。网络故障不能解释成“没有值得记的内容”；拒绝某条坏提议不必让其他独立提议全部失败。后台失败不改变已经成功结束的主 Agent 结果。

假设概览已到第 100 条，而第 30–40 条过去没成功整理：默认保留缺口，不自动补齐。若用户以后明确请求重新整理 30–40 条，可以处理其中的记忆，但不能用覆盖到 40 的旧概览覆盖到 100 的新概览，也不能把概览缺口自动涂掉。既有显式概览刷新仍按实际可读范围生成，不为此次优化建设强制完整覆盖机制。

## 8. 模型调用、等待时间和资源预算

推荐每批有有效提议就做 B，即使未检索到旧项，也检查新提议是否得到原文支持。零有效提议跳过 B。A、B 复用本任务冻结的既有模型与调用适配，不新增供应商、密钥或模型服务，也不为每条提议单独启动 Agent。

| 场景 | 正常逻辑调用量 | 说明 |
| --- | --- | --- |
| A 没有有效提议 | 1 次 | 概览仍可保存 |
| 一批有有效提议且比较材料装得下 | 2 次：A＋B | B 批量比较，不按提议数倍增 |
| B 的完整比较组放不下 | 至多一次 B，只处理能完整装下的组；没有可处理组则跳过 B | 其余组记录超限并跳过；共用旧 ID 的提议不能拆开各自覆盖 |
| A/B 或提交失败 | 不追加失败重试调用 | 失败部分直接跳过，已独立提交成功的结果保留 |

每个来源批次 A 至多一次、B 至多一次；格式错误或调用失败不增加修复模型，单个完整比较组超限就记录并跳过，不自动转交主 Agent 换一条路径补做。既有 search/read 仅保留正常的显式查询能力。

当前代码默认每任务最多 3 批、总时限 300 秒，单次输入 16000/output 4096 tokens、最多 8 条提议、自动注入 2000 tokens。这些是 `MemorySettings` 的代码默认值，不是对用户实际配置的读取结论。300 秒还包括等待来源保存和并发槽位，评测须分开记录等待与模型执行。改成两阶段后，首次正常处理 3 批最多约 6 次逻辑调用；SDK 尝试另计但受总期限约束，不能假定原 300 秒仍足够。

新方案要共同约束 A 的来源大小、提议数、B 的旧项/证据总量，以及一次任务的总调用和 token。初轮以现有时间/批次数为基线测量，不先扩大真实配置；新增配置项及默认值由对应 Spec 给出依据，变更真实环境配置仍需明确授权。

详细 Spec 采用“无旧项也复核有效提议”的单一策略，不增加“仅命中旧项才做 B”的运行开关。真实效果与成本由 S0 对照旧单阶段基线验证，不以减少新事实复核来掩盖两阶段成本。

用量按 A/B、来源批次和所属会话记录，同时报告成功、失败、跳过数及预算中止；实际缺失显示未知，不填 0。日志记录阶段、数量、错误码和引用身份，不写完整私密引文或模型正文。数据量增至十倍时仍用有界分页和总预算，未处理范围可见，不全量扫描后宣称“全库没有重复”。本次不增加记忆业务重试，也不顺带改变既有模型适配层的传输重试配置；逻辑调用与实际 SDK 尝试仍分别统计。

## 9. 如何知道优化真的有效

先冻结一份人工标注的旧行为基线，再实施；样本按真实问题类型组织，不用保存数量增加当成质量提高。沿用现有 `docs/research/memory00/` 的实验习惯与测试工具，保留旧集合回归，新增独立留出集用于验收。

| 要检验的能力 | 必备样例或故障 | 检查结果 |
| --- | --- | --- |
| 输入完整性 | 跨消息限定、单轮过长、代码块、多个工具并发、超长无标点文本 | 原文位置准确、调用结果不串、遗漏明确、重叠不重复计时 |
| 证据绑定 | 空格/反引号、相同句子出现两次、同一消息多个片段 | 正确编号能定位，不靠模糊匹配猜位置 |
| 语义支持 | 真引用配相反结论、删除否定、临时尝试变永久规则、助手猜测 | 分别记录模型误判，禁止用“引用存在”算正确 |
| 新旧比较 | 系统 Python→`.venv`、相同事实不同标题、不同条件同标题 | 找到应比较的旧项；更正/并存/冲突结果符合标注 |
| 前台召回 | 短查询、冗长同意图、多事项、无关编号、跨语种同义改写 | 应命中的事实是否进入有限结果；误注入是否增加 |
| 生命周期 | 原文消失、版本变化、过期、遗忘、跨项目来源 | 不绕过访问/遗忘；没有新证据不续期或转正 |
| 失败隔离 | A 后退出、B 超时、部分写成功、写成功但状态未记、CAS 冲突 | 不自动重跑、不覆盖新版、不把故障当空结果，保留独立成功项 |
| 概览 | 概览与记忆分别失败，补处理旧范围 | 成功独立保留，覆盖不虚报、不倒退 |

程序门禁采用确定性测试：禁止项必须拒绝，失败后不重试且不降低门禁，删除/遗忘后的在途提议不能复活旧内容。模型质量用固定输入与人工答案对照，报告事实召回、错误新增、错误覆盖、重复新增、候选数量、证据绑定拒绝率及样本分母；报告多次真实模型结果的波动，不能用单次全对代替稳定性。

样本先标注“原文哪些事实值得记、对应证据是什么、应该与哪些旧项比较”。再分别统计 A 提议召回、后台旧项召回、B 决策正确率、程序拒绝原因、最终可用记忆召回，前台召回另报。这样才能区分“模型没提出来”“没找到旧项”“比较判断错”“程序过严拒绝”，真正回答最初的丢失问题。

同时测数据库查询数、逻辑调用与 SDK 尝试、token、耗时和预算中止比例。质量与成本一起比较。评测协议在调参前冻结：确定性门禁全部通过，专门构造的误覆盖/范围扩大负例必须逐项分析；新方案在留出集的召回改善不能靠增加错误覆盖换取。具体数值目标在基线测量后、调参前写入评测 Spec，不能看结果再改答案或门槛。

| 分片 | 完成后可观察的变化 | 主要验收与依赖 |
| --- | --- | --- |
| S0 基线与评测协议 | 现有失败样例、正确答案、质量和成本口径固定 | 先于调参；不改生产行为 |
| S1 输入与证据编号 | 按对话关系装批，模型选原文编号，程序能准确还原片段 | 边界、超长、工具配对、多片段及当前严格门禁回归 |
| S2 证据保存与生命周期 | 新证据属性可保存；旧记录、删除、遗忘、跨项目读取有明确结果 | 项目/个人库迁移与读取回归，不自动重新推理旧记忆 |
| S3 提议检索与批量比较 | A 后按事项找旧项，B 判断新增/更正/并存；失败或超限直接跳过 | 验证新值能找旧值，同 ID 单次决定，概览/记忆独立成功，不重试、不绕过校验 |
| S4 前台召回与整体验收 | 少量完整问题独立查询，沿用最终注入预算 | 可在 S0 后独立开发；最终与 S1–S3 联合做质量、成本和迁移验收 |

原稿“中断继续与提交回执”分片已撤销，失败跳过及诊断验收并入 S3。若 S1/S2 单独已产生可验证收益，可以按完整既有单阶段合同验收；新旧临时实现的清理在启用最终链时同步进行。

预计总影响仍超过 8 个文件，涉及 `application/memory/` 的批次、runner、来源、写入、查询和注入，`contracts/` 的内部提议合同，`storage/memory_sql/` 的证据与既有结果记录，项目及个人库证据结构迁移，以及来源读取、必要展示和对应测试。不新增草稿库、恢复账本或继续公开接口。若证据状态增加公开字段，Spec 必须列出现有消费者并同步更新，不能只改后端。

优先复用现有 MemoryJobs、FTS、模型适配、单库事务和任务观察入口。runner 已接近文件长度上限，必要时按“提议比较”“来源装配”真实职责拆模块；不增加通用工作流、全库语义锁、新服务、新依赖或第三方账户。不改现有模型运行框架、图压缩职责或隐藏思考保存策略。

迁移只改结构和必要的确定性数据转换：旧 active/candidate 保持状态，原始时间不变，升级不续期、不转正、不扩大引文可见性。缺少新属性的旧证据标为旧格式；只有原归档可读且有权限时才能补核验，不能从 `role=human/tool` 猜出真实用户来源或工具成功。

项目库与个人库升级前停止所有相关写入进程，用已有机制取得各库内部一致的备份，记录同一暂停窗口的库身份、版本及备份路径；不新建跨库事务或自动成组恢复平台。不自动遍历历史调用模型。旧程序启动应拒绝不兼容格式，但已经打开的旧连接须先停止，不能混用两版写进程。只改算法且未改数据时可回退代码；发生新格式写入后，恢复要使用匹配程序及同一暂停窗口的备份，并处理升级后新增数据，不能宣传为无损一键回滚。

产品实施各片按 TDD 和现有项目构建/测试入口验证；提交前跑全部已有测试与构建。真实模型质量评测独立报告，不用单元测试通过代替。迁移或新接口上线前进行已有数据副本演练，不在本轮执行生产数据迁移、发布或部署。

## 11. 进入详细 Spec 的行为选择

| 编号 | 行为选择 | 本轮采用的实施规格 | 影响 |
| --- | --- | --- | --- |
| D1 | 没找到旧记忆时，新提议还要不要独立复核？ | 有有效提议就批量做 B；每批通常从 1 次变 2 次逻辑调用，提升复核集中度但增加成本 | S3 与预算 |
| D2 | 删除会话后，要不要仍能展开该会话留下的引文？ | 首版保持当前行为：记忆正文留存，引文不可展开；普通保留期清理与主动删除分开 | S2 的证据留存合同 |
| D3（已确认） | 后台失败后的处理 | 沿原设计失败跳过，不重试、不保存可恢复提议、不新增继续入口；允许遗漏，优先避免错误记忆 | 已并入 S3，撤销原恢复分片 |
| D4 | 是否继续允许充分的新证据自动生效，或每条都人工审批？ | 沿用自动生效路线：程序硬门禁＋B 语义复核；推断/未解决冲突进入 candidate，不引入逐条审批 | S2/S3 的状态策略 |
| D5 | 首轮是否直接加向量检索或通用适用条件系统？ | 先做事项查询、最多 4 个前台问题及现有条件；依据留出集的同义漏召回/误用证据再扩展 | S0/S4 与工程范围 |

用户已要求开始编写分片详细 Spec，本轮沿上述推荐方向细化，不重复请求确认恢复能力。最多 4 个查询等参数仍是待实施的评测初值，并非已修改的运行配置。真实模型评测、真实数据迁移与产品实现均未在本轮执行；实施发现新证据导致合同需要改变时，先同步相应 Spec。
