# 场景8：不完整会话与重启恢复

从[十二组场景总览](十二组场景总览.md)整理为独立文件；保留原讲解内容和当时的版本、验证边界。

- **问题**：进程退出/取消/故障后，图、应用元数据与工具副作用可能处于不同确认阶段。
- **当前路径**：SessionPersistence.arecover/_recover_checkpoint→校验checkpoint与恢复分类；restore_approval分支重新验证并安装待审批；continue分支记录recovery_id/源checkpoint，按cleared/paired/finished执行END/tools/END更新，补结果，再确认可用并保存。
- **状态**：原始checkpoint保留；恢复记录、工具配对、清理执行状态、新checkpoint、数据库会话状态。
- **失败**：重读身份/阶段不匹配拒绝；任一步失败不可标ready；重复恢复按已保存阶段继续；未知已生效操作不能自动重放。
- **判断**：分阶段可重入、保护原历史是必要设计。一个持久化协调类同时做恢复分类、执行计划、内部图编辑和会话安装，职责偏重。
- **目标**：分类得出可检查恢复计划，图适配按阶段应用并确认，存储协调只发布已确认结果。restore approval和修复未知结果保留不同规则，不强行共用一套恢复策略。
- **保护**：源checkpoint不变、无重复副作用、陈旧版本拒绝、失败不开放准入。
- **测试入口**：`tests/test_session_recovery.py::test_three_updates_preserve_results_then_only_new_input_calls_model`。

## 场景8补充：分类、未知结果与分阶段恢复（2026-10-20）

本段以当前HEAD c5ca965及工作树核对。恢复整理已保存事实并结束旧路径，不自动重跑模型/工具/Auto、不自动批准、不自动发送草稿。当前Web在选择旧会话时prepare并按recovery动作自动恢复；服务启动不因旧行仍为running就启动旧run。

示意：源thread TH1的最新checkpoint P0包含HumanMessage h、AIMessage ai（工具调用a=read、b=write），以及a的真实ToolMessage actual-a；b可能已完成文件写入但ToolMessage未保存。不能从“缺b结果”推断“b未执行”。应用会话行中的confirmed_checkpoint_id可能还是更早点；历史读取使用TH1最新checkpoint，不能退到旧确认点掩盖后续事实。

| recovery.kind | 当前含义与入口 |
|---|---|
| ready | 已确认完成checkpoint与会话行一致、消息配对、无待执行/任务；普通restore安装会话，不修图 |
| pending_approval | 严格证明是唯一正式审批节点在本批工具执行前暂停；可提供restore_approval及明确continue放弃旧批，MCP旧审批仅提供continue |
| interrupted_execution | 可读且可判定的中断/失败/确认不一致，或已有恢复marker尚未完成必要保存；continue整理后等待新输入 |
| unavailable | thread/namespace错误、不可读/坏消息/配对歧义、配置不可用或当前进程正在拥有等；不提供自动修复动作 |

classify_recovery只分类；_read_history还核对当前模型/思考/工具/模式/工作区及进程所有权，才开放actions。is_pre_tool_approval要求固定next节点、唯一task及其path、无task结果/错误/子状态、唯一interrupt；最后AIMessage与tool_execution的batch_id、逐项call id/name/args对应，pending可重建。任意interrupt不等同审批。调用ID在不同AI批次可复用，配对检查按批次处理。

```text
选择旧会话 → prepare/读取最新历史及recovery描述
  → POST recover {checkpoint_id:P0, action:continue或restore_approval}
  → Web与新run共用start_lock；校验当前开放动作和checkpoint
  → AsyncPersistentApplication.arecover_session
  → SessionPersistence.arecover：history lock + _recovering占用
  → _recover_checkpoint：重读row/配置/工作区绑定/TH1最新状态
  → 比较提交P0与服务端actual，重做分类
      ├→ restore_approval：当前权限/目标复核→保存interrupted→安装pending，等待新决定
      └→ continue：建立或验证恢复record→END/tools/END更新及逐阶段确认
  → 验证无next/tasks/缺结果/歧义，tool_execution={}，run_stopped=False
  → finish_run事务保存归档/ready/最终checkpoint/last_run_status=recovered
  → install_restored_session；返回会话视图，下一条新消息才开新run
```

恢复自身没有新的ActiveRun/run_started/model/tool事件；用_recovering而非普通busy run隔离准入，并直接等待必要IO。当前会话已装载、_active/_blocked/_recovering占用均不能通过恢复入口绕过。HTTP recover不采用场景7的request_id回执合同：旧checkpoint过期直接拒绝，重复恢复已装载会话也拒绝。

身份具体核对：前端从服务端视图取P0；Web先比较当前视图P0，后端再次读取TH1最新actual并与提交值比较，旧值不写入。另查snapshot的thread_id等于row.thread_id、根namespace为空、配置/绑定可用及恢复分类允许。恢复record由服务端uuid4生成recovery_id K1，包含version=1、session_id S1、thread_id TH1、source_checkpoint_id P0、source_namespace空、original_state、pre_tool_approval和phase。持久位置是新checkpoint.metadata.naiyue_recovery的JSON；schema键、版本、归属、32位十六进制ID及合法phase均校验，不由前端声明当前阶段。

| continue阶段 | 图更新与作用 |
|---|---|
| cleared | aupdate_state(values=None,as_node=END)：把旧任务已保存pending writes合入新checkpoint并清除旧任务；保留真实消息和其他通道值 |
| paired | aupdate_state(values=build_recovery_update(...),as_node=tools)：仅追加缺失结果，保留已有ToolMessage正文/块/artifact；清空tool_execution并重置run_stopped |
| finished | 再END，清理tools更新可能排出的后继，避免自动进入模型 |

as_node=tools是按节点写入规则更新状态，不调用工具函数。第一步END不等于丢弃全部pending writes：本机LangGraph1.2.12先apply已保存的非ERROR/INTERRUPT任务输出，再保存完成checkpoint。get_state最新视图能投影pending writes，不等于普通update自动以该投影为基底；这三步同时避免应用自行回写全部状态，保留源checkpoint及原任务记录。不是三步数据库原子事务。

build_recovery_update对缺失b构造status=error的ToolMessage，tool_call_id=b，reason=result_unconfirmed，正文明确“操作可能已经生效，未自动重放，请先核对”。它不是b执行失败证明。消息ID为recovery-加sha256(json.dumps([owner_ai_id,tool_call_id]))，同时利用批次拥有者ID避免历史调用ID复用冲突。严格前置审批若用户明确continue，则reason=cancelled_before_approval，可说明未执行；不能把这句话套给普通中断。

每阶段在源config附上对应phase的record再aupdate，随后按thread重读，比较snapshot.config与该次aupdate返回的config，并比较重读record与服务端record相等，再进入下一步。重试若发现已有record，先重读其source_checkpoint，确认TH1/根namespace/source ID、created_at有效、源没有另一恢复marker，pre_tool_approval声明也必须可由源快照证明；再从已完成phase之后继续。每次重试提交新读取的最新checkpoint，不继续提交旧P0。

若paired已落盘后失败，再次恢复跳过paired，不重复补ToolMessage；若finished已保存而SQL会话元数据失败，再次只需最终核对、保存并安装。写入或取消故障不能先标ready；await_settled结算已开始IO后才释放_recovering。最后的SQL finish_run在事务内写归档与会话行，成功后才安装内存会话；恢复不是把原工具副作用变成“已确认成功”。

restore_approval复用场景3合同：重查工具可用/活动集合、模式、参数、规范化subject及当前本地allow/ask/deny；旧临时session_allow不复活，不通过读Skill正文或调用Auto恢复授权。旧MCP连接身份不跨重启恢复，当前只允许明确continue取消旧批。普通Web默认pending走restore_approval；复核失败不自动改选continue，也不循环重试；只保留历史/草稿、刷新当前状态并显示错误。
