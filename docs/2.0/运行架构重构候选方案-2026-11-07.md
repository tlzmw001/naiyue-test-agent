## 2. A：执行方持有运行事实

### 2.1 当前问题与目标

`RunObservation` 的 `mode/stage/status/failure/_suppress_terminal` 被运行控制、记忆权限、必要保存、子执行和记忆任务共同消费。它既记录事实，又发布观察；移除或调整观察实现时容易碰到业务规则。

事实入口：[run_events.py](../../naiyue_test_agent/application/observability/run_events.py):107、[session_controls.py](../../naiyue_test_agent/application/sessions/session_controls.py):84、[agent_session.py](../../naiyue_test_agent/application/sessions/agent_session.py):54、[session_persistence.py](../../naiyue_test_agent/application/sessions/session_persistence.py):212。

建议新增一个应用内部值类型 `RunExecutionFacts`，置于 `application/run_outcome.py`。它表达当前已知事实和候选终态；由执行所有者更新，观察方消费快照。采用不可变值并由所有者替换引用，不引入新的共享可变容器或锁。

```text
根 RunLifecycle / 子执行片段 / Memory drive
          │ 产生并持有本次 RunExecutionFacts
          ├─→ 控制与权限检查：读取 mode/stage
          ├─→ SessionPersistence：读取结果并进行必要保存
          └─→ RunObservation：产生既有观察通知

RunObservation 不再写回运行结果；原异常仍由执行栈持有。
```

根运行通过 `ActiveRun` 持有这一值；子 Agent 每个执行或审批恢复片段各持有一个，整个子实例的 `phase/status/settled` 仍归 SubagentRegistry；Memory drive 持有自己的值，业务 `partial` 等结果仍归记忆任务。

### 2.2 字段和更新合同

| 字段 | 保留语义 | 谁写、谁读 |
|---|---|---|
| mode | 现有 message/approval_resume/compact/memory | 各执行入口创建；控制、持久化和事件读取 |
| stage | 现有 prepare/execute/finalize 转移点 | 执行所有者推进；停止许可、记忆 scope 检查读取 |
| status | 现有 completed/interrupted/stopped/failed 候选值 | 执行结果判定；持久化、子实例投影、终局读取 |
| failure | 现有脱敏 `RunFailureData` 或空 | 同一套失败分类规则；保存相关判断与观察消费 |
| suppress_terminal | 控制信号不能伪造业务终局时抑制发布 | 执行边界判定；观察发布读取 |

当前 status 初始是 completed 候选，并不代表运行已经成功。首片保持该语义，不新增 running/unknown 状态，不迁移数据库；明确只有对应收尾阶段才能使用它决定终局。失败描述里的 cleanup 等阶段继续保留，不强塞进执行 stage。

`SessionState` 的 pending/manual_review、ActiveRun 的队列/controls_open、子实例 settled、Memory partial 均不复制进这个值。原始 `primary_error/secondary` 仍留在执行栈，不写入事件或长期对象。

根事实引用在现有 `SessionRuntime.lock` 内核对 run 身份并替换；跨线程控制读取也使用这把锁。失败分类、日志、publisher 调用与 IO 在锁外执行。子片段及记忆局部值按原执行所有者更新；不得为了共享类型引入跨作用域锁。更新锁表时核验所有新增间接获取路径。

已持有这把非重入锁的控制/权限方法直接读取当前事实，不调用再次取锁的 accessor。子实例仍先遵守原 phase=finalize 和停止竞争规则，再接收片段结果；不能用共享值类型抹平实例状态机。

普通 `failed(Exception)` 分支保持现有顺序：本 run 的异常注解 → 应用分类器 → 执行阶段的 runtime 分类器 → 安全 unknown 回退。`cancelled()` 保持独立的 runtime-only 分类，不经过前两层；`failed()` 收到非普通异常或 `GraphBubbleUp` 时保持终局抑制和传播。策略由现有装配位置创建并复用，结果判定与 scope 使用同一份策略，不能借提取函数合并这三条分支或复制两套分类器配置。

### 2.3 逐个迁移消费者

| 当前调用 | 迁移后的责任 |
|---|---|
| `RunObservation.result/failed/cancelled` 决定结果 | 各执行所有者先更新事实，再调用观察方法通知 turn/control/context |
| `RunObservation.start/control_close_reason` 读取自身 mode/stage/status | start 消费事实生成原事件；关闭原因在执行方按事实推导，再交控制观察消费 |
| `RunObservation.finish` 读取自身结果 | 消费传入的事实快照；计时与 HTTP capture gap 保留在观察对象 |
| `SessionPersistence.afinish` 接收 observation | 接收执行事实；继续负责保存确认和受限状态 |
| ControlQueue 读取 observation.mode/stage | 读取根运行事实；控制对象本身仍沿已有能力引用 |
| `AgentSession.validate_memory_scope` 读观察 stage | 读运行事实，原身份、环境、工具与权限校验不变 |
| `SubagentRegistry._subagent_steps` 读观察 status | 从当前 child 片段事实更新实例；保护已完成与停止竞争 |
| Memory drive 直接赋 observation 字段 | 在自己的执行边界完成业务结果到 run 状态的既有映射 |

首片允许 `RunObservation.bind` 继续装配 scope，保留停止控制和 runtime policy 的实际接线。因此验收只能说“运行结果权威已分离”，不能宣称这个类已成为纯展示对象。抽走 scope/控制装配是另一项设计，不混入本片。

`contracts/cloud_observation.py` 的同名 `RunObservation` 是云端消息 schema，保持不变。`RunObservationPorts` 也是不同类型，不做机械全仓替换。

### 2.4 正常、失败及边界验收

- 普通成功：图结果判定 → 子实例收束 → 控制窗口关闭 → 必要保存 → 按原规则释放根运行 → 发布根终局。
- 根执行方在释放 ActiveRun 前取得最终不可变事实快照，释放后以局部快照发布终局；不通过 current run 或 `require_run` 重新取值。快照保留到本次调用退出，避免旧终局读到下一次运行。
- 保存失败：结果判定不能提前变成对外成功；原 blocked、错误码与故障描述保持。
- 已有模型主异常 + 保存普通 Exception：保留主异常对象及次要诊断。`release_run` 内部错误、任意 BaseException 并不因这条合同自动获得绝对不覆盖保证，应分别按现有传播路径验证。
- 保存期间外层取消：排空保存；调用者收到取消与 DB ready/根 completed 可以同时成立。
- 根审批：本 run interrupted，恢复创建新 run 事实；原审批来源和许可绑定不变。
- 子审批：每段 child run 有独立事实，父 run 保持活动；child run_finished 仍可早于整个子实例 settled。
- compact 保留原 Memory skipped 处理；regenerate 激活前的准备失败不人为补发运行事件。
- Memory 的 partial 业务结果按原逻辑投影，不新增 run 状态。
- observer 普通故障不回写执行事实；控制信号/进程信号按原传播和终局抑制规则处理。

最脆弱前提：把当前共享结果字段移动后，所有执行路径都在正确时点显式更新。漏掉子审批恢复或 Memory 直接赋值，会造成错误终局。应先用消费者清单和失败测试约束，而不是靠字段重命名完成迁移。

最小替代方案是只改类名、加职责注释，保留现有耦合；实施成本更低，但控制/保存仍依赖观察对象，达不到本次所有权目标，因此不作为首选。

## 3. B：保留一致性协调，迁走不属于它的工作

### 3.1 推荐结构

保留 `SessionPersistence` 作为一个应用层一致性协调者。其 `_active/_recovering/_blocked/_prepared` 与每会话 history 门闩保持唯一；保存、恢复、删除围绕同一份状态协调。普通 SQL 继续由现有 Repo/UOW 完成，不增加新的 persistence/recovery/state manager 层级。

| 内容 | 建议归属 | 必须保持的条件 |
|---|---|---|
| start、必要 finish、prepare、restore/recover、delete | 原一致性协调者 | 原预留、锁顺序、恢复阶段及 actor 安装顺序 |
| `prepare_memory` | 现有 MemoryAPI 的内部上下文准备入口 | 正式运行与 preview 共用；preview 不提交目录使用事实；个人/项目异常边界保持 |
| 受 scope 约束的历史工具查询 | 现有历史域内部查询函数 | role、身份、真实执行路径校验保留；不通过完整应用 service locator 查询 |
| status/history 展示投影 | sessions/history 的查询函数 | 只拿协调状态快照；不让调用方直接改私有 set |
| `save_memory_sources` | 原必要历史同步入口 | Memory 写入证据前，在同一 history 门闩内完成 |
| Memory `after_finish` | 协调者显式调用既有 `MemoryJobs.after_finish` | 绑定必要保存成功/失败；不经完整 MemoryAPI，不从可降级事件触发 |
| 其他对象借 `persistence.storage` 获取 Repo | 装配时直接传所需现有 Repo | 仍共享原 storage/连接所有者；借用者不关闭资源 |
| usage flush、标题、裁剪等 | 现有具体模块；协调者保留调用顺序 | 首片不改成后台；可降级不等于可任意推迟 |

正常保存仍为：history 门闩 → 核对本 run 预留 → usage flush → 核对 checkpoint → 收集归档 → UOW 必要提交 → 原有后续处理 → 清 active → 返回生命周期收尾。

必要 UOW 失败仍回滚、标记 blocked、以 failed 通知等待中的记忆工作，然后抛保存未确认；能否释放 ActiveRun 由原生命周期判断。Memory after_finish 会决定等待中的任务是否释放/停止，具有执行控制语义。

具体装配保持原顺序：先创建 storage/jobs/sessions → `assemble_session_runtime` 创建 persistence 与图 → ProjectHost 创建 MemoryAPI 并绑定 sessions → 创建会话时把可选 MemoryAPI 传给 RunLifecycle。准备上下文由 RunLifecycle 已有 `_memory` 和上下文预览入口调用 `MemoryAPI.prepare_context`；内部复用 `memory_context.prepare_memory_parts` / `MemoryJobs.prepare`，权限策略从装配处传入现有对象。没有能力时保持空 prompt parts，不为 Runner 补建完整宿主。

协调者不保存 MemoryAPI 引用：必要保存后的调用仍直达现有 `_memory_jobs`。这样不新增 `Persistence → MemoryAPI → Persistence` 环，也不增加晚绑定入口。`prepare_context` 是内部借用能力，沿已受理运行或已有查询入口的生命周期，不重新 `owner.operation/check_open`；after_finish 在原 history 门闩内执行，不重取同一门闩，也不重新准入。关闭期间必要收尾不能被新包装拒绝。

### 3.2 不可破坏的跨模块约束

- 正常 graph checkpoint 与产品 UOW 不同事务；云 Runner 的必要 history journal 仍与对应产品事务一起提交。删除 checkpoint 表的 UOW 是另一个明确合同。
- actor busy、协调者 blocked、数据库 running 三者独立；不合并成一个布尔状态。
- S1 每会话异步门闩与 S2 短同步协调锁保持分工，短链维持 S2 → registry → actor；不持 S2 做 SQL 或 await。
- `aprepare` 已持 history 门闩调用 `arestore`；不能让 `arestore` 无条件再获取同一不可重入门闩。
- MemoryAPI、本机云任务准入也用同一个 history 门闩。迁移后必须仍共享同一实例，不能悄悄各建一把锁。
- `aprepare` 会安装 actor、同步归档并更新 prepared，因此留在协调者；不能因为名字包含 prepare 就归为纯查询。
- 本机和云 Runner 复用 `assemble_session_runtime`；没有 MemoryAPI/usage 的组合也要可运行。
- 后续可降级调用目前仍影响返回/释放时机；移动职责时保持时序，性能改变另行评估。

最脆弱前提：现有 Memory/History 资源能够覆盖迁移后的全部消费者。正式运行、上下文预览、临时/个人会话、云 Runner 都必须检查；不能为了常规 Web 路径顺畅而新增对完整 ProjectHost 的反向依赖。

| 公开 subscribe 注册者 | 同步调用；当前 run 固定 handler 快照 | 普通 Exception 隔离，不覆盖 BaseException；不能反向进入上游锁 |

注册与实现见 [host_assembly.py](../../naiyue_test_agent/application/projects/host_assembly.py):63、[run_delivery.py](../../naiyue_test_agent/web/run_delivery.py):137、[run_api.py](../../naiyue_test_agent/application/sessions/run_api.py):157、[RunnerObservations](../../naiyue_test_agent/cloud_runner/observations.py):25。

退订影响后续 publisher，不移除已创建 publisher 的 handler 快照。子 publisher 共用根序号。同线程重入先加入 pending，当前事件的其他 handler 完成后再交付；当前 pending 主要处理重入，不是慢消费者的后台积压队列，失控重入仍没有明确容量上界。

### 4.2 首选改法与条件

保留同步有序接收 + 消费者各自缓冲。先维护上表及锁表，补一个可重复的慢 handler 探针，用事件同步证明它阻塞哪个生产者；耗时采样按事件类型/handler 身份记录，不记录正文、凭证或模型内容。

探针属于离线验证，不先加入产品配置、全局监控器或同步回调超时机制。等待/持有时间、owner loop 延迟、载荷大小以及两个独立会话的相互影响分开测。无代表性数据时只报告机制与样本，不声称吞吐改善。

若热点在 logging sink，评估该 sink 的有界投递；若在 Web 投影，先看重复序列化和载荷；若为新慢消费者，沿现有模式定义自己的容量、丢弃/降级、关闭排空合同。

整体单 worker 总线是备选。只有多个接收者的实测开销显著且单消费者处理不足时才讨论；必须额外解决以下交付屏障，不能简单用 create_task 替换 handler：

1. usage flush 前，先前模型事件已到达 usage 接收队列。
2. controls/context 的 outbox 交付先于根 run_finished。
3. AsyncEventStream.finish、Web job.done/退订之前，相关终局已交付或明确触发重同步。
4. 根/子顺序、有限容量、反压、取消、关闭排空、异常与订阅快照语义均有定义。

最脆弱前提是把“可降级”误读为“可以任意延迟或丢弃”。它不允许破坏 run ID 建立、正常用量刷新、流式关闭和显式不完整提示。整体队列化的结构收益目前不足以证明这些新增责任必要。
