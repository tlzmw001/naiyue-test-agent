# 事件架构：执行权威、交付方式与前端投影

日期：2026-10-20。阶段：架构讨论，非实现授权。关联[调用链复盘](当前架构与调用链复盘.md)和[32类事件附表](事件全集与消费附表.md)。本页随同主题讨论修订，不逐轮保存对话流水。

## 1. 当前建议与决策顺序

当前建议保留LangGraph拥有图执行/状态提交、应用拥有准入/审批/必要保存、事件消费者拥有显示/用量/诊断的职责。用户随后确认按此顺序讨论，并要求先以理想架构评价，暂不以最小实现/迁移成本压低设计标准；具体对照见第8节。先判断每类数据由谁提交、谁必须等待、消费失败的后果，再决定同步/异步与对外协议。

这是一组AI建议，用户尚未批准事件迁移或架构改造。用户随后补充面试讲解与持续演进目标：担心链路长、类/事件抽象缺少依据、频繁返工；对应的待确认决策基线见第10节。插话持久化已降为未采纳方案，当前建议保留内存队列，见[场景1](场景01-插话与自然结束.md)。

四个核心问题：

1. **状态权威**：这个结果由谁正式确认？图、会话拥有者、持久事件日志还是显示投影？
2. **时序依赖**：生产者继续前是否必须取得消费/提交确认？
3. **失败合同**：消费失败要让业务失败，还是诊断、标记不完整并恢复？
4. **负载与恢复**：工作是轻量内存、IO还是CPU？队列满、取消、断线、重启如何处理？

事件名称、事件数量、前端框架和是否写了`async`，都不能单独回答以上问题。

## 2. 同步/异步是交付方式，不决定业务职责

| 形式 | 生产者何时继续 | 适用与代价 |
|---|---|---|
| 同步内联handler | handler返回后 | 轻量内存投影、简单有序通知；慢handler/序列化会延迟生产者，错误是否隔离要另定 |
| await异步handler | 被等待的handler完成后 | 同一协程中等待IO确认；等待期间事件循环可执行其他任务，但本次生产者仍等待，异常/取消也须定合同 |
| 有界后台队列 | 成功入队后；阻塞入队时仍受背压影响 | 隔离生产者与较慢消费者；需容量、溢出、顺序、退出排空及遗漏可观测性；入队成功不等于处理成功 |
| 持久日志/可靠工作流交付 | 按提交与确认合同 | 只有事件成为恢复/执行依据时才需要相应持久化、幂等、重放/版本合同；异步不自动提供这些性质 |

顺序也分两件事：串行await可保留同一流顺序；把每个handler扔成独立task，完成顺序不再保证。前台入队FIFO也不自动保证多worker完成顺序。

CPU密集的JSON、哈希或渲染不会因为改为async自动变轻；应先减少重复计算/载荷，必要时单独安排计算资源。

### 本项目当前属于混合方式

- `ApplicationEventSubscriptions.publisher`选择全局和本会话订阅者；`RunEventPublisher._deliver`同步按序调用，普通Exception诊断后在本run停用相关handler。
- Web的`DeliveredRun.observe`同步更新有界投影/事件缓存，之后唤醒异步SSE交付；不等待浏览器绘制确认。
- `ModelUsagePersistence.accept`和`DiagnosticPersistence.accept`同步筛选/入队，后台任务异步写入，队列受预算约束。
- 必要会话保存由`SessionExecution._afinish_run → SessionPersistence.afinish`等直接被等待，不能塞进可随意失效的普通观察订阅。

因此“同步总线”不代表每条通知同步写数据库或等网络。“异步总线”也不代表运行可以立刻跳过所有消费者。

当前用量/诊断写入是允许报告不完整的观察合同；若未来有不可丢的财务对账要求，应独立讨论必要提交保证，不能沿用可丢队列并宣称完整。

## 3. 前端是否缺少独立模块

用户假设：没有Pi式独立前端模块，导致为了显示新增大量事件。当前源码未支持这个因果关系。

现有生产链：

```text
图/middleware/回调产生运行事实
  → RunEventPublisher
  → DeliveredRun.observe
      → StreamingMessageProjection / 工具与子Agent投影
      → 有界RunView与事件缓存
  → HTTP快照 + SSE增量
  → runSubscription.subscribeRun（游标、校验、重连、重取快照）
  → events.applyEvent / agentEvents.applyAgentEvent
  → RunView / MessageRow / ToolState
  → Conversation / ToolCall / ReasoningContent / ContextPanel
```

我们已经有独立的传输、重连、reducer、投影及组件模块。多个文件还是独立npm包，主要影响复用和组织方式，不能自动消除跨进程同步需求。

可确认的额外复杂度：后端32类运行事件大体沿同一类型协议通用转发；前端即使没有专门业务处理，也需推进公共sequence。内部观察分类与界面交付分类存在耦合，但协议共享本身不必然错误。

事件增加有不同来源：

- 模型返回与项目响应接受、主模型与摘要/Auto用量，是运行/核算需求。
- run/turn/控制交付/审批确认，是生命周期与诊断需求。
- 分片/完整消息校准、工具进度、上下文展示，是产品显示需求。
- 消息不可读/超帧/游标缺口/重同步，是跨进程与有界交付需求。

第一段11次发布中的invocation两类服务用量/诊断，model_call两类服务CLI/诊断，常规turn没有专门显示消费。因此不能把这11次都归因于前端展示。

### Pi Web UI的版本边界

- 当前参考73f8de80和本地a69bef789树中均无`packages/web-ui`。GitHub历史确认b141e1fa提交移除workspace；删除前559a7168版本仍可查。
- 历史`AgentInterface.ts`在`session.subscribe`中消费AgentEvent，message_update交给StreamingMessageContainer，renderMessages直接读取同一个session.state.messages/pendingToolCalls。
- 这个历史示例的同对象直接订阅路径，与Python服务器/浏览器跨进程复制状态有不同约束。它不能证明我们的独立传输/恢复事件不需要。
- 当前Pi RPC模式：`session.subscribe → toJsonEvent → stdout JSONL`，另以核心异步监听器等待stdout背压。前端一旦跨进程，也有协议/交付边界。

建议复用我们已有Web投影和前端reducer，先按消费者核对必要信息；只有证据表明内外协议耦合造成实际维护/性能问题，再讨论收敛交付事件，不提前再加一套通用协议框架。

## 4. 其他项目怎样处理

以下为固定源码/官方材料的实例，不代表总体统计。未执行参考项目模型请求或产品运行。

### Pi：直接事件订阅与会话适配

核心Agent先用事件更新内部状态，再await核心监听器；coding-agent会话又维护扩展、保存和外部事件。RPC适配负责JSONL。借鉴点是核心事实和展示组件各自集中；它也存在背压与结算边界，不是只有几条日志。

### OpenCode：服务端事件、客户端同步，部分事件具持久投影语义

核对dev固定db45c950：

- SDK文档公开`event.subscribe()`的SSE订阅。
- `packages/app/src/runtime/server/sync.tsx`集中监听serverSDK事件，并管理目录子store、bootstrap刷新/刷新队列与连接生命周期。
- `packages/core/src/bus.ts`区分durable与volatile：durable分支经事务执行projectors/提交序号与事件，再通知；提供历史log/replay及live通道。
- `session/message-updater.ts`按durable SessionEvent更新消息模型。

这表明前端模块化可以与较细事件共存；是否有持久事件语义取决于它的状态模型，不能直接把我们可失效的观察总线升级成同样角色。

### OpenHands SDK：事件历史属于Agent输入与会话事实

核对固定33d8aa29：

- Agent.step读取事件历史，产生Action/Observation/Message等事件，后续步骤再读取这些事实。
- LocalConversation的默认callback先`ConversationState.append_event`，再调用用户callback；必要持久化失败会阻止后面的通知链。
- 会话状态、事件存储、Agent Server HTTP/WebSocket及前端各有边界；流式token/progress回调与完整事件也分开。

它的事件日志在执行/恢复中有更重职责，不能按普通UI通知的故障隔离规则处理。

### AI SDK UI：界面传输协议的实例，不是另一个Agent运行时

官方Stream Protocol以SSE传递消息start、text/reasoning的start/delta/end、工具输入/输出、结束等，前端useChat消费协议形成消息。Python后端也可实现兼容协议。借鉴的是稳定的UI数据合同与客户端状态更新；它不会自动解决我们额外的审批、持久恢复、子Agent和用量合同。

### LangGraph：我们已采用的框架也区分执行与投影

本机LangChain1.4.2、LangGraph1.2.12。当前项目`ainvoke_with_message_observation`用`astream`的messages/updates/values/custom构造观察数据。节点返回值、reducer、Command/路由决定状态与调度。

官方现有stream_events typed projections（messages/values/subgraphs/output等）；本机已确认公开方法/签名存在，未验证它替换本项目观察器后的行为。该接口的存在可作为后续减少重复适配的候选，不构成本轮迁移建议或已验证替代。

## 5. 事件能否更新状态：先区分三种状态

| 状态 | 当前权威所有者 | 事件消费者能做什么 |
|---|---|---|
| 图执行状态：messages、下一节点、interrupt/checkpoint | LangGraph及项目明确注册的节点/middleware | 普通显示/日志消费者不反向推进图；节点经返回值/Command等更新 |
| 应用会话状态：busy、审批、控制队列、run资源 | AgentSession/SessionState/ActiveRun等应用拥有者 | 用户命令经公开应用入口校验并修改，事件报告确认程度 |
| 显示投影：工具卡、草稿、按钮、运行快照 | DeliveredRun及前端RunView/reducer | 消费事件更新投影，缺口时重取快照/历史；这些更新有实际产品作用 |

因此“事件不控制图”与“前端事件reducer更新状态”可以同时成立。区别是更新哪份状态、谁拥有提交权。

### 命令、必要状态提交、通知

用户点击停止或批准，是要求系统执行动作的命令。正确入口是应用控制/审批API，明确校验当前身份与状态，并通过现有RunControl/HITL恢复路径处理。control_accepted/approval_requested等报告接受/待处理/生效事实，不靠浏览器消费通知后才决定工具是否可运行。

同理，图通过节点返回的ToolMessage更新messages并路由回模型；tool_call_finished消费者更新工具卡，不负责向图补ToolMessage。审批、工具副作用和必要保存也不应通过可停用普通handler偷偷接线。

### 合理的事件参与方式

1. 在一个明确状态拥有者内部，以确定性reducer处理事件更新该拥有者的状态，Pi核心就是一例。
2. 以持久事件日志作为明确的历史/恢复依据，OpenHands、当前OpenCode部分durable事件有相应机制；还需可靠提交、版本/序号、重放与幂等边界。
3. 把执行事实投影为UI、用量和诊断；本项目当前普通观察总线采用这一角色。

这三类可以互通，但同一事实的提交、执行推进和失败所有者要明确。不能在LangGraph之外再让任意普通订阅者独立推进同一工具循环，造成双重调度。

旁查AgentX3fcfa0e：transitionTo更新workflow状态→AgentEventBus.publish→AbstractAgentHandler.processEvent/transitionToNextState，确实以事件调用链推进工作流；该事件总线与本项目观察总线不是同一种合同，不能仅按名字替换。

## 6. 正常/失败例子与验收依据

正常：模型请求read→图提交AIMessage/tool_calls→工具返回→图提交ToolMessage→路由回模型；事件分发到Web投影、CLI、诊断。Web关闭/断线后执行仍由后台producer继续，恢复显示从快照/历史开始。

普通观察失败：Web或诊断handler异常→记录观察故障/不完整→执行按原结果继续；缺事件的显示按既有恢复合同处理。同步慢handler即使不抛异常，仍可拖慢生产者，这是需要度量的负载边界。

必要失败：工具无法确认副作用、审批状态不匹配或必要会话保存失败→执行/会话拥有者按其合同阻断或上报；不能归入普通观察失败后忽略。

候选改造的验证应包含：无Web订阅仍完成工具循环；慢/抛错消费者；同session顺序与跨session隔离；队列满/退出排空；断线后快照+增量不丢不重；审批不因UI订阅缺失而绕过；必要保存失败不被吞。

这些是讨论中的验收方向，不表示本轮新增了相应实现/测试。

## 8. 理想的图状态更新与当前设计对照

用户问题：基础模型—工具循环之外，业务控制是否增加了很多直接节点指令？本节先讨论目标设计，不以最小实现或迁移成本决定优劣；无生产改造授权。

### 8.1 理想目标

理想目标是每个业务转移有清楚的触发、前置条件、状态提交、后继选择与失败/恢复合同，新增控制能力后仍能解释所有转移。节点数少或没有Command/jump_to，不是独立验收指标。

语义上的阶段图（不是要求新增同名节点/枚举）：

```text
运行准入/准备
  → 模型前边界：停止、输入选择、请求准备
  → 模型调用/响应接受
    ├─ 工具请求 → 权限/审批 → 工具执行/结果确认 → 模型前边界
    └─ 无工具 → 自然结束边界
                  ├─ 已接纳steering/follow-up → 模型前边界
                  └─ 无待办 → 关闭接纳窗口 → 运行收尾/保存 → 释放

等待审批：暂停并保留准确恢复点；恢复重入时必要前置工作须可重入。
停止：禁止新的不允许操作，处理在途工作与配对结果，再完成收尾。
异常：保持主异常和副作用确定性；无法确认的结果按合同阻断并恢复。
```

执行阶段、停止意图、工具结果确定性、会话是否可用属于不同维度，不能压成一个busy或run_stopped；也不必为它们的所有组合制造一个总枚举。哪些事实需持久化由恢复合同决定，task/锁/临时计划不应机械塞入图状态。

### 8.2 一次转移应满足的合同

1. **输入可解释**：采用当前图状态、已接纳的控制输入与已确认结果；恢复需要的事实不能只藏在不可重建的闭包/临时对象中。
2. **规则有归属**：在哪个安全边界处理steering、follow-up、stop、approval及其竞争有明确规则。一个拥有者负责对应事实，不等于所有逻辑塞进一个超级router。
3. **状态和路由协调**：先确认合法更新，再进入允许的后继；不能宣布停止却继续启动新工具，不能历史尚有未配对调用就发下一次不合法模型请求。等待审批/在途阶段允许有未完成调用。
4. **副作用确认**：工具已开始、结果已知、未执行、结果未知分清；外部副作用与DB不能假定有全局原子事务。
5. **必要提交可确认**：图/会话的必要保存失败必须显式影响结果；分阶段提交需要可重入、阶段记录和失败后的可用性判断。
6. **恢复准确**：审批恢复、输入溢出局部重试、异常恢复、重新生成是不同操作，不能统一成“回model再跑一次”。
7. **观察不抢控制权**：观察可以报告开始/草稿/完成的不同事实；已提交的消息必须有实际提交依据。普通订阅者不能决定图下一跳。

### 8.3 当前真实图与框架语义

使用正式build_async_local_application和现有ToolModel/一个合成工具，仅编译不运行。LangChain1.4.2/LangGraph1.2.12的该配置产生15节点：2个起止哨兵、model/tools、11个hook节点。它不是所有配置的固定节点数。

11个hook：TurnBoundaryMiddleware.after_model、ToolSetMiddleware.before_agent/before_model、ToolBatchMiddleware.after_model、reset_run_control.before_agent、compact_before_new_run.before_agent、inject_before_model.before_model、inject_at_natural_end.after_agent、BatchApprovalMiddleware.after_model、PermissionMiddleware.after_model、StopBoundaryMiddleware.after_model。wrap_model/tool不会因此各自变成独立节点；hook节点也不都产生路由变化。

本机factory._resolve_jump及注册边确认：

- `jump_to='model'`映射loop_entry_node，当前为ToolSetMiddleware.before_model，再经过inject_before_model，才到model；不是绕过全部前置处理直达模型调用。
- `jump_to='end'`映射exit_node，当前为inject_at_natural_end.after_agent，再到END或按该边界继续；不是跳过应用收尾。stop状态会阻止自然结束边界再取消息。
- `Command(update=...)`只是通过reducer提交更新；它不等于Command(goto=...)。审批Command(resume=...)也不是任意指定新节点。
- before/after hooks编成节点和边是框架公开扩展机制，不能把使用这些接口本身判为不合理。

图证据：`build/graph-state-design-20261020/graph.json`。0次模型请求、0次session run，不读取真实模型配置/用户数据库。

### 8.4 按实际职责评价

| 当前机制 | 评价 |
|---|---|
| 节点返回dict、wrapper返回ExtendedModelResponse/Command | 符合框架状态提交机制，本身合理 |
| before_model注入steering，after_agent选择follow-up并继续 | 语义边界合理，但产品“继续处理待办”目前由框架after_agent回跳表达，读者需额外理解 |
| stop在模型等待、响应后、审批/Auto、工具dispatch等处检查 | 多个安全检查点有必要；风险在于终止规则/配对/优先级表达分散，不应把所有检查合并到一个位置 |
| HITL中断/按checkpoint恢复并重验授权 | 符合显式恢复语义；恢复不是工具自动获准 |
| 溢出恢复只重试模型请求，成功后以Command合并新历史/响应 | 有合理提交边界；不应改成重跑整个工具循环 |
| ToolBatchMiddleware在context建立临时并发计划 | 有明确运行范围；临时计划不是正式执行历史，恢复必须从可信状态重新准备 |
| TurnBoundaryMiddleware.after_model只mark_ready并返回None | 未控制业务状态，但观察需求进入持久执行拓扑；从职责纯度看值得改进，重设计须保持准确完成时点 |
| manual_compaction用as_node=model再END；recovery用END/tools/END；regenerate用START/END构造新thread | 公开API合法、有阶段确认/故障测试，不能据此判错；但维护操作与内部节点语义耦合较强，是结构改进的重点 |

这里的“控制分散”不等于多个对象同时随意写同一份图：当前仍主要由LangGraph提交。问题是业务转移知识分布在多个hook、运行控制对象、自然结束队列和图外checkpoint操作里；需要结合框架路由和应用收尾才能看清全貌。

### 8.5 典型转移与竞争规则

正常工具：模型返回调用→图提交AIMessage→权限/审批→工具返回→图提交ToolMessage→下一次模型。事件消费者不承担结果回填。

停止与工具调用同时出现：应先禁止后续新操作；已开始工作按其可取消/需等待语义结算；未执行调用补配对结果；原有失败/未知副作用不能被“用户停止”抹去。当前响应后停止和工具dispatch两层检查都有各自时点作用。

自然结束与新输入竞争：一个同步确认边界完成“选择已接纳输入继续”或“关闭接纳窗口准备结束”。已接纳消息不得掉进两者之间；结束后新输入走新run准入。当前finish_run_boundary在session锁内选择steering优先、follow-up FIFO或关闭窗口，具备这一方向。

输入溢出：重试对象是当前模型请求，成功前保留可用历史，已执行工具不重放。恢复与重新生成涉及副作用历史，不能仅由UI“重新生成”按钮名称推导为安全重放。

### 8.6 设计判断与下一步

当前设计**部分符合目标**：状态提交入口、权限/审批门禁、配对/停止、局部重试、保存确认有实际合同和测试；控制语义的集中表达、观察与执行拓扑分离、维护操作的语义封装仍不足。

从设计上应先写清三个关键边界的转移表：模型调用前、工具副作用前、自然结束前；再定义停止/失败/审批恢复、压缩/恢复/重新生成的独立合同。运行图承载合法工作流，framework adapter负责dict/Command/jump_to/as_node的具体翻译。这里不要求立刻创建统一Decision类/路由平台，也不以现有代码规模决定结论。

与Pi73f8de80对照：runLoop在明确位置读取steering、工具批次terminate、finishTurn决策及follow-up。业务控制仍存在，只是循环函数显式表达；我们用create_agent的hooks/边适配相似控制需求。AgentX3fcfa0e则通过workflow state事件推进handler，并非另一种可直接替换的LangGraph实现。

图状态专题11项现有定向测试通过（1.12s）：steering最终响应期间注入、自然结束steering优先、响应后停止绕过审批/工具、批准/拒绝门禁、模型前停止、溢出不重跑工具、手动压缩提交故障、分阶段恢复。它们证明所测行为，不能证明架构已经达到理想状态；生产代码未改。随后12组场景的补充验证见第9节。

补充一手材料：[LangChain middleware状态与跳转](https://docs.langchain.com/oss/python/langchain/middleware/custom)、[LangGraph中断重入](https://docs.langchain.com/oss/python/langgraph/interrupts)、[update_state/as_node与后继](https://docs.langchain.com/oss/python/langgraph/use-time-travel#from-a-specific-node)。

## 9. 复杂场景逐项评估

用户要求将优化项以及基础循环之外的复杂控制逐项展开，详见[复杂控制场景与目标职责](十二组场景总览.md)。按12组记录当前路径、状态、失败/竞争、是否清晰及改进方向，避免本页超过500行。

进一步核对明确三处职责混合：RunObservation承载必要持久化读取的status；call_observation与工具observation承载必要响应/调用门禁；Auto审查与摘要各保留仅一个异步生产驱动器的生成器转发。它们不是可以整体删除的纯观察，也不能因接口都叫async就忽略间接。

## 10. 面向持续演进的地基：待确认决策基线

### 10.1 本轮目标与证据范围

用户希望项目用于面试时能解释主链与取舍，并像逐层建楼一样继续增加能力；重点是减少不必要的结构返工。本节提供决策依据，不承诺零返工，也不因新增原则直接授权重构。设计讨论不例行重跑测试，本轮未运行测试；已有测试证据保留各自日期。

用户已认可按这套方式开始逐场景讨论，并补充教学要求：先给通俗的具体例子，再展示真实对象/数据和调用链；术语第一次出现即用日常语言解释，区分方法所在文件、实际执行对象和框架调用时点。先讲谁接收、谁保存、谁取出、谁决定继续、谁负责通知，再讨论类/事件是否必要。该确认不等于产品代码改造授权。首个完整例子见[插话走读](场景01-插话与自然结束.md#8-通俗走读工具执行中又收到两句话)。

稳定基线应优先说明状态所有者、合法转移、身份与生命周期、必要等待/失败、能力插入点。类名、文件层数和事件数量是实现选择，不能代替这些合同。

### 10.2 三种交互先分清

| 交互 | 例子 | 调用方期待 | 失败语义 |
|---|---|---|---|
| 命令/必要操作 | 请求steering、执行工具、必要保存 | 明确接纳/返回/拒绝或异常；必要时等待 | 按业务合同处理，不能当普通通知失败丢弃 |
| 执行结果/状态提交 | ToolMessage、middleware状态更新、图路由决定 | 被正式拥有者校验并提交 | 提交失败按执行失败处理；返回结果不自动等于已持久保存 |
| 事实通知 | message_delta、tool_call_finished、run_finished | 消费者更新显示/统计/诊断 | 按通知合同隔离、标记缺失或重同步 |

同一次工具调用可产生ToolMessage和tool_call_finished：前者进入模型执行状态，后者描述调用处理结果；工具配对、图循环不应依赖普通显示订阅者回填。当前tool_call_finished也不证明ToolMessage已提交，详见事件表。

事件也可作为某个系统的权威状态输入或控制扩展点；需要明确唯一状态拥有者及返回/确认合同。DSH的agent/pre-step返回enter/reject，AgentX的handler会推进workflow，Pi的循环读取条件/决策；不能按“event”一词推断职责。我们已有LangGraph调度，当前建议让正式控制和提交沿显式调用链表达，观察通道传播已确定事实。

### 10.3 状态与生命周期基线

| 事实维度 | 建议的正式拥有者/边界 |
|---|---|
| 图内messages、模型—工具下一步及checkpoint | runtime与LangGraph的执行/提交合同 |
| 会话准入、busy、插话窗口、根运行及子工作结算 | AgentSession/SessionExecution及会话服务 |
| 请求参数、模型适配及供应商响应转换 | 模型接入模块；每次请求按既定时点冻结 |
| 工具注册、参数/权限复核、实际主体与结果 | 工具及执行边界；模型文字不能替代授权 |
| 历史归档与必要保存 | 显式持久化入口，由拥有者等待 |
| 流式草稿、卡片和连接状态 | Web/CLI读投影，由正式事实校准 |

这是目标职责图，当前仍有混合点：RunObservation的结果被必要保存读取；模型/工具观察模块含门禁。不能先把这些对象整体视作可关闭观察。历史、图状态和展示可以存有相关数据，关键是每种事实谁有最终确认权，以及其他副本怎样派生/校准。

身份合同至少要讲清session_id/run_id/reply_id/message_id/tool_call_id；follow-up可以在同run开启新reply，审批可以在新run延续工作。Run返回结果、图停止/中断、必要保存结束、busy释放和Web producer退出分别表达不同边界，不能合为一个“结束”。

### 10.4 类和调用层的决策点

| 情况 | 优先形式 | 本项目例子/理由 |
|---|---|---|
| 表达一份有形状的数据 | 数据对象/dataclass | QueuedInput、SessionState；数据对象不自动需要服务类 |
| 只计算输入到输出，没有需要拥有的状态 | 普通函数 | 分类、校验和转换等；是否有副作用另行标注 |
| 多个操作共同维护状态、资源或不变量 | 有明确生命周期的对象 | AgentSession维护窗口/队列，RunControl维护停止状态/模型等待 |
| 已有不同实现或确定的跨模块窄边界 | Protocol/适配器 | SessionPort让runtime取得所需操作，避免拿整个会话任意修改 |
| 只做内部转发，没有隔离、策略、适配或实际合同 | 先考虑直接调用 | 不因分层名称给每个操作重复增加入口；公开入口/框架hook需核实实际合同 |

每加一个类先回答：它拥有什么；为何需要独立生命周期/规则/替换边界；谁使用它；去掉后哪个具体责任失去所有者。没有状态且没有实际替换需求时，不先建设Manager/Service/Factory组合。

同样职责第三次重复遵循AGENTS提取；文件拆分不必增加运行时对象，mixin/模块组织也不自动等于新增业务层。纯转发可能有真实公共边界作用，不能只按方法行数删除。

链长按“每层是否承担独立责任、是否反复解释同一事实”评价。权限复核、必要保存和框架适配会增加调用深度，但可有明确价值；为了减少栈帧删除它们会破坏合同。对外讲解展示责任主链，具体调试再展开函数链。

### 10.5 一种事件的准入问题

新增/保留事件要能回答：

1. 具体报告哪个已经确定的事实？哪个对象确认、在哪个时点？
2. 谁实际消费？会据此改变什么显示/统计/诊断，或承担什么明确的执行合同？诊断可以是实际用途。
3. 与已有事件是否有独立确认边界或处理合同？只是同一事实的结果差异，通常先考虑status/phase字段。
4. 丢失、重复、晚到、消费者报错时，业务与界面分别怎样表现？哪些顺序需要保证？
5. 是否需要跨重启保留？是否可从正式状态重建？必要存储确认由谁等待？
6. 现有身份和有限载荷能否表达？要传完整对象还是标识/增量，成本和敏感信息边界是什么？

事件数量由独立事实、确认点和实际消费者决定，不设理想固定数；当前目录的32类不能直接和Pi核心10类比较。也不为每个函数、每个if或每个按钮增加类型。比如run_finished(status)可覆盖多种终态，message_delta和message_completed则有增量与确认的不同合同。

model_call与model_invocation分别表达项目逻辑调用接受和框架实际调用观察（也覆盖摘要/Auto用途）；同名started/finished不自动表示重复。用户了解control三阶段时点及诊断通道后，决定保持现状：control_delivery_started暂不补入SQLite诊断，遇到真实排查不足再增加，不删除运行事件或更改日志配置。三者INFO日志默认被WARNING过滤的限制保留。普通通知不提供隐含持久保证，必要保存不经可禁用的普通observer。

### 10.6 控制演进成本的方式

先把已列12组场景填到同一基线上：触发条件、状态拥有者、实际动作、提交/返回、失败、通知、收尾。每组可得出保留、澄清文档、局部调整或需要产品决策；不能预设每组都要改。

| 后续能力 | 应主要接入的位置 | 评审时要解释的扩散 |
|---|---|---|
| 新模型供应商 | 模型接入与必要配置/错误适配 | 为何需要改会话生命周期或工具循环 |
| MCP/新增工具 | 注册/参数合同、执行权限、连接资源生命周期 | 为何需要让图认识每个具体工具实现 |
| 工具进度展示 | 工具进度协议、后端/前端投影 | 为何显示需求要修改核心状态路由 |

界面、序列化和配置随能力合理变化可以跨文件；目标是相关变化集中在相应职责，其他已确认合同保持稳定。新增机制必须有当前场景依据；合适的抽象让已知变化局部发生，不为未知变化预置通用平台。

重构准入建议：已确认合同不满足、真实扩展反复修改无关模块，或职责混合导致故障语义难以保证。其余保留。决策改变时写明发生变化的需求/证据，避免仅因新参考项目而反复切换。

后续确认顺序：先确定本节的所有权/交互/生命周期规则，再沿12组场景逐项判断，汇总有证据的结构调整，获批后按依赖顺序实施；未来功能引用同一基线和事件表。面试可先讲主链、关键分支与取舍，再按追问展开框架细节；文档清晰不能自动证明用户已独立掌握。
