# 总结一：哪些事件有记录之外的实际功能

日期：2026-10-20。依据本机工作树的注册表、生产消费者及现有测试源码，只读核对，未重跑功能测试。并行开发正在实施Spec118：本快照已采用callback发布的单套`model_call_started/finished`，共30类注册事件；不代表Spec118整体完成验收。原[事件全集](事件全集与消费附表.md)的32类、两套模型事件属于迁移前基线。

## 1. 先区分执行状态、保存状态和展示状态

用户让Agent读取日志，模型调用read，页面展示工具卡片；用户随后点击停止：

```text
正式执行：应用接纳停止 → RunControl记录请求 → 安全点检查 → 已开始工具结算
          → 图提交停止结果 → 必要保存 → 释放运行占用
观察交付：control_accepted → 页面显示“停止中”
          tool_call_finished → 工具卡片更新结果
          run_finished → 页面显示终局，残留草稿标为未确认
```

第二条链路确实有产品功能，但不代替第一条链路。

| 状态 | 谁拥有 | 普通观察事件的作用 |
|---|---|---|
| 执行状态 | LangGraph消息/节点、RunControl、权限及待审批对象 | 不通过订阅这些事件来决定执行；走直接业务调用和图提交 |
| 必要持久状态 | checkpoint、应用会话行、正式聊天归档 | 必要保存由运行/恢复流程直接等待，不靠消息观察订阅补存 |
| 展示与统计状态 | Web运行投影、消息草稿、工具卡片、CLI显示账本、累计用量 | 有；这是当前事件主要的非日志功能 |

`TurnObserver`等对象的直接方法可能同时做判断、维护内部状态和发布事件。“调用这个方法有执行作用”不等于“发出的同名事件被订阅后驱动执行”。模型响应门禁、预算检查、审批校验都要沿实际方法调用定位。

以下口径是**仓库内已接线的专门消费者**；通用日志、诊断SQL、SSE转发或公共sequence推进不单独算作每类事件的业务功能，不推测仓库外订阅者。

## 2. 全量分类：22类直接功能、1类间接统计功能、7类主要用于观察留痕

按最直接的专门用途分类，30类互不遗漏。一个事件可以同时参与日志、诊断及其他消费者。

“22类直接功能”不表示22类都驱动业务：其中14类涉及Web/交付投影或审批刷新；另外8类以用户提示为主，是`control_delivered/applied/discarded/outcome_unknown`、`model_call_started`、`compaction_started`、`context_recovery_started/finished`。control_delivered也有Web通知，其余这些专门提示主要在CLI。提示有交互价值，但不应夸大为执行控制。

### A. 运行登记与终局：2类

| 事件 | 已经发生什么 | 消费者实际做什么 | 时点限制 |
|---|---|---|---|
| `run_started` | 应用准入后建立实际run身份，开始本段运行 | `DeliveredRun.observe/_ready`取得实际run_id、登记Web任务、完成启动等待；Web记录模式，子面板显示running；CLI按实际run分组 | 不表示模型已发送。启动登记还有后续实际帧的降级路径，并非绝对依赖这一帧 |
| `run_finished` | 主链已得出本run终局；正常路径已做必要收尾，失败路径按异常合同报告 | Web/CLI显示completed/stopped/interrupted/failed、人工核对标记；残留草稿及未结束工具标为未确认；CLI避免重复终局提示 | 事件本身不保存、不释放busy；producer的直接finally还会设置done，不以这一帧代替关闭流程 |

例：A1只收到“原因是……”就失败。结束事件让它显示为unconfirmed，不因页面已有文字就升级为成功回答。根run与子执行段的范围由信封和source区分。

### B. 消息正文与可信程度：5类

| 事件 | 实际功能 | 主要消费者 |
|---|---|---|
| `message_delta` | 按message_id和index累加正文草稿，边生成边显示 | `StreamingMessageProjection`、前端`applyEvent/applyAgentEvent` |
| `message_reasoning_delta` | 累加推理展示草稿，维护独立index | 同上及前端`reasoningDelta` |
| `message_completed` | 用完整快照校准同ID草稿并标记完整；工具调用/结果及展示元数据进入对应视图 | 服务端/前端消息投影、子面板、CLI |
| `message_revised` | 用新快照替换同一消息的旧展示；按指纹避免重复显示 | 同上 |
| `message_snapshot_unavailable` | 标记观察视图不完整，CLI提示不完整；交付校准不能把当前投影当成完整事实 | `StreamingMessageProjection.incomplete`、CLI；Web通过包含该标记的视图处理缺口 |

例：A1的delta先得到“配置”，完整快照是“配置缺失导致登录失败”。完成事件替换A1，而不是再添加一个重复气泡。合并时还看run、revision及草稿/完整状态，不是仅凭同ID无条件覆盖。

它们维护展示消息，不把HumanMessage/ToolMessage写回LangGraph，也不执行必要聊天归档；图和正式归档各走自己的提交/保存入口。

### C. 工具卡片、进度和结果：3类

| 事件 | 实际功能 | 不能误读的含义 |
|---|---|---|
| `tool_call_started` | Web卡片变running；CLI建立进度账本并提示正在处理 | 可能早于等待串行位置/并发名额，不保证工具主体已开始 |
| `tool_progress` | 更新活动、阶段和进度文本；CLI合并过密更新 | 消费者核对tool_call_id、run、工具名、batch_id及旧状态，防止旧进度覆盖当前调用 |
| `tool_call_finished` | 结束卡片/进度显示，区分success、error_result、not_executed、exception、outcome_unknown | 本次分发边界结束不等于业务成功；普通错误结果仍可能交给模型继续处理 |

例：R1中AI消息B1请求工具T1。卡片以T1定位，进度还带batch_id=B1。下一批复用调用ID时，旧B1进度不能更新新批卡片。真正执行工具的是分发/handler，卡片变running不会反向启动工具。

### D. 控制反馈和审批交互：6类

| 事件 | 记录之外的功能 | 执行权威在哪里 |
|---|---|---|
| `control_accepted` | 停止时Web设stop_requested、子面板显示stopping；CLI显示接纳回执，累计各kind回执计数，命令据此避免重复打印，后续进度显示“停止中” | 队列接纳或RunControl.request_stop等正式入口，不是UI消费后才停止 |
| `control_delivered` | Web/CLI提示补充消息已加入上下文 | 已确认HumanMessage出现在图状态；消费者不执行插入，也不保证模型遵从 |
| `control_applied` | 当前CLI对kind=approval显示“审批决定已由审批流程处理；工具结果另行确认” | 停止确认/审批处理各自的直接流程；用于停止和审批，但目前没有通用Web applied状态机 |
| `control_discarded` | CLI提示未执行、已随运行结束清理，避免用户误以为仍会处理 | 队列关闭/清理逻辑已处理；提示不再次清队列 |
| `control_outcome_unknown` | CLI提示已取出或提交但未确认交付/生效，需要核对 | 不自动重试，不把未知改为成功 |
| `approval_requested` | CLI展示待审项；Web重新读取会话/审批批次，使根审批面板出现；子面板显示awaiting_approval | 服务端当前pending_tool_approval及approval_batches；用户决定经正式API和批次校验提交 |

完整例子：服务端先建立待审批P1，再通知approval_requested。前端收到→refreshSession→得到approval_batches=[P1]→展示面板。用户提交P1后，服务端由当前pending计算批次ID再比较，另查对象归属和调用内容；旧通知不能代替当前审批状态。

### E. 模型上下文和操作反馈：6类

| 事件 | 实际功能 | 限制 |
|---|---|---|
| `model_call_started` | 当前callback协议中，purpose=agent时CLI提示模型正在处理；用量写入器建立实际调用记录 | 以invocation_id配对；不是旧逻辑准备开始，不触发压缩，也不证明对端已收到网络请求 |
| `model_context_snapshot` | Web保存请求快照，ContextPanel展示组成和估算/报告信息 | 只读展示，前端不替后端做预算/压缩门禁；帧太大可省略载荷并表示不可用 |
| `compaction_started` | CLI显示正在压缩 | 当前没有仅靠它驱动的Web专门压缩状态机；维护任务还用正常run交付 |
| `compaction_finished` | CLI反馈applied/skipped/fallback/failed等；手动trigger时Web保存compaction_result并显示结果 | 操作失败/跳过与run完成分别看；通知不提交摘要、不自动续跑 |
| `context_recovery_started` | CLI提示输入超过窗口、正在尝试恢复 | 实际恢复由runtime异常分支执行 |
| `context_recovery_finished` | CLI反馈恢复成功、失败或未确认 | 重试判断、候选和正式提交属于直接恢复流程，不由消费者决定 |

### F. 经SQL形成产品统计：另外1类

`model_call_finished`有间接产品功能，不能简单算成“只存SQL”：

```text
模型callback完成/失败/取消
  → model_call_finished(invocation_id=I1, status=returned/failed/cancelled, usage_status=…)
  → ModelUsageWriter.accept有界入队 → SQL调用用量记录
  → 查询API聚合 → SessionUsage展示累计、模型/用途/主子分项及未知项
```

配套started已归E；两者通过实际callback的invocation_id关联。这里SQL是统计产品的输入，和只存诊断日志不同。页面按读取/本根run交付完成等时机刷新，不是每个finished都直接刷新React。

缺失用量不能当0，失败可能只有partial。returned只说明模型返回，不代表通过应用响应门禁，更不代表工具/run成功。此事件不作为压缩门禁、不自动扣总预算；未来Spec119的耗时/预算能力不能当成已接线功能。

### G. 目前没有专门产品消费者：7类

| 事件 | 当前主要价值 | 当前没有做什么 |
|---|---|---|
| `turn_started`、`turn_resumed`、`turn_finished`、`turn_suspended` | 记录逻辑turn的新建、接续、结束/暂停，供诊断和测试观察 | Web不据此切换run终局；turn_finished不结束整个run |
| `turn_observation_unavailable` | 说明turn观察缺口，便于诊断 | 没有专用UI恢复分支，不自动停止运行 |
| `context_messages_changed` | 描述模型上下文消息变化，便于追踪压缩/控制合入 | 不提交图状态，也不据此删除聊天窗口历史 |
| `control_delivery_started` | 留下取出/提交控制的中间时点，区分未取出与结果未确认 | CLI虽进入_control，但没有此kind的专门显示分支；Web也无专门消费 |

它们仍经过已订阅通道、公共序号和有界交付。“无专门消费者”不等于无价值或已授权删除；删减须另查诊断需求、测试合同及实际外部消费者。
