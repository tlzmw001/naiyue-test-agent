## 1. 结论与评价标准

当前不是多个事件订阅者任意调度同一张图。LangGraph仍负责主要图状态提交，应用负责会话和必要保存。但控制规则、运行结果、执行门禁、观察和维护操作的边界仍有混合，读者需要自行拼出状态机。

评价“是否最优”以当前目标为标准：规则可理解、状态所有者清楚、恢复与副作用有准确合同、变化不要求跨多个无关模块修改同一事实。没有对所有替代实现做比较或性能压测，不宣称数学意义的全局最优。

明确建议：保留有用保护；重整业务语义与框架适配的边界；避免用新增总线、通用router或全局状态对象替代必要的职责分析。

| 场景 | 当前评价 | 设计方向 |
|---|---|---|
| 1. Steering/Follow-up与自然结束 | 关键接纳/竞争保护合理；业务阶段表达分散 | 集中输入选择、回复归属、窗口关闭合同 |
| 2. 停止/外部取消/退出 | 多时点检查与settle必要；终止事实跨对象分布 | 统一终止语义，保留各安全检查点 |
| 3. 权限/Auto/HITL | 准备、审批与执行复核分层合理；Auto局部驱动间接可收敛 | 审批快照+确定执行许可，直接异步审查流程 |
| 4. 工具批次/错误反馈 | 明确软错误和机制失败；failed策略表达粗 | 调度与失败策略独立，继续规则显式 |
| 5. 请求准备/动态配置 | 冻结与下一请求刷新有必要；多处解析同一请求 | 按请求形成一致输入事实及生效时点 |
| 6. 主动压缩/输入溢出 | 安全切点、局部重试合理；主动检查时点和单驱动生成器值得改进 | 每次请求前明确预算决策，保持局部恢复 |
| 7. 手动压缩 | 独立维护操作合理；as_node序列暴露内部节点语义 | 明确上下文替换提交/确认合同 |
| 8. 不完整会话恢复 | 不重放未知副作用正确；规划、图编辑、存储协调耦合 | 恢复判定、补齐计划、框架提交及确认各有归属 |
| 9. 重新生成 | 新分支和幂等/可见激活合理；准备链知道过多内部细节 | 准备分支、激活、执行分开表达 |
| 10. 子Agent | 唯一driver、独立thread、作用域取消必要；实例状态是大dict | 明确子生命周期和待审批状态合同 |
| 11. 准入/必要收尾/保存 | 所有者与结算保护合理；RunObservation混入正式运行结果 | 运行结果由执行拥有，观察接收已确定事实 |
| 12. 事件/观察/显示交付 | 故障隔离与快照恢复合理；必要门禁藏在观察命名模块 | 执行边界、可选观察、显示投影分别可识别 |

## 2. 基础循环与三个业务边界

当前主要执行顺序：

```text
应用准入/准备
  → 工具视图/初始压缩/控制初始化
  → 模型前置边界
  → 选模/请求装配与适配/模型调用/响应门禁
  → 响应后停止边界
  → 权限批次准备/Auto → HITL → 工具计划 → turn观察就绪
  → tools：批次放行 → 调用门禁/反馈 → 执行授权 → 工具主体
  → 图合入ToolMessage → 下一次模型前置边界
  → 无待执行工具时进入自然结束边界
  → 应用结算子工作/必要保存/释放
```

这是正常语义顺序；异常、中断、停止、结构化输出/return_direct等有各自分支。wrap并不都对应独立图节点。应始终分清`Command(update)`、`Command(resume)`和路由跳转。

### 2.1 模型调用前

| 输入/条件 | 应明确的动作 | 后继及提交要求 |
|---|---|---|
| 已接纳停止 | 禁止新模型调用，整理既有结果 | 终止/收尾，不能丢失已有失败/未知副作用 |
| Steering已接纳 | 选择并标注真实HumanMessage/回复归属 | 消息成为可信输入后调用模型 |
| 模型/思考/工具配置有新版本 | 按明确生效时点读取一致输入 | 本次调用内不混用多个版本 |
| 请求超过软预算 | 判断是否存在合法压缩方案 | 必要时摘要、预算复核，不能拆坏工具配对 |
| 请求合法 | 形成当前请求事实并调用 | 外部模型调用失败不伪造响应 |

### 2.2 工具副作用前

| 输入/条件 | 应明确的动作 | 后继及提交要求 |
|---|---|---|
| 模型响应截断/调用身份不匹配 | 阻断主体执行并形成匹配反馈 | 不能把不完整参数交给工具 |
| 批次等待或限流 | 等待符合顺序/并发条件 | 等待期间取消须唤醒其余等待者 |
| 需要审批 | 保存对应请求及身份，暂停 | 决定必须匹配原批次/参数；恢复前工作可重入 |
| 已获许可 | 执行前重新核对绑定/目标 | 审批展示通过不等于最终执行获准 |
| 已接纳停止 | 不启动尚未开始的工具 | 形成未执行结果，已开始工作另行结算 |
| 主体返回/异常 | 分清正常、软错误、机制失败、结果未知 | 配对结果后继续；必要失败交执行/会话拥有者 |

### 2.3 自然结束前

| 输入/条件 | 当前明确语义 | 后继及提交要求 |
|---|---|---|
| 停止 | 不再取待办 | 进入结算，保留/清理输入按合同 |
| Steering非空 | 当前实现优先取全部steering | 保持当前回复归属，再进模型前边界 |
| Follow-up非空 | 当前实现FIFO取一个 | 新回复身份，同一run可继续 |
| 都没有 | 在锁内关闭接纳窗口 | 后到输入明确被拒绝或经新run入口，不能悬空 |

转移表属于业务合同；`after_agent → jump_to=model`只是当前映射。最终图返回、必要保存完成、producer退出是不同确认时点。

## 3. 十二组场景详解

### 1. Steering、Follow-up及自然结束竞争

- **问题**：执行中用户补充消息；最终模型响应到达时还可能有新输入。选择时点还影响回复分组、重新生成边界和Auto对人类意图的识别。
- **当前路径**：`AgentSessionControls.steer/follow_up`在锁内入ActiveRun队列；`inject_before_model → drain_steering → prepare_control_messages`；`inject_at_natural_end → finish_run_boundary`选择steering/follow-up或关闭窗口，再返回messages/jump_to。
- **状态**：ActiveRun队列/steering_open、HumanMessage身份与输入kind、run.reply_id、图active_reply_id。Steering附着当前回复，Follow-up产生新回复身份。
- **失败/竞争**：停止不继续取输入；故障收尾清理队列；自然结束与入队共用锁避免已接纳输入落空。队列在内存，不因此具有重启后可靠投递保证。
- **判断**：当前选择规则与锁边界值得保留。欠清晰处是接受、选择、身份标注、图提交及事件确认分布多处；after_agent名称也容易让人误判已经结束。
- **目标**：集中定义输入接纳/选择/关闭及归属规则，由应用拥有队列，runtime边界将选定输入提交给图。若要升级为跨重启可靠输入，须另定持久接纳/确认语义，不能只换队列类型。
- **保护**：新设计须保留steering优先、follow-up FIFO、可信人类标记、回复归属和窗口竞争断言。
- **测试入口**：`tests/test_application_follow_up.py::test_natural_end_closes_follow_up_before_busy_gate_is_released`。
- **逐场景讨论**：[插话设计](场景01-插话与自然结束.md)核对Pi与DeepSeek Harness实际类/调用及持久Inbox；当前建议保留内存队列，不因参考项目而新增跨重启保证。按场景/承诺/质量目标/代价决策；持久接纳与对账分析保留为未采纳方案，非实施要求。

### 2. 用户停止、外部取消与应用退出

- **问题**：停止可能落在摘要、模型等待、Auto、审批、工具排队或正在写文件等不同阶段。
- **当前路径**：`request_scope_stop → RunControl.mark_requested/request`；`await_model`取消受拥有的模型等待；`StopModelMiddleware`把UserStop变为图停止更新；`finish_stopped_batch`补未执行结果；审批/dispatch边界重复检查；`await_settled`保护已开始工作与必要清理。
- **状态**：ActiveRun.stop_requested、RunControl.signal/reason、图run_stopped、应用结果和manual_review_required各表达不同事实。
- **失败/竞争**：外部CancelledError不是用户停止；已开始线程不能靠取消Future终止；未知副作用与主失败不能被停止状态掩盖；根停止要结算子工作。
- **判断**：多个时点检查和settle是必要保护。需要统一解释“接纳停止→禁止新操作→结算→终止确认”，而不是删除重复检查或把所有检查放在一个hook。
- **目标**：运行拥有者持有权威终止意图与结果，执行边界只实施相应动作；图停止字段是提交结果之一。明确跨对象一致性和取消优先级，不机械合并所有状态维度。
- **保护**：未开始工具不执行、已开始工具结算、原异常身份、未知结果阻断、busy释放时点。
- **测试入口**：`tests/test_active_stop.py::test_stop_drains_started_tool_but_skips_waiting_tool`。
- **通俗走读与时点**：[停止设计](场景02-停止与取消.md)以已开始工具A和排队工具B说明接纳、跳过、结算、图返回、保存/释放；明确control_applied早于应用必要收尾、tool_call_started可早于主体执行。本轮只读源码和既有测试，没有运行测试。

### 3. 权限、Auto审查与HITL审批

- **问题**：模型提出工具调用后，可信策略准备目标；部分调用可执行，部分需要额外判断或人类决定。
- **当前路径**：`PermissionMiddleware.prepare_local_batch/aafter_model`保存参数/目标/策略结果；Auto按fast/detailed审查；`BatchApprovalMiddleware → ObservedHumanInTheLoopMiddleware`中断；根恢复用新run及Command(resume)，子恢复用其driver；`ExecutionAuthorizationMiddleware._authorize`消费匹配的一次许可，工具再校验目标。
- **状态**：checkpoint的tool_execution批次、待审批身份/参数、应用待审批记录、一次许可和会话允许规则；恢复不重新把所有ask按新模式审查。
- **失败/竞争**：Auto不可用回ask；控制信号不降为ask；审批陈旧/不匹配拒绝；拒绝成为工具反馈；目标变更不能复用旧授权。
- **判断**：准备、审批、最终授权三步分开合理，不能为减少层数合并。Auto内部`_review_steps → areview.next/send/throw`只有一个生产驱动器，额外间接不利于阅读。
- **目标**：保留审批快照及一次授权合同；Auto改为可直接阅读的异步两阶段流程，纯输入预算与响应校验保留独立函数。审查器给候选决定，最终许可由确定性机制确认。
- **保护**：不再审已保存ask、next-batch配置生效、原参数绑定、禁止跨会话/子实例消费许可。
- **测试入口**：`tests/test_auto_permission_pipeline.py::test_two_asks_pause_entire_batch_and_resume_does_not_review_again`；`tests/test_auto_permission_review.py::test_review_stage_contract_and_no_shared_model_mutation`。
- **通俗走读与时点**：[权限与审批设计](场景03-权限与审批.md)以外部Read串起批次准备、HITL中断、新run恢复同thread/turn、一次许可和执行前复核；对照Pi有返回值的工具hook与DSH审批请求/持久审计。当前仅建议保留合同，Auto生成器简化仍待讨论，未实施。

### 4. 工具批次并发、串行与失败传播

- **问题**：同轮多个调用有顺序/并发要求；一些错误供模型处理，一些机制故障必须终止。
- **当前路径**：`ToolBatchMiddleware.aafter_model`按待执行ID建AsyncBatchPlan；tool wrapper经execute等待condition/semaphore；ToolErrorMiddleware调用tool_error_feedback；执行授权后进入主体。
- **状态**：图中的tool_execution批次与运行context内临时计划分开；position/failed/condition不属于可直接持久化的事实。
- **关键纠正**：当前普通RuntimeError可转成error ToolMessage，后续工具继续。只有异常穿透工具反馈边界或取消等到达AsyncBatchPlan，才置failed，阻止尚未开始调用；不能泛称“一个工具失败就停全批”。
- **判断**：批次隔离、执行ID配对和并发门闩合理。单个failed标记把取消、权限机制失效、执行系统故障归为同一种后续策略，语义偏粗；是否允许继续属于待确认产品策略。
- **目标**：调度只处理可运行时点；失败分类明确指出软反馈、阻断当前调用、终止批次、终止run、结果未知等后果。先明确规则，不增加一个无真实需求的通用策略注册平台。
- **保护**：顺序、已完成结果保留、等待取消唤醒、普通软错误继续、未执行结果、重复执行拒绝。
- **测试入口**：`tests/test_tool_batch_scheduling.py::test_ordinary_failure_allows_later_tool_body_in_sequential_batch`。
- **通俗走读与时点**：[工具批次与失败传播](场景04-工具批次与失败传播.md)以A/B/C说明临时计划、位置/名额门禁、普通RuntimeError转结果后继续；对照Pi整批串行及DSH屏障/组结算。混合批屏障和机制故障影响范围待讨论，并行机制失败的整组结算是待核验边界，未复现为缺陷，未实施产品修改。

### 5. 模型/工具/提示词/权限配置在运行中变化

- **问题**：配置可以更新，但模型看见的工具定义、预算估算、审批目标与实际执行必须对应同一个请求/批次。
- **当前路径**：ToolSetMiddleware在before_agent准备首视图，before_model刷新后续视图；select_model wrapper解析模型；项目指令/Skills按run准备；权限按批次读取并保存；预算与输入适配另有调用。
- **状态**：SessionState配置、ActiveRun资源、context工具对象快照、tool_execution中的工具名/批次、模型请求副本各有时效。
- **失败/竞争**：运行中更换模型/工具/权限是当前可达行为，不能假定整个run配置不变。权限测试已确认审查期间换模式影响下个批次，当前批次保留快照。
- **判断**：冻结定义与后续刷新均必要；不足是同一请求事实由多个位置解析，初始压缩与实际模型调用读取模型的时点也不同。
- **目标**：明确run、请求、工具批次三个版本边界；对某次请求，模型/工具schema/提示词/预算来自一致准备结果，再供请求适配、观察与授权关联使用。不是要求所有配置整个run冻结，也不是立刻新建多套快照类。
- **保护**：当前批次不被热切换改写；新批次按约定读新设置；子角色固定配置与根动态选择的区别保留。
- **测试入口**：`tests/test_auto_permission_pipeline.py::test_mode_switched_during_review_applies_to_next_batch`。

### 6. 主动压缩与模型输入溢出恢复

- **问题**：上下文超过预算时需要安全压缩；供应商真实拒绝后还需局部恢复。
- **当前主动路径**：`compact_before_new_run.abefore_agent → _acompact_messages → _compaction_steps → arun_summary_steps → summary model`；检查切点、摘要有效性、压缩后预算，再返回RemoveMessage/summary/preserved更新。
- **当前溢出路径**：`recover_input_overflow.awrap_model_call`识别输入溢出→强制压缩→只重试当前handler一次→响应接受后ExtendedModelResponse/Command提交替换历史及响应。不是重跑此前工具。
- **失败**：某些临时/空/截断摘要且原请求仍安全时可回退；强制恢复不能回退已拒绝输入；重试失败不能把摘要当成功提交。
- **判断**：安全切点、局部重试和成功后提交是强项。主动压缩只挂在run开始；同run多轮工具/steering增长不等于每次都做主动压缩，后续有观测和溢出兜底。这是触发策略限制，不直接证明请求必定失败。
- **目标**：在实际每次模型请求前定义预算决策，不等于每次都摘要；与第5组请求事实一致。保留供应商拒绝后的单次局部恢复。当前摘要生成器只有arun_summary_steps一个生产驱动器，可改为直接async流程，纯切点/预算算法保持可测试。
- **保护**：原历史不被失败摘要破坏、配对不拆坏、既有工具不重放、响应门禁仍适用、原异常/失败阶段可见。
- **测试入口**：`tests/test_context_overflow_recovery.py::test_tools_before_overflow_are_not_replayed_and_checkpoint_continues`。

- **完整走读**：[自动压缩与溢出恢复](场景06-自动压缩与溢出恢复.md)。

### 7. 手动压缩

- **问题**：用户明确要求压缩，目标是维护模型上下文，不是生成一次普通助手回答，也不删除聊天归档。
- **当前路径**：SessionService.acompact准入→SessionExecution.arun(compact=True)→compact_checkpoint；仅允许安全完成checkpoint；摘要后aupdate_state(as_node=model)再END；重读验证；进入共用必要收尾。
- **状态**：执行配额/busy、源checkpoint、上下文替换、摘要事件、聊天归档和操作结果；它复用run寿命，不实际运行正常模型—工具图。
- **失败**：摘要失败与提交不确定分开；ManualCompactionCommitError触发核对/阻断；已开始写入需settle。
- **判断**：独立维护操作及共用准入合理。`arun(compact=True)`的任务类型分支与内部节点模拟降低语义清晰度；只看arun不容易知道可能完全不跑图。
- **目标**：应用显式发起上下文维护操作，复用运行所有者/收尾保护；由图状态维护适配完成基于源版本的替换与确认。摘要生成和提交是两阶段，不能为统一接口掩盖。
- **保护**：审批中禁止压缩、源状态一致、失败不误报成功、展示历史保留。
- **测试入口**：`tests/test_manual_compaction.py::test_replacement_failure_is_not_reported_as_summary_failure`。

- **完整走读**：[手动压缩](场景07-手动压缩.md)。

### 8. 不完整会话恢复

- **问题**：进程退出/取消/故障后，图、应用元数据与工具副作用可能处于不同确认阶段。
- **当前路径**：SessionPersistence.arecover/_recover_checkpoint→校验checkpoint与恢复分类；restore_approval分支重新验证并安装待审批；continue分支记录recovery_id/源checkpoint，按cleared/paired/finished执行END/tools/END更新，补结果，再确认可用并保存。
- **状态**：原始checkpoint保留；恢复记录、工具配对、清理执行状态、新checkpoint、数据库会话状态。
- **失败**：重读身份/阶段不匹配拒绝；任一步失败不可标ready；重复恢复按已保存阶段继续；未知已生效操作不能自动重放。
- **判断**：分阶段可重入、保护原历史是必要设计。一个持久化协调类同时做恢复分类、执行计划、内部图编辑和会话安装，职责偏重。
- **目标**：分类得出可检查恢复计划，图适配按阶段应用并确认，存储协调只发布已确认结果。restore approval和修复未知结果保留不同规则，不强行共用一套恢复策略。
- **保护**：源checkpoint不变、无重复副作用、陈旧版本拒绝、失败不开放准入。
- **测试入口**：`tests/test_session_recovery.py::test_three_updates_preserve_results_then_only_new_input_calls_model`。

- **完整走读**：[不完整会话与重启恢复](场景08-不完整会话与重启恢复.md)。

### 9. 最后一轮重新生成

- **问题**：替换最后一个任务的可见结果，同时保留前缀；再次执行可能再次产生工具副作用。
- **当前路径**：session_regeneration.regenerate检查request_id/回复/会话revision→正常准入→取源checkpoint和真实输入→记录preparing动作→新thread用START/END构造前缀与新输入→事务activate切换可见分支→session.arun运行→必要收尾。
- **状态**：原/新thread、reply边界、conversation_revision、动作幂等记录、输入新身份与可见归档。
- **失败**：准备或激活失败不能改变原可见分支；激活前后取消必须分清；重试同request_id不能重复启动执行。
- **判断**：分支准备与可见激活的两阶段方向合理，不能改为直接截断原messages重跑。当前一个函数跨读库、图编辑、动作账本、可见激活和run寿命，内部协议知识过多。
- **目标**：明确“准备候选分支→确认并激活→正常执行”的状态合同；应用拥有可见性与幂等，图适配拥有候选checkpoint构造，存储拥有激活事务。保留独立于第8组恢复的语义。
- **保护**：文件不随重新生成回滚，副作用不会因新thread自动变得幂等；准备残留和可见成功必须区分。
- **测试入口**：`tests/test_last_regeneration.py::test_replace_only_last_task_preserve_prefix_reopen_and_deduplicate`。
- **完整走读**：[场景9重新生成](场景09-重新生成.md)：末尾reply边界、三项请求身份、四次候选写入、先激活后执行、文件副作用与失败/取消合同；本轮只读测试，无产品修改。

### 10. 子Agent执行、独立审批与父运行结算

- **问题**：根工具委派子任务；一个子等待审批时，其他子可能仍运行，父调用不能提前返回最终结果。
- **当前路径**：prepare_subagent_instance核对父许可并建立独立thread→ainvoke_subagent创建唯一driver→_subagent_steps循环创建子执行段→图中断后登记live审批并等future→按interrupt ID恢复同一子图→最终报告投回父ToolMessage。
- **状态**：子身份/父调用关联、独立thread、每执行段run_id、status/phase/settled、driver、pending.future、子RunControl、父拥有关系。
- **关键区别**：根审批通常结束根执行段，后续新run恢复；live子审批由原driver在父run内等待并继续，不等于重新启动父run。
- **失败**：根取消/关闭须通知并等待子driver；不能同一实例双驱动；当前进程重启不自动复活旧driver/审批future，恢复不自动重放子任务。
- **需明确的策略**：部分子模型/调用上限/checkpoint故障被转换为父工具反馈；反馈不是副作用回滚。当前错误文本提示不要自动重试，并不等于系统禁止以新的父调用重新委派同一任务。是否进一步阻断需按失败确定性讨论，不能机械禁用所有后续任务。
- **判断**：独立driver与作用域所有权是必要复杂度。实例以大dict同时保存稳定身份、临时task/future及多种状态，合法组合与转移不够直观。
- **目标**：明确子生命周期、暂停恢复与结算的状态合同，使稳定事实、暂态资源和转移校验可辨识；保持唯一driver，不能照搬根运行的“审批结束run”而破坏并行体验。
- **保护**：父许可只消费一次、子审批不串用、其余子可继续、父收尾等待所有被拥有工作。
- **测试入口**：`tests/test_subagent_approval_resume.py::test_a_approved_and_finished_while_b_still_runs_whole_child_batch_waits`。
- **完整走读**：[场景10子Agent生命周期](场景10-子智能体生命周期.md)：独立thread与同一driver的多执行段、审批身份/一次许可、单子/根停止、分段终局与完整结算、子控制观察与根的差异；现有测试只读，未实施改造。

### 11. 准入、运行结果、必要保存与busy释放

- **问题**：图返回/抛错后仍有子工作、控制窗口、聊天归档、checkpoint确认和资源清理。
- **当前路径**：SessionService._admit→AgentSession.admit_run→SessionExecution.arun/aresume_tool_approval→result/_on_failure→await_settled(_afinish_run)→结算子driver/关闭窗口→SessionPersistence.afinish→release_run→终局通知。AsyncApplication和Web另有自己的producer寿命。
- **状态**：准入名额、ActiveRun、运行状态/失败/阶段、manual_review、checkpoint及会话持久状态。
- **失败**：主异常优先，清理/保存次要故障另记；无主异常的必要保存失败向外抛；无法确认保存时阻断。
- **新发现**：RunObservation并非纯可选观察器，它保存status/stage/failure，并拥有RunControl；SessionPersistence.afinish读取observation.status决定ready/interrupted/failed。不能删除事件订阅后顺便删掉这个对象。
- **判断**：收尾顺序与异常优先级保护合理；正式运行结果依附观察对象，是职责混合，值得优先整理。
- **目标**：运行拥有者确认结果与可用性，必要保存读取该结果；观察对象消费结果并发布事件。根/子可共享必要结果合同，但不强制共用所有生命周期流程，也不新建无调用价值的通用状态框架。
- **保护**：图结束不提前释放busy、子工作未结算不释放、保存失败可见、主异常身份不变。
- **测试入口**：`tests/test_application_run_events.py::test_success_events_follow_cleanup_without_changing_result`。
- **完整走读**：[场景11准入、必要收尾与保存](场景11-运行准入收尾与保存.md)：准入安装/开始事件/持久running的区别、控制窗口与busy、图checkpoint/归档事务、保存失败阻断、原异常优先、保存中取消和根终局；本轮测试只读，未改产品。

### 12. 响应门禁、观察、流式适配与Web交付

- **问题**：正文/思考分片需要提前显示，完整消息需校准，断线要重取快照；同时模型响应和工具调用必须通过必要校验。
- **当前路径**：ainvoke_with_message_observation驱动astream并收集最终values/interrupt，再调用可选消息/turn/控制观察；RunEventPublisher分发→DeliveredRun投影/有界缓存→subscribeRun重连→applyEvent更新显示。读baseline失败可在执行开始前降级为ainvoke，不能误说成执行了两次。
- **新发现**：call_observation._ModelSelectionMiddleware承担选模、活动停止等待、响应接受门禁及事件；tool_execution.observation._prepare_tool_call/tool_guard_reason阻断截断/不匹配调用，_ToolCallObservationMiddleware会改变是否执行主体。它们不全是可选观察。
- **状态**：可信执行结果/已提交完整消息，与草稿、哈希、观察turn、sequence/显示投影不同；pending_turn为观察恢复数据，不能视为框架审批恢复凭证。
- **判断**：分片/完整校准、断线不取消producer、有界快照恢复均合理。必要执行与观察命名混合、纯turn观察节点进入图、全历史hash和重复快照/额外context查询增加复杂度。
- **目标**：执行适配拥有最终结果/interrupt，必要模型/工具门禁明确归执行边界；可选观察读取相应事实。显示投影独立；内外协议是否拆分按实际消费决定，不直接丢掉共用sequence中的帧。
- **保护**：关闭/故障订阅不改变执行；必要门禁仍生效；丢帧重同步不重发执行POST；预览不能冒充已保存消息。
- **测试入口**：`tests/test_application_run_events.py::test_observer_failures_do_not_change_success_or_primary_error`；`tests/test_async_tool_batch.py::test_truncated_calls_are_error_results_without_execution`。
- **完整走读**：[场景12事件、观察、前端投影与交付](场景12-事件观察投影与交付.md)：astream驱动与观察边界、分片/完整消息、真实run登记、同步发布/有界缓存、SSE与快照重连、归档校准和失败草稿；本轮测试只读。12组本轮讲解收束后回原第七章，不自动批准设计改造。

## 4. 优先优化的设计问题

以下为设计优先级，不是线上故障严重度，也不是已批准实施顺序。

1. **正式结果与可选观察分开**：先明确RunObservation中的必要结果/控制所有权；再分清model/tool observation模块中的门禁。否则“观察故障可忽略”可能被错误推广到必要逻辑。
2. **控制转移集中表达**：按第2节三个边界写清优先级、输入归属与关闭合同；保留实际安全检查点，减少同一规则的多份解释。
3. **请求事实一致与预算触发**：模型/工具/提示词/预算按请求边界一致准备；区分软阈值、发送上界、供应商溢出，明确同run增长策略。
4. **移除无额外消费者的局部驱动间接**：Auto审查、摘要各只有一个异步生产驱动，可将yield/send/throw流程改成直接async；保留纯算法和原有失败/取消语义。
5. **维护操作以业务语义呈现**：压缩替换、恢复修复、候选分支激活分开；共用同一种checkpoint IO/确认机制，但不因都调用aupdate_state就共用完整策略。
6. **子生命周期可检查**：明确稳定事实与driver/future等暂态资源；让status/phase/settled的合法转移显式，避免依赖散落dict赋值推导。
7. **观察纯度和重复开销**：turn观察节点、低消费事件、重复上下文读取、消息全量hash分别核验；不能为删事件破坏游标/重同步或准确阶段合同。

## 5. 目标架构怎样更清晰

```text
用户命令 → 应用会话拥有者（准入、输入/审批、终止意图、运行结果）
                    │
                    ├→ 图执行适配 → 三个控制边界 → 模型/工具循环
                    │                   └→ 合法状态更新/路由
                    ├→ 状态维护操作 → checkpoint适配/阶段确认
                    │   （手动压缩、恢复修复、候选分支）
                    └→ 运行结算 → 子工作完成 → 必要保存 → 释放

上述已确认事实 → 可选观察 → Web/CLI投影、用量、诊断
```

这些是职责，不要求分别创建新服务或新类。可以沿现有AgentSession/SessionExecution、runtime模块、SessionPersistence及投影收敛；也不把所有规则塞进一个SessionManager。

框架装配仍是当前create_agent路线。理想验收是业务转移可直接追踪、公开适配有清楚合同；如果完整转移表证明关键恢复/控制语义长期只能靠难以确认的节点模拟表达，再有证据讨论图拓扑调整，不能仅用节点数或框架名称决定。

参考：Pi73f8de80将prepareNextTurn/工具terminate/finishTurn/队列选择放在显式循环位置；AgentX3fcfa0e通过transitionTo→事件总线→handler推进workflow。二者说明控制规则需要承载位置，不能证明某一种写法天然更优。本项目事件消费者不应因此取得第二份图调度权。

## 6. 一次设计验收要能回答什么

- 新输入在任意接纳/结束竞争点到达，属于哪个任务、是否确认交付、失败后是否重放？
- 停止、审批与工具启动并发时，哪些操作允许开始、哪些需等待、未知结果如何阻断？
- 模型返回但项目门禁拒绝时，是否仍有错误的工具执行或成功事件？
- 摘要、Auto、子Agent和主模型分别属于谁的调用/预算/用量，失败会影响哪个层级？
- 手动维护或新分支准备中途退出，哪份状态仍可用，哪份只是候选，下一次如何确认？
- 没有Web/CLI/诊断订阅时，必要提交与运行结果是否完整？反过来必要提交失败是否显式失败？
- 根/子审批与取消各由谁驱动，进程重启后明确支持什么，不自动恢复什么？
- 一份关键规则改变时，能否只改它的所有者与适配/测试，避免跨多个模块重新解释同一事实？
