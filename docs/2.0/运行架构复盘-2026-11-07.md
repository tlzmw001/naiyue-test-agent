# 运行架构复盘：从一次请求到必要保存完成

日期：2026-11-07。基线：`frontend-ui-refactor`，HEAD `4629067` 加当前未提交工作。本文核对工作区源码，不把 HEAD 当作全部被读内容。状态：复盘与设计讨论，未授权产品重构。

本机 Python 3.12.14、LangChain 1.4.2、LangGraph 1.2.12。本文替代旧[调用链复盘](当前架构与调用链复盘.md)作为本次运行架构讨论入口；旧文保留其历史版本。具体改法见[三项重构候选方案](运行架构重构候选方案-2026-11-07.md)。

## 1. 先读懂这四件事

1. 谁拥有一份状态，谁有权修改，谁负责关闭资源？
2. 一次模型调用、一个图执行片段、一次根运行和一个长期会话何时结束？
3. 用户看到结果、图状态已保存、产品记录已提交，是哪些不同事实？
4. 失败、取消和观察丢失之后，还能相信什么，谁决定下一步？

范围集中在本机主会话的准入、执行与收尾，并核对共享实现的子 Agent、记忆任务和云 Runner。云端 Coordinator 的任务代际、SSH、更新器、附件传输及前端交互不在本次完整审查范围。本文不是全项目安全或性能审计。

结论：保留 Python + `create_agent` 路线，保留会话/运行分离、显式协作者、必要保存与取消收束。优先讨论运行结果的所有权，再讨论持久化协调职责；事件整体队列化暂不推荐。

### 对上一轮口头判断的更正

- `SessionPersistence` 已经位于应用层，SQL 已下沉到仓储/UOW；它主要是跨图状态、产品存储和存活会话的一致性协调者，不能按名称当成普通数据库封装。
- 当前同步发布器的用量、诊断和 Runner 消费者已经采用有界缓冲及后台写入。同步调用 handler 不等于同步完成全部数据库或网络 IO。
- 根 `run_finished` 在必要收尾尝试之后发布；子 Agent 每个执行片段的 `run_finished` 可早于外层子实例的 MCP 释放和持久结算。子实例 settled 是另一个完成边界。
- 必要保存期间取消外层等待，可能在保存成功后向调用者抛 `CancelledError`，同时根终局仍为 `completed`、数据库为 `ready`。不能统一把所有取消转换为业务失败。

## 2. 从产品承诺推导结构

| 产品承诺 | 必须存在的机制 | 当前承担者 |
|---|---|---|
| 同一会话不能同时推进冲突的根运行 | 检查与登记原子完成；旧运行不能清理新运行 | `SessionService._admit`、`SessionRuntime.require_run` |
| 关闭网页不等于停止已受理任务 | 执行任务与连接拥有不同生命周期 | `RunDelivery._launch/_produce` |
| 停止后不能提前关闭仍被使用的资源 | 停止意图、任务收束、释放分开 | `RunControl`、`RunLifecycle`、`await_settled` |
| 审批只能应用于原调用和原身份 | 保存审批对象；恢复与执行重新核对 | `ApprovalBook`、执行授权 middleware |
| 会话可以跨轮继续 | 持久会话身份、图 thread 和单次 run 分开 | `SessionState`、checkpointer、`ActiveRun` |
| 保存失败后不能假装安全可继续 | 必要保存确认及受限状态 | `SessionPersistence`、`RunUnitOfWork` |
| 显示或统计失败可诊断，不随意覆盖执行结果 | 观察故障隔离及不完整标记 | publisher、usage、diagnostics、Web 投影 |

设计顺序是：场景 → 必须保持的条件 → 状态归属 → 生命周期 → 失败合同 → 接口和类 → 锁、事务与执行方式。第一版仍可很小，但这些问题应及早明确。

## 3. 当前对象怎样组成

下面是所有权及装配关系；箭头不表示每次请求都调用全部对象。

```text
Application / ApplicationLifetime
  ├─ 模型资源、个人记忆、项目登记、跨项目准入
  └─ HostManager → ProjectHost
       ├─ 图、存储、MCP、用量/诊断及资源关闭栈
       ├─ SessionAPI / RunAPI / HistoryAPI / MemoryAPI 等入口
       └─ SessionService → AgentSession
            ├─ SessionRuntime：唯一 state/run/短锁句柄
            │    ├─ SessionState：跨轮事实
            │    └─ ActiveRun | None：当前根运行
            ├─ ControlQueue：控制输入与停止
            ├─ ApprovalBook：根/子审批
            ├─ SubagentRegistry：子实例和 driver
            └─ RunLifecycle：执行及必要收尾

Web RunDelivery → DeliveredRun：另持展示投影、事件窗口与生产 task
```

装配入口见 [service_application.py](../../naiyue_test_agent/application/service_application.py):65、[host_assembly.py](../../naiyue_test_agent/application/projects/host_assembly.py):21、[sessions/assembly.py](../../naiyue_test_agent/application/sessions/assembly.py):5。运行时借用这些资源；借用者不能自行关闭共享模型或数据库。

| 对象 | 状态与修改责任 | 生命周期及约束 |
|---|---|---|
| `SessionService` | 会话注册、共享角色定义、准入协调 | 宿主级；根图按宿主装配，运行时传入身份 |
| `AgentSession` | 会话配置、只读快照；创建四个显式协作者 | 已加载会话；没有旧会话 mixin 继承树 |
| `SessionState` | model/thread/tools/permission、pending、revision 等长期事实 | 存储显式映射；不保存一份重复的完整 messages |
| `SessionRuntime` | 当前 `run` 槽位、会话事实引用、共同短锁 | 进程内句柄；协作者共享同一实例 |
| `ActiveRun` | 本次身份、控制窗口、队列、子实例、执行能力、observation | 准入到允许释放；必要保存期间仍占用 |
| `RunObservation` | 当前同时持有 status/failure/stage，并发布观察 | 根运行、子片段、记忆任务分别创建；这是建议一要澄清的交叠 |
| 编译图 / checkpointer | 模型—工具循环、图消息和执行状态 | 图对象与 thread 状态分开；图复用不代表历史共享 |
| `SessionPersistence` | 活动/恢复/阻断记录、每会话 history 门闩、持久事实协调 | 宿主级；不是单纯仓储 |
| `ProjectStore` / `RunUnitOfWork` | 明确存取方法、产品必要事务 | 单一存储所有者负责关闭 |
| `DeliveredRun` | Web 消息/工具投影、回放窗口、展示终局 | 派生视图；不决定工具执行许可或会话恢复资格 |

关键定义见 [session_state.py](../../naiyue_test_agent/application/sessions/session_state.py):19、[agent_session.py](../../naiyue_test_agent/application/sessions/agent_session.py):14、[run_events.py](../../naiyue_test_agent/application/observability/run_events.py):107。

同一数据可有多个读者，但应明确写入职责。当前协作者共享 `SessionRuntime`，锁与身份检查保证部分约束；字段修改责任仍需靠方法合同阅读，不能把“拆成四个类”视为已经完成全部封装。

场景：用户发送“读取项目并给出结论”；模型请求一个工具，工具结果回填，再生成回答。下列是调用链说明，未请求真实供应商。

## 5. 状态变化：busy、保存状态和返回结果分开看

以下是当前状态的解释表，不是建议新建一个通用状态机框架。

| 时点 | 运行占用 | 产品持久事实 / 下一步 |
|---|---|---|
| 准入前 | `runtime.run is None` | 仍须检查 pending、blocked、执行目录和容量；空闲不自动可运行 |
| 准入、执行 | 有 `ActiveRun` | 持久 start 标记 running；模型和工具推进图状态 |
| 图返回 | 仍有 `ActiveRun` | 只代表本次图结果可读取，必要收尾尚未完成 |
| 收束子任务、关闭控制窗口 | 仍可能 busy，controls 已关闭 | 不能继续投递控制，也不能因此提前关闭依赖 |
| 必要保存成功 | 按条件释放 `ActiveRun` | 普通完成可 ready；根审批挂起则 interrupted，等待显式决定 |
| 必要保存未确认 | 若子任务已收束可释放运行槽位 | `_blocked` 仍阻止继续；不能仅凭 busy=false 认定恢复安全 |
| 子执行片段结束 | 子实例仍可能存在 | 片段终局不等于实例 settled；根收尾负责等待实例收束 |

`session_id`、`thread_id`、`run_id`、子实例身份、工具调用 ID 各有用途。审批恢复可能创建新 run；重新生成可能切换 thread 并递增 revision。不要用一个 ID 代替所有生命周期。

## 6. 失败与取消的具体合同

| 场景 | 当前处理 | 不能做的简化 |
|---|---|---|
| 模型/工具机制抛异常 | 保留主异常，执行必要收尾；次要故障记录诊断 | 用保存或显示异常覆盖原故障 |
| 没有主异常，必要保存失败 | 抛 `SessionPersistenceError`，标记保存未确认并阻断 | 返回生成过的回答就当成功 |
| 主异常与保存失败同时出现 | 原异常对象继续传播，保存故障作为次要诊断 | 统一包装导致异常身份与根因丢失 |
| 必要保存期间外层 task 被取消 | 排空已开始保存；成功可发布 completed/保存 ready，调用者仍收到取消 | `CancelledError` 一律映射 stopped/failed |
| 子 Agent 等待审批时关闭应用 | 停止并收束子 driver/future，完成必要保存后关闭资源 | 根 task 结束就关闭模型/数据库 |
| 根审批挂起并重启 | 恢复待审批事实，显式恢复/决定后继续 | 重启自动重复已完成工具或自动批准 |
| 普通 observer 抛 Exception | 隔离该 run 的失败 handler、诊断；其他观察仍可继续 | 把普通观察当作必要提交 |
| 控制异常或图控制信号 | 按原类型传播与终局抑制合同处理 | 大范围 catch 后转成普通工具错误 |

现有确定性证据入口：[test_session_lifecycle_integration.py](../../tests/test_session_lifecycle_integration.py):36 的参数化用例同时覆盖 success/save_failure/primary_error/cancel/close。它用事件同步阻塞真实保存入口，检查 busy、控制窗口、子实例清空、终局顺序与异常身份；模型和工具是固定测试对象，不是供应商请求。

“保留主异常”在此指上述受控故障组合；不能推广成 finally 内任何 BaseException、运行身份断言或释放失败都绝不会覆盖原异常。普通 failed、执行取消、进程/图控制信号当前还有不同分类与终局合同，重构时逐支保持。

## 7. 持久化与观察的边界

```text
图执行 → 官方 checkpointer 保存图状态
        → 应用读取并核对安全结束状态
        → RunUnitOfWork 事务提交归档/回复/会话等必要事实
        → 根运行释放及终局

观察事件 → Web 投影 / 有界用量队列 / 有界诊断队列 / Runner 观察队列
                     → 各自交付或后台写入
```

当前图 saver 和产品存储可使用同一 SQLite 文件的不同连接。普通运行收尾先确认 checkpoint，再提交产品事务；不是一个横跨图执行与所有业务写入的大事务。删除路径等特殊操作须按自己的 UOW 核对，不能把普通收尾结论推广到所有操作。见 [storage/resources.py](../../naiyue_test_agent/storage/resources.py):44、[SessionPersistence.afinish](../../naiyue_test_agent/application/sessions/session_persistence.py):212、[RunUnitOfWork](../../naiyue_test_agent/storage/unit_of_work.py):24。

云 Runner 也复用会话装配与 UOW，存在必要的 history journal。实时事件交付和必要历史提交必须分别核对；不能因为都与“事件/历史”有关，就把它们一起移入允许丢失的观察队列。

## 8. 锁和异步怎样由这些合同推出来

| 机制 | 当前保护对象 | 执行边界 |
|---|---|---|
| `SessionRuntime.lock` | run 身份、控制队列和配对的内存变化 | 短同步临界区；模型与数据库等待在外部 |
| 每会话 `history_lock` | 保存/恢复/删除等互斥流程 | 异步门闩可跨 await；不串行所有会话 |
| DB 连接锁与事务 | 同一连接及产品原子写入 | 同步工作移到受控 worker；保持事务边界 |
| `RunControl` 的锁 | 停止意图及模型 task 集合 | 锁外通知事件循环取消 |
| 文件目标预留 | 某目标正在执行的事实 | 预留跨 IO 存在，但不意味着 mutex 一直持有 |
| publisher 锁 | 同一根流序号、重入 FIFO、同步交付 | 当前仍在锁内执行 handler；慢 handler 可影响生产者 |

完整获取顺序以[锁层级表](../lock-hierarchy.md)及真实代码共同核验；发现历史消费者残留时先追调用方。未来任何锁嵌套变更要同步表格与确定性并发回归。

纯校验和状态计算保持同步；模型/网络使用异步；已有同步 IO 通过 `run_blocking` 执行。`await_settled` 等待已经开始的工作收束，代价是取消可能要等 IO 完成。异步、并发、流式和 checkpoint 的 `durability='sync'` 是不同维度。
