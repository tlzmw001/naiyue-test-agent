# 场景3：权限判断、Auto审查与人工审批

日期：2026-10-20。阶段：源码走读与方案讨论，未实施产品修改。沿用当前工作树及LangChain 1.4.2、LangGraph 1.2.12；参考Pi 73f8de80、DeepSeek Harness 687f282e。下文示意路径、消息和身份均为教学值，不是真实模型或文件访问记录。

## 1. 本场景要解决什么

用户让Agent读取工作区外的普通文件。模型可以提出调用，系统需要独立回答：当前规则允许吗；如果需要人类决定，在哪里暂停；批准后怎样确保执行的仍是原来那次操作。

三个职责：

1. 权限准备：校验参数、解析目标、匹配规则，形成该批次的决定快照。
2. 审批暂停与恢复：保存待确认调用，以人类决定恢复图。
3. 执行复核：把一次许可绑定到具体调用，并在工具接触目标前重新检查。

事件报告这些阶段发生的事实。图中断/Command恢复和执行许可分别承担暂停、恢复与授权。

## 2. 具体数据

工作区为`/work/project`；用户请求读取`/shared/test-data.md`。模型返回：

```python
AIMessage(
    id='ai-1', content='',
    tool_calls=[{'id': 'call-1', 'name': 'read',
                 'args': {'path': '/shared/test-data.md'}}],
)
```

无显式允许/拒绝规则、无会话允许记录，Default模式下该外部普通文件得到ask。

权限批次的简化形状如下；实际subject还包括解析路径、目录身份锚点、运行环境等字段：

```python
tool_execution = {
    'batch_id': 'ai-1', 'mode': 'Default', 'session_allow': [],
    'calls': [{
        'id': 'call-1', 'name': 'read',
        'args': {'path': '/shared/test-data.md'},
        'validation': 'valid', 'decision': 'ask', 'source': 'default',
        'subject': {'operation': 'read', 'requested': '/shared/test-data.md',
                    'resolved': '/shared/test-data.md', 'workspace': '/work/project'},
    }],
}
```

`subject`是可信代码解析的目标信息。审批页面展示值和实际执行必须能追到同一份准备结果。

## 3. 先看完整分支

`prepare_permission_call`先校验参数/准备目标，然后依次匹配配置deny、配置allow、会话允许、工具默认决定。前面的规则匹配后不继续落入后面的默认规则。

| 准备结果 | 后续动作 |
|---|---|
| allow | 不经人工审批；执行前仍需要生成并检查执行许可 |
| deny | 不执行工具主体，形成配对的错误ToolMessage |
| ask + Default | 进入人工审批 |
| ask + Auto | fast审查；有效ask再进入detailed；最终ask进入人工审批 |
| ask + NoAsk | 转deny，形成未执行反馈 |
| ask + BypassApprovals | 转allow；显式deny不会被此分支覆盖 |
| 参数无效/目标准备失败 | 按已有参数/工具反馈合同返回；不把它们一律送去人工审批 |

Auto中fast返回合法allow就结束；fast返回合法ask才询问detailed。输入不可用、普通审查错误或非法响应会降为ask；停止/外部取消等控制异常保留控制语义，不能解释成用户批准。

## 4. 主链A：第一次运行在工具前暂停

```text
AsyncApplication.arun
  → SessionService._admit / AgentSession.admit_run
  → SessionExecution.arun
  → ainvoke_agent_run_with_resources → ainvoke_agent_run
  → 图调用模型，得到ai-1 / call-1
  → PermissionMiddleware.aafter_model
      → prepare_local_batch → prepare_permission_call
      → 返回tool_execution批次更新
  → BatchApprovalMiddleware.aafter_model
      → _local：只把本批ask的call_id列入人工审批
      → ObservedHumanInTheLoopMiddleware.after_model
      → 官方HumanInTheLoopMiddleware.after_model
      → interrupt(hitl_request)
  → 图返回含__interrupt__的状态结果
  → SessionExecution：pending_tool_approval校验并提取待审批项
      → replace_pending_approval保存会话待审批信息
      → announce_approval发布approval_requested
      → RunObservation.result确定interrupted，报告turn_suspended
  → _afinish_run结算、必要保存、释放ActiveRun
      → run_finished(status='interrupted')
```

`interrupt()`由框架识别并保存暂停位置；应用得到可返回的中断结果。根run会结束，不保持这个Python调用栈等待点击。

如果同一批有两个调用，一个allow、一个ask，当前实现会在tools阶段前暂停整批，两个主体都尚未执行。此规则与工具执行后发生普通错误是否停止其他调用，是不同问题。

持久化应用使用SQLite checkpointer保存图状态，同时保存会话/消息历史信息；纯内存应用没有跨进程恢复保证。`approval_requested`发布早于本次应用必要收尾完成，不能当成全部保存成功的回执。

## 5. 主链B：批准后恢复同一条图线程

### 5.1 入口和一次许可

Web入口`WebService.approve`检查当前approval_batch_id、origin_run_id及每行approval_id，拒绝旧批次/重复或缺失决定，再经RunDelivery.resume进入应用恢复入口。低层`aresume_tool_approval`接收当前pending对应的有序approve/reject列表。

```text
AsyncApplication.aresume_tool_approval
  → SessionService.aresume_tool_approval
  → _admit(mode='approval_resume')：新run_id、原session/thread
  → AgentSession.admit_run：校验pending/busy/决定，恢复pending_turn
      → 记录control_accepted(kind='approval')
  → SessionExecution.aresume_tool_approval
      → prepare_resume生成OneUseApprovalGrants
      → 准备本次资源 / observation.bind
      → control_delivery_started(boundary='invocation')
  → aresume_agent_run_with_resources
      → Command(resume={'decisions': [{'type': 'approve'}]})
      → ainvoke_agent_run：使用原thread_id
```

一次许可绑定`session_id / agent_path / batch_id / call_id / tool_name / args / subject`。它保存在本次可信调用上下文，按匹配的call_id消费一次；不会给模型一个可自行声称拥有的全局权限标记。

### 5.2 审批节点恢复与实际执行

LangGraph恢复时从被中断节点开头重新执行，`interrupt()`收到这次resume值。之前已经提交的模型响应和权限批次继续使用；不会为原调用重新请求模型或重新跑Auto审查。

```text
恢复的审批节点
  → 重新收集原待审批调用
  → interrupt取得approve/reject
  → 官方HITL处理决定
  → ObservedHumanInTheLoopMiddleware确认匹配候选集合
      → control_applied(kind='approval', boundary='approval_hook')
  → 工具批次调度 / 工具观察 / 工具错误反馈包装
  → ExecutionAuthorizationMiddleware._authorize
      → 核对call_id/name/args与准备批次
      → ask调用必须消费完全匹配的一次许可
      → 向当前工具runtime放入_execution_permit
  → Read主体：require_file_target → require_tool_permit / verify_file_target
      → 复核目标解析及目录身份等准备事实
      → 真实读取
  → ToolMessage回填图状态
  → 原turn工具结果配齐，turn_finished
  → 下一次模型调用启动新turn，模型回答后正常收尾
```

文件复核防止批准后解析目标被改变，例如符号链接换向；不能据此声称文件内容被锁定、具有完整文件系统沙箱或事务回滚保证。目标变更按工具错误反馈返回，许可缺失/错配属于PermissionMechanismError，不能悄悄继续。

拒绝时：官方HITL移除对应待执行调用，并产生status='error'的配对ToolMessage；工具主体不运行。`control_applied`仍成立，因为确认的是决定已处理。当前包装还为该拒绝发布stage='approval_resolution'的tool_call_started/tool_call_finished，outcome='not_executed'、reason='approval_rejected'；started在这里不代表主体开始。

## 6. 身份、状态与事件的精确时点

```text
session S / thread T
  run R1：turn U模型调用 → 审批暂停 → run结束interrupted
  等待人工决定：busy已释放，但pending审批仍禁止普通新消息运行
  run R2：恢复同一turn U → 工具结果配齐 → turn U完成
          → 新turn V调用模型 → 回答 → run结束completed
```

| 事件 | 触发点 | 消费作用/证明范围 |
|---|---|---|
| approval_requested | 应用校验图中断结果并安装pending后 | 前端刷新审批信息、CLI呈现审批；不授予权限 |
| turn_suspended | R1的RunObservation.result发现pending | 报告逻辑turn暂停，保留原turn身份 |
| run_finished(interrupted) | R1必要收尾/保存及释放之后的正常路径 | 报告这一run已暂停结束；不代表原任务做完 |
| control_accepted(kind=approval) | R2准入记录决定；start后刷新观察通知队列 | 接受本次决定，关联origin_run_id=R1 |
| control_delivery_started | R2资源准备后、绑定恢复调用服务时 | 开始把决定交给恢复调用；不保证hook处理完 |
| turn_resumed | 恢复调用读取baseline后、重新驱动图前 | 接续原turn身份；不表示新发了一次模型请求 |
| control_applied(kind=approval) | 审批hook处理完、候选调用集合匹配 | 决定已处理；approve/reject都会确认，不能当工具成功 |
| tool_call_started/finished | 实际工具分发；拒绝也有单独approval_resolution阶段 | 须结合stage/outcome理解，不能单凭started认定发生IO |
| turn_finished | 对应AI调用的结果配齐并满足观察完成条件 | 原turn完成；拒绝可体现为error_result_count增加 |
| run_finished(completed) | R2及后续循环正常结束并完成必要收尾 | 本次恢复run完成 |

表格是单例正常因果顺序；流式消息/并发通知可插入。日志里的run_interrupted/run_completed是运行日志名称，正式运行终局事件是run_finished加status，不应混列成新的事件类型。

## 7. Auto在这条链上的位置

`PermissionMiddleware.aafter_model → _pending_asks → prepare_review_input → AutoPermissionReviewer.areview`只处理前面规则留下的ask。输入由可信人类消息、项目约束、既往调用事实和当前准备目标构成；审查回复不混入主模型对话。

fast/detailed只返回allow或ask。最终ask仍进入相同HITL暂停链。模式和会话允许取批次快照；恢复审批使用保存批次，运行中修改模式影响后续新批次。

当前`_review_steps`生成器由唯一异步`areview`用next/send/throw驱动。它没有形成两套产品执行入口，但增加理解跳转；直接async流程是可读性优化候选，未批准实施。不得为精简而删除预算限制、响应校验、控制异常或失败回ask合同。

## 8. Pi与DeepSeek Harness的实际对照

### Pi：工具前hook的返回值控制执行

固定73f8de80：`AgentSession._installAgentToolHooks → _beforeToolCall → ExtensionRunner.emitToolCall`，循环`prepareToolCall`先await beforeToolCall，再读取block/terminate；block形成工具错误结果，不进入主体。

这里的扩展tool_call是有返回合同的执行拦截点；不能把它当作本项目的纯观察tool_call_started。上述链能支持执行前询问/阻断；没有据此证明其所有产品路径都使用本项目这种跨run/checkpoint审批。

### DeepSeek Harness：请求通道与持久审计分开

固定687f282e：`Tools.prepareExecution → tools/pre-execute waterfall → ask → serviceAsk → ApprovalService.request`。

```text
session.append('approval/asked')
  → await decide
      → await ctx.waterfall('approval/request')
      → 返回allowed-once / rejected / cancelled / unavailable
  → session.append('approval/decided')
  → 把结果返回工具执行链
```

`approval/request`是进程内有返回值的询问，普通该路径等待其结果；asked/decided是成对持久审计，不进入模型对话。只有allowed-once放行。无人回答、答复异常或非法返回值降为unavailable并拒绝；控制取消丢弃迟到答复。任一必要审计append无法提交，会使审批请求失败。

持久审计不等于一个await Promise可以跨进程恢复；这条局部链未证明重启后原审批等待自动续接。我们的根审批用checkpoint+新run恢复；二者都要求明确决定来源和执行前门禁，框架及生命周期合同不同。

旁查AgentX本地3fcfa0e：BuiltInToolRegistry.createToolsForAgent → AbstractBuiltInToolProvider.createToolExecutor → executeTools → supportsTools/参数解析 → doExecute。该链能说明工具注册/执行分工，不能证明其有同等人工审批和checkpoint恢复保证，本场景不类推。

## 9. 设计判断与失败边界

建议保留三段职责及checkpoint恢复。理由是它们分别解决政策选择、人工等待和批准后的目标一致性，每段都有独立失败场景；层数增加有实际合同。

| 场景 | 当前边界 |
|---|---|
| 浏览器漏收approval_requested | pending/图暂停状态仍存在，可重新读取会话发现；观察通知不能成为唯一审批数据源 |
| 提交旧批次或另一会话的决定 | Web批次/行身份及当前pending校验拒绝，不执行 |
| 用户拒绝 | 未执行反馈交给模型，不自动等价于整次run失败 |
| 一次许可缺失/错配/重复消费 | PermissionMechanismError阻断，不作普通授权成功 |
| 批准后文件解析目标变化 | 工具复核失败并反馈，不把旧批准套给新目标 |
| 必要checkpoint或会话保存失败 | 按必要保存错误传播/标记，不能当普通观察失败忽略 |
| 等待审批期间用户停止 | 专门审批停止入口，恢复时用停止信号补未执行结果并收尾；不假设R1仍活动 |

仅因DSH审计append为必要操作，不要求我们把普通事件总线变为持久权威日志。当前权威暂停位置和准备批次由图checkpoint拥有，应用拥有pending及提交入口，一次许可由可信恢复上下文拥有；诊断是排查材料，不负责重放审批。

子Agent采用live_child审批，根run/子driver可能仍然存活；不把上面的paused_root生命周期套给它。子生命周期在后续独立场景展开。
