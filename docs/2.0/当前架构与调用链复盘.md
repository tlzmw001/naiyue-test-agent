## 1. 先保留旧知识，再替换旧地址

没有被推翻的主干：

```text
用户输入 → 会话准入 → 运行资源/可信context → Agent图
  → 模型给出AIMessage
    ├─ tool_calls → 工具 → ToolMessage回填 → 下一次模型
    └─ 无工具调用 → 自然结束边界：检查停止/steering/follow_up
  → 应用判断结果 → 必要收尾/保存 → 终局与返回/抛错
```

事件是事实的投影与分发；循环继续主要由图状态、工具结果、hook返回及jump_to决定。异常描述D不替代原异常，不自动重试；failed也不表示必要收尾已经完成。

要替换的主要地址：

| 旧地址/理解 | 当前对应 |
|---|---|
| LocalApplication.run、同步/异步平行应用入口 | 正式应用入口为AsyncApplication及其持久化子类的异步方法 |
| SessionService集中管理所有会话的可变dict、队列和执行 | Service登记/准入；每个AgentSession拥有自己的SessionState与ActiveRun |
| _run_steps/_resume_steps交出IOCall，驱动器send/throw | SessionExecution中的普通async方法，直接await；IOCall/arun_steps已删除 |
| 十余个回调散传Runtime | SessionPort协议，当前由同一个SessionService对象提供相关能力 |
| 工具在agent_runtime/tools下 | 实际工具在tools；框架工具调度/权限/审批在agent_runtime/tool_execution |
| 很多单会话操作逐层转发 | 应用内部require(sid)后直接调用AgentSession；运行仍经Service统一准入 |

## 2. 旧图与当前图

### 旧课堂版本：Lesson65/73

```text
build_local_application / 持久化工厂
  → LocalApplication / PersistentApplication
    → SessionService.run / resume_tool_approval
      → _run_steps / _resume_steps 生成器
        ↔ IOCall + run_steps/arun_steps 驱动器
          → invoke/resume runtime → Agent图 → 模型/工具
```

093曾先删同步执行面、保留异步生成器；102才进一步删除剩余IOCall/arun_steps。不能把这两个迁移混成一个决定。

### 当前对象关系

```text
AsyncPersistentApplication（继承AsyncApplication）
  ├─ ModelCatalog：共享模型、供应商客户端及模型配置
  ├─ ToolRegistry：共享工具定义
  ├─ 根Agent编译图 + checkpointer
  ├─ SessionService：登记、共享定义、跨会话准入/名额、Runtime能力路由
  │   └─ _sessions[sid] → AgentSession
  │       ├─ SessionState：本会话配置/历史身份/待审批等事实
  │       └─ ActiveRun | None：本次运行/观察/队列/子实例
  ├─ SessionPersistence / SessionStorage：必要保存、查询与恢复
  └─ ModelUsagePersistence / DiagnosticPersistence：有界观察写入
```

对象关系不等于每次调用都经过全部对象：

- AsyncPersistentApplication.arun继承AsyncApplication.arun，不是先调用一个持久化对象、再调用另一个应用对象。
- AgentSession继承SessionExecution等按职责拆分的实现。session.arun实际在session_execution.py定义，但self仍是同一个AgentSession，没有另建SessionExecution服务。
- SessionPort是Protocol，不是新建的Port服务对象；Runtime只使用协议声明的9项能力，拿不到require、完整AgentSession、State或锁。
- 根图按thread区分状态；同图复用不等于会话共用历史。子角色有自己的编译图/执行thread，不与根混用历史。

### 当前正常执行链

```text
app.arun(sid, messages)                           AsyncApplication
  → _execute(...)
    → sessions.arun(agent, sid, messages)         SessionService
      → _admit(...) → session.admit_run(...)      名额/本会话原子准入
      → session.arun(agent, messages, run=run)    方法实现在SessionExecution
        → _prepare_resources(run)
        → observation.bind(...)
        → ainvoke_agent_run_with_resources(...)  有工作区时
          → ainvoke_agent_run(...)
            → ainvoke_with_message_observation(...)
              → agent.astream(...)               同一次图执行的流式观察
                → middleware → 模型/工具循环
        → observation.result(...) / _on_failure(...)
        → finally: await_settled(_afinish_run(...))
```

没有工作区的执行直接调用ainvoke_agent_run；手动压缩有独立算法分支，不按普通用户任务调工具。本课只定位，压缩内部留第七章。

## 3. 三份数据，分别由谁拥有

以下ID/路径是说明值，不是一次真实模型请求输出：

```python
# 跨会话登记
sessions._sessions['S1']  # AgentSession对象

# 逻辑会话事实：SessionState，实际字段节选
SessionState(
    thread_id='T1', model_id='A', workspace_root=Path('/example/project'),
    active_tool_names=('read', 'ls'), permission_mode='Default',
    pending_tool_approval=None, manual_review_required=False,
)

# 本次运行：ActiveRun，实际字段节选
ActiveRun(
    run_id='R1', observation=observation,
    steering_queue=deque(), follow_up_queue=deque(), subagent_instances={},
)

# 图状态中的消息，以下是内容形状而非完整对象
[
    HumanMessage(content='读README'),
    AIMessage(content='', tool_calls=[
        {'name': 'read', 'args': {'path': 'README.md'}, 'id': 'call-1'}]),
    ToolMessage(content='文件正文', tool_call_id='call-1'),
    AIMessage(content='总结'),
]
```

SessionState不保存一份全部messages；模型当前消息状态由图/checkpointer管理，展示历史另有归档。ActiveRun存在表示本会话仍被该run占用，包含必要收尾阶段。

Session是逻辑会话；thread定位执行历史；run是一次准入至收尾的执行；turn对应模型与相关工具的观察生命周期；tool_call_id配对调用/结果。审批恢复可新建run并续接原turn。重新生成最后任务时session可切换当前thread，并递增conversation_revision，所以不能把“一个session永远一个thread”当成当前不变量。

## 4. 用熟悉的正常例子走当前主链

现有测试test_application_composition.py中第一任务：模型A先请求read_probe，工具返回private-tool-result，模型再返回A-one；这是确定性假模型，不是真实供应商。

| 阶段 | 当前负责者/方法 | 输入、输出或状态变化 |
|---|---|---|
| 装配 | build_async_local_application；Web用open_async_persistent_application | 准备注册表/目录，创建Service，assemble_runtime调用create_agent；此时不执行用户任务 |
| 创建会话 | app.acreate_session → Service创建AgentSession | 会话S1映射T1，选择模型A，_run=None |
| 准入 | SessionService._admit → AgentSession.admit_run | 校验版本/待审/人工核对/本会话占用/全局名额，安装ActiveRun(R1) |
| 资源 | SessionExecution._prepare_resources | 准备本次项目指令与可读资源，冻结到run |
| 运行context | RunObservation.bind → make_invocation_context | 关联S1/R1、观察/错误策略/控制对象；config另传T1 |
| 图执行 | ainvoke_agent_run → ainvoke_with_message_observation | 读取历史基线，astream驱动图并消费messages/values等分片 |
| 选模 | _ModelSelectionMiddleware._prepare | 经SessionPort.resolve_model(S1, agent_path)取得当前作用域模型A |
| 工具循环 | 工具集合/权限/批次/调用观察/错误边界/执行授权 | read_probe结果变ToolMessage，按call-1配对，图再次请求模型 |
| 自然结束 | inject_at_natural_end | 没有工具调用后检查停止与补充队列；无后续输入才结束图 |
| 收尾 | observation.result → _afinish_run | 子驱动结算、关窗口/清队列、必要保存、释放ActiveRun、发布终局后返回 |

这里astream既执行图也提供分片，没有先执行ainvoke再执行一次astream。prepare、context与config都不是直接作为用户正文发给模型；模型最终输入由模型输入中间件装配。

## 5. 已学控制机制怎样迁移

过渡版本曾为：AsyncApplication.steer → SessionService.steer → AgentSession.steer。

当前：

```text
AsyncApplication.steer(sid, text)
  → 检查文本
  → SessionService.require(sid)返回拥有者
  → AgentSession.steer(text)                    入本run的队列

图的inject_before_model
  → SessionPort.drain_steering(sid)
  → Service路由到同一个AgentSession           取队列、生成HumanMessage
  → hook返回messages                          更新图状态
```

follow_up仍在自然结束边界交付，必要时jump_to='model'。request_stop仍通过RunControl和执行边界生效；收尾的await_settled不因删除IOCall而删除。阻塞文件/存储IO仍可由run_blocking在线程中执行，原生异步模型/进程/网络则await，不能推成“所有同步代码都已消失”。

并发从全局单活动run改为按会话拥有run；不同会话可并行，同一会话不能重入，全局根run名额仍受AppSettings.max_active_runs约束。根run数与一批工具的max_concurrency是不同限制；子Agent及Auto审查也不能简单按根run数当作供应商请求上限。

## 6. 工具/权限与两类审批

### 当前工具链

```text
tools中的ToolSpec → ToolRegistry → 会话活动集合
  → ToolSetMiddleware给模型提供工具schema/本批视图
模型给出tool_calls
  → PermissionMiddleware准备可信审查对象与决定
  → BatchApprovalMiddleware处理本批需要Ask的调用
  → ToolBatchMiddleware建立尚未完成调用的批次计划
实际工具wrapper
  → 调度 → 调用观察 → ToolErrorMiddleware
    → ExecutionAuthorizationMiddleware → 工具体
```

这是关键阶段图，不替代装配点所有hook/wrap的精确顺序。完整顺序在agent_runtime/__init__.py的_build_runtime_agent注释；先wrap为外层、after hook反向等原理沿用第三章。

| 结果/分支 | 后续 |
|---|---|
| Allow | 授权检查后执行，正常ToolMessage回填 |
| Deny或用户Reject | 错误ToolMessage配对原调用，工具不执行，模型可据此继续 |
| Ask | 工具执行前图中断；批准后才恢复执行 |
| 可反馈的工具错误 | ToolErrorMiddleware生成错误消息，循环通常继续 |
| 权限机制/批次调度/进程清理/未知副作用等故障 | 保持异常传播，应用核对并可能阻止自动继续，不伪造普通结果 |

### 根审批：原机制保留，负责人改变

```text
R1：Permission → BatchApproval/HITL → interrupt → 保存图暂停位置
  → SessionExecution.arun安装pending → interrupted → 必要收尾
用户提交审批
  → app.aresume_tool_approval → SessionService统一准入
  → AgentSession.aresume_tool_approval
  → prepare_resume产生一次性grant
  → aresume_agent_run_with_resources构造Command(resume=decisions)
  → 同thread，新R2 → 执行处检查/消费grant → ToolMessage → 模型
```

审批决定恢复控制流程，grant授权精确调用，工具仍复核当前条件。这两份东西不等于一个“已允许”的通用布尔值。

### 新增子审批分支

根模型通过注册的subagent工具委派；AgentSession拥有子实例/driver，子有独立thread、模型工具快照与agent_path。一层前台同进程执行，不是独立后台服务。

子暂停时，父run可仍在运行等待该工具及其他子任务；主界面提交live_child批次经asubmit_subagent_approval唤醒该子driver，子用Command恢复。不能把“根审批结束R1再开R2”套到父run；子执行段自身的run身份会更新。根收尾必须等所属子driver结算。

前端approve/stopApproval收到成功回执即移除相应审批批次；失败保留选择，兄弟批次保留，旧刷新跨越回执时重读，避免面板重现。此界面收起不表示工具或run已经执行完毕。

### 新工具与权限变化接在同一条链

- ls/find的名称清单不再按隐藏/私有内容默认过滤；工作区/外部范围、显式规则等边界仍检查。read/grep/write/edit继续检查内容权限，Auto不等于沙箱或全部放开。
- aitest_kit直接argv执行外部AITest CLI；web_search顺序调用配置供应商，失败/空结果才回退；web_fetch读取网页并在请求/跳转时检查网络目标。
- 三项都是ToolSpec进入现有管线，没有恢复test_agent策略层；AI结合提示词/Skills使用它们。实际AITest业务与搜索账户/质量未因离线机制验证而成立。

## 7. 事件从“看见过程”扩展到多种消费者

```text
模型/工具/消息/控制的事实
  → Observer / model invocation callback
  → RunEventPublisher：本run身份、序号、顺序与故障隔离
    ├─ 日志
    ├─ DeliveredRun.observe → 消息/工具/子实例投影 + 有界SSE队列
    ├─ ModelUsagePersistence.accept → 调用用量/成本事实
    └─ DiagnosticPersistence.accept → 有预算/淘汰的运行诊断
```

ApplicationEventSubscriptions.publisher按注册顺序选择全局和本session的订阅者，不再让所有Web job先收到所有会话事件再各自过滤。全局用量/诊断消费者仍可观察所有会话。

RunDelivery拥有后台producer任务和回执；DeliveredRun拥有单run的交付投影/事件缓存。Web前端断开SSE不等于取消producer，重连读快照/游标，不重放执行POST。普通消费者故障按合同诊断降级；必要会话保存由_afinish_run→SessionPersistence.afinish负责，不能用“事件发出过”代替保存确认。

缓存标记是模型请求配置，cache_read是响应反馈；本地聊天/事件缓存是另一回事。ModelCatalog加载声明能力并经prompt_cache_model_settings生成供应商参数；命中仍由供应商决定。用量事件与持久化记录不保证每次请求都有完整价格/计数，缺失不冒充0或完整账单。

## 8. 模型状态、展示历史、事件交付三条线

| 数据 | 主要拥有者 | 用途 |
|---|---|---|
| 当前图状态与checkpoint | LangGraph/checkpointer；应用保存thread/checkpoint身份 | 执行、模型上下文、审批/恢复 |
| 会话消息归档 | SessionPersistence/SessionStorage的聊天档案及查询 | 持久历史、上滑分页、正文分块、子历史 |
| 事件队列/诊断投影 | DeliveredRun及DiagnosticPersistence | 实时更新/重同步、有限运行排查 |

三者可在同一SQLite文件中有不同表和生命周期，并不是三份同义messages。压缩改变模型上下文，不删除展示归档；事件淘汰也不删除聊天。

旧GET session恢复会话并序列化全部历史，start/compact/approve又借整份view准入，因此显示预算可能卡住执行。

当前关键链：

```text
显式准备：aprepare_session → SessionPersistence.aprepare
发起任务：WebService.start → _session_status（轻量）→ RunDelivery.start
看历史：WebService.session/messages → aget_chat_page → 有界页/正文预览
继续看：上滑旧页；需要全文时message_content/aget_chat_message有界分块
```

真实执行的当前状态先更新投影，超大事件可以因传输预算不入队，旧游标要求resync；不让超大完成帧永久留下旧草稿。最新已保存助手预览自动取全文；代码先完整纯文本呈现，再由Worker有预算地着色，回退不删正文。

新增reply_id让同一用户请求跨模型/工具/审批多个run仍可归成回复块；它不是run_id或turn_id。最后任务重新生成从其前置保存边界构造替换历史，更新thread/版本并走原运行生命周期，不是重新同步。重新同步只修复显示/订阅，不重新执行模型工具。

nyt仅是安装入口：cli.main默认转web.__main__.main，nyt chat转application.cli.main；包内前端/rg/fd和五平台发行没有新造Agent运行时。

## 10. 收束

记住七个地址：

1. ModelCatalog：共享模型与客户端。
2. AsyncApplication：对外异步操作和任务/资源生命周期。
3. SessionService：登记、跨会话准入、Runtime能力路由。
4. AgentSession：单会话行为；SessionState为会话事实，ActiveRun为在途执行。
5. SessionExecution：同一个AgentSession的执行/失败/收尾实现。
6. create_agent产物与middleware：模型—工具循环及状态更新。
7. RunDelivery/DeliveredRun：Web任务管理与显示投影；持久化按执行/归档/用量/诊断区分。

### Pi的准确边界

已核对本机Pi提交a69bef789及对应公开源码：

- [agent-loop.ts](https://github.com/earendil-works/pi/blob/a69bef789/packages/agent/src/agent-loop.ts)：runLoop按工具批次terminate、steering、shouldStopAfterTurn和follow-up决定下一轮；不是等待tool_execution_end监听器返回“继续”。
- [agent.ts](https://github.com/earendil-works/pi/blob/a69bef789/packages/agent/src/agent.ts)：processEvents先更新Agent._state，再await监听器；agent_end之后还要等监听器和finishRun才idle。事件有状态同步/交付职责，不是无作用的日志。
- Pi的EventStream还以agent_end判断流完成。必须分清“执行循环选分支”和“事件消费者如何判断结束”。本项目Web流由job.done等交付状态结束，两者不能按事件名机械等同。
- 本项目普通订阅者同步轻量，异常诊断并隔离；不是Pi监听器等待合同的复制。以上是源码事实，未运行Pi实网请求。

### 主测试：一次工具调用，再给最终回答

入口：tests/test_application_message_events.py::test_tool_loop_publishes_all_content_once_and_default_logs_are_metadata。

测试定义probe(value:str)将value追加到called并返回合成PRIVATE_TOOL；假模型预设第一条AI带文本PRIVATE_THOUGHT及probe(value=PRIVATE_ARG,id=c1)，第二条AI为PRIVATE_ANSWER。用户输入PRIVATE_INPUT。PRIVATE前缀全为测试合成值，用于检查正文不泄露到默认日志。

app由真实build_async_local_application装配，ToolSpec显式默认allow；monkeypatch只替换模型目录加载。图、middleware、执行/观察和调用关系都是真实代码；外网模型被替换，没有HTTP/SQLite持久化消费者。本测试用同步小工具经现有异步适配运行，无手动create_task/Event门闩，适合作为主阅读入口。

三个列表的用途：called检查工具真正执行及参数；result['messages']是图的业务结果；events是订阅者记录的RuntimeEvent，不能把events当模型历史。Fake的i在两条回复后循环回0，不表示模型没有被调用。

### 主要参数与返回地图

| 方法 | 关键输入 | 主要行为/输出 |
|---|---|---|
| AsyncApplication.arun | sid、新messages、max_concurrency | 进入应用操作作用域，交_execute，再交Service |
| SessionService._admit | sid、可选run_id、mode='message' | 构造publisher/RunObservation；检查全局名额与会话准入，返回(session,run) |
| AgentSession.admit_run | run_id、mode、observation、capacity_available | 核对会话版本/人工核对/待审/busy/名额，安装ActiveRun；拒绝不发布run_started |
| AgentSession.arun（SessionExecution） | agent图、messages、已准入run | start→资源→execute→解释结果/失败→finally收尾 |
| ainvoke_agent_run | agent、messages、sid、thread_id、run_id、运行资源 | input为消息或Command；context投影可信服务；config指定thread；返回图状态 |
| ainvoke_with_message_observation | agent、input、context、config、publisher | seed旧历史→消费astream分片→返回最终状态；关闭迭代器并保护原异常 |
| _ModelSelectionMiddleware.awrap_model_call | ModelRequest、handler | _prepare选模型/开始turn→await handler→_accept校验结果或_failed后raise |
| aobserve_tool_dispatch | ToolCallRequest、handler、dispatch | 开始观察→批次调度→内层调用→结束观察→返回ToolMessage或raise |
| RunObservation.result | 图result、pending | 设置completed/stopped/interrupted，更新turn/control观察；不释放占用 |
| _afinish_run | run、agent、primary_error | 子驱动/控制清理→必要保存→释放run→终局；处理次要错误优先级 |

astream的part分支：messages是模型分片，可能发正文/思考delta；values是已合入图的状态，校准完整消息和turn/control；updates收集interrupt；custom接工具进度。恢复时先seed基线避免把旧消息当本run新增。这个messages流分支与状态字典中的messages列表是不同层的概念。

| 21 | model_invocation_started | 第二次实际模型调用 |

| 25 | model_call_finished accepted | 最终AI校验通过，无tool_calls |

| 27 | turn_finished completed | 该turn无工具，AI可见且ready后结束 |
| 28 | run_finished completed | 解释结果与必要收尾后发布终局 |

本例假模型不是逐token网络流，所以invocation_finished早于唯一delta；真实流式可以先有多个delta。model_call是项目逻辑边界，invocation是实际模型回调边界；returned不等于通过项目响应校验，也不等于run完成。

消息快照：MessageStateObserver.observe比较ID/hash；基线不发新增，首次见ID发message_completed，同ID内容变化发message_revised，可信状态移除消息时发context_messages_changed；无法可靠观察发message_snapshot_unavailable。delta为草稿，完整快照做校准。

turn结束必须同时满足ready、AI在图values中可见、同一批tool_call_id均有对应ToolMessage，并且不是仅recovery_view。故tool_call_finished早于ToolMessage可见，model_call_finished也不能单独关闭含工具的turn。

真正的下一跳：本机LangChain1.4.2 factory._make_model_to_tools_edge读取jump_to和最后AI/工具消息；有未配对调用则Send到tools，无tool_calls则去结束节点，已有人工工具结果等分支可回model。_make_tools_to_model_edge在普通工具结束后回模型入口；return_direct/结构化输出有独立退出分支。event_type未参与这些条件。

### 收尾逐阶段

SessionExecution.arun可概括为：

```python
primary_error = None
try:
    result = await execute_graph()
    observation.result(result, pending)
    return result
except BaseException as error:
    primary_error = error
    await on_failure(error)
    raise
finally:
    await await_settled(finish_run(primary_error))
```

此代码仅是结构示意。return的值先确定，finally执行完才真正返回；finally抛错也可能阻止原return。

1. _afinish_run在有主异常时请求所属任务停止；settle_subagent_drivers等待子driver并核对。
2. _cleanup_run→close_control_window保存待审turn快照、清队列、关闭接收窗口、清本次prompt；控制观察为未交付请求记录discarded/unknown。
3. 有persistence时await SessionPersistence.afinish，核对/保存会话及归档；主测试为内存应用，不能从它声称SQLite已验。
4. 窗口关闭且无未结算子实例后release_run，self._run=None，busy解除；身份检查防旧run清掉新run。
5. observation.finish先flush控制/上下文观察，再发run_finished；有原主异常时后续故障日志不能替换它，无主异常的关键清理/保存失败要变为失败并抛出。
6. 调用栈回到app.arun；测试取得result再检查断言。Web若在场，RunDelivery._produce此后还要取消订阅、job.done=True、释放该job占位并唤醒流，前端再确认快照。run_finished与Web producer彻底结束不是同一个时点。

### 控制/异常分支怎样岔开

| 分支 | 执行链与观察证据 |
|---|---|
| steering/follow_up | 会话实际队列入队→control_accepted；hook取队列→control_delivery_started；Human已进入图values→control_delivered；hook返回messages/jump_to决定再调用模型 |
| 根审批 | pending安装→approval_requested→turn_suspended→run_finished interrupted；新run构造Command→control_delivery_started/turn_resumed→HITL实际处理→control_applied→工具/模型继续 |
| 审批拒绝 | 同ID error ToolMessage，无工具主体；会有boundary=approval_resolution的tool_call_started/finished，outcome=not_executed，不能凭started断言已执行 |
| 用户停止 | request_stop修改RunControl并记录accepted；native模型等待取消转换UserStop→StopModelMiddleware返回run_stopped更新；结果确认后control_applied；未交付补充被discarded，run终局stopped |
| 可反馈工具异常 | ToolErrorMiddleware变error ToolMessage→tool_call_finished error_result→图继续模型；run仍可completed |
| 机制/未知结果故障 | 原异常上抛→_on_failure核对/人工核对→必要收尾→failed；不自动重试 |
| 观察者抛错 | publisher诊断并禁用该handler，本run其他handler继续；结果或原主异常不变 |
| 准备/执行/结果整理失败 | _on_failure记录对应stage，finally清理；同一异常对象返回调用者 |

停止主测试中出现turn_finished failed与run_finished stopped：当前模型turn被取消，整个run按用户停止结束，两者层级不同。

其他事件族：message_reasoning_delta在供应商分片含可见思考时发出；compaction_started/finished和context_recovery_started/finished分别跟踪上下文操作及恢复，不是每次run都出现；turn_observation_unavailable和control_outcome_unknown表示观察证据不足，不自动等价业务执行失败。

### 异步测试的两条时间线

tests/test_async_application.py::test_waiting_model_accepts_steering_then_follow_up使用entered/release两个Event：

```text
测试协程：create_task(arun) → await entered → steer/follow_up → release.set → await task → 断言
运行协程：准入/事件 → 模型_next记录seen → entered.set → await release → 模型返回 → hooks/后续两次模型 → finally → task完成
```

entered只证明第一模型已到指定等待点；release只是测试放行门闩。steer/follow_up才是生产控制输入。wait_for(...,5)为卡死保护，不表示正常等5秒。测试finally中release/gather/app.aclose是测试资源清理，与生产_afinish_run分开。messages断言为start/one/steering/two/follow-up/three，seen长度3。

tests/test_architecture_semantics.py::test_application_final_save_settles_before_repeated_cancellation_escapes[False]：Persistence替身卡在afinish，图执行被最小替身替换；entered证明确实到保存，取消两次时busy仍true、无终局；release后保存完成、终局/解除占用，调用者才收到第一次CancelledError。True分支保存失败需诊断，保留原取消。这里证明取消/所有权顺序，不证明真实SQLite写入。

注意外部取消发生在finally保存中时，成功保存的终局可仍为completed而等待方收到CancelledError；事件记录的执行结果与调用者等待是否取消要分开。
