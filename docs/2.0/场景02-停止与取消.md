# 场景2：点击停止后，什么时候才真正结束

日期：2026-10-20。阶段：源码走读及设计讨论，无产品改造授权。本轮未运行测试或模型请求。关联[架构基线](事件架构讨论.md#10-面向持续演进的地基待确认决策基线)、[十二场景](十二组场景总览.md)、[事件表](事件全集与消费附表.md)。

用户最新决定：插话的control_delivery_started保留现状，暂不补入持久诊断；遇到真实定位不足再考虑。后续讲解必须标明动作/事件时点，用具体例子与实际函数解释术语。

## 1. 具体例子与四个时点

教学示意：一次模型响应提出两个工具调用。A已进入必须完成收尾的同步写入阶段；B仍排队、尚未通过执行前检查。用户此时点击停止。

期望行为：接纳停止 → 不启动B/后续模型 → 等A结算并保留结果 → 完成必要保存和释放。示意A/B对应已有同步工具结算场景，不表示本轮真实写文件或执行测试。

| 时点 | 当前含义 | 不能混同 |
|---|---|---|
| 接纳停止 | 会话记录请求、设置运行停止信号、关闭插话窗口 | 所有工作已经退出 |
| 执行检查点响应 | 还没开始的工作检查到信号，不再进入主体 | 任意线程被强杀、已写内容被撤销 |
| 图返回停止结果 | result包含run_stopped=True，应用识别停止分支 | 应用必要保存/子工作结算已经全部完成 |
| 应用收尾并释放 | 按合同结算工作、保存、释放_run，报告终态 | Web发送最终视图的producer也恰好同时退出 |

## 2. 入口调用与实际负责者

```text
POST /api/runs/{run_id}/controls，kind="stop"
  → RunDelivery.control(run_id, body)：校验活动job与控制请求身份
  → AsyncApplication.request_stop(session_id, run_id=..., agent_path='root')
  → AgentSession.request_scope_stop(..., reason='user')
      → 检查目标run、接纳窗口和finalize状态
      → 在会话锁内设置ActiveRun.stop_requested=True、steering_open=False
      → RunControl.mark_requested('user')：设置停止信号
      → ControlObserver.accept('stop')：排入接纳通知
      → 锁外RunControl.request('user')：通知受它拥有的模型任务取消
      → 对子实例传播停止/唤醒失效审批等待
      → flush控制事件，返回尚未消费文本
  → Web返回accepted=True，显示正在停止
```

停止请求直接改变控制状态，不进入steering队列，不需要模型理解“请停止”。Web回执确认接纳，未等待本次run完整退出。

RunControl可以理解为“本次运行共享的停止信号及模型任务登记簿”；ControlObserver则记录控制动作进展并发通知，二者职责不同。

## 3. 主例子：A完成、B不启动

### 3.1 B为什么不会执行

```text
ToolBatchMiddleware._adispatch_tool_call
  → AsyncBatchPlan.execute：等待顺序或并发名额
  → 获准调度后执行guarded()
      → 检查RunControl.requested
      → 已停止：返回stop_tool_message，不调用后续工具主体
```

本例B可能要等A结算后才轮到这个检查，并非点击时立即从等待队列消失。停止不需要为B执行真实操作，仍需给模型提出的调用配上结果。

示意返回：

```python
ToolMessage(
    tool_call_id="B",
    content="Tool was not executed because the user stopped this run. ...",
    status="error",
    additional_kwargs={"naiyue_not_executed": "user_stop"},
)
```

status=error表达这次调用没有得到正常成功结果；项目另用naiyue_not_executed明确未执行，不等于工具主体运行后失败。观察结果是tool_call_finished(outcome='not_executed', reason='user_stop')。

### 3.2 A为什么可能仍写入成功

RunControl.request取消登记的模型任务，不会强制终止任意工具线程。普通叶子工具执行有await_settled保护；该辅助函数等待受保护工作结算，外部取消也不能让拥有者提前释放资源。工具仍可自行读取同一个停止信号，在安全位置提前返回。

本例A已经进入必须结算的阶段，因此继续到可确认结果：返回成功ToolMessage，报告tool_call_finished(outcome='success')。已有真实write的测试在os.replace阶段阻塞后请求停止，约定保留完成替换后的成功结果；本轮仅阅读该测试。

停止不回滚已经发生的文件修改。若操作已越过最后可停止检查点，按已开始工作结算；不能承诺每条机器指令都可被停止按钮打断。

### 3.3 为什么不再调用模型

```text
A、B的ToolMessage合入图
  → 下一次模型前的inject_before_model
  → SessionPort.is_stop_requested(session_id)为True
  → 返回run_stopped=True、jump_to='end'
  → 自然结束检查也看到停止，不取steering/follow-up
  → 图返回结果
```

跳转仍经过框架出口及相应hook，应用finally收尾继续执行。本例只有最初产生工具调用的那次模型处理，不再发一次请求让模型总结停止。

## 4. 事件触发时点与含义

| 事件 | 实际触发点 | 具体含义 |
|---|---|---|
| control_accepted(kind='stop') | request_scope_stop已记录请求/设置标记，ControlObserver.accept建立记录；锁外flush发布 | 用户停止命令已接纳，不证明线程退出 |
| tool_call_started | aobserve_tool_dispatch进入调用处理时，在批次等待/主体前 | B即使仍在排队，也可能已有此事件，不能据它认定主体启动 |
| tool_call_finished(outcome='success') | A调用链得到可确认成功结果 | 保留A既有结果，未证明整轮已收尾 |
| tool_call_finished(outcome='not_executed') | B执行前检查命中停止，返回匹配ToolMessage | B主体未执行；事件可早于结果正式合入图 |
| control_applied(kind='stop', boundary='active') | 图返回后，RunObservation.result → ControlObserver.run_result检查到run_stopped=True | 图已走停止分支；应用仍可能busy且正在准备收尾 |
| run_finished(status='stopped', stop_mode='active') | 正常停止的应用收尾/必要保存及释放之后，RunObservation.finish | 报告本次运行停止终态；Web producer可能稍后退出 |

前三个control阶段是steering/follow-up的消息交付流程。停止正常使用accepted → applied，不产生自己的delivery_started/delivered；它不是要进入模型对话的一条HumanMessage。

表为因果时点，不承诺所有工具/控制事件在全局流中彼此紧邻。发布器按实际发布分配sequence；control.accept先放通知队列再flush，其他并发事件可插入。观察可用、无主失败的本例才得到正常stopped终态。

## 5. 应用收尾与busy释放

```text
图返回run_stopped=True
  → SessionExecution.arun设置finalize阶段
  → RunObservation.result：识别stopped、发布control_applied
  → finally: SessionExecution._afinish_run
      → settle_subagent_drivers / assert_subagents_settled
      → close_control_window：清理未消费输入与运行资源引用
      → SessionPersistence.afinish：必要保存
      → release_run：允许时将self._run=None
      → RunObservation.finish：run_finished
```

等待结算就是等待已开始的工作得到可确认结果并清理资源，不保证每个工具必须做完全部原任务。内存run存在期间，应用仍拒绝重叠运行。保存/清理出错可把终态变为failed；已发布control_applied不能保证随后保存成功。

## 6. 停止落在其他位置时

| 位置/条件 | 当前响应方式及边界 |
|---|---|
| 模型前尚未开始 | 模型前停止检查返回结束，不发该次请求 |
| 正在等待原生异步模型 | RunControl.request取消登记的本地模型task；await_model将本次用户停止转为UserStop，StopModelMiddleware捕获并返回run_stopped更新，不伪造助手回答 |
| 模型采用同步回退 | 当前模型wrapper未登记可取消的原生异步task，可能等返回后再检查停止 |
| 模型刚返回工具调用，主体尚未开始 | StopBoundaryMiddleware.after_model/权限阶段停止分支补未执行结果，跳到结束 |
| 工具等待调度 | 到执行前检查时跳过；不因停止请求就强行释放前面仍在执行的工具 |
| 文件工具已开始且尚在安全检查点前 | 工具自身check_tool_stop可提前结束，不必完成全部原任务 |
| Bash/PowerShell等进程工具运行中 | 工具自身负责停止进程及清理，结算后才能释放；不能套用“所有工具都只等待自然完成” |
| 根run已经因审批退出、正在等人工决定 | 通过审批停止入口处理，不能假设仍有活动run可请求停止；后续审批场景展开 |
| 用户停止与工具真实失败/未知副作用重叠 | 保留真实失败及人工核对合同，不统一改报成功停止 |
| 外层async task被取消 | CancelledError继续传播，和用户停止不同；必要结算仍执行 |

原生异步模型停止只说明本地请求任务取消，不能单凭此断言供应商已经停止计算或计费。这里的task是一次被调度的异步工作，不等同于线程。

## 7. 三份停止信息为什么同时存在

| 数据 | 作用 |
|---|---|
| ActiveRun.stop_requested | 会话负责人知道用户已经要求停止，后续输入/边界按此处理 |
| RunControl.signal及登记的模型tasks | 正在运行的模型/工具共享信号；模型等待可被定向取消 |
| 图结果run_stopped | 图实际选择停止分支的结果，供应用确定stopped并保存 |

它们表达接纳、传播和执行结果的不同事实；需要时序一致的写入/读取合同，不按同名一律删除。多个检查点分别保护模型前、模型返回后、工具主体前及工具自身安全位置。

当前设计评价：保留明确停止入口、共享信号、模型取消、未执行结果配对及必要收尾；不新增事件驱动调度器。工具保护存在于observation命名模块，属于可读性/职责表达的候选调整，不能当纯通知代码删除；整体结构调整仍待逐场景评审后确认。

参考核对：Pi固定73f8de80的Agent.abort设置AbortController，循环/工具执行读取signal；DSH固定687f282e的ReactLoopAgent.cancel清理/保留Inbox后设置abort信号。它们同样需由循环和操作响应信号，不能据signal推断任意外部副作用立即回滚。AgentX本地3fcfa0e的interruptSession先标记interrupted再发送SSE；这条局部链不足以证明其所有工具都可取消，未作此推断。
