# 场景9：最后一次任务重新生成

日期：2026-10-20。基线：生产HEAD c5ca965及当前工作树。阶段：源码走读与设计复盘，无产品改造授权。关联[12组场景](十二组场景总览.md)、[Spec111第8节](../specs/111-remaining-conversation-features.md#8-仅最后一次任务重新生成)。

## 1. 问题与范围

只重做主会话最后一个reply任务，保留更早前缀，新结果成为后续对话基础。任务可包含多轮模型/工具、已送达Steering、跨审批run及子Agent；reply不是最后一条AIMessage，也不是run_id。

新任务按当前模型/思考、工具和权限规则正常执行，可能再次调用工具；不回滚文件，不复制旧工具批次或一次性许可。仍有效的session_allow按正常权限合同参与判断，不因重生成自动清空或升级。没有历史编辑、版本选择或子侧栏独立重做。

贯穿例子（全部为教学代号）：会话S1、当前thread TH0、revision=4；G1是早先任务，G2是末尾“生成报告并写文件”的任务。G2的write已把report.md写成v1并返回旧答复。重新生成从G2之前的上下文开始，只重发G2的人类输入；文件仍为v1，新模型若再次write，写入基于当前文件状态。

## 2. 权威对象与身份

| 身份/数据 | 来源与持久位置 | 实际用途 |
|---|---|---|
| request_id Q1 | 浏览器UUID，naiyue_regenerations按(session_id,request_id)唯一 | 防止同一重做请求再次执行；比较已存reply_id/revision |
| reply_id G2 | 人类输入标记；图响应携带；归档/边界表保存 | 标识整个末尾任务及其人类输入 |
| conversation_revision=4 | 会话行及SessionState，前端从会话视图取得 | 激活时递增到5，阻断旧界面请求/详情/分页及旧live视图 |
| source thread/checkpoint P0 | reply边界source_thread_id/source_checkpoint_id，服务端必要归档生产 | 取得目标任务之前的模型上下文；不由浏览器选择任意源点 |
| new_thread TH1、run R1 | 服务端UUID；重做动作表保存 | TH1准备候选，R1复用一次正常准入和执行寿命 |
| 新输入消息ID及新reply G3 | 服务端复制真实HumanMessage时uuid4及mark_human_messages生成 | 防止继承旧任务归属，正常图写入按同ID合并不重复输入 |

reply边界由collect_chat_updates从正式图历史收集：非Steering HumanMessage的reply标记、首次出现时parent checkpoint、归档input_sequence；save_boundaries必要保存。工具消息归属由拥有该调用的AI批次关联。较早归档迁移到TH1时保留source_thread_id/source_checkpoint_id，不能伪造成新thread产生。

## 3. 当前完整主链

```text
前端确认整任务重做/文件不回滚
  → POST regenerate {request_id,expected_reply_id,expected_conversation_revision}
  → WebService.regenerate：查持久动作或核对当前末尾身份
  → RunDelivery.regenerate/_launch：真实job、订阅与后台producer
  → AsyncPersistentApplication.aregenerate_last_reply
  → session_regeneration.regenerate
      → 查同Q1已存动作；核对G2/4后返回replayed，不执行
      → SessionService._admit(mode=message)取得新ActiveRun R1
      → 重读row/boundary，核对ready、revision4、末尾G2、无blocked
      → 取P0的prefix并校验无G2及工具配对无歧义
      → 从当前TH0归档查询G2所有HumanMessage，复制新ID/归属
      → 记录动作preparing，准备TH1的四次状态更新
      → 检查新快照无next/tasks、未请求停止
      → _commit_replacement：SQL激活事务 + 内存thread/revision更新
      → session.arun(inputs,run=R1)：正常模型/权限/工具/保存/释放
```

前端不提交新任务文本、thread或checkpoint。已有动作以S1/Q1查找，再比较G2及4；相同Q1改目标/修订返回request_id_conflict。新Q1要求仍是服务端last_reply且revision匹配，否则regeneration_stale。普通新消息可能改变末尾reply而不增加此修订，所以两项都要检查。

prefix来自边界P0；来源存在时读取并比较checkpoint ID，前缀不含G2，且_message_facts返回无缺配对/无歧义。无源checkpoint只允许归档input_sequence=1，否则拒绝，不按界面文本猜起点。图前缀可能已压缩；完整较早聊天仍靠归档迁移，不能用这份模型上下文替代完整聊天。

重发输入由归档的(session_id,current_thread,reply_id,message_type=human)按sequence查询，包含该组实际收到的人类消息。旧reply_id/input_kind剥离，消息ID更新，增加naiyue_input_source=regenerated_task，再统一标记新任务身份。旧AI回复/ToolMessage不随目标任务重发，未送达内存队列不伪造为历史。

## 4. 候选thread的四次写入

| 步骤 | 更新与结果 |
|---|---|
| 1 START | 在TH1写prefix，tool_execution={}、run_stopped=False、active_reply_id=None |
| 2 END | 清调度，取得只含prefix的安全锚点P_head |
| 3 START | 写入新ID的真实重发输入，形成P_input |
| 4 END | 清调度，取得包含输入的完成checkpoint P_seed |

这些aupdate_state不是模型/工具执行。P_head用于新归档同步head，使之后能收集P_head之后已保存的重发输入；P_seed用于会话激活指针。提前保存真实输入，避免激活后立刻退出时任务输入丢失。

后续正常arun仍传入相同inputs；LangGraph add_messages按消息ID合并/替换，不新增第二份。流观察baseline明确排除regenerated_task输入的ID，使已准备输入仍能作为本run消息正确交付。

当前准备完成检查是snapshot.next/tasks及run.stop_requested；不虚构逐字比较prefix/input的额外校验。准备期间TH0仍为当前分支；候选失败可能留下未激活checkpoint，当前不自动清理或执行它。

## 5. 激活是可见切换点

reply_storage.activate在BEGIN IMMEDIATE事务中再次检查row仍ready、thread为动作记录的TH0、revision仍4，然后：

1. 按G2的input_sequence删除被替换任务的旧可见归档和reply边界。
2. 将较早根消息/边界迁移到TH1，保留正文、消息ID、序号和真实来源。
3. 新chat_sync以P_head为锚点，更新归档修订/版本。
4. 保留较早任务仍引用的子档案，删除被替换尾部不再引用的子可见档案；不复用旧driver。
5. 会话行切TH1/P_seed，revision加1，state=running，run_id=R1；动作变activated。

随后session.activate_regenerated_thread以同一run对象身份核对，再改内存thread/revision。SQL事务只覆盖SQL操作，内存更新紧接其后由_commit_replacement协调，不把整个过程说成跨对象数据库事务。

可见切换发生在新模型执行之前，不是等待新答复成功再替换。旧框架checkpoint仍存在，不等于提供可切换的旧回答版本；旧尾部可见归档已经替换，文件未回滚，用量/诊断也不扣减已有消耗。

激活后直接复用session.arun，不再次公开arun重复准入。run_started此时才发布；四次候选准备和激活之前没有普通模型/工具事件。之后用正常事件交付新任务结果，必要保存更新动作最终状态；没有靠branch事件消费者切换分支。

## 6. 失败、停止、重试

| 分支 | 当前行为 |
|---|---|
| 旧目标/旧revision/源点不可用 | 拒绝；不选择其他任务，不调用模型 |
| 候选写入失败或激活前检测停止 | 标记已有动作prepare_failed，关闭窗口/释放占用；TH0及旧可见结果保持；不承诺清理候选残留 |
| 激活SQL失败 | 事务回滚可见归档/会话根，动作记录为准备失败；不运行模型 |
| 激活等待期间外部取消 | await_settled完成已开始的提交；通过activated或实际内存thread变化判定已切换，不仅依赖await后的布尔赋值；已切换则要求核对并保留新输入，后续按场景8恢复 |
| 激活后模型失败/停止/审批中断 | 新分支沿既有必要收尾与恢复处理；不自动切回旧结果，不隐瞒新副作用 |
| 重试相同Q1 | 返回同一动作/已有真实job；不再次启动模型。prepare_failed也不会因同Q1自动重做 |
| 重启后Q1动作在但job不在 | 返回持久动作status/replayed，不伪造可订阅run；新分支状态需要时沿原恢复入口处理 |

conversation_revision是实际一致性字段：新修订5拒绝旧修订4的普通发送和消息/思考/文件差异详情，旧live视图不混入新会话，旧分页版本也被拒绝。消息序号及消息revision可能在替换后重用，不能仅按序号取新内容给旧请求。

## 7. 代表性测试及证据边界

本轮仅阅读现有确定性测试，没有重跑或请求供应商：

- `test_activation_sql_failure_rolls_back_visible_tail_and_root`：临时库触发器在DELETE旧尾部时中止；断言旧thread/归档保持、busy释放、模型不新增调用、动作prepare_failed。
- `test_cancel_during_activation_settles_root_and_preserves_replay_input`：事件同步阻塞提交，再取消调用；断言提交结算后SQL/内存都指新thread，真实输入保留，重开按场景8整理，无旧任务自动重放。
- `tests/test_web_regeneration.py::test_repeated_write_uses_current_file_and_old_detail_scope_is_rejected`：fake模型驱动真实临时文件write两次，检查second覆盖当前first、差异为first→second、旧会话修订无法读取新详情；只证明受控文件场景，不证明任意外部副作用幂等。

## 8. 参考与设计评价

Pi固定73f8de80的AgentSession.navigateTree在选择user条目时把leaf移到parent并返回editorText；经SessionManager.branch/resetLeaf或branchWithSummary后_refreshFinalizedContext，用会话投影更新Agent消息。它支持用户历史树导航，不等于本项目末尾任务直接重做接口。本项目按已确认范围只维护一份当前可见结果，不增加版本选择，Pi树机制也不能回滚文件。

AgentX本机3fcfa0e本轮核对ConversationAppService.chat→prepareEnvironmentByRequestType→MessageHandlerFactory.getHandler→handler.chat的普通执行入口；未据此声称它具有相同末尾替换/激活协议，不拿普通chat链替代本项目的分支与保存合同。

当前保留必要边界、一次准入、候选准备后激活、持久动作去重与实际文件状态。可读性代价是regenerate函数跨归档、图维护、事务、内存和运行寿命，值得解释但未批准重构；不扩大Spec118范围。
