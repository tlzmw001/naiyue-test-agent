# 场景4：工具批次、串行并行与失败传播

日期：2026-10-20。阶段：源码走读与设计讨论，未实施产品修改。核对当前工作树、LangChain 1.4.2 / LangGraph 1.2.12；固定参考Pi 73f8de80、DeepSeek Harness 687f282e。示意ID/工具轨迹不是实际模型运行。

## 1. 本节先回答三个问题

1. 模型一次返回多个工具调用，谁决定可以同时执行还是必须等待？
2. 一个工具返回错误，为什么有时后续继续，有时运行失败？
3. 工具事件如何反映排队、结果和异常，它们是否调度下一项？

当前事实：普通叶子工具的ToolException、RuntimeError等可在反馈边界转成error ToolMessage，后续工具继续；不能泛称“一个工具失败就停止整批”。进入调度器捕获分支的异常才会把本批failed置True；计划缺失等错误也可在进入execute前直接阻断。

## 2. 数据与所有者

沿现有test_unexpected_error_does_not_fail_sequential_plan教学：一个probe工具被调用三次，label B时抛RuntimeError。为便于阅读，调用身份简称T1/T2/T3，实际测试用A/B/C作call_id。

```python
AIMessage(id='A1', content='', tool_calls=[
    {'id': 'T1', 'name': 'probe', 'args': {'label': 'A'}},
    {'id': 'T2', 'name': 'probe', 'args': {'label': 'B'}},
    {'id': 'T3', 'name': 'probe', 'args': {'label': 'C'}},
])
```

probe注册为execution_mode='sequential'且权限允许；权限决定和调度模式是不同字段。准备好的临时计划相当于：

```python
AsyncBatchPlan(
    call_ids=('T1', 'T2', 'T3'),
    sequential=True,
    run_id='R1',
    error_type=ToolBatchSchedulingError,
)
# position=0, failed=False
```

| 数据 | 所有者/生产者 | 用途 |
|---|---|---|
| ToolSpec.execution_mode | 注册工具的可信代码 | 声明工具可parallel或需sequential；不是模型自行决定 |
| tool_execution批次 | 图状态；权限/工具视图准备 | 保存调用、策略结果等可恢复事实 |
| AsyncBatchPlan | ToolBatchMiddleware在当前invocation context创建 | 临时执行次序、failed、Condition/Semaphore；不进checkpoint |
| ToolMessage.tool_call_id | 工具结果构造者 | 把每项结果配回原调用 |
| 事件与进度 | 工具分发/观察包装 | 提供显示与诊断，不负责position推进或释放名额 |

execution_mode和side_effects分开。当前调度器看execution_mode，不根据read_only/工具名字自动推导并发安全；ToolSpec默认parallel，因此注册声明必须负责。内置Read/Ls等用parallel，Write/Edit/Shell等显式sequential；Subagent声明parallel但副作用unknown，不能把parallel等同只读。

## 3. 完整主链与关键函数

```text
模型返回AIMessage及tool_calls
  → 响应门禁/权限准备/必要审批
  → ToolBatchMiddleware.aafter_model(state, runtime)
      → _registered_pending：取最后AI消息，排除已有ToolMessage配对调用
      → _modes：从工具定义读execution_mode
      → 在context['_naiyue_tool_batch_plan']安装新计划
  → 框架ToolNode._afunc为各调用创建协程并asyncio.gather
  → 每个调用进入工具wrapper
      → ToolSet选择工具
      → ToolBatchMiddleware.awrap_tool_call
          → aobserve_tool_dispatch：started及结果通知
          → _adispatch_tool_call
              → queued进度
              → AsyncBatchPlan.execute(call_id, name, guarded, limit)
                  → 等位置或并发名额
                  → guarded检查停止，未停止才进入下游
              → 单调用门禁/结算保护
              → ToolErrorMiddleware
              → ExecutionAuthorizationMiddleware
              → 工具主体
  → 各调用返回ToolMessage或传播异常
  → 正常批次由ToolNode按输入调用顺序组合结果，图合入消息
  → 普通循环进入下一模型边界；异常走应用失败/核对/必要收尾
```

`handler`是下游执行函数。把guarded作为execute参数，是先等调度条件，满足后再调用函数；不在等待前执行主体。序列化工具结果、状态更新和raise是不同出口。

本机ToolNode._afunc实际使用asyncio.gather，因此协程已创建不代表工具主体都已开始。本项目的Condition/Semaphore在各调用内部实施调度。普通批次结果按输入顺序收集；执行完成事件可能按真实完成次序出现。

## 4. 串行分支：position管放行

当前只要本批任一待执行工具声明sequential，整批顺序执行。

| 调用 | 在call_ids中的下标 | 放行条件 |
|---|---:|---|
| T1 | 0 | position==0 |
| T2 | 1 | position==1 |
| T3 | 2 | position==2 |

T2/T3可以先进入wrapper并等待Condition。T1下游返回结果后，计划把position从0增为1、notify_all；只有T2满足条件。T2返回后position增为2，再放行T3。

放行边界是下游调用链返回，不要求全部外层观察通知都已发布。事件订阅者不调用notify_all。每项进入执行前还检查停止；保护合同沿用停止场景，不重讲工具自身安全点。

串行表示次序，不自动表示“上一项成功才运行下一项”，也没有自动回滚。如果后一项依赖模型读取前一项结果后才能决定参数，应跨模型轮次决定；当前调度器不构造业务依赖图。

## 5. 并行分支：Semaphore管数量

所有待执行工具均parallel时，execute使用本批Semaphore(limit)。例如limit=2：T1/T2可重叠，T3等待名额；任一返回释放名额后，T3才可继续。

```text
时间 →
T1  [执行─────────]
T2  [执行──]
T3         [执行────]
```

图只表示允许的重叠，不承诺工具具体耗时或完成顺序。limit来自调用配置max_concurrency；它不是整个应用跨会话工具操作的全局上限。parallel允许重叠，不保证同步Python CPU任务获得多核加速，线程/协程取舍已在此前工具场景讨论。

## 6. 错误分支：返回错误消息与继续抛异常

### 6.1 普通叶子工具错误：形成结果后继续

```text
T2主体抛RuntimeError
  → ToolErrorMiddleware捕获普通Exception
  → tool_error_feedback返回安全错误文字
  → 官方middleware构造ToolMessage(status='error', tool_call_id='T2')
  → 下游正常返回这条消息
  → AsyncBatchPlan收到返回值，position递增；failed仍False
  → T3继续
```

结果是T1 success、T2 error、T3 success；下一次模型同时看到三份结果。普通RuntimeError/KeyError等用安全类型及通用说明，不把原异常正文直接展示；ToolException提供预期的公开错误内容。工具错误转反馈有诊断记录，不是空catch。

应用正常完成不等于每项工具成功，模型业务任务是否完成还需另外验证。当前反馈不会自动重试副作用。

### 6.2 机制异常：保留异常并阻止后续放行

例如PermissionMechanismError（许可错配）、ProcessCleanupError（进程清理结果不明）不会转换为普通反馈。ContextCompactionError/ModelResponseRejected/ToolBatchSchedulingError也在反馈保留规则中；但发生位置不同，不保证它们都先经过同一个plan异常分支。

```text
T2抛出不能转换的机制异常
  → tool_error_feedback返回None
  → ToolErrorMiddleware重新抛原异常
  → execute捕获handler的BaseException
      → failed=True；串行分支notify_all
      → 原异常继续抛向框架和应用
  → 等待调用若继续进入本批计划，看到failed就返回未执行反馈
```

failed路径不保证图最终提交每个等待项的合成结果；主异常可能使这一轮没有正常完整批次输出。上层SessionExecution._on_failure保留异常、检查部分工具结果/必要人工核对，再做收尾和保存。

并行时failed只阻止之后通过名额门禁的调用，不撤销已开始的兄弟调用，也不自动回滚。当前plan没有整个组的Task集合或all-settled屏障；不能仅凭plan代码声称所有已开始并行工具均先结算再释放会话。完整并行机制失败的拥有/结算需要作为独立验收边界核对，本轮未复现，不报告为已确认缺陷。

### 6.3 控制与更早的门禁

- 用户停止：guarded看到RunControl.requested时返回配对的未执行结果；这条正常返回自身不把failed置True。
- GraphBubbleUp/真实interrupt：官方ToolErrorMiddleware直接传播，不能转成工具正文；后续按框架控制语义处理，不统称run失败。
- 外部取消：保留CancelledError。串行Condition等待和handler取消被plan相应捕获时置failed；并行等待Semaphore的取消位于handler的try外，不假称所有取消路径都由此设置failed。
- 缺失计划、调用不在计划、重复/缺失ID等在相应入口拒绝；不能绕过调度。串行已完成调用重复进入会拒绝，这不是任意工具全局exactly-once承诺。
- subagent是委派编排入口，非ToolException异常保留；不把普通叶子RuntimeError反馈规则套给子执行系统故障。

## 7. 事件时点与结果身份

| 通知/结果 | 时点及含义 |
|---|---|
| tool_call_started(stage=dispatch) | 进入批次分发wrapper、尚未等位置/名额；主体可能还未启动 |
| tool_progress(activity=queued) | 等待调度前；可选观察 |
| tool_progress(activity=preparing) | 已通过调度、未停止，准备进入下游授权/执行；仍不是主体成功 |
| tool_call_finished(outcome=success) | 分发返回正常结果 |
| tool_call_finished(outcome=error_result) | 分发返回error ToolMessage，普通软错误可在此终结 |
| tool_call_finished(outcome=not_executed) | 停止、前置门禁、先前批次异常等未执行路径；结合reason判断 |
| tool_call_finished(outcome=exception/outcome_unknown) | Exception/CancelledError传播；当前ProcessCleanupError映射outcome_unknown；保留原异常 |
| ToolMessage.tool_call_id | 结果和原模型调用的配对键；图/TurnObserver依此识别结果，不由finished事件回填 |

GraphBubbleUp由分发观察包装直接传播，不强行补一个普通失败finished。没有新增tool_batch_started/finished事件；position、failed、释放名额由执行代码更新，不靠消费者。

## 8. Pi与DeepSeek Harness对照

### Pi固定73f8de80

`executeToolCalls`读取executionMode；配置强制sequential或有任一sequential工具，则executeToolCallsSequential，否则executeToolCallsParallel。串行for逐项await；工具主体普通异常在executePreparedToolCall转成isError结果，后续继续，停止信号另处理。并行先按顺序prepare，再Promise.all执行已准备项并按输入次序形成消息；这条固定实现未使用本项目的Semaphore限流。

因此，当前“出现串行项就整批串行”和普通工具错继续，与该Pi版本的主要规则相近；不据此推断权限、取消与持久化完全相同。

### DeepSeek Harness固定687f282e

`ReactLoopAgent`的工具阶段→executeToolCalls→runGroup→Tools staged prepare/dispatch/finalize。Tools.executionMode用工具的isConcurrencySafe(args)判断，精确true才并行；未声明/不可见/并发判定函数抛错等归exclusive。

它把exclusive作为屏障：前面的安全调用可以并行，全部结束后执行独占项，再处理后面的安全组。例如：

```text
调用顺序：readA readB writeC readD readE
本项目： A → B → C → D → E（本批有sequential）
DSH：    [A 与 B可并行] → C独占 → [D 与 E可并行]
```

DSH池有上限，并在后续调用开始前重新分类；prepare与结果提交保持顺序，主体dispatch可重叠。结果以tool/result追加session日志并关联已开始tool/call的序号。scheduler故障停止新分发、Promise.allSettled已开始dispatch后再抛；不能把它只当普通展示事件系统。

AgentX本地3fcfa0e旁查：TaskExecutionHandler.processEvent→逐子任务executeSubTask→AiServices构建/调用，以及BuiltInToolRegistry→ToolExecutor→provider.executeTools→doExecute。这里的应用子任务顺序不等同单次模型tool_calls调度，未证明同等批次并发合同，不直接类比。

## 9. 当前评价与待讨论项

建议保留工具注册模式、运行内计划、ID配对、并发上限，以及“普通反馈继续/机制错误保留”边界。它们分别有当前调用方和行为合同。

需要产品决定的有：混合批次是否升级exclusive屏障；哪些机制故障只阻断当前调用、哪些必须终止整批。单个failed汇合取消、机制异常等，语义表达可进一步细化；不因此立即新增通用策略平台。

验收还应明确并行机制失败后所有已开始工作如何结算、何时可释放会话。DSH把组结算放在调度拥有者，本项目不能把本地Semaphore/工具shield直接等同这一组级保证。没有故障复现前不自动宣称bug或实施修复。
