# 场景11：运行准入、必要收尾与保存

日期：2026-10-20；生产源码HEAD `c5ca965`。学习复盘，仅维护课堂文档。已讲解，用户独立调试/实现未评估；测试只读，未重跑，无真实供应商请求。Spec118/119保持各自草案范围。

## 1. 问题与具体对象

贯穿例子：用户要求运行登录测试并把结论写到reports/login.md。模型/工具循环结束，文件可能已写、最终AI也已提交，但父应用还要确认子工作、关闭控制窗口、归档真实历史并保存会话结果，然后才释放本次运行。文件副作用、图checkpoint、应用元数据/聊天归档不是一个总事务。

示意会话S的长期事实：`SessionState(thread_id='T0', model_id='M', workspace_root=..., active_tool_names=(...), permission_mode='Default', pending_tool_approval=None, manual_review_required=False, ...)`。空闲时`AgentSession._run=None`，busy由这个事实计算，不是一个需单独置False的字段。

准入后：`ActiveRun(run_id='R1', observation=O1, controls_open=True, steering_open=True, stop_requested=False, subagent_instances={}, ...)`，保留至必要收尾结束。O1初始stage=prepare/status=completed是默认值，不是完成确认。持久行原state=ready、checkpoint_id=P0；运行开始另写state=running/run_id=R1。

| 对象/层 | 权威事实与职责 |
| --- | --- |
| AsyncApplication | 应用是否open、已接受操作完成信号、自己创建的stream producer、关闭共享资源 |
| SessionService | 会话注册、跨会话准入锁、max_active_runs总名额；不维护第二份_active_runs表 |
| AgentSession / ActiveRun | 单会话互斥、当前run对象、控制窗口、子工作、人工核对标志 |
| SessionExecution | prepare→execute→finalize，失败分类、受保护的必要收尾及返回/异常 |
| RunObservation | 当前仍保存status/stage/failure及RunControl，同时发布观察；不是纯可选订阅者 |
| LangGraph / saver | messages、调度、interrupt与执行checkpoint；持久路径durability=sync |
| SessionPersistence | _active[S]=R1所有权、_blocked、历史锁、收尾状态及确认/归档协调 |
| SessionStorage | SQLite元数据/聊天事务、聊天sync修订校验；不是模型/工具执行者 |

## 2. 完整主链与准入

```text
AsyncApplication.arun → _owned_operation / _execute
 → SessionService.arun → validate_tool_concurrency → _admit
 → AgentSession.admit_run → 安装ActiveRun（busy/名额从这里占用）
 → SessionExecution.arun
   → run_started
   → Persistence.start：预留_active，再mark_running
   → 准备/冻结项目提示词与资源，标记实际人类输入
   → 图执行（模型/工具/控制）
   → result或_on_failure
   → finally await_settled(_afinish_run)
       → 必要时请求根/子停止
       → settle_subagent_drivers / assert_subagents_settled
       → close_control_window
       → Persistence.afinish
           → 用量flush（普通异常允许降级）
           → 计算持久state，必要时确认最终checkpoint
           → collect_chat_updates
           → Storage.finish_run事务
       → 满足条件才release_run
       → run_finished
 → arun真正返回结果或抛错，应用操作完成信号释放
```

_admit持Service锁查会话，生成/接收R1，创建观察器，统计`sum(actor.is_busy()) < max_active_runs`并调用该会话admit_run。会话锁内依次检查expected_conversation_revision、manual_review、根pending与mode是否允许、已有_run、审批决定与remember内容、容量；通过后才安装ActiveRun。创建观察器不等于发布start。

同会话重复运行、根待审时普通消息、人工核对标志、过期conversation_revision、满容量均可拒绝；准入拒绝不进入SessionExecution，不为它发送run_started，不写运行输入/数据库running。不是排队机制。手动压缩同样占根名额；live子依附父名额。`approval_resume + stop=True`可绕过总容量，但仍核对该会话可恢复/无活动run等条件，服务已有待审停止。

准入与实际准备分开。持久start在锁内先检查_active/_recovering/_blocked并登记S→R1，锁外mark_running；数据库失败时仅在_active[S]仍等于R1时撤销该owner。_blocked是在此入口阻断必要持久运行，不应误写为AgentSession.admit_run也检查了这个集合；Web还会提前使用can_run。

run_started在mark_running和资源准备之前发布，表示本次已准入运行进入应用执行，不能证明数据库running写入完成、模型开始或工具执行。准备失败仍走失败/必要收尾。持久start本身失败且owner已撤回时，afinish看到_active不匹配直接返回，避免假装保存另一次运行。

## 3. 图返回、业务结果和会话状态

SessionExecution正常取得result后置stage=finalize；提取并保存根pending/必要时发布approval_requested；observation.result优先pending→interrupted，其次run_stopped=True→stopped，否则completed。即使已经return result，Python仍先执行finally里的await_settled(_afinish_run)，调用者尚未拿到返回值。

普通工具错误若已经转ToolMessage，图仍可completed；这不是测试业务全部成功。手动压缩的operation failed也可由维护run正常completed，沿场景7，不在此重定义。

失败时先保存primary_error，同一异常随后继续raise。_on_failure做运行失败描述，并对普通Exception检查部分图：若固定pre-tool审批可证明则不因它认定副作用未知；否则取最后AI调用ID与后续ToolMessage ID之差。有未配对调用、图读取不能确认、ProcessCleanupError、执行阶段CancelledError或手动压缩提交不确定等，设置manual_review_required并清根pending。这个检查不是验证外部工具效果；只读到配对也不构成业务效果证明。

| 当前运行结果 | 必要保存成功后的持久state | 可用性 |
| --- | --- | --- |
| completed | ready | 释放后通常允许新请求 |
| stopped（正常停止） | ready | 确认图安全结束后可继续；last_run_status仍stopped |
| interrupted（根审批） | interrupted | busy释放，但pending禁止普通新消息，等待批准/拒绝/停止 |
| failed、无人工核对标志 | failed | 当前已加载会话不必一律禁止新run；重启恢复按场景8分类 |
| 任意结果且manual_review_required | review_required | 标志优先，禁止自动继续 |
| 必要保存失败 | 原行可能仍running；_blocked加入S | 可释放本次busy，但can_run=False，不冒充ready |

RunObservation仍是必要状态来源：afinish直接读取其status选持久state。删掉普通事件订阅不影响这个调用；删除观察对象本身会破坏现有执行/保存合同。正式结果与观察职责混合是既有待讨论项，未批准本轮重构。

## 4. 必要收尾与busy释放

_afinish_run先在primary存在时request_scope_stop(reason=failure)，等待拥有的子driver并assert。assert要求settled、无driver/approval且状态是completed/stopped/failed；此后才移除实例，沿场景10。再close_control_window：保留必要pending_turn投影、清未消费队列、关闭控制观察、controls_open/steering_open=False、清run停止标记及prompt资源。

**窗口关闭不是释放。** _run仍是R1的ActiveRun，因此保存中的会话依旧busy，也计入根容量。

release_run在必要持久收尾之后；要求controls_open=False且实例表空，方法内部再次_require_run校验。最后设置_run=None。MCP occupied标志改为“是否仍根待审批”：根待审批虽不占活动根名额，连接仍可受审批占用保护，不要求每个run结束立刻关闭根MCP连接。

若子工作或控制窗口不能确认结算，当前条件不满足就不释放；不保证任意failed终局都意味着busy=False。既有未结算句柄单测只验证release保护，不将未复现的组合故障认定为bug。

身份校验必须分层：

| 校验 | 具体比较与限制 |
| --- | --- |
| 当前run | `_run is run`比较对象身份；旧对象即使run_id字符串与新对象相同，也不能关窗/释放新run |
| 持久owner | `_active.get(S) == R1`，不匹配的afinish返回；不是DB层同一CAS |
| 图范围 | 当前session.thread_id=T0；ChatUpdate读取还核对snapshot.config.thread_id=T0且checkpoint_ns为空 |
| 聊天归档修订 | 候选expected_revision=7与该(S,T0,namespace)的chat_sync.revision=7比较；不符拒绝；成功改8 |
| 会话分支修订 | conversation_revision用于旧UI/重新生成防串，不等于chat_sync修订，不在正常run中每次递增 |

Storage.finish_run的最终会话UPDATE按session_id，没有额外WHERE run_id=R1的CAS；归属由上层当前run和_active合同保护。持久行run_id也未在finish_run清空，保留最近运行身份；公开busy/run_id由已加载Actor覆盖，不能以数据库run_id非空判断仍在运行。

## 5. 保存什么、什么时候提交

持久应用工厂用官方AsyncSqliteSaver，同一文件中另有应用SessionStorage；它们不是把全部图IO包进finish_run同一个事务。当前LangGraph1.2.12的astream在sync模式每步等待_put_checkpoint_fut；它保证图步骤持久顺序，不原子提交文件/远端效果与图/应用历史。

afinish持该会话history lock，确认_active后先flush本run用量。其普通异常诊断后降级；自动标题也失败只记录。它们被await不等于成功与否属于必要运行完成条件。

计算state后，从原行取已确认checkpoint P0。仅state=ready时读取T0最新snapshot，要求checkpoint_id=P1存在、next为空、所有task无interrupt/error，才将确认指针推进P1。interrupted/failed/review_required保留原确认指针，但仍收集最新真实图历史；“不推进可安全恢复指针”不等于删除失败/审批过程或回滚图。

collect_chat_updates沿当前checkpoint祖先链从旧chat_sync head增量收集，忽略其他分支；消息必须BaseMessage且有非空唯一ID。构造ChatUpdate(thread_id,namespace,agent_path,expected_revision,checkpoint_id,messages,stopped,boundaries)。父真实subagent调用推导子thread并收集子历史。此函数返回候选，不直接提交聊天库，普通事件不是归档来源。

Storage.finish_run在`BEGIN IMMEDIATE`事务内读取会话、比较归档expected_revision、写根/子消息与sync heads/reply边界、更新适用的重新生成动作结果、更新会话state/checkpoint/last_run_status。消息以ID定位、hash比较和必要修订，避免重复添加。SQL失败事务回滚；此前图checkpoint、文件写入或远端工具效果不会因此回滚。

必要保存失败：_blocked.add(S)，抛SessionPersistenceError('session_save_unconfirmed')；finally撤销持久_active owner。根收尾随后在条件允许时释放Actor，不占住已无工作的一次执行；状态API结合_blocked、数据库state、busy、manual_review、pending给出can_run=False。移除_blocked不是本轮提供的恢复操作，继续按场景8正式入口分类处理。

## 6. 异常优先级和取消

| 主执行 | 收尾 | 向调用者报告 |
| --- | --- | --- |
| 成功 | 正常 | 原result |
| 原异常E | 正常 | 同一个E对象 |
| 原异常E | 普通清理/保存异常 | 同一个E；次要失败另记，保存失败仍标_blocked |
| 成功 | 必要清理异常 | 清理异常；其后的普通保存异常不覆盖它 |
| 成功 | 必要保存异常 | SessionPersistenceError，cause保留底层保存故障 |
| 普通观察订阅异常 | 执行/保存正常 | 诊断并隔离观察，不改成功或原异常 |

这是当前普通Exception/明确取消路径的合同；GraphBubbleUp和其他控制BaseException不硬造普通失败事件。

await_settled先ensure_future实际操作，shield等待；外层取消先记住，再继续等待；操作结算后重抛原取消。run_blocking用同样保护等待to_thread实际worker，不能释放busy后让数据库线程仍写。若等待期间操作也失败，有已记录取消则记录drained_operation_failed并保留取消，操作自身已执行的错误处理仍有效。

取消时点分开：执行阶段取消进入_on_failure，status=failed并人工核对；到受保护的_afinish_run保存中才取消，内层收尾不因此重新分类。原执行completed、保存成功时，可以先保存ready/释放/发completed，再让外层调用者收到CancelledError。组合测试的[cancel]明确断言这组结果，不能只见调用者取消就改写为“模型任务一定失败”。

## 7. 事件、调用返回与关闭

事件外层`{session_id:S,run_id:R1,sequence:N,...}`；根source=None。run_started数据mode=message/approval_resume/compact；run_finished数据status/stop_mode/manual_review_required/failure。无主异常的保存失败例：status=failed、failure.stage=finalize、category=persistence_error、reason=session_save_unconfirmed。有主执行异常时保留原失败描述，次要保存故障不替换它。

| 时点 | 已发生/未发生 |
| --- | --- |
| admit完成 | _run已安装，尚无run_started/mark_running/模型请求 |
| run_started | 准入通过，尚未确认mark_running/准备成功 |
| 图返回与turn/control结果通知 | 图结果已取得，子结算/保存/busy释放未全部完成；不新增graph_returned事件 |
| 根run_finished正常完成路径 | 必要收尾已尝试且结果已归类；普通成功路径在保存/释放后，失败需结合failure/manual_review/can_run |
| arun实际返回/抛错 | finally已走完；事件可能投递失败，不以收到终局作为唯一事实来源 |

CLI/Web按终局投影状态，诊断writer记安全字段；必要保存不靠订阅run_finished执行。Web producer在await应用返回后还要结算自己的job/receipt，App _owned_operation完成信号也在操作退出时才解除。busy=False不代表浏览器已收到所有帧、diagnostic缓冲全部落盘或共享模型资源已关闭。交付细节留场景12。

应用close拒绝新外部操作，请求停止已加载会话，先关闭/结算MCP资源，再等已接纳操作完成信号与自己创建的producer，之后关catalog；持久子类关用量/诊断writer，工厂退出saver并关storage。它等操作作用域，不等待同一调用者之后的无关工作。应用关闭不在本节重新展开场景2。
