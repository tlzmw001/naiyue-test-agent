# 场景1：插话的状态、事件与循环边界

日期：2026-10-20。阶段：设计讨论；本文建议尚未成为获批实现Spec。本轮只更新讨论文档，未修改生产代码；工作区另有其他会话的并行改动。

参考固定版本：DeepSeek Harness `687f282e8625c6b8d11ff58211a90524be2e4317`；Pi `73f8de80bc87021375f8b525292ac07492253002`。参考代码核对是静态证据，没有运行这两个项目的恢复测试或真实模型。

## 1. 当前判断：保留内存队列，先确认承诺再选择机制

用户指出未要求插话跨服务重启保留，认为内存队列已经适合当前场景。重新评估后的建议：保留现有内存队列与两个输入边界，不将持久Inbox列为当前改造要求。本文第5—6节保留上一轮增强方案及其代价，仅供将来需求变化时查考。

上一轮建议把“已接纳输入跨重启可恢复”当成了目标，进而推导出必要保存、交付凭据和两份存储对账；这个前提未经确认。DSH有相关机制、历史消息需要保存、项目追求生产级，都不足以单独证明我们也需要持久化待处理插话。

- Steering：最近一次允许接入输入的模型边界，延续当前回复。
- Follow-up：当前任务自然结束后，FIFO开始下一条回复；同一个run可以接着执行。
- Steering不隐含取消正在进行的模型请求或工具，也不追溯改变已经冻结的请求。
- 当前接纳表示进入活动执行的内存队列，不承诺服务崩溃/重启后仍保留未消费输入；历史消息的持久化与待办接纳是分别选择的合同。
- 正常运行的顺序/归属/窗口竞争必须正确；运行失败时清理待办，不能仅凭这一点判定为丢消息缺陷，需要对照已承诺的异常合同。

决策顺序：实际场景 → 对用户的正常/异常承诺 → 必须保持的规则 → 关键质量目标与约束 → 比较完整方案及长期代价 → 接受的限制 → 重新决策的触发条件。理想设计应完整满足已选目标；增加保证需要独立理由，不能用机制反推需求。

只有明确要求排队输入跨重启保留、外部提交后必须可靠处理，或实际使用反复证明当前丢失边界不可接受时，才重新讨论持久接纳。参考项目用来发现候选与代价，不能替代本项目需求；可读性调整也不自动要求增强恢复保证。

讨论阶段不例行重跑已有测试。只有明确行为疑问需要实验、修改代码或进入验收时再选择必要验证；下面保留的测试结果是上一轮证据。

## 2. 先把输入数据和三个确认时点分开

示意任务：“修复登录测试”，当前回复`r1`、执行`run1`。用户在工具执行时补充：

```text
u1: steering，“先不要修改生产代码” → 关联r1
u2: follow_up，“完成后再解释失败原因” → 预分配新的回复身份r2
```

本例用稳定input/message身份、模式、内容和回复归属表达输入；不由这些字段推导必须入库。下面区分确认时点，并注明持久方案额外承诺的部分。

| 时点 | 能保证什么 | 不能据此声称什么 |
|---|---|---|
| 接纳完成 | 输入及其模式/目标已被活动会话接受；只有选择持久接纳合同才要求此时入库 | 当前模型请求已经看到、服务重启后必然保留 |
| 图提交完成 | 对应HumanMessage已进入图；持久运行由checkpoint提供保存，新增独立交付凭据属于增强方案 | 远端模型已收到、已经理解/遵守 |
| 请求发出 | 此输入确实在该次冻结请求中 | 模型成功响应、任务已经完成 |

“取出队列”不等于进入模型上下文。当前故障时可以按约定终止并清理待办；若另选可靠接纳合同，才需要额外保存副本直到确认。界面若使用“已生效”，必须说明指进入上下文还是进入某次请求；不要混称“已交付”。

## 3. DeepSeek Harness的类与层级

### 3.1 这是组合关系，不是逐层继承

```text
Cordis Context：服务装配/作用域
  ├─ ctx.agents → AgentRegistry：创建、恢复、管理AgentHandle
  │                  └─ AgentFactory由AgentLoop注册
  │                       └─ ReactLoopAgent：一个会话的实际循环驱动
  │                            └─ ReactLoopInbox：待处理输入命令接口
  ├─ ctx.sessions → SessionStore：管理Session实例
  │                  └─ Session：顺序事件日志 + 可见消息表面
  ├─ ctx.sessionProjections：日志折叠成inbox等当前读视图
  └─ ctx.sessionPersistence → 后端：存储日志、flush、恢复
```

| 对象 | 主要职责/接口 | 本场景消费的数据 |
|---|---|---|
| AgentRegistry | `create/resume`通过已注册factory生成AgentHandle | 会话身份、Agent选项；不是模型循环 |
| AgentLoop | 注册factory、turnBoundary/inbox投影；创建/恢复具体Agent | Session、模型/工具/提示词服务 |
| ReactLoopAgent | `send(message, target, wakeup)`、`steer/followup/inject`、`turn/preStep/step` | 待处理输入、当前phase、模型与工具结果 |
| ReactLoopInbox | `splice/append/remove/claim`等命令接口 | 两个列表：`next-step`和`next-turn` |
| Session | `append(type, data, opts)`校验/快照/分配seq并提交日志 | 已发生的会话事实；部分事实进入模型消息表面 |
| SessionProjectionRegistry | 把已提交日志折叠成当前状态 | `agent/inbox/spliced`还原两个待办列表 |
| SessionPersistence及后端 | 读写已提交日志，`flush`提供持久性屏障 | 可序列化SessionEvent，不另造第二套持久事件类型 |

`Agent`是接口，`ReactLoopAgent`是具体实现；`AgentLoop`虽然名字像循环，本身主要是创建/恢复服务。本项目不需要照搬Cordis容器才能实现这些职责。

源码：[AgentRegistry](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/core/agent/src/index.ts)、[AgentLoop](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/core/agent-loop/src/index.ts)、[Session](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/core/session/src/index.ts)。

### 3.2 三类机制，不能只按事件名判断

| 类别 | 本场景例子 | 是否影响执行 |
|---|---|---|
| SessionEvent：可恢复事实 | `agent/inbox/spliced`、`user/message` | 日志/投影是队列和历史事实，后续循环会读取 |
| Agent普通实时通知 | `agent/inbox/inserted/claimed/discarded`、`agent/status` | 通知观察者；本身不是“再调用模型”命令 |
| 能力扩展点 | `agent/pre-step` waterfall返回enter/reject；`agent/turn-stopping`串行等待 | 参与主控制链，返回值/等待期间的必要动作有执行语义 |

`agent/inbox/spliced`虽然以`agent/`开头，却属于持久日志；不能按前缀划分。`agent/pre-step`虽叫事件，实际类似可返回决定的middleware hook。持久化需求回答“哪些事实恢复后还需要”，控制语义回答“谁有权决定下一步”，是两条独立轴。

### 3.3 Steering的真实链路

```text
ReactLoopAgent.steer(message)
  → send(message, 'next-step', true)
  → inbox.splice(target, Infinity, 0, [message])
  → Session.append('agent/inbox/spliced', 插入描述)
  → inbox投影反映变化
  → emit('agent/inbox/inserted', {message})
  → wakeDriver（已运行则由现有driver读取；空闲可启动）

ReactLoopAgent.turn()
  → preStep(target, {turn,step})
  → inbox.claim(target, turn)：提交删除splice，再发claimed通知
  → 提示词组装 + agent/pre-step → enter/reject
  → enter时step() → prepareRequest()
  → Session.append('user/message', message, {surfaceOp:'append'})
  → buildRequest() → 模型流 → 工具执行/结果
  → 按结果、next-step待办和turn-stopping后的复核继续/结束
```

首个step会取全部next-step及一个next-turn；后续step只取next-step。一个turn结束后还有待办，driver再开下一个turn。`steer`/`followup`会唤醒，`inject`不会；我们的当前入口只接纳活动run，不需要自动继承其空闲唤醒行为。

注意术语：DSH的step大致是一次模型调用及其工具；turn可跨多个step。不能把它的turn直接等同本项目TurnObserver定义。

源码：[循环实现](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/core/agent-loop/src/agent.ts)、[Inbox](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/core/agent-loop/src/inbox.ts)。

### 3.4 两个必须看清的保证边界

1. **日志提交不等于落盘完成**：Session.append是同步内存提交/通知；后端可批量写入，flush才是持久性屏障。`session-checkpoint-policy`在模型stream、顶层工具执行以及pre-step边界等待flush；保存失败时不进入对应外部调用。它是必要操作的显式等待，不是可丢失的UI通知。
2. **claim不等于进入模型历史**：此版本claim先提交队列删除，之后才执行pre-step和user/message提交。若中间失败/被拒绝，不能仅凭claimed认为已交付，也不能由“持久Inbox”推导零丢失或恰好一次。`agent/inbox/claimed`接口注释明确：拒绝的proposed step不产生user/message。`steer`另有“reject仍parked”的注释，与当前claim路径不一致；这里以实现和claimed合同为准。

第一点来源：[持久化合同](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/docs/subsystems/persistence.md)、[checkpoint策略代码](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/session/session-checkpoint-policy/src/index.ts)。第二点是基于固定源码顺序的边界分析，未做DSH崩溃注入；接口注释见[runtime-types](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/core/agent/src/runtime-types.ts)。

## 4. Pi与本项目对照

### 4.1 Pi实际拥有者

`Agent`拥有两个内存PendingMessageQueue；`steer/followUp`入队，`agentLoop`用`getSteeringMessages/getFollowUpMessages`取出。工具结果合入后检查steering，只有内层自然停止才取follow-up。支持one-at-a-time/all，当前默认one-at-a-time。

## 5. 未采纳的增强方案：持久接纳的职责与链路

本节以“已接纳待办必须跨重启保留”为额外前提，记录上一轮方案分析；当前不推进，不是现有实现的缺陷清单。

### 5.1 谁拥有哪份事实

| 当前对象/职责 | 建议职责 | 不该承担 |
|---|---|---|
| AsyncApplication / Web / CLI | 校验入口、提交模式/目标/幂等身份、返回接纳回执 | 各自维护另一份业务队列 |
| AgentSession | 接纳/顺序/回复归属/关闭窗口；在会话内串行化并发操作 | 由UI消费者反向决定图路由 |
| 现有持久化边界 | 保存待办和最终处置，查幂等身份 | 通过可禁用observer执行必要保存 |
| SessionPort + runtime边界 | 按阶段请求输入决定；把消息/交付凭据提交图 | 看到input_accepted事件就直接重入模型 |
| LangGraph/checkpointer | 提交messages/active_reply_id及必要交付凭据 | 反推尚未进入图的用户待办 |
| 观察/前端投影 | 显示pending/进入上下文/失败等已确定状态 | 将“通知收到了”当成可靠保存或模型理解 |

不要求新增以上每个名词对应的类；优先在现有所有者中表达。建议用现有SQLite持久化边界保存输入记录，不再为同一份模型历史建立第二套完整事件溯源系统。借鉴DSH“重要事实可恢复”，不要求所有正式事实都必须通过公共event bus写入。

### 5.2 正常例子：工具执行时插话

1. Web/CLI提交u1和稳定幂等身份。会话校验活动执行代次、接纳窗口、模式，生成/确认稳定message_id。
2. 必要保存成功后才返回accepted；失败明确返回错误。等待IO不持有会被runtime同步回调获取的线程锁；接纳与关窗口须有同一串行化机制，保存中请求不能被当成不存在。
3. 可选通知使界面显示“待处理”；通知失败不撤销已保存输入。
4. 当前工具批次按既有权限/停止规则结算并配对ToolMessage。Steering本身不打断主体。
5. 下一模型边界选择u1并临时预留；构造HumanMessage(message_id=u1的稳定身份，reply_id=r1)。u2仍待办。
6. 图将HumanMessage、active_reply_id和交付凭据一起提交；等待必要checkpoint写入确认，再结算待办。观察到values不足以代替持久确认。
7. 当前请求冻结时包含u1，再调用模型。若随后模型失败，仍保留“已进入上下文但调用失败”的事实；不能重新显示为从未接纳。
8. 当前任务自然结束，优先复核steering；没有steering才选一个follow-up u2，以预先稳定的新回复身份r2开始下一回复。全空则原子关闭窗口，再进入应用必要收尾。

本项目持久运行已经传`durability='sync'`，但新增交付确认仍需验证“hook更新已保存且下一外部操作未开始”的具体框架切点，不能直接以stream values替代。LangGraph官方将sync定义为下一步开始前持久保存：[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)。

### 5.3 两份存储的崩溃窗口

待办存储与LangGraph checkpoint即使都用SQLite，也不自动共享一次事务。建议通过稳定输入/批次身份及checkpoint交付凭据对账，不声称跨库恰好一次。

| 崩溃/失败时点 | 建议恢复行为 |
|---|---|
| 输入保存之前 | 不确认accepted；同幂等身份重试不能生成两个输入 |
| 已保存，尚未选取 | 重开可见未处理输入，等待用户继续/处置 |
| 已选取，图尚未提交 | 原始待办仍在；释放失效预留，不自动触发执行 |
| 图已持久提交，待办结算未保存 | 从checkpoint凭据确认已进入图，修复待办状态，不重复注入/重放执行 |
| 模型请求已发，响应未确认 | 只能确认本地发起；远端接收/计费及副作用按实际证据标未知 |
| checkpoint/必要保存不可读 | 明确阻断自动继续并报告；不能猜测为未投递后重新运行 |

凭据需独立于可被compaction删除/替换的消息正文，并保留到对账完成；不能只在最新messages里搜id。输入还须绑定图分支/执行代次，避免重新生成或重启后误投到另一任务。具体字段、提交切点和回收策略留实施Spec验证。

### 5.4 并发与终止建议

| 条件 | 建议行为 |
|---|---|
| 模型请求已开始时插话 | 不修改已冻结请求，下一个允许边界才接入 |
| 工具执行中插话 | 当前批次按合同结算，下一模型边界消费 |
| 自然结束和入队竞争 | 同一所有者决定先后；先accepted必须被消费或明确保留/处置；先关窗口则明确拒绝旧run输入 |
| 多个steering | 保持FIFO、当前边界取全部；过大输入按请求预算处理，不悄悄截断 |
| 多个follow-up | FIFO一次一条；不在工具后抢占当前任务 |
| 用户停止 | 不再选输入；保留未处理文本并标记取消/待重发，不自动跨run运行 |
| 运行失败/服务重启 | 保留记录和已知交付位置，未处理输入待用户确认；不自动唤醒未知副作用 |
| 已结束/已暂停审批且无活动run | 保持明确入口限制；是否允许排队到暂停任务属于另一个产品决定，不能从DSH行为直接继承 |

“保留未处理文本”与当前故障时丢弃队列不同，是本次建议的产品语义变化，不是已实现。

## 6. 选择持久接纳合同后，哪些需保存、哪些只需通知

| 事实/动作 | 持久入口所需 | 执行方式 |
|---|---|---|
| 已接纳输入、模式、顺序、目标 | 必须保存 | 显式必要写入，成功后才确认接纳 |
| 消息进入图及交付凭据 | 必须保存 | 图状态/checkpoint提交 |
| 输入已取消/已处理/尚待确认 | 保存终态或足够恢复的事实 | 所有者显式处置，支持重开查询 |
| 正在选取/界面转圈/队列数量 | 通常可从状态重建 | 过程通知可内存、可合并 |
| SSE连接/重连与前端刷新 | 非业务持久事实 | 通知及快照恢复，不决定模型循环 |
| 是否继续当前回复/开启follow-up | 是执行决定，不是观察通知 | 边界方法返回决定；runtime映射messages/路由 |

数据是否可丢与函数是否async不是同一分类：必要保存通常需要await IO；轻量通知可以同步发送。必要持久写入不能包在会吞掉普通观察错误的observe里。

## 8. 通俗走读：工具执行中又收到两句话

### 8.1 一个具体任务

以下文本、文件及缩短ID是教学示意；调用顺序依据本轮读取的当前代码，不是本轮模型运行轨迹。

- 原任务：“读取tests/test_login.py，说明当前测试覆盖了什么。”
- Agent已让read工具读文件，当前run是run1，回复身份是reply_a。
- 用户用steering补充：“重点分析缺少哪些失败场景。”
- 用户再用follow-up排队：“分析完后，再整理成测试清单。”

队列就是按约定次序暂存待处理内容的容器；边界就是程序约定检查这些内容的时点。图在这里指负责安排模型、工具及下一步的调度程序。

### 8.2 谁接收、谁暂存

```text
POST /api/runs/run1/controls
  → RunDelivery.control(run1, body)
  → AsyncApplication.steer(session_id, text)
  → SessionService.require(session_id)：找到该会话对象
  → AgentSession.steer(text)：检查本次运行是否仍接纳输入
  → self._run.steering_queue.append(QueuedInput(...))
```

follow-up走同样入口选择follow_up方法，写另一个队列。入队后的示意数据：

```python
steering_queue = [
    QueuedInput(message_id="m2", text="重点分析缺少哪些失败场景。", kind="steering")
]
follow_up_queue = [
    QueuedInput(message_id="m3", text="分析完后，再整理成测试清单。", kind="follow_up")
]
```

实际容器是deque。QueuedInput只有message_id/text/kind三个字段，尚不是发给模型的HumanMessage。这里的“保存”是保存在运行内存，未消费输入没有新增落盘承诺。

AgentSession.steer的方法定义在AgentSessionControls，AgentSession继承其方法；执行时self仍是同一个AgentSession，没有额外创建控制对象。ActiveRun是它的_run，暂存只属于本次运行的数据。区分文件拆分与运行时对象，有助于避免把多个文件误看成多层业务服务。

入口检查两件事：Web目标run必须仍是当前活动job；会话接纳窗口必须仍开放。后者可在busy释放之前关闭，因此两项检查不是同一时点的重复判断。当前任务已经结束/窗口关闭则明确拒绝。

### 8.3 下一次模型前，谁把steering取出来

read结果先成为ToolMessage并进入图。运行图随后经过已注册的模型前检查函数：

```text
inject_before_model(state, runtime)
  → SessionPort.drain_steering(session_id)
      → 实际由SessionService按session_id找到AgentSession
      → AgentSession.drain_steering()取出全部steering并清空队列
  → prepare_control_messages(...)把QueuedInput变为HumanMessage
  → 返回messages和active_reply_id
  → LangGraph合入状态，继续既有模型前置/请求流程
```

SessionPort是一份runtime允许调用的会话操作清单；生产对象由应用提供，并非每次调用都创建一个新的Port对象。runtime通过这份窄接口询问/请求会话操作，不拿整个会话任意读写。

准备出的消息示意：

```python
HumanMessage(
    id="m2",
    content="重点分析缺少哪些失败场景。",
    additional_kwargs={
        "naiyue_human_input": True,
        "naiyue_input_kind": "steering",
        "naiyue_reply_id": "reply_a",
    },
)
```

HumanMessage表示人类输入；reply_id是回复归属标记，帮助界面和任务操作知道它仍属于当前回复，不是又启动了一个run。

模型前函数返回的关键数据是：

```python
{"messages": [prepared_message], "active_reply_id": "reply_a"}
```

图按返回值更新messages，既有请求装配再把消息转换为供应商输入。工具后本来就有下一次模型处理；此处只是加入补充输入，不需要靠事件消费者再调用模型。已经发出的请求不会被这次入队追溯修改。

### 8.4 当前分析结束，follow-up怎样继续

假设模型完成当前分析，且没有还需执行的工具，运行图会经过inject_at_natural_end。名字中的after_agent是框架注册时点，此时仍可继续，应用保存/释放尚未完成。

```text
inject_at_natural_end
  → finish_run_boundary()
      1. 已停止：不再选输入
      2. steering非空：先取全部steering，保持当前回复
      3. 否则follow-up非空：取最早的一条
      4. 否则：关闭接纳窗口，允许结束
  → prepare_control_messages(...)
  → 返回messages、active_reply_id及jump_to="model"
```

本例取出m3时才生成新的reply身份reply_b，并更新run.reply_id；run_id仍是run1。返回示意：

```python
{"messages": [follow_up_message], "active_reply_id": "reply_b", "jump_to": "model"}
```

jump_to="model"是“继续走模型循环”的框架指令；当前框架映射会先经过循环入口的前置处理。新的测试清单请求随后执行。它与上一节的区别是：工具后原本就在循环中，自然结束位置需要明确返回继续指令。

### 8.5 事件通知单独看

```text
入队成功 → ControlObserver.accept → control_accepted
选中输入 → ControlObserver.select → control_delivery_started
构造消息 → record_messages记录消息身份关联
图值/恢复读取见到对应HumanMessage.id → observe → control_delivered
```

ControlObserver是记录控制输入进展并发通知的对象。observe保护普通观察失败，队列和图调度仍按正式控制方法运行。控制记录另有control_id，record_messages把它与message_id关联，两个ID不要求相等。

| 通知 | 通俗含义 | 当前主要消费 |
|---|---|---|
| control_accepted | 已进入活动运行的待处理队列 | CLI提示、诊断 |
| control_delivery_started | 已从队列选中，尚未确认进入图 | 通用记录/转发，无专用界面动作 |
| control_delivered | 已在图值或恢复读取中看到消息 | CLI、诊断；Web根控制提示“补充消息已加入本次上下文” |

最后一项不证明模型已回答、理解或遵守，也不凭通知证明持久落盘。无消费者收到该通知时，图仍按前面返回值继续；显示/诊断可能缺失，这是不同的影响。

用户认可三个阶段有助于诊断；了解默认记录通道后，最新决定是保持现状：control_delivery_started暂不补入持久诊断，遇到实际定位不足再增加。不删除该运行事件、不调整日志级别/格式。“阻塞”仍须区分产生处同步记录/有序投递与等待持久落盘/外部消费；不自动升级为可靠待办或每条日志落盘后才能继续执行。

记录通道核对：三种事件都经过application/run_events.py的_log_event，以INFO调用logger，字段放在LogRecord.application_event；默认Web启动级别WARNING会过滤三者，默认格式也不展开application_event，且没有自动创建日志文件。Web的DeliveredRun.events通常保留三者，但属受容量限制的内存缓存。SQLite后台诊断白名单当前只包含control_accepted和control_delivered，缺少control_delivery_started；前两者也受预算、写入失败及清理策略限制，不承诺每条必存。

因此“存在事件/调用日志入口”不能等同于“默认环境能事后查到完整三阶段记录”。当前默认记录能力的限制已说明，用户接受暂不补齐，不把完整三阶段持久记录列为当前待实施项。诊断元数据存储与插话待办持久化/自动恢复分别决策。

### 8.6 结束与失败分支

| 条件 | 当前动作/结果 |
|---|---|
| 同时排着steering和follow-up | 最近模型前先取steering；自然结束时也优先steering |
| 多条follow-up | 每次自然结束FIFO取一条，分别开始新reply |
| 最终模型响应期间收到steering | 自然结束检查仍可取出，继续当前reply |
| 所有输入已处理且自然结束 | 锁内关闭窗口，随后应用收尾/必要保存/释放run |
| 运行失败，输入尚未处理 | close_control_window清理队列；未选中和已选中未确认的控制分别报告丢弃/未知，不自动重放 |
| 窗口已经关闭，新输入才到 | 明确拒绝，不因busy尚未释放就接纳 |

相关函数：application/async_application.py的steer/follow_up；application/session_controls.py的steer/drain_steering/prepare_control_messages/finish_run_boundary；agent_runtime/__init__.py的两个注入hook；application/agent_session.py的close_control_window/release_run；application/session_execution.py的_afinish_run。

本场景当前设计结论：保留内存队列、两个消费时点、会话所有者、回复归属和窗口竞争保护。QueuedInput作为数据对象足够，事件观察不承担模型调度；不新增持久Inbox或输入调度平台。控制中间通知的必要性另按实际消费/诊断价值判断。
