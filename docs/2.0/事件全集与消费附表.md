## 1. 判断

保留执行、必要保存与普通观察的职责分离；当前事件粒度比专门消费者的需求更细，适合先优化重复读取/载荷，再决定诊断类事件是否保留。测试或通用转发在用，不自动构成永久保留每一类事件的理由。

Pi对照以官方73f8de80bc87021375f8b525292ac07492253002为准；旧a69课堂对照仅是历史版本。Pi核心AgentEvent为10类，coding-agent的AgentSessionEvent另扩展agent_settled、queue_update、compaction、retry等，不能用我们全域32类对比它核心10类来断言谁冗余。

- [Pi核心类型](https://github.com/earendil-works/pi/blob/73f8de80bc87021375f8b525292ac07492253002/packages/agent/src/types.ts#L516)：围绕Agent、turn、消息和工具，部分事件直接携带message/result。
- [Pi Agent](https://github.com/earendil-works/pi/blob/73f8de80bc87021375f8b525292ac07492253002/packages/agent/src/agent.ts#L565)：事件先更新Agent状态，然后await核心监听器；正常结束后仍需finishRun。慢核心监听器影响结算，不等于普通产品会话监听器也都异步。
- [Pi AgentSession](https://github.com/earendil-works/pi/blob/73f8de80bc87021375f8b525292ac07492253002/packages/coding-agent/src/core/agent-session.ts#L196)：扩展事件；_handleAgentEvent等待扩展，普通_emit同步通知公共监听器，并在message_end分支追加会话消息。
- [Pi循环](https://github.com/earendil-works/pi/blob/73f8de80bc87021375f8b525292ac07492253002/packages/agent/src/agent-loop.ts)：读取工具结果/控制条件/队列路由；事件与继续条件分别核对。本次未执行Pi模型请求。
- 按项目规则旁查AgentX 3fcfa0e：AgentWorkflowContext.transitionTo→AgentEventBus.publish→AbstractAgentHandler.handle→processEvent/transitionToNextState，这条事件链承载工作流推进；它与本项目观察事件的职责不同，不作为替换方案。

本项目收益：普通观察故障隔离；必要保存显式失败；统一身份/序号/子来源；Web可校准草稿、恢复交付缺口；实际模型调用用量独立于逻辑调用。代价：消息/调用/turn多层状态机，重复序列化/哈希/复制，全部事件通用转发，事件和UI查询耦合。同步handler仍会阻塞当前投递，异步写入只是相关消费者自己有界入队；未做生产性能压测，不能用事件条数证明快慢。

## 2. 公共信封与消费者代码

RuntimeEvent为event_type/session_id/run_id/sequence/timestamp/data/source；Web投影另加version=1。子事件仍由根publisher分配公共sequence，根run_id在信封，子执行段在source.agent_run_id，父工具关联在source.parent_tool_call_id。

所有有效事件均经过默认日志函数及已订阅通道的通用分发，默认日志是否输出取决日志级别；Web可保留/转发事件，但受帧和缓存预算限制。这不算每类都有专用业务消费者。

下表只列专用消费，不把推进游标、通用日志或原样SSE算作专用消费：

- W：Web后端投影、前端reducer/状态hook/上下文界面。
- C：CliEventDisplay建立身份、输出内容/进度/状态。
- U：ModelUsagePersistence，实际调用用量写入，只接受invocation两类。
- D：DiagnosticPersistence有限元数据白名单，共22类；不是正文归档，也不承诺每条永久保存。
- —：没有上述专用消费者，只有通用日志/通道转发/外部订阅可能性。

普通聊天与checkpoint的必要归档不依赖消费message_completed事件，而由SessionPersistence等实际保存路径完成。

## 4. 首段11次发布评估

11次发布包含9个不同事件类型，message_completed两次（human/ai），model_context_snapshot两次（前/后）。除turn_started只有通用消费外，其余都有专门用途，但专门用途也有UI、用量与诊断等不同强度。

1 run_started(W/C/D)→2 human completed(W/C/D)→3 turn started(通用)→4 model_call started(C/D)→5 context snapshot(W)→6 invocation started(U/D)→7 invocation finished(U/D)→8 delta(W)→9 context snapshot(W)→10 model_call finished(D)→11 AI completed(W/C/D)。

边界不同不代表零重复：逻辑model_call的响应校验、输入溢出恢复与实际invocation/摘要/Auto调用分开有用途；普通请求时两套事件会重叠。同样，delta负责提前呈现，完整快照负责工具结构和最终校准，不能用其中一个简单替换另一个。

本轮同一合成测试实测：前11项RuntimeEvent紧凑JSON合计6395字节；两份context事件1204/1205字节，内部snapshot仅status改变，estimate相同。此处不是SSE/网络实际流量，也不是生产性能基准；真实供应商的结束快照还可补usage，因此终态通知有价值，重复估算载荷可评估收敛。

另一个明确开销路径：App始终调用useContextView；该hook把run.context_snapshot纳入key，key变化会调用api.context。WebService.context又读取应用上下文/图状态，再用live.context_view覆盖latest_request。故事件已有数据仍可能触发额外GET和checkpoint读取；实际请求次数受渲染批处理等影响，本轮未测固定次数或耗时。

## 5. 取舍建议，尚未实施

1. 保留消息/工具/运行、实际调用用量、权限控制结果和异常可观察边界；没有发现需要为精简重写成事件驱动执行的证据。
2. 优先去掉同一上下文快照的重复读取，评估请求完成只更新状态/usage或复用已有估算，保留请求中和终态的真实信息。
3. 四个常规turn、control_delivery_started、context_messages_changed是低专用消费候选；按诊断价值决定保留、降级或移除。它们被测试、日志和通用通道使用，不等于没有消费者，也不自动形成永久公开合同。
4. 不能仅在SSE中丢弃这些帧：当前根/子共享连续sequence，前端即使不渲染也推进游标；跳过会触发sequence_gap/resync。若收敛类型必须同步生产、消费、序号合同及行为测试。
5. 同步轻量通知继续适合当前消费者，IO型持久化消费者已有有界队列。是否改异步总线要以慢消费者证据判断，不能仅因事件多而升级基础设施。

## 6. 控制事件的时点与身份关联（三场景汇总）

### 6.1 正常时序及关键字段

| 输入/事件 | 事实成立的时点 | boundary及相关字段 |
|---|---|---|
| Steering/Follow-up：control_accepted | 会话在锁内接纳文字并放入对应ActiveRun队列 | application；control_id，message_id此时尚未写入控制事件 |
| Steering：control_delivery_started | 模型前边界或自然结束边界选出这批steering | queue；保留原control_id，尚不证明消息入图 |
| Follow-up：control_delivery_started | 自然结束边界选出最早的一条follow-up | queue；同上，仍在同一run |
| Steering/Follow-up：control_delivered | 已选择记录关联的HumanMessage.id出现在观察到的消息状态 | message_state；同control_id、message_id、visibility=graph_values/recovery_view |
| Stop：control_accepted | 校验当前活动run/接纳窗口后，设置停止意图并记录请求 | application；control_id，所属run_id在事件外层 |
| Stop：control_applied | 当前run结果包含run_stopped=True，且该观察对象有停止记录 | active；同control_id；早于应用必要保存和释放 |
| approval_requested | 图已中断，应用校验/安装pending后提出待用户回答的问题 | ApprovalRequestedData携approval_batch_id、tool_call_ids、items；没有这份用户回答的control_id |
| Approval：control_accepted | 用户提交决定，恢复run准入检查通过并记录决定 | application；新control_id、tool_call_ids、decisions、origin_run_id |
| Approval：control_delivery_started | 资源准备后，observation.bind开始提交恢复调用 | invocation；保留上述字段 |
| Approval：control_applied | 审批hook处理完，收集的调用ID集合与本次决定对应集合一致 | approval_hook；保留同control_id；approve/reject都会确认 |

正常停止不经过delivery_started。插话的delivered证明消息可见，不能证明模型已经阅读/遵守，也不能代替持久化确认。审批applied不能证明工具成功或后续保存完成。

control_discarded/control_outcome_unknown是未走完上述确认的收尾通知：观察记录仍在accepted则discarded，已到selected但没有确认则unknown。它们反映控制观察协议的阶段，不能据此推断已经发生的副作用被回滚；停止信号在accepted阶段就可能已传出。

### 6.2 先分清每种ID

| 标识 | 生产者/含义 | 用在哪里 |
|---|---|---|
| session_id | 应用创建逻辑会话 | 路由会话、限定审批/执行许可的归属 |
| run_id | SessionService准入分配或接收本次身份 | 事件外层及当前ActiveRun归属；审批恢复使用新run |
| control_id | ControlObserver.accept生成UUID | 串起同一控制的accepted/started/delivered或applied；多个同文输入仍不同 |
| message_id | 入队创建QueuedInput时生成，构造HumanMessage时沿用 | 把观察记录与真正进入消息状态的输入关联 |
| tool_call_id | 模型tool_calls中每项id，经响应/批次门禁校验 | 标识一个具体工具调用；后续ToolMessage.tool_call_id引用它 |
| batch_id | 当前产生工具调用的AIMessage.id | 标识工具批次，和批次内每项tool_call_id不同 |
| approval_batch_id | 根审批对session、原batch_id、requested_run_id及pending items做稳定JSON后SHA256 | Web核对提交针对当前待审批快照 |
| approval_id | 根审批为每行生成approval_batch_id:index | 前端行决定映射回原工具调用，支持按行ID重排，拒绝重复/缺失/多余项 |
| origin_run_id | 待审批来源run的身份，控制记录从pending复制 | 新run的审批决定明确关联原run |

thread_id用于恢复图的同一条checkpoint线程；turn_id用于审批前后接续同一逻辑turn；reply_id标注回复归属。它们不是插话入图或审批hook确认的主要比较键。事件sequence用于所属发布流排序，不是控制/授权身份。

### 6.3 插话：先FIFO关联，再检查消息ID可见

```text
steer('补充内容')
  → QueuedInput(message_id=M1, text=..., kind=steering)
  → ControlObserver.accept生成C1
      _queue_ids[steering]记录C1，与业务队列同顺序
  → select按FIFO选出C1，记录phase=selected，发布started
  → prepare_control_messages构造HumanMessage(id=M1)
  → record_messages按所选批次顺序关联C1 → M1
  → observe收集当前HumanMessage.id集合
      若C1已selected且M1在集合中 → delivered(C1, M1)
```

control_id和message_id是两次独立生成的身份，不要求相等。record_messages先核对批次与消息数量，再按顺序zip；它没有通过文字内容或额外业务ID搜索映射。两个相同文本的输入会有不同C/M，不能据文本判断投递。可见性确认只比较消息ID及HumanMessage类型，没有逐字比对正文。

### 6.4 停止：当前运行的对象归属与结果标志

request_scope_stop先定位会话的ActiveRun；若显式传run_id，必须等于当前run.run_id，还要检查接纳窗口/阶段。ControlObserver属于该run的RunObservation，accept记录_stop_id=Cstop，并对重复stop去重。

run_result读取同一观察对象的_stop_id，结合当前调用返回的run_stopped=True发布applied，保留Cstop。图结果没有回传control_id再作相等比较；它依赖本次运行对象/调用链归属，不应表述为所有控制都靠结果回传ID确认。根run收尾修改会话时还核对ActiveRun对象身份，防止旧收尾操作新run。

### 6.5 审批：分四层核对，不能只看control_id

1. **形成待审批项**：pending_tool_approval核对图中断action与保存的ask调用数量、顺序、工具名、参数；ApprovalRequestedData还核对展示items的tool_call_id顺序与tool_call_ids一致。
2. **接受用户提交**：Web/AgentSession核对当前pending的approval_batch_id、origin_run_id；resolve_approval_rows要求提交行ID集合与当前行集合完全相等，拒绝重复/缺失/多余项，然后按原审批顺序取决定。低层aresume_tool_approval直接接收针对当前pending的有序列表，不把Web身份检查误称其额外参数。
3. **确认hook处理**：新run的control记录保存C、原tool_call_ids及决定；begin_approval_hook清集合，_create_action_and_config收集实际call.id；super.after_model正常返回且未走停止后，approval_applied要求非空候选集合与保存ID集合完全相等。只检查相应调用集合和处理阶段，不独立逐项回读/比对approve/reject决定，也不检查工具执行结果。
4. **执行授权**：prepare_resume为批准项保存binding={session_id, agent_path, batch_id, call_id, tool_name, args, subject}；_authorize先核对原调用id/name/args，再按call_id查一次许可并比较整个binding。匹配后删除该许可；不匹配/不存在则阻断，不能跨会话/批次/参数消费。工具再检查permit及实际目标。

例如当前两行P:0→T1、P:1→T2，前端先提交P:1再提交P:0也可由行ID还原为T1/T2对应决定；不会只因两个工具都叫read就交换批准对象。实际P为完整哈希，本例是缩写。
