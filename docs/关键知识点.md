## 1. LangChain `create_agent` middleware 的注册、调用时点与执行顺序

适用范围：本项目安装的 LangChain **1.4.2**、同步 `create_agent`/`agent.invoke` 路径。下面的普通执行顺序由本机 `langchain/agents/factory.py` 的图连线和 wrapper 组合源码核对，并用两个自定义 middleware、假模型两次回复和一个合成 `echo` 工具的最小探针观察；不是实际模型供应商请求，也不是异步或未来版本的保证。

### 1.1 Python 覆盖与框架注册是两件事

子类定义与父类同名的方法，实例调用时优先使用子类实现，这是 Python 的方法查找规则。`ToolBatchMiddleware(AgentMiddleware)` 定义自己的 `after_model` 和 `wrap_tool_call`，属于这种覆盖。

仅继承和覆盖不会让框架自动发现它。本项目在 [`agent_runtime/__init__.py`](../naiyue_test_agent/agent_runtime/__init__.py) 中显式传入 `create_agent(middleware=[ToolBatchMiddleware(tools), ...])`。框架检查实例所属类哪些 hook 覆盖了 `AgentMiddleware` 基类实现：`after_model` 被注册成图节点，`wrap_tool_call` 被编入工具执行的 wrapper 链。`model=` 和 `tools=` 是另外传入的参数，不因 middleware 继承而自动注册。

### 1.2 一次普通“模型调用工具后再回答”的阶段顺序

```text
START
  → before_agent                 普通运行入口
  → before_model                 第 1 次模型调用前
  → wrap_model_call 进入 → 模型 → wrap_model_call 返回
  → after_model                  第 1 次模型回复后
  → 如果 AIMessage 有待执行工具调用：
       每项调用分别经过 wrap_tool_call 进入 → 工具 → wrap_tool_call 返回
       工具结果作为 ToolMessage 加入消息状态
       → 回到 before_model
  → wrap_model_call 进入 → 模型第 2 次回答 → wrap_model_call 返回
  → after_model                  第 2 次模型回复后
  → 如果没有待执行工具调用：after_agent → END
```

`before_model` 与 `after_model` 围绕**每次**模型调用，所以一次运行中可能出现多轮；`wrap_tool_call` 是**每个待执行工具调用**各走一遍。普通路径的 `before_agent` 在运行入口，`after_agent` 在准备自然结束时；若 `after_agent` 使用 `jump_to='model'` 注入后续消息，循环会继续，不能机械地把它理解为永远只调用一次。多工具批次若可并行，不同调用的 wrapper 链可能交错执行。

### 1.3 同类 hook 的顺序：先看阶段，不能对整个列表套一个方向

假设 middleware 列表为 `[A, B]`，且 A、B 都实现了相应 hook：

| 同类 hook | 普通路径中的顺序 |
| --- | --- |
| `before_agent`、`before_model` | `A → B` |
| `after_model`、`after_agent` | `B → A` |
| `wrap_model_call`、`wrap_tool_call` | 请求 `A 进入 → B 进入 → 内层调用`；结果 `B 返回 → A 返回` |

这些 hook 并非“同一个节点”：每个 `before_*`/`after_*` 实现会成为自己的图节点，框架按阶段连接它们。只实现某个 hook 的 middleware 只参加那一类顺序。例如模型选择 middleware 只参加模型调用包装，不会凭列表位置成为一个 `after_model` 节点。

### 1.4 `wrap_*` 的 `handler(request)` 是“继续到内层”

列表 `[A, B]` 的模型包装可理解为 `A(B(实际模型调用))`：

```text
A: 进入
  B: 进入
    实际模型调用
  B: 返回
A: 返回
```

A 收到的 `handler` 会继续到 B；B 收到的 `handler` 会继续到实际模型。工具包装同理，最内层是工具执行。某层不调用 `handler`，内层就不会执行；某层抛异常，普通的“返回”代码也不一定执行。我们的批次调度器正是在轮到某个调用时才调用 `handler(request)`，从而放行内层工具链。

### 1.5 本项目的审批与批次规划顺序

本项目将 `ToolBatchMiddleware` 放在 `HumanInTheLoopMiddleware` 前面；二者都实现 `after_model`。当前版本的 `after_model` 按列表逆序连接，所以相关顺序是 **HITL 审批检查 → 批次规划**，中间若有其他 `after_model` hook，也按其列表位置执行。

- 无需审批：HITL 直接通过，随后批次规划。
- 需要审批：HITL 调用 `interrupt()`，首次运行暂停，尚未进入批次规划。用户决策后恢复；HITL 先处理批准/拒绝并更新消息，再继续到批次规划。拒绝项产生错误 `ToolMessage`，不应占用待执行顺序。
- 工具执行时，`wrap_tool_call` 按列表前项为外层：当前项目的批次调度器先决定是否放行，随后才进入工具事件记录、HITL 的工具包装和实际工具。实际链路只包含当次装配中实现了该 hook 的 middleware。

### 1.6 本机探针与边界

两个 middleware `A/B`、假模型首轮请求 `echo`、次轮输出文本，实际记录到：

```text
A.before_agent → B.before_agent
A.before_model → B.before_model
A.wrap_model:enter → B.wrap_model:enter → B.wrap_model:exit → A.wrap_model:exit
B.after_model → A.after_model
A.wrap_tool:enter → B.wrap_tool:enter → echo → B.wrap_tool:exit → A.wrap_tool:exit
A.before_model → B.before_model
A.wrap_model:enter → B.wrap_model:enter → B.wrap_model:exit → A.wrap_model:exit
B.after_model → A.after_model
B.after_agent → A.after_agent
ToolMessage(tool_call_id='call-1', content='ok')
```

这说明当前版本的普通同步路径与上面的顺序一致。`interrupt()`、`jump_to`、`return_direct`、wrapper 不调用 `handler`、异常和并行工具都可能改变具体轨迹，分析时应沿当次调用链逐个节点核对。用户目前提出了关键问题并参与讨论；这条知识点只记录为**已讲解**，不自动视为能独立实现或应对面试追问。

本机源码入口：`.venv/lib/python3.12/site-packages/langchain/agents/factory.py` 中的 `create_agent`（收集 hook、建立图边）、`_chain_model_call_handlers`、`_chain_tool_call_wrappers`、`_make_model_to_tools_edge`；审批路径在 `.venv/lib/python3.12/site-packages/langchain/agents/middleware/human_in_the_loop.py` 的 `HumanInTheLoopMiddleware.after_model`。项目入口是 [`agent_runtime/__init__.py`](../naiyue_test_agent/agent_runtime/__init__.py) 的 `_build_runtime_agent`，本项目批次 hook 在 [`agent_runtime/tool_batch.py`](../naiyue_test_agent/agent_runtime/tool_batch.py)。

## 2. 上下文预算参数与安全切点算法

适用范围：2026-10-07 本项目的 Python + LangChain 1.4.2 同步本地应用路径。配置与默认值以 [`model_access/__init__.py`](../naiyue_test_agent/model_access/__init__.py) 为准，压缩行为以 [`agent_runtime/context_compaction.py`](../naiyue_test_agent/agent_runtime/context_compaction.py) 为准；[对应测试](../tests/test_context_compaction.py)使用确定性假模型验证接线。以下 token 数由 LangChain `count_tokens_approximately` 估算，不是供应商返回的精确用量，也不能证明配置的窗口就是供应商真实支持的窗口。

### 2.1 五个配置参数分别控制什么

这些字段放在**每个模型条目**下。切换当前模型时，后续运行使用新模型的参数；配置文件未填时采用下表默认值。

| 配置字段 | 未配置时的值 | 作用 |
| --- | --- | --- |
| `context_window_tokens`，记为 `W` | `128000` | 本项目假设的模型总上下文窗口，用于预算计算；它不是发送给供应商的“扩大窗口”命令，也不是供应商能力的证明。 |
| `max_output_tokens`，记为 `O` | `16384` | 单次模型请求的最大生成 token 数。模型接入层把它映射到相应供应商参数；摘要请求还会受更小的独立上限约束。它不是“当前回答一定会生成这么多”。 |
| `compaction_reserve_tokens`，记为 `R` | `min(16384, max(1, W // 4))` | 希望在输入尚未贴近发送上界时，提前触发压缩的余量。它参与**触发阈值**，不等于供应商单独保留了一块实际空间。显式配置过大不会被静默改小。 |
| `compaction_keep_recent_tokens`，记为 `K` | `min(20000, max(1, W // 4))` | 找完整轮次切点时，希望原样保留的最近消息 token **至少约有多少**。它是寻找边界的目标，不是保留内容的上限；为了保留完整用户轮次，实际保留量常常超过 `K`。 |
| `compaction_summary_output_tokens`，记为 `S` | `min(2048, O, max(1, R * 4 // 5))` | 单次摘要模型请求的输出上限，用于摘要请求预算与压缩后请求的保守预估。显式值必须为正，且不能超过 `O` 或 `R`。它不是正常回答的上限。 |

代码先估算本次系统提示词（含工作区项目指令）、消息和工具描述的输入 token，记为 `E`。主要有两个不同的界限：

```text
有效预留 H = max(O, R)
软触发阈值 T = max(0, W - H)
估算发送上界 B = W - O

E <= T：通常不压缩
E > T：开始考虑压缩
压缩后的正常请求估算值 <= B：才允许继续发送
```

`T` 是**什么时候提前处理**，`B` 是**按最大输出预留空间后，估算输入还能占多少**。当 `R > O` 时，`T < B`，输入可能已经跨过软阈值，却仍处于发送上界内。如果此时没有安全切点，当前实现会记录 `no_safe_cut_within_send_budget` 并继续运行，而不是仅因软阈值报错。若 `H >= W`，正常的“不压缩”快速路径也不会成立，不能把 `T=0` 理解为预算安全。

例如 `W=530、O=20、R=50、K=30、S=8`，则 `H=50、T=480、B=510`。一次请求估算 `E=490` 已触发压缩考虑，但仍低于估算发送上界；`E=605` 则已超过发送上界，必须找到可行的缩短方案。默认 `W=128000` 且其余字段也都未配置时，`O=16384、R=16384、K=20000、S=2048`，于是 `T=B=111616`。这些数值只说明本项目怎样做近似预算，不能保证真实模型接受边界附近的请求。

### 2.2 `cutoff` 的含义与第一轮寻找

`cutoff` 是保留后缀的**起始消息索引**：`messages[:cutoff]` 交给摘要模型，`messages[cutoff:]` 原样保留。只有当前本地应用新一次 `run` 开始时，`before_agent` 才执行这套压缩判断；同一 run 内工具结果后的每次模型调用并不会重新执行这段切点算法。

第一轮调用 `_cut_at_complete_turn(messages, K)`：从最后一条消息向前逐条累加近似 token，第一次达到或超过 `K` 的位置记为 `crossing`；然后从 `crossing` 向前找最近的 `HumanMessage`，以它作为保留段起点。这样优先保留一个完整用户轮次，而不从轮次中间的 AI 或工具结果开始。若累加到头仍不到 `K`，或只能退到最开头，返回 `cutoff=0`：没有可供摘要的更早完整轮次。`0` 不表示可以摘要全部消息。

示例：最后三条消息依次是索引 4 的工具结果（约 208 token）、索引 5 的 AI 分析（约 11）、索引 6 的新用户问题（约 7）。当 `K=30`，从后往前得到 `7 → 18 → 226`，在索引 4 首次跨过目标；再向前找到索引 2 的用户请求，于是完整轮次切点是 **2**。保留索引 2 之后的全部消息，因此实际保留量会远大于 30。

### 2.3 完整轮次仍放不下时，如何找轮次内部切点

若第一轮得到非零 `cutoff`，代码先用“系统提示词 + 摘要消息前缀 + 最多 `S` 个摘要输出 token + 保留后缀 + 工具描述”预估正常请求。若该值 `<= B`，直接采用完整轮次切点。若 `cutoff=0` 且原请求 `E <= B`，跳过压缩；否则才从原切点**之后**按索引递增查找下一个可行边界。查找不把最后一条本次最新消息作为切点，优先选择最早可行者，以尽量多保留原文。

每个候选依次过四道门：

1. **消息类型**：候选只能是 `HumanMessage` 或 `AIMessage`，不能是 `ToolMessage`。从工具结果开始保留可能丢掉它所对应的 AI 调用。
2. **消息结构与工具配对**：分别检查 `messages[:candidate]` 和 `messages[candidate:]`。每一边的有效工具调用 ID 都必须在**同一边**找到对应结果；未配完、孤立结果、无法安全摘要的内容或同一 AI 消息中有效/无效调用 ID 冲突，都不能作为这个切点。如果候选是 AI，还须向前找到它所属轮次的真实用户消息；之前生成的摘要标记消息不算该轮用户请求。
3. **摘要请求预算**：候选前缀序列化后，摘要模型的输入估算 `+ S` 必须 `<= W`。摘要模型本身也不能收到超窗口请求。
4. **正常发送预算**：系统提示词、工具描述、摘要前缀、最多 `S` 个摘要输出 token 和候选后缀的估算必须 `<= B`。通过就选中该候选，停止继续扫描。

在[切分测试](../tests/test_context_compaction.py)中，完整轮次切点 2 的预计发送量是 `611 > B=510`；索引 3 是 AI 工具调用，工具调用和结果可一起保留，但预计 `530 > 510`；索引 4 是 ToolMessage，类型不允许；索引 5 是 AI 分析，其前缀包含成对的工具调用和结果，摘要请求加上限约 `524 <= W=530`，预计发送量约 `296 <= 510`，因此最终 `cutoff=5`。移除的是索引 0–4，原样保留的是索引 5–6。切在 AI 前时，摘要请求把早期历史与当前轮次已完成的前缀分别标为 `<conversation>`、`<turn-prefix>`，让摘要保留理解后续 AI 消息所需的原请求与工具事实。

另一个可行形状是从 `AIMessage(tool_calls)` **之前**切：该 AI 调用及其 ToolMessage 一起留在后缀即可。相反，若一次 AI 发出两个调用而切点前只收到其中一个结果，前缀仍有未完成调用，候选会被拒绝。单条超大的用户消息没有消息内部边界，当前算法不会截断它；找不到其他可行切点时明确报 `no_safe_cut`。

若已有完整轮次切点，只是“摘要可能写满 `S`”使保守预计超出 `B`，而后续也找不到可行候选，代码仍允许按原完整轮次方案尝试一次摘要；实际摘要可能比上限短。收到摘要后会用**实际摘要内容**重新估算正常请求，超过 `B` 则报 `compacted_request_over_budget`，不提交替换消息或继续调用正常模型。由此，“找到候选切点”不等于“摘要和后续模型调用一定成功”。
