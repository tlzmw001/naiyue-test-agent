## 用户总结

以下是用户原理解的要点，精确边界见下一节。

- ProjectHost 持有 SessionAPI、RunAPI，两者共享 SessionService 和 SessionPersistence；服务提供管理和持久化能力，依赖逐层交给会话使用。
- RunLifecycle 负责每次会话运行，AgentSession 构造中创建 runtime；原理解为 persistence 也放进 runtime。
- ProjectStore 下的会话仓储、聊天归档仓储和运行收尾对象分别处理业务，共用其 DB 对象，供 SessionPersistence 调用。
- 退出程序时将聊天和线程归档；重启后 session_id、thread_id 不变。
- 新的运行使用新的 ActiveRun，继续用原来的图和 checkpoint 加入消息。

## 对应纠正

| 需要补准的位置 | 当前代码的精确行为 |
| --- | --- |
| 两个服务都交给 AgentSession | SessionService 登记、查找 AgentSession，并通过 build_session 传递必要依赖；没有把整个 SessionService 注入每个会话。共享的 SessionPersistence 会传给 AgentSession、RunLifecycle 等使用方。 |
| persistence 在 runtime 中 | SessionRuntime 持有 session_id、SessionState、当前 ActiveRun、锁和待发送图片等；RunLifecycle 同时引用这个 runtime 和 SessionPersistence。SessionRuntime 与图调用的 RuntimeContext 是不同类型。 |
| 调用从 AgentSession 触发 | RunAPI 经 SessionService 找到 AgentSession，再直接调用其 lifecycle.admit_run/arun；AgentSession 负责组织会话对象和配置，RunLifecycle 管理本轮执行及收尾。 |
| 退出时才保存聊天和线程 | 图执行期间由 checkpointer 写 checkpoint；每轮必要收尾收集归档候选，由应用事务提交聊天归档、同步位置和会话确认 checkpoint 指针。历史 prepare 还可能补同步。退出主要处理资源收束，正常续聊不能依赖退出时才保存。 |
| 重启只换 ActiveRun | 服务进程重启后，Host、服务、存储连接、图与 checkpointer 对象重新装配；恢复时新建 AgentSession、SessionState、SessionRuntime 及协作者。逻辑 session_id、thread_id 使用原值。 |
| 重启即创建新 ActiveRun | 正常恢复后的 runtime.run=None；下一次发送通过准入后，才创建新 ActiveRun 和本轮 run_id。 |
| 使用之前的图和 checkpoint | 使用新装配的图和 checkpointer 对象访问原存储，以原 thread_id 定位状态。普通 restore 要求元数据 state=ready，确认 checkpoint/命名空间与当前图状态一致，无待执行节点及相关中断/错误，才安装会话；运行时继续核对执行条件。 |
| SessionState 全部原样恢复 | 按字段映射保存和恢复配置；当前正常恢复保留模型、工具、权限模式等，运行占用、队列、准备的提示词片段和 session_allow 等瞬态状态重新开始。 |

这里的 thread_id 定位图状态线程，不是操作系统线程。项目范围的 scope_id 直接使用 project_id；普通聊天 scope_id='chats'，project_id=None。

## 对象与运行主链

```text
Host 装配：存储 D → 服务 S → 持久化 P(storage=D, sessions=S)
                         S._persistence=P → 图 G → 各 API
S._sessions[S1] → AgentSession C1
                  ├─ _runtime=R1 → state=Q1(thread_id=T1)，run=None/ActiveRun
                  └─ lifecycle=L1 → _runtime=R1，_persistence=P
P.storage=D → sessions:SessionRepo / conversation:ConversationRepo / runs:RunUnitOfWork
三个存储使用方 → 同一个 D.database

发送 → 找到 C1 → 准入登记新 ActiveRun → 图以 T1 接续状态
     → 图返回 → 必要保存 → 释放运行占用 → 本轮终态
重启 → 新 Host/服务/图连接原存储 → 核对 S1/T1 的确认位置
     → 重建 C1'/Q1'/R1'/L1'，R1'.run=None → 新消息再进入运行准入
```

## 候选交付与三类数据

- 图 checkpoint 是执行状态；会话元数据持有身份、配置、状态和确认位置；聊天归档供回看。HistoryAPI.messages 读图当前消息，HistoryAPI.page 读归档；压缩后两者可以不同。
- 课堂示意：归档边界 K0、同步 revision=4；沿选中父链收集 K1～K4，正向扫描消息。候选可能包含已归档前缀；同 ID 同正文跳过，正文改变则以较后版本覆盖候选。中间快照已收集的消息不会因后续压缩消失而从候选移除。
- collect_chat_updates 返回 tuple[ChatUpdate]，包含 T1、expected_revision=4、目标 K4 和消息候选；P.afinish 用局部变量 updates 接收，再作为参数交给 D.runs.finish_run。候选本身尚未提交。
- 事务先核对同步 revision，再跳过已有相同消息、插入新消息或更新已有消息；一起更新归档同步位置与会话确认位置。消息 sequence、消息 revision 与同步 revision 各有职责。
- 应用事务回滚不回滚此前框架已写 checkpoint。必要保存失败会阻止继续运行，即使根运行占用已释放；异常分类和重新生成留到场景07。
