# 第二课 · 工具批次执行与异常反馈

2026-11-08，对应场景 02。本页整理用户章末复述与对应纠正。

## 用户总结

以下保留用户原理解的要点，精度问题见下一节。

- 主要涉及批次、审批和异常中间件，本课重点是批次与异常。
- 模型响应后，批次中间件按工具的串行/并行属性整理 batch，放到 runtime 中供后续使用。
- 并行受最大并发量限制；串行通过 Condition，按调用 ID 的位置与 position 决定放行。
- 框架的工具调用一起进入执行方法，再由计划保证串行。
- 异常中间件包住工具执行，捕获错误；可处理的反馈给模型，其他继续抛出，后续工具不再执行。

## 对应纠正

| 需要补准的位置 | 当前代码的精确行为 |
| --- | --- |
| 涉及三个中间件 | 本课聚焦批次与异常，审批是相邻前置步骤；执行链还包括工具选择、观察和执行前授权。 |
| batch 放到 runtime | 计划为 AsyncBatchPlan，保存于框架 runtime.context 所引用的项目上下文 invocation.tool_batch。后续同批调用取得同一个计划。 |
| 所有工具一起进入 execute | 各调用由框架调度，何时进入还受调度与并发配置影响，不能保证同时或全部预先进入；串行顺序由计划保障。 |
| Condition 锁实现串行 | Condition 协调状态检查与通知；index 由 call_ids.index(call_id) 查出，position 指定当前轮到的位置。锁外执行工具，等待时释放锁。 |
| 相等且无报错才继续 | 正常时 index == position 才执行；failed=True 也会唤醒等待者，但它们随后返回跳过消息。错误 ToolMessage 本身不会触发 P.failed。 |
| 异常中间件能捕获各种异常 | 它捕获包在内层的执行链中的 Exception，图控制信号直接传播，取消等 BaseException 分支也不按普通工具错误处理；外层批次故障不在它的捕获范围。 |
| 框架处理可反馈异常 | 项目 tool_error_feedback 决定返回反馈内容或 None，框架 ToolErrorMiddleware 负责包装错误 ToolMessage 或重新抛出原异常。 |
| 异常抛出后其他工具不再执行 | 计划的等待/执行分支收到异常后标记 failed。随后经过失败检查的调用跳过；已进入工具体的并行调用不能靠该标记撤销或直接取消，外层仍需收束。 |

```text
模型响应 → 权限/审批 → 批次计划 P
工具选择 → P.execute → 观察 → 错误包装 E → 授权 → 工具体
                                  ↑
       项目反馈函数决定 ────────────┤
       内容：E 返回错误消息 → P 正常推进 → 后续调用/模型
       None：E 重新抛错 → P 标记失败 → 等待调用跳过，异常向上传播
```

本课涉及的关键顺序是模型后钩子反向连接、工具调用包装先注册者在外层。两种执行形式应分别追踪。[图装配](../../naiyue_test_agent/agent_runtime/__init__.py) · [计划与调度](../../naiyue_test_agent/agent_runtime/tool_execution/async_batch.py) · [项目错误反馈](../../naiyue_test_agent/agent_runtime/tool_execution/feedback.py)
