## 用户总结

以下保留用户原理解的要点，字段和顺序问题见下一节。“Run Circle”按 RunLifecycle、“SQL”按本课上下文中的 Skills 理解。

- 新运行开始，生命周期逐层调用，读取项目指令并发现点目录下的 Skills，整理后保存在 runtime 中。
- 进入模型前处理，取得选定模型和已保存的项目资料，结合基础系统提示词与工具定义，形成 PreparedRequest。
- 随后从 PreparedRequest 取出图中的历史消息，与配置和系统消息组合成 ModelRequest。
- 发送前，观察中间件统计字符等信息、估算用量；模型返回后，再用响应中的 input_tokens 补充用量记录。

## 对应纠正

| 需要补准的位置 | 当前代码的精确行为 |
| --- | --- |
| 项目资料保存在 runtime 中 | 精确位置是 SessionRuntime R 所持有的本次 ActiveRun U：U.prompt_parts、U.project_instructions；不与框架 Runtime 或项目 RuntimeContext 混称。 |
| 点目录保存 Skills，统一加载 | 当前检查执行根目录的 .agents/skills 和 .claude/skills；注册表存在 read 时启用发现。准备的是可用 Skill 的索引，不把所有正文加入系统消息；选用后由工具读取正文。 |
| before_model 取得之前选择的模型 | 每轮重新读取会话当前模型/工具选择；项目资料从 U 的本次运行快照取得。整条系统消息每轮重组，不能说同一 run 内必然完全不变。 |
| 组装后才得到 PreparedRequest | select_model._prepare 先创建包含模型、编号和工具名称的 PreparedRequest，prepare_request 再补充工具定义与 SystemMessage，保存到 C.invocation.model_call.prepared。 |
| 从 PreparedRequest 取历史消息并组装 ModelRequest | PreparedRequest 不存对话消息。框架模型节点先用 state['messages'] 创建 ModelRequest Q；select_model 包装器再把 P 中的模型、工具和系统消息应用到 Q。 |
| 组装后直接观察并发送 | 中间还经过 ModelInputMiddleware，根据模型能力整理消息。需要改写的图片消息使用副本；发送适配不因此改写图的原始历史，临时图片承载消息不写回历史。该分支本次未独立复述。 |
| 字符统计就是估算用量 | 字符数、框架近似 token 估算、响应报告的 usage 是三种信息。响应未提供 input_tokens 时保持 None；主测试中的 31 为预设用量，不是真实供应商计费证据。 |
| 观察到 returned 表示运行完成 | returned 仅表示该次内层模型调用返回；工具执行、下一轮模型、外层响应检查和生命周期收尾仍可能继续。统计位于适配器生成供应商请求之前。 |

## 数据来源与创建顺序

```text
RunLifecycle L → SessionRuntime R → 本次 ActiveRun U
                                   └─ prompt_parts：本 run 的项目资料

before_model：
  会话当前模型/工具选择 + U 中资料 + 基础提示词
    → 创建并补齐 P：PreparedRequest
    → C：RuntimeContext.invocation.model_call.prepared 持有 P

模型节点：
  图 state['messages'] → 框架创建 Q：ModelRequest
  P.model / P.tools / P.system_message → select_model 更新 Q 的对应字段
  Q.messages → ModelInput 整理本轮发送副本
    → observe_model_request 统计 → 框架组合系统消息并调用模型
    ← ModelResponse → 补充 usage / returned 状态 → 日志和上下文快照
```

项目指令与 Skills 索引在一次正常 run 内复用；下一次 run 及正常审批恢复会重新准备。审批恢复不重新检索所有资料，例如已准备的记忆片段会复用。主测试只注册 read_probe，不启用 Skills 索引；Skills 分支由注册真实 read 的现有测试补充。
